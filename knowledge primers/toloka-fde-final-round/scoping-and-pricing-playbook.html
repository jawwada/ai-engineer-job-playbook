Functional requirements: the discovery conversation

Ask in this order. Each answer changes the design, the agreement you can promise, and the price.

  1. 01
    What decision does this data feed?Training a reward model for the ranker wants volume with modest redundancy; a launch gate or offline eval wants fewer items at high confidence. Everything downstream follows from this answer.
  2. 02
    Define “prefer” before anything else.One holistic choice, or dimensions (relevance to intent, quality, freshness, safety) plus an overall? The rubric is the single biggest lever on agreement. Propose a one-page rubric with ten contrastive examples, written together in week one.
  3. 03
    Whose preference?Locale, language, age band, expertise. Differences between populations are signal, not noise — but only if the pool is quota-sampled to the population the product serves.
  4. 04
    Unit of judgment.Pairwise A/B with “tie” and “can’t judge” is the most robust choice without ground truth. Likert scores drift between annotators; ranked lists of k multiply cost.
  5. 05
    What does the annotator actually see?Two full 3-minute videos is 6+ minutes per task — the cost driver. First 60 s plus keyframes plus transcript, with a minimum watch time enforced, often preserves the judgment at a third of the cost. Ask what the product shows users.
  6. 06
    Volume, cadence, distribution.One-off 100k pairs or 10k per week forever? Head vs tail queries, duplicates, languages. Cadence decides whether you build a standing pool or a project pool.
  7. 07
    What agreement is good enough?Most clients don’t know. Propose a 2,000-pair pilot to measure the natural agreement, then size the overlap to reach a target item confidence. Never promise an α before the pilot.
  8. 08
    Golden items.Can the client supply 200 pairs with an obvious answer? If not, you build them in the pilot with expert adjudication. Without goldens there is no annotator quality signal.
  9. 09
    Content and people.Unreleased videos (private hosting, no download, watermark), faces and PII (consent basis), NSFW or violent content (annotator wellbeing, opt-out, rotation). These set the pool, the tooling and the NDA.
  10. 10
    Delivery contract.JSONL with every vote or the aggregate only? Rubric version and annotator ids in every record? Acceptance by client re-judging 2% of pairs, with a dispute window? Agree the schema before the pilot ships.
Say it to the clientPreference data has no answer key, so I won’t promise accuracy. I’ll promise an agreement level you can measure, a confidence on every pair you can filter on, and a rubric you can audit.

System design considerations

  • Task design first. Randomise A/B position, allow tie and “can’t judge” with a reason, enforce a minimum watch time, keep the query on screen. Half of all “noisy annotator” complaints are task-UI problems.
  • Adaptive redundancy. Start with three votes; escalate to five only when the split is 2/1 and the item confidence is below threshold. That is where the book’s COGS lever (5.75 → 3.60 per pair) comes from.
  • Aggregation that knows who voted. Dawid–Skene (or a simpler weighted vote) learns per-annotator reliability, so the aggregate and its confidence reflect who voted, not just how many.
  • Pool as a system. Qualification test on goldens, continuous golden injection at 5–10%, honeypots for speed-runners, skill scores that gate access to harder batches, rotation for content exposure.
  • Disagreement review loop. Weekly rubric clinic on the lowest-confidence items with the client’s owner present; every clinic ships a rubric version and a re-qualification.
  • Pipeline. Ingest → dedupe → task generation → routing by quota → votes → aggregation → QA sampling by experts → export with manifests. Dashboards on α, unanimity, goldens and throughput per batch.
  • Cost control. Shorter stimuli where the judgment survives it, adaptive overlap, and better qualification beat a lower hourly rate every time — and they raise α instead of lowering it.

Estimation lab: size a 50,000-pair preference program

This lab starts with the client’s requested output and works backwards to judgments, hours, annotators, calendar time, quality evidence, cost, and price. The important habit is to keep items, judgments, and accepted items separate. A request for 50,000 labeled pairs is not a request for 50,000 clicks.

Intuition

The unit multiplies before it moves through the factory

One pair first becomes several independent judgments. Some pairs then receive extra judgments because the first votes disagree. A fraction is reworked or adjudicated. Goldens consume annotator time even though they are not delivered. Finally, only accepted pairs count toward the contract. Estimation is the accounting system that follows those transformations without mixing them together.

delivered pairs → base judgments → escalation judgments → golden judgments → QA/rework → accepted pairs

If you quote only “three raters per pair,” you omit the work that makes the three ratings trustworthy. The largest errors usually come from forgetting escalation, assuming every paid hour is productive, and dividing total hours by headcount without allowing for ramp-up.

Step 2 · Convert delivered pairs into judgments

  1. Base judgments. 50,000 pairs × 3 = 150,000 judgments.
  2. Adaptive escalation. Twenty percent of pairs get two additional votes: 50,000 × 0.20 × 2 = 20,000.
  3. Goldens. If 8% of the queue is golden, productive judgments are 92% of all judgments. Therefore (150,000 + 20,000) / 0.92 = 184,783 total judgments, of which about 14,783 are golden exposures. Do not add 8% to the final total unless “8% injection” explicitly means 8 goldens per 100 production tasks; both conventions exist.
  4. Replacement. Five percent of delivered pairs are replaced after audit. A simple planning approximation is 184,783 / (1 − 0.05) = 194,508 judgment attempts. A more precise model applies rejection separately to base and escalated work, but the approximation is sufficient before the pilot.
  5. Convert to hours. 194,508 × 4.5 / 60 = 14,588 annotation hours.
Sanity check: each delivered pair consumes about 194,508 / 50,000 = 3.89 judgment attempts. At 4.5 minutes, that is 17.5 human minutes per delivered pair. If someone quotes 13.5 minutes, they counted only the three base votes.

Step 3 · Turn hours into a pool and a schedule

An active annotator supplies about 4.5 productive hours/day × 20 days = 90 hours during the production month. The mathematical minimum is 14,588 / 90 = 162 active annotators. That is not the recruiting target. Some workers never qualify, some churn, and demand varies by language and hour.

Qualification funnel

Suppose 70% of invited workers start qualification, 60% of starters pass, and 80% of passers remain active for two weeks.

invite yield = .70 × .60 × .80 = 33.6%

To retain 200 active workers, invite about 200 / .336 = 596.

Operational headroom

Use 20–25% headroom above the mathematical minimum for absence, locale imbalance, and demand spikes.

target active pool = 162 × 1.25 ≈ 203

Round to 200–210, not to a false-precision 203-person promise.

Ramp shape

Week one rarely reaches steady-state. A realistic curve might be 40%, 75%, 100%, 100% capacity across four weeks.

effective month = 0.40 + 0.75 + 1 + 1 = 3.15 steady weeks

If the deadline begins at kickoff, recruit earlier or add a fifth week.

Step 4 · Understand the quality metrics with numbers

Raw agreement versus chance-corrected agreement. Imagine 100 pairs and two labels, A or B. Raters agree on 85 pairs, so observed agreement is 0.85. If both raters choose A 90% of the time, chance agreement is 0.9² + 0.1² = 0.82. Cohen’s κ is (0.85 − 0.82) / (1 − 0.82) = 0.17, which is poor despite 85% agreement. The intuition: when one label dominates, two inattentive raters can agree often by always choosing it.
Krippendorff’s α. α uses disagreement rather than agreement: α = 1 − Do/De. If observed disagreement is 0.12 and disagreement expected by chance is 0.50, α is 1 − .12/.50 = .76. That lands in the tentative band. α handles more than two raters and missing votes, which is why it fits a live factory better than pairwise percent agreement.
Golden accuracy uncertainty. A worker who passes 18 of 20 goldens has 90% observed accuracy, but twenty trials are too few to know whether true accuracy exceeds 90%. The approximate 95% Wilson interval is roughly 70%–97%. After 90 of 100, the interval narrows to about 83%–94%. Use a minimum exposure count before suspending someone on a percentage.
Position bias. In 10,000 decided pairs, left is chosen 5,300 times. The left rate is 53%. Its standard error near 50% is sqrt(.5×.5/10,000) = 0.5%, so 53% is about six standard errors from neutral—unlikely to be random. Inspect UI placement and worker segments.
Item confidence. A 2–1 vote does not always mean 67% confidence. If the dissenting worker has 98% golden accuracy and the other two are near 75%, a reliability-aware model may remain uncertain or even favor the dissenter. Confidence summarizes the evidence for this item; α summarizes consistency across a batch. They answer different questions.

    Problem format.Verifiable answer (numeric, expression, multiple choice) is cheap to check and usable for RL. Proofs and open legal analysis need rubric grading by a second expert — slower, dearer, and the rubric becomes part of the deliverable.

    Solution and rationale spec.Step granularity, notation, LaTeX, target length, “no leaps” rule, alternative solutions, common wrong paths. Write the style guide with five exemplar items before anyone else starts.
  6. 06

  7. 07
    Volume and difficulty mix.Say 5,000 accepted: 70% hard, 30% very hard, quotas by domain, delivered in batches. Accepted, not attempted — the number the invoice is written against.
  8. 08
    Verification protocol.Blind second solve, automatic answer equivalence, adjudication of mismatches; for proofs a rubric review by a third expert. Is model-assisted checking allowed, and is it disclosed?
  9. 09

System design considerations

  • The pipeline. Brief + style guide → authoring portal (LaTeX preview, versions, comments) → automatic checks (format, compile, dedupe, contamination) → model gauntlet → blind verification → adjudication → rationale review → client sample → delivery.
  • The gauntlet is the engineering centrepiece. Batch APIs, response caching, cheap models first as a filter, K models × n samples, answer equivalence (SymPy canonical forms with tolerance; an LLM judge with a rubric for proofs and legal), and a cost cap per item.
  • Verification by design. Second expert solves blind; final answers are compared automatically; humans adjudicate only mismatches. For proofs, a third expert grades against the rubric. Verification cost is a third of authoring cost — keep it there.
  • Yield management. Rejection-reason taxonomy, per-expert yield and coaching, calibration items in every batch. Batch 1 yield sets the price of batches 2–10; treat it as the pilot’s main output.
  • Difficulty drift. Re-run the gauntlet before each delivery and stamp hard_as_of; items that became solvable move down a tier instead of being thrown away.
  • Secrecy as infrastructure. No export from the portal, per-viewer watermarks, phrase-level leak detection, access logs — the same controls a benchmark owner expects.
  • Verifiable answers for RL. Canonical answer forms, multiple-answer handling, tolerances, and the answer kept in its own field so a verifier never has to parse prose.

Estimation lab: deliver 500 accepted reasoning problems

Reasoning-data estimates are yield models. The client buys accepted problems, but the factory pays for every serious attempt, including candidates rejected as too easy, invalid, ambiguous, contaminated, or incorrectly solved. The first question is therefore not “how long does one problem take?” It is “how many authored candidates must enter each stage for 500 to leave?”

Intuition

Estimate a funnel, not an assembly line

In a simple annotation job, most inputs become outputs after predictable work. In frontier reasoning data, the product must satisfy several independent gates: valid question, unique or well-defined answer, verified solution, desired difficulty, clean rationale, and contamination controls. A candidate can consume most of its cost before failing the final difficulty test.

accepted = authored × validity yield × verification yield × difficulty yield × editorial yield

Multiplying separate yields exposes where loss occurs. Treating “overall yield = 50%” as a permanent constant hides the operational lever. If difficulty screening rejects 40%, improve prompts and pre-screening; if second solvers disagree, improve author qualification and verification tooling.

Step 1 · Define acceptance as a checklist

Step 4 · Understand difficulty metrics through examples

pass@1 is a probability. If a reference model solves 30 of 100 single attempts, empirical pass@1 is 30%. It says a random attempt succeeds about three times in ten. It does not say the model solved exactly 30% of distinct problems unless every item was sampled once under the same protocol.
pass@4 is “at least one success.” If independent attempts each succeed with probability 0.30, the chance at least one of four succeeds is 1 − (1 − .30)^4 = 0.760. Requiring failure on at least three of four attempts is a different item-level rule. Always state whether the metric summarizes attempts across items or gates each item.
Observed four-sample result is noisy. A model going 1/4 on one item does not prove its true success probability is 25%. Four trials distinguish obviously easy from obviously hard items, not fine difficulty bands. For benchmark claims, run more seeds or aggregate many items with confidence intervals.
Second-solver agreement. If 490 of 500 accepted items have an independently matching answer, agreement is 98%. But if twenty disagreements were simply discarded before the denominator was defined, the statistic is misleading. Report agreement among items entering blind verification and the reasons items exited.
Contamination rate. Suppose semantic search flags 40 of 1,000 candidates, human review confirms 12 copied or near-copied items, and misses are estimated from a random sample. The confirmed rate is 1.2%, but detector precision is 30%. Report both; a noisy detector can create large review cost without implying widespread contamination.

System design considerations

  • Collection pipeline. Onboarding and consent → device kits → capture app with task prompts and checklists → resumable upload → automatic QA (exposure, blur, sync, duration) → privacy pass (faces, plates, screens, audio PII) → catalogue with metadata.

  • Active-learning loop. Route low-confidence proposals to humans; fine-tune the proposal models on verified labels every week; watch acceptance rise and human minutes fall. This loop is the engineering the client is paying for.
  • Measure the cost curve. Human-minutes per video-minute per layer per week on one dashboard; the contract’s price step-downs are tied to it.

  • Gold and audit. Gold clips with expert labels (2%), double annotation (3%), privacy audit (1% of frames) — all sampled by the pipeline, not by hand.
  • Delivery. Parquet or JSON with manifests and checksums; LeRobot/RLDS exporters when the client trains with them; batches lag collection by at most two weeks.

Estimation lab: collect and annotate 5,000 usable video hours

Video programs fail when “hour” is left undefined. A recorded hour is not necessarily uploaded, consent-valid, technically usable, privacy-processed, diverse, or accepted. An annotated hour may also contain several label layers whose costs differ by an order of magnitude. This lab keeps collection yield, media volume, annotation expansion, and automation separate.

Intuition

There are two linked factories with different units

The collection factory turns participant time into accepted media hours. Its losses come from setup, failed uploads, poor framing, consent problems, duplication, privacy rejection, and quota imbalance. The annotation factory turns accepted media minutes into labels. Its expansion factor is human minutes per video minute, which depends on the label layer and proposal-model quality.

recorded hours × collection yield = usable hours
usable video minutes × human-minutes/video-minute = human work minutes

Never combine those into one blended “cost per hour” until the two models are shown. Otherwise the client cannot tell whether the expense comes from recruiting and logistics or from dense annotation.

Step 6 · Understand quality metrics with concrete segments

Temporal IoU. The reference action runs from 10 s to 20 s; an annotator marks 12 s to 21 s. Intersection is 8 s (12–20), union is 11 s (10–21), so IoU is 8/11 = .727. It passes a 0.70 target. If the annotator marked 14–22, IoU would be 6/12 = 0.50 despite identifying the right action.
Boundary error complements IoU. For the 12–21 prediction, start error is 2 s and end error is 1 s. On a two-second action, the same errors would be catastrophic; IoU captures that scale dependence. Report median absolute boundary error as an interpretable operational metric and IoU as the overlap metric.
Proposal acceptance rate. If the model proposes 10,000 segments and annotators accept 7,200 unchanged, acceptance is 72%. But a model could propose only obvious actions and miss half the video. Pair acceptance with proposal recall from a human-labeled audit set. High precision with low recall does not reduce total work as expected.
Track quality. For object masks, frame-level IoU may average 0.82 while identity switches make the track unusable. Include track continuity or ID-switch rate. Metrics must match how the downstream policy consumes the labels.
Usable-hour yield. If 1,000 recorded hours produce 740 accepted hours, yield is 74%. Report rejection reasons: 12% framing, 5% privacy/consent, 4% upload corruption, 5% quota excess. Percentages should reconcile to the funnel rather than becoming an unrelated dashboard list.

System design considerations

  • Authoring workflow. Scenario from a real post-mortem → Dockerfile that bakes the broken state → oracle → behaviour tests → self-validation CI (oracle passes, unsolved fails, five runs) → blind human solve → agent gauntlet (K models × N trials) → difficulty tier → registry.
  • Tests that cannot be gamed. Probe from outside (run the cron job, check permissions, hit the port) instead of diffing files; mount the tests after the agent finishes; keep the test directory immutable; detect test edits; plant canaries.
  • Races that reproduce. A race condition is a task only if the fault reproduces every run: controlled scheduling, barriers, stress tools, fault injection by seed. Otherwise it is a flaky test with a story.
  • Realism. Multiple interacting faults, red herrings, logs that mislead — the way production actually fails. Single-fault tasks are solved by pattern matching.
  • Infrastructure. A build farm with an image cache, a private registry with digests, a sandboxed parallel eval runner, cost tracking per run.
  • Harness adapters. One task source, exporters for Terminal-Bench/Harbor, SWE-bench and the client’s harness; never maintain three copies of a task.
  • Calibration drift. Re-run the gauntlet before delivery; stamp hard_as_of; nightly validation for the contract’s life; quarantine tasks that stop reproducing.

Estimation lab: produce 100 validated coding tasks

A coding task is accepted only after authoring, environment construction, oracle creation, hidden-test review, blind solving, repeated determinism runs, and difficulty calibration. The naive estimate—author hours times an hourly rate—usually misses rejection, infrastructure, review loops, and maintenance. Treat the task as a small software product with a validation funnel.

Intuition

Separate task creation from proof that the task is valid

The visible artifact may be a repository or Docker image, but the purchased value is evidence: the initial state really fails, the oracle really passes, hidden tests measure behavior rather than a specific patch, the task does not leak its answer, repeated runs are deterministic, a competent human can solve it, and reference agents land in the desired difficulty band.

accepted tasks = candidates × build yield × blind-solve yield × determinism yield × difficulty-band yield

The final difficulty gate often happens after most engineering cost has been spent. That makes early screening and reusable templates valuable, but it also means a cheap task author who produces invalid scenarios can be more expensive than a senior author.

Step 5 · Understand validation metrics with examples

Determinism rate. Ninety-six tasks pass 5/5 clean replays, four pass 4/5. Reporting 98.8% successful runs hides that 4% of tasks are flaky. For benchmark validity, the task-level metric is stricter: only 96% are deterministic. Quarantine the four rather than averaging them away.
Oracle and unsolved-state checks. The oracle passing proves at least one valid solution exists. The initial state failing proves work is required. Neither proves the hidden tests reject shortcuts. Add mutation or adversarial solutions: if deleting the failing check, hard-coding output, or editing tests passes, the task is gameable.
Reference-agent pass@1. If three agents run five seeds each, a task with 3 successes in 15 attempts has empirical success 20%. Its sample is small; use difficulty bands such as 0%, 1–20%, 21–50%, not a claim that true difficulty is exactly 20%.
Human solve rate and time. If nine of ten qualified humans solve a task within two hours, human solve rate is 90% and median time may be 55 minutes. One expert taking six hours could indicate ambiguity or simply a mismatch in specialization. Capture failure reasons before rejecting.
Hidden-test precision and recall. Create known-good alternative solutions and known-bad partial fixes. If tests accept 18 of 20 good solutions, recall is 90%. If they reject 27 of 30 bad solutions, specificity is 90%. A test suite can be deterministic and still encode the wrong behavior.

System design considerations

  • Architecture. A runner drives the episode loop between the agent under test, the user simulator and a tool gateway of MCP mocks backed by a per-episode database snapshot; a grader reads the end state, the action trace and the transcript; every episode is stored as a trace.
  • Task authoring. Policy clause → scenario → initial state → user instruction → expected end state and forbidden actions. Subject-matter experts write, engineers encode, an oracle agent validates each task before it enters the bank.
  • Mock fidelity. Schemas from the real APIs, realistic errors, pagination, rate limits and latency, with faults injected by seed so a run is reproducible.
  • Reward design. Binary success on the end state plus penalties for forbidden actions; partial credit only when the client asks; audit sampled episodes for reward hacking — simulator jailbreaks and shortcuts that satisfy the diff without serving the user.
  • Simulator robustness. The simulator follows its own policy, detects manipulation by the agent, has its model and prompt pinned, and is evaluated separately with human realism ratings before any agent is scored.
  • RL interface. reset(seed) returns an observation; step(action) returns observation, reward, done and info; batched; curriculum by difficulty; episode caps.
  • Versioning and drift. Environment semver; a frozen eval split; nightly validation runs with reference agents; a changelog that explains every pass-rate shift.
  • Observability. Agent, tool, simulator and grader spans in one trace per episode; replay from the store; the same trace feeds the training set when the client trains.

Step 5 · Understand the gym metrics through examples

Task validity. A task is valid if the seeded state satisfies preconditions, at least one policy-compliant path reaches the goal, the grader recognizes all allowed outcomes, and resets reproduce the start. If 147 of 150 pass every check, validity is 98%, but the delivery target should still be 100%: quarantine three rather than ship a noisy denominator.
Grader precision and recall. Human auditors label 200 trajectories, 50 as true passes. The grader calls 55 passes, of which 47 are real. Precision is 47/55 = 85.5%; recall is 47/50 = 94%. High recall with weak precision inflates agent scores. Improve outcome rules before comparing agents.
Policy grader. Outcome success and compliance are separate. An agent may issue the refund correctly but violate the rule requiring identity verification. Report outcome success, policy compliance, and joint success. A single pass bit hides why behavior failed.
Simulator goal adherence. In 100 audited conversations, the simulated user reveals a hidden account number without being asked in 12, accepts an invalid alternative in 7, and follows the intended goal in 81. Goal adherence is 81%, which places an 81% ceiling on clean evaluation if failures are not detected and retried.
pass^k. If single-run success is 0.8 and runs were independent, probability of succeeding all four times is .8^4 = .4096. The reliability question is strict: a seemingly strong 80% agent is stable on four repetitions only about 41% of the time. Use empirical task-level pass^k where possible because runs are not perfectly independent.
Environment failure rate. If 2% of episodes fail because reset, tool, or simulator infrastructure breaks, the observed agent success is biased downward and variance rises. Tag infrastructure failures separately and publish their rate next to agent metrics.

The mental model: an estimate is a transparent model, not a guess

An estimate is a chain of quantities connected by formulas. The client states a desired outcome—perhaps 100,000 accepted labels, 500 hard reasoning items, or an agent gym with 150 tasks. Your job is to translate that output into the work the factory must attempt, the people and machines required to perform it, the calendar needed to coordinate it, the evidence required to accept it, and the price that covers cost and risk.

requested output × work per output ÷ productivity = capacity and time
capacity × loaded rates + non-labor cost = COGS
COGS ÷ (1 − target gross margin) = price

The formulas are easy. The hard part is choosing the right units and finding the multipliers hidden in words such as accepted, high quality, expert, urgent, and benchmark-grade. Each adjective implies a gate or constraint. Your model should make those consequences explicit.

First principle

Every estimate has a numerator, a denominator, and a definition of done

When someone says “we need 50,000 annotations in four weeks,” ask what one annotation means. Is it one worker click, one item with three independent labels, one accepted item after adjudication, or one hour of video with three label layers? The word is the numerator. Then ask what produces it: judgments per productive hour, accepted items per candidate, or tasks per engineer-week. That is the denominator. Finally ask which metric makes the item accepted.

A well-formed statement sounds like this: “We will deliver 50,000 aggregated pairs, each built from three base votes plus adaptive escalation, accepted when batch α is at least 0.80 and item confidence is at least 0.85, within twenty production days.” Now volume, quality, and time are all calculable.

The seven transformations

  1. Outcome → deliverable. Translate business intent into an artifact: training records, benchmark tasks, collected hours, an environment, or graded trajectories. “Improve the model” is an outcome; it is not yet a unit you can price.
  2. Deliverable → accepted unit. Define one unit and the acceptance gate. For preference data, one unit might be an aggregated pair. For coding data, it is a task whose oracle passes, initial state fails, hidden tests resist gaming, and repeated runs are deterministic.
  3. Accepted unit → attempted work. Add overlap, yield loss, goldens, audit samples, escalation and rework. This is where 50,000 outputs can become 195,000 attempts.
  4. Attempted work → labor and compute. Multiply work by measured time or tokens. Separate roles and stages because an expert hour, annotator hour, GPU-hour and project-management hour have different constraints and costs.
  5. Labor and compute → capacity and calendar. Divide by productive capacity, then add ramp, dependencies, batching, holidays, review queues and acceptance buffer. Headcount arithmetic is not a project schedule.
  6. Capacity → cost. Use loaded cost: pay, platform fees, employer burden or vendor markup, infrastructure, management, tooling, compliance, and a reserve for named uncertainty.
  7. Cost → commercial offer. Choose unit price, fixed milestones, time-and-materials, or a hybrid. Calculate margin, state volume and scope assumptions, and define which changes reopen the price.

A tiny example from end to end

A client wants 10,000 accepted classifications in ten workdays. Each item gets two labels; disagreements (estimated at 15%) get a third. Five percent of task exposures are goldens, 4% of items require replacement, and a valid judgment takes 90 seconds.

  1. Base judgments: 10,000 × 2 = 20,000.
  2. Disagreement judgments: 10,000 × .15 = 1,500.
  3. Golden injection: if production work is 95% of exposures, 21,500 / .95 = 22,632 total exposures.
  4. Replacement: 22,632 / .96 = 23,575 attempts.
  5. Labor: 23,575 × 1.5 / 60 = 589.4 hours.
  6. Capacity: at five productive hours per worker-day over ten days, mathematical minimum is 589.4 / 50 = 11.8; with 25% headroom, plan fifteen active workers.
  7. Direct labor at $18/h is $10,609. Add $4,000 setup and PM, $1,500 platform, and 8% reserve: COGS ≈ $17,397, or $1.74 per accepted item.
  8. At a 35% target gross margin, required price is $17,397 / .65 = $26,765, or $2.68 per item.

That example is not a rate recommendation. Its purpose is to show the full chain and expose the dominant variables. If judgment time is actually three minutes, direct labor doubles. If disagreement is 25%, it rises modestly. The pilot should measure time before debating a five-point change in the management allocation.

Fermi estimation: how to proceed with incomplete information

In an interview you rarely receive every number. Make bounded assumptions, label them, and use known relationships. A useful pattern is: state the unit, choose a round base case, compute, sanity-check against another method, then give a range.

Anchor

Choose a quantity you can reason about: minutes per judgment, hours per expert task, video bitrate, or productive hours per person-day.

Decompose

Break a hard unknown into easier factors. Monthly judgments = active workers × days × productive hours/day × judgments/hour.

Round deliberately

Use 20 workdays, 60 minutes, and simple percentages. False precision hides uncertainty. Preserve exact arithmetic only when it clarifies a sensitivity.

Cross-check

Estimate throughput both bottom-up from workers and top-down from historical batch velocity. Large disagreement means a missing constraint.

Units prevent most estimation errors

Write units into formulas as if doing dimensional analysis in physics. If task time is minutes per judgment and volume is judgments, their product is minutes. Dividing by sixty minutes per hour yields hours. If a result is “workers per hour” when you expected workers, the model is wrong.

Scope inputs: the minimum information needed for a real estimate

The scoping conversation is not a feature checklist. Each question should map to a variable, a constraint, or an acceptance rule in the model. If an answer will not change design, schedule, cost, risk or quality, it is probably not an early discovery question.

1 · Decision and downstream use

Ask what decision the artifact changes. Training data, an offline benchmark, a launch gate, regression monitoring and RL episodes can use similar-looking records but require different confidence, representativeness, secrecy and repeatability. A training corpus may tolerate probabilistic labels across millions of items; a benchmark demands clean, stable tasks because one bad item corrupts the score.

Example: A client asks for 100,000 preference pairs. If the use is reward-model training, three votes with confidence and broad coverage may be enough. Same count, different product.

Volume and yield: converting output into attempted work

Volume estimation is a conservation problem. Follow units through each gate and ensure every loss is accounted for. The most reusable patterns are redundancy, funnel yield, rework, sampling and recurring cadence.

Redundancy and overlap

When several independent people judge the same item, output work multiplies. Fixed overlap is simple: items × raters. Adaptive overlap needs expected value.

expected judgments/item = base overlap + Σ(probability of escalation path × extra judgments on that path)
Example: Start with two raters. They agree on 78% of items; the remaining 22% receive a third. Ten percent of those still require two expert votes. Expected judgments are 2 + .22×1 + .22×.10×2 = 2.264 per item. For 100,000 items, plan 226,400 production judgments before goldens and rework.

Adaptive overlap is powerful because most easy items avoid unnecessary votes. But a two-rater start cannot estimate all agreement statistics in the same way as three independent votes, and tie-handling must be explicit. Operational savings should not silently change the quality contract.

Sequential yield versus parallel failure reasons

If stages occur sequentially, multiply conditional yields. If failure categories are mutually exclusive outcomes of one stage, add their rates and subtract from one. Confusing the two produces large errors.

Sequential

90% pass validity, then 80% verification, then 75% difficulty.

yield = .90 × .80 × .75 = 54%

From 1,000 candidates, 540 survive all three.

Mutually exclusive

Of raw video, 10% fails framing, 4% upload, 6% privacy. If each hour has one primary outcome:

yield = 1 − .10 − .04 − .06 = 80%

Do not multiply unless each check is conditional among survivors.

Overlapping reasons

An hour can fail framing and privacy. Adding rates double-counts overlap. Use an observed accepted/raw ratio or model joint outcomes.

Rework versus replacement

Rework repairs the same unit; replacement creates a new unit. Their time and success differ. Suppose 8% of items fail QA. Sixty percent are repairable in five minutes with 90% success; forty percent require replacement at the full twenty-minute cost.

expected extra minutes/item = .08 × [(.60 × 5) + (.40 × 20)] = .88 min

If repair can fail, include its second path: .08 × .60 × .10 × 20 = .096 additional replacement minutes. Modeling every rare branch may be unnecessary, but distinguish cheap correction from total restart.

Golden and audit sampling conventions

“Ten percent goldens” is ambiguous. It may mean ten golden exposures per one hundred total exposures, or ten added for every one hundred production tasks. The first requires dividing by 0.90; the second multiplies by 1.10. For 100,000 production judgments, results are 111,111 versus 110,000. The difference is small here but the habit matters.

QA sampling may trigger more work. A 3% expert sample of 50,000 items is 1,500 audits. If each audit takes six minutes, that is 150 expert hours. If a failed audit rejects an entire 1,000-item batch, expected rework depends on batch failure probability and policy—not simply 3%.

Batch acceptance expected value

Example: Fifty batches of 1,000 items each have an estimated 6% chance of rejection. A rejected batch requires reviewing all 1,000 items at two minutes each, but only 30% need relabeling at four minutes. Expected additional minutes per batch are .06 × (1,000×2 + 300×4) = 192. Across fifty batches, 160 hours. A batch-level rejection rule creates correlated rework and should be modeled separately from item-level defects.

Recurring demand, backlog and Little’s Law

For steady-state systems, flow matters more than total project volume. Little’s Law states L = λW: average work in process equals throughput rate times average time in system.

Example: A reasoning factory accepts 50 problems per week and each candidate spends an average of three weeks from submission to final decision. Average work in process is 50 × 3 = 150 accepted-equivalent items; because yield is 50%, roughly 300 candidates may be somewhere in the funnel. If dashboards show 600, queues or blocked reviews are doubling cycle time.

Little’s Law is a diagnostic, not a schedule by itself. It assumes a stable system. During ramp or a one-time deadline, use a week-by-week flow model.

New workers or authors do not start at mature throughput. Model cohorts by week. Suppose forty annotators start, with productive hours per person of 10, 18, 24 and 25 across their first four weeks. A second cohort of twenty starts in week three.

Demand variability and service levels

Average arrival rate is not enough when daily demand varies. Capacity near 100% utilization causes queues to explode because there is no room for bursts or slow tasks. The goal is not to average the two; it is to learn why they differ.

Capacity and schedule: turning hours into a believable delivery plan

A capacity estimate answers “how much can the system produce?” A schedule answers “when will this specific scope be accepted?” They are related but not identical. Capacity may be parallel; dependencies, ramp, reviews and client decisions create a critical path.

Productive time is not paid time

An eight-hour paid day contains training, breaks, meetings, tool latency, queue starvation, clarification, QA feedback and administration. Estimate productive time from telemetry or use a conservative range. For crowd annotation, 4–6 productive hours per active day may be reasonable depending on task availability. For engineers, 20–30 focused task hours per week may be more realistic than forty. Do not hide utilization inside task-time assumptions; keep them separate.

productive capacity = people × active days × paid hours/day × utilization
or directly: people × measured productive hours/person-period
Example: Twenty engineers for six weeks is 4,800 paid hours at 40 h/week. At 65% productive allocation, usable project capacity is 3,120 hours. If your bottom-up work estimate is 3,000 hours, the plan has only 4% headroom before accounting for dependencies. It is not a comfortable six-week plan.

Headcount from hours

The first calculation is simple:

people required = total productive hours ÷ (productive hours/person-period × periods available)

Then adjust for specialization, parallelizability, management span and headroom. If 1,000 hours require a licensed reviewer and 4,000 require general annotators, five thousand divided by an average person is meaningless. Size each constrained role separately.

Throughput, cycle time and work in process

Throughput is completed units per time. Cycle time is elapsed time from start to completion for one unit. Work in process is everything currently inside the system. Little’s Law connects their averages: WIP = throughput × cycle time.

Example: A coding-task factory accepts ten tasks per week and average candidate cycle time is four weeks. It should contain about forty accepted-equivalent tasks in progress. At 70% yield, roughly 57 candidates may be active. If the actual queue is 120, either cycle time is longer than reported or throughput is about to rise. This turns queue size into a diagnostic.

Utilization and queue behavior

High utilization sounds efficient but harms latency in variable systems. When reviewers are busy almost all the time, any burst creates a queue. The exact relationship depends on arrival and service distributions, but the practical rule is clear: the stricter the turnaround SLA and the more variable the work, the more headroom you need.

Predictable batch work

Tasks are similar, deadlines are weekly, and backlog is allowed. Planned utilization can be higher, perhaps 85–90%.

One-day SLA

Arrivals vary and some cases take much longer. Plan 65–80% or keep an overflow pool.

Scarce expert gate

One expert outage can stop delivery. Use multiple qualified reviewers, appointment blocks, or a longer stated SLA.

Variability: average task time is not enough

Suppose median task time is four minutes, mean is six, and p90 is fifteen because a small number of difficult items take much longer. Labor cost follows the mean total time, not the median. Operational staffing and timeout policy need the distribution. Estimate by strata or use sampled totals.

Example: 80% of tasks take 3 minutes and 20% take 18. Mean is .8×3 + .2×18 = 6 minutes. Staffing from the 3-minute “typical” task underestimates labor by half. Routing the hard 20% to specialists may improve both predictability and quality.

Machine capacity

For compute work, distinguish service time, concurrency, rate limits and utilization. The theoretical wall-clock time for independent jobs is total service time divided by concurrency. Then adjust for long tails, retries, setup and provider throttles.

ideal wall time = jobs × average service time ÷ concurrent slots
planned wall time = ideal ÷ target utilization × retry factor
Example: 20,000 model-judge calls average 12 seconds. With 100 concurrent slots, ideal time is 2,400 seconds, or 40 minutes. At 70% utilization and 8% retry overhead, planned time is 40/.70×1.08 = 61.7 minutes. If the API limit is only 1,000 requests/minute, rate limit—not concurrency—sets a floor of twenty minutes, still below the adjusted capacity floor.

Metrics and confidence: know what each number can and cannot prove

Metrics are part of scope because they define acceptance and create work. Choose a metric by the question it answers. Agreement asks whether raters are consistent; accuracy asks whether predictions match a trusted reference; precision and recall describe different error costs; IoU measures overlap; calibration asks whether confidence means what it claims; pass@k and pass^k answer different reliability questions.

Start with the decision and the error matrix

For any binary gate, write true condition versus predicted decision. If FAIL is the positive class:

Human says FAILHuman says PASS
System says FAILTrue positive: caught defectFalse positive: good item sent to review/rejected
System says PASSFalse negative: bad item shippedTrue negative: good item passes

Precision asks, “When the system says FAIL, how often is it right?” Recall asks, “Of all true failures, how many did it catch?”

precision = TP / (TP + FP)
recall = TP / (TP + FN)
F1 = 2 × precision × recall / (precision + recall)
Worked confusion matrix: Human audit has 100 failures and 900 passes. A judge catches 92 failures and flags 45 good items. Precision is 92/(92+45)=67.2%; recall is 92/100=92%. This may be good for triage—most failures are caught—but poor for automatic rejection because one third of rejections are wrong.

Accuracy and class imbalance

If only 1% of items fail, a classifier that always says PASS is 99% accurate and useless. Report class-specific metrics, prevalence and confusion counts. Balanced accuracy averages recall for each class. Precision depends on prevalence: the same detector looks less precise when true failures are rare.

Base-rate effect: A detector has 90% failure recall and 95% specificity. At 20% failure prevalence, among 1,000 items it catches 180 failures and falsely flags 40 passes: precision 81.8%. At 2% prevalence it catches 18 and falsely flags 49: precision only 26.9%. Threshold and workflow must match deployment prevalence.

Agreement is not accuracy

When no ground truth exists, measure whether independent raters apply the rubric consistently. Raw agreement is intuitive but can be inflated by dominant categories. Chance-corrected measures compare observed disagreement with disagreement expected from label marginals.

Krippendorff α = 1 − observed disagreement / expected disagreement
Example: Observed disagreement is 10% and expected disagreement from marginals is 40%. α is 1 − .10/.40 = .75. If expected disagreement were only 12%, the same 10% observed disagreement gives α = 0.17 because near-unanimous marginals make chance agreement high.

Use α when rater counts vary or votes are missing. Cohen’s κ fits exactly two raters; Fleiss’ κ assumes a fixed number. Report item confidence separately. High batch agreement does not guarantee every item is unambiguous.

Reliability of a metric estimate

A sample metric is uncertain. For a pass proportion, attach a confidence interval. The Wilson interval behaves better than the simple normal approximation for small samples or proportions near zero and one.

Example: A client audits 47 of 50 items and all 47? Clarify the denominator: suppose 47 of 50 pass, observed 94%. The approximate 95% Wilson interval is about 84%–98%. You cannot confidently claim the true pass rate exceeds 92%. With 470 of 500, the interval narrows to roughly 91.6%–95.7%, making the acceptance decision more stable.

Sample size depends on the desired margin of error, confidence and prevalence. Near 50%, a rough 95% sample for ±5 percentage points is about 385 independent items. For ±2 points it is about 2,400. Finite population correction matters only when sampling a large share of a small batch.

Design the sample around the decision and defect taxonomy. Critical defects may require zero tolerance; minor defects can use a rate. Stratify by language, task family or risk so easy majority classes do not hide failure in a small segment.

Calibration and expected calibration error

A confidence of 0.8 should be correct about 80% of the time. Group predictions into confidence bins, compare average confidence with observed accuracy, and weight the absolute gaps. That is expected calibration error (ECE).

Example: In the 0.8–0.9 bin, 200 items have average confidence 0.85 but only 150 are correct, accuracy 0.75. That bin contributes 200/N × |.85−.75| to ECE. An overconfident judge may rank items usefully yet make unsafe auto-accept decisions.

Calibration can drift when rubric, language, domain or model version changes. Calibrate on one set, choose thresholds on another if possible, and evaluate on a held-out set. Never report confidence as a probability without checking calibration.

Temporal and spatial overlap

Intersection over union is intersection / union. It penalizes both missing coverage and extra coverage. For temporal segments, lengths are seconds; for masks or boxes, areas.

Example: Reference interval [5, 15], prediction [8, 18]. Intersection is 7, union is 13, IoU = 0.538. Boundary errors are +3 s start and +3 s end. If downstream training tolerates rough boundaries, IoU 0.5 might be adequate; for short surgical actions it may be unusable. Targets come from use, not convention.

pass@k and pass^k

These notations are frequently confused. pass@k asks whether at least one of k attempts succeeds. Under independent constant success probability p, it is 1 − (1 − p)^k. pass^k asks whether all k attempts succeed: p^k. The first rewards sampling; the second measures repeatability.

A data factory controls label process metrics; the client ultimately cares about model lift, safety incidents, or task success. Downstream change can be affected by model architecture, training recipe and evaluation. Offer a joint experiment: frozen training recipe, comparable baseline, held-out evaluation and confidence intervals. Do not guarantee lift solely from annotation agreement.

Cost is what delivery consumes. Price is what the client pays. Margin is the space between them that funds sales, product investment, corporate overhead and risk. A defensible commercial model shows cost blocks, avoids double counting, and matches payment structure to who controls the uncertainty.

Loaded rates

The rate paid to a worker is not necessarily the effective cost per productive hour. Platform fees, payroll burden, benefits, idle time, qualification, supervision and currency/payment costs may apply.

Example: An annotator receives $16 per paid hour. Employer/platform burden is 25%, so paid-hour cost is $20. If 80% of paid time is productive, effective productive-hour cost is $20/.80 = $25. Using $16 against productive task hours understates labor by 36%.

For external experts paid per accepted unit, convert to an expected cost per attempted unit using yield. For salaried staff, use loaded annual cost divided by realistic productive hours, not 2,080 without adjustment.

Fixed-cost amortization and volume

Setup cost per unit falls with committed volume. If tooling and rubric design cost $80,000, it adds $8 per unit at 10,000 units and $0.80 at 100,000. A low volume tier cannot receive the same unit rate unless setup is charged separately.

unit COGS = variable COGS/unit + fixed program cost ÷ committed accepted units
Example: Variable COGS is $5.20/pair and fixed cost is $60,000. At 10,000 pairs total COGS is $11.20; at 50,000 it is $6.40. A $9 price loses money in the first case and supports 28.9% gross margin in the second. Volume discounts should follow amortization and real efficiency, not optimism.

gross margin = (revenue − COGS) / revenue
price for target margin = COGS / (1 − target margin)

Choose a commercial structure by uncertainty and control

Fixed price

Use for bounded deliverables with stable inputs and acceptance. Protect with assumptions, milestones, exclusions and change control.

Unit price

Use for repeatable accepted output. Define the unit, mix, minimum volume, yield ownership and what happens to rejected work.

Time & materials

Use for discovery, uncertain integration, evolving policy and client-controlled priorities. Add a cap or checkpoint for budget confidence.

Hybrid

Fixed setup + unit production + pass-through compute + maintenance retainer. Often best for data factories and gyms.

Outcome-based

Use only when the outcome is measurable, causal influence is clear, baseline is agreed and downside is bounded.

Sensitivity and break-even

Change one driver at a time to see what moves unit economics. Rank by elasticity: percentage change in outcome divided by percentage change in input. In labor-heavy tasks, minutes per attempt and yield often dominate. For software-heavy environments, fixed engineering scope and maintenance dominate.

Automation break-even: A proposal model costs $120,000 to build and operate for the program. It saves 1.5 human minutes per item at $24/productive hour, or $0.60/item. Break-even volume is $120,000/$0.60 = 200,000 items. At 50,000 items, it is not justified purely by labor savings, though quality or schedule benefits may still matter.

Cash flow and milestones

A profitable project can be cash-flow negative if recruiting, devices and engineering are paid before client acceptance. Align payment milestones with irreversible spend. For example: 20% at kickoff, 20% at design acceptance, 25% after pilot, 25% on production batches, 10% at final acceptance. For long programs, monthly invoicing reduces financing risk.

Price waterfall example

A program has $420,000 base COGS including expected risk. Target margin is 35%, so list price is $420,000/.65 = $646,154. The client commits volume that saves $25,000 fixed cost and prepays, earning a $10,000 discount. Revised COGS is $395,000 and net price is $636,154, margin 37.9%. Prompt: Deliver 200 accepted problems. Candidate gates: completeness 92%, automated validity 90%, blind solve 80%, difficulty 60%, editorial 95%. Authoring is three hours/candidate at $100/h. Case 5 · Gym operating cost

Prompt: Run one million episodes per month. Mean episode uses 30,000 input tokens and 3,000 output tokens, lasts 50 seconds, writes 200 KB compressed trajectory data, and has 5% infrastructure retry. Case 7 · Metric choice

Prompt: An LLM judge evaluates rare critical failures. In 10,000 audited items, 100 are true failures. The judge catches 95 but falsely flags 297 good items. Compute accuracy, failure recall and precision. Decide whether it can auto-reject.

  2. Accuracy = (95+9,603)/10,000 = 96.98%.

How to audit an estimate before presenting it

A second pass should try to break the model, not merely check arithmetic. Read every line and ask whether the units reconcile, whether a loss is applied at the correct stage, whether work is counted once, and whether the schedule respects dependencies. Then inspect incentives: could a team hit the named metric while producing something the client does not want?

  1. Reconcile volumes. Begin with inputs and follow every branch. Candidates should equal accepted units plus rejects, unless items can be repaired or split. Judgment attempts should reconcile to base votes, escalations, goldens, audits and replacements. If dashboard categories overlap, do not add them.
  2. Reconcile hours. Total stage hours should equal items entering that stage multiplied by time per entering item. Confirm whether time is median, mean, paid, active or accepted-only. Labor cost should use productive hours with an effective productive-hour rate.
  3. Reconcile people. Each role’s required hours must fit the named people and calendar. Check part-time allocation, ramp, attrition, holidays and review duties. A lead counted as 100% production and 100% management is double-booked.
  4. Reconcile calendar. Confirm prerequisites and approval waits. Adding more people cannot compress work that depends on one client decision, one scarce reviewer, or a serial environment foundation.
  5. Reconcile metrics. Every target needs a population, protocol and sample. Make sure denominators include failed or abstained cases appropriately and that acceptance sampling can actually distinguish the threshold.
  6. Reconcile money. Sum cost blocks to COGS, calculate margin from revenue rather than cost, and verify fixed costs are amortized over committed—not hoped-for—volume. Confirm discounts do not push price below variable cost.

“The automation saves 70%.”May ignore build cost, recall, QA and maintenance.At what volume does total cost break even at equal accepted quality?
“We can double throughput by doubling people.”Recruiting, tooling, reviewers and client feedback may not scale.Which stage becomes the next bottleneck?

More rapid drills

Agreement pilot

A 1,000-item pilot uses three raters. Fourteen percent of votes are missing, and 180 items receive only two votes. Which agreement statistic fits? How would missingness affect capacity and confidence?

Batch audit

You observe 96 passes in a 100-item audit against a 95% target. Explain why observed 96% alone is not strong proof and what larger sample or acceptance rule you would use.

Queue bottleneck

Authors submit 40 items/week, reviewers clear 32, and current review backlog is 96. Estimate backlog growth and waiting time if nothing changes. How many reviewer-equivalent items/week close the gap in six weeks?

Mix shift

A flat-price task portfolio moves from 10% to 30% concurrency tasks, whose unit cost is 2.5× normal. Calculate the weighted-cost increase and identify the contractual protection.

Utilization

A 20-person pool supplies 500 productive hours/week and demand averages 470 with a 100-hour standard deviation. Is average capacity sufficient for a one-week SLA? Propose overflow or headroom.

Yield investment

A $40k training program raises accepted yield from 45% to 58%. Candidate cost before final gates is $300 and target output is 500. Estimate candidate savings and whether the investment pays back.

Model answer to the yield-investment drill

At 45% yield, 500 accepted units require 500/.45 = 1,112 candidates. At 58%, they require 500/.58 = 863, saving about 249 candidates. At $300 of pre-gate cost each, savings are $74,700. After the $40,000 training investment, net program savings are about $34,700. The investment also reduces schedule load and review queue size. Validate that the higher yield does not come from making items easier or relaxing acceptance; yield improvement must be measured at the same definition of done.

How to update an estimate after the pilot

Replace assumptions with measured distributions, not just averages. Record task time by stratum, yield by gate, rework path, worker activation, reviewer queue time, model-token use, infrastructure retries and client decision latency. Recalculate base, optimistic and conservative cases. Compare predicted versus observed pilot cost and explain variance line by line.

For example, suppose the pilot predicted 4.5 minutes per judgment and 20% escalation. Observed time is 5.2 minutes and escalation 13%. Time raises labor about 15.6%; lower escalation reduces expected votes perhaps 4%. Net cost still rises. A mature readout says which effect wins rather than announcing that one metric improved.

Freeze a baseline version after the pilot: scope, unit, mix, rubric, workflow, rates, yields, metrics and dependencies. Production performance can then be compared against that baseline. When the client changes the rubric or target model, create a new version and quantify the delta. This is estimation as an operating discipline, not a one-time spreadsheet.

Thinking aloud in the room

Clarify (two or three questions, not ten) → scope (what is in, what is out, the unit) → design (the pipeline, the parts that can be wrong) → measure (how you will know) → price (the unit and the levers) → risks (what you would watch first). Say which step you are on. Interviewers grade structure they can see.

How to talk about price

  • Price the unit the client gets value from. An accepted problem, a usable hour, a validated task, an environment milestone. Never an hour of annotator time — that hides the yield and the quality inside their risk.
  • Show what is inside the unit. Overlap, escalation, goldens, QA, PM. A competitor’s cheaper unit usually has less in it; put yours side by side.
  • Give a range with its assumptions. “$1,300–1,800 per accepted item at 50–65% yield, PhD authors, verifiable answers.” A single number without assumptions is a promise you can’t keep.
  • Name the levers and who holds them. Shorter stimuli, adaptive overlap, expert tier, automation, difficulty tier. Most levers raise quality and lower cost together; say which ones don’t.
  • Price the pilot to discover the unknown. Yield, natural agreement, acceptance rate, human-minutes per video-minute. The pilot is fixed-price; production is priced on what the pilot found.
  • Tie step-downs to measurable improvement. Price falls when the proposal acceptance rate crosses 70%, or when yield passes 60%. The client shares in the engineering gain and has a reason to help.
  • Change control for the spec. A rubric or ontology change re-baselines the price; say so on day one, kindly.
  • Know your own margin; never say it. The book’s example: COGS $5.75 on a $9 pair is 36% gross margin; the levers take COGS to $3.60 and margin to 60%. That is why you fight for the levers, not for the rate.

Red flags before you price, and the checkpoints after

Red flags

  • No decision owner. Nobody can say “accepted”; every batch becomes a negotiation.
  • No definition of done. “High quality” without a metric or a sample review.
  • No goldens and no appetite to make them. You cannot measure annotators or a judge.
  • The rubric changes weekly. Every change re-baselines; price it or stop it.
  • “We’ll sort the format later.” Delivery disputes at the end.
  • Unlimited revisions in the contract. Yield risk with no cap.
  • Data that can’t legally be used. Consent, licences, residency — ask early.
  • A deadline the pilot can’t fit inside. You will be pricing blind.

Checkpoint cadence

  • Kickoff. Decision, done, owner, constraints, schema draft.
  • Spec sign-off. Rubric or style guide or policy document, goldens, acceptance criteria, in writing.
  • Pilot readout. The unknown number (yield, α, acceptance rate) and the production price it implies.
  • Batch reviews. Acceptance sampling, metrics vs targets, rejection taxonomy, rework.
  • Monthly steering. Levers pulled, step-downs earned, change requests, risks.
  • Close-out. Provenance pack: versions, annotator and expert pools, agreement history, audit trail.

pass@k versus pass^k

Run a task n times and count c successes. Two different questions have two different estimators:

pass@k — can it?

pass@k = 1 − C(n − c, k) / C(n, k)
# probability that at least one of k attempts succeeds
# n = 8, c = 6:  pass@1 = 0.75   pass@2 = 0.964   pass@4 = 1.0

Rewards ability. Rises with k. Fine for “is this task solvable by this model”.

pass^k — can you deploy it?

pass^k = C(c, k) / C(n, k)      # ≈ (c / n)^k for large n
# probability that all k attempts succeed
# n = 8, c = 6:  pass^1 = 0.75   pass^2 = 0.536   pass^4 = 0.214   pass^8 = 0.0

Rewards reliability. Falls with k. The τ-bench number; the one a customer-facing deployment needs.

The numbers above are the ones labs/dataset-examples/12-agentic-gym/gym.py prints for six successes in eight trials. The gap between the two curves is the variance you would ship. Two scoping consequences: pass^k is only meaningful if the environment is deterministic (same seed, same simulator), and a simulator that fails 5% of the time by itself puts a ceiling of about 0.95k on any agent’s pass^k — which is why the simulator’s own failure rate is reported next to the agent’s.

Judge designs per data type

Every judge is the same five-part prompt with a contract: the task definition, the inputs the criterion needs and nothing else, a precise rubric with boundary examples, a reasoning-first instruction, and a structured schema with the verdict last. Temperature zero; prompt version on every score; agreement with humans published.

Preference pre-screen
Pairwise, both display orders, tie allowed. Output: winner, confidence, and the same closed reason taxonomy the annotators use, so judge reasons and human reasons can be compared item by item.
Reasoning — equivalence
Inputs: reference answer, candidate answer, answer type. Runs only after exact match and SymPy fail. Output: equivalent true/false plus the normalisation it applied. Measured as FAIL recall on known mismatches.
Reasoning — rationale
Inputs: problem, solution, style guide. Checklist: every step justified, no leaps, notation consistent, final answer matches the answer field. Output: per-check pass/fail, then the verdict.
Video — label verifier
Inputs: sampled frames for the interval, the ASR, the proposed narration and boundaries. Question: “does the camera wearer perform <verb> on <noun> within this interval?” Output: yes/no, boundary adjustment, confidence.
Coding — task review
Inputs: instruction, Dockerfile, tests, oracle. Checklist: instruction unambiguous; tests probe behaviour; not solvable by editing tests; realistic; difficulty estimate. Output: per-check, then verdict. A human still accepts.

FLIP = {"A": "B", "B": "A", "tie": "tie"}

def judge_pair(q, a, b):

    v2 = call_judge(PAIRWISE.format(q=q, a=b, b=a))     # B shown first

            "confidence": min(v1["confidence"], v2["confidence"]) if consistent else 0.5,
            "reasons": sorted(set(v1["reasons"]) | set(v2["reasons"])),
            "judge": JUDGE_MODEL, "rubric_version": "v3", "temperature": 0}

A preference is counted only if it survives the swap; otherwise it is a tie with low confidence, which routes the pair to humans. The judge model is from a different family than any model that produced the videos’ rankings.

The calibration protocol

The same loop used to improve any classifier, with the judge prompt as the model — and two rules specific to a data factory: the calibration set is labelled by the experts who own the rubric, and it is disjoint from the goldens that annotators are paid against.

  1. 01
    Measure the humans first.Two experts label the same 100 items. Their κ is the ceiling. Below 0.6, fix the rubric before touching the judge — a criterion experts disagree on cannot be judged.
  2. 02
    Build the calibration set.300–500 items, stratified by difficulty and by label, each with a one-line critique. The critique is what makes a label teachable. Keep it disjoint from any eval or golden set.
  3. 03
    Run the judge under the contract.Temperature 0, a fixed prompt version, both display orders for pairwise, structured output, a model family different from the one under test.
  4. 04
    Compute and publish.Accuracy, κ against the experts (and its ratio to the inter-expert κ), FAIL precision and recall, swap consistency, ECE. These numbers travel with every score the judge ever produces.
  5. 05
    Read every disagreement.They cluster: a rule the rubric never stated, a boundary case humans handle one way, a formatting pattern that confuses the judge.
  6. 06
    Edit the rubric, not the verdicts.Add the missing rule; add two or three few-shot examples from the critiques per failure mode; tighten the definition.
  7. 07
    Re-measure, version, re-baseline.Agreement should rise. The new rubric gets a version; old scores are not compared with new ones.
  8. 08
    Deploy by role, with thresholds.Pre-screen only with high-precision PASS; triage by confidence; audit by random sample. Judge verdicts are never shown to annotators before they vote.
  9. 09
    Monitor drift weekly.A fresh 100-item human sample; alarm if κ drops by more than 0.10 or FAIL recall falls below target; the rubric or the distribution moved.
  10. 10
    When prompt editing plateaus.An ensemble of two or three families with majority vote and disagreement routed to humans; or a judge fine-tuned on the calibration labels and critiques, evaluated the same way.

# judge_metrics.py — standard library only
from math import comb, sqrt
from collections import Counter

def cohen_kappa(a, b):
    """Two raters, equal-length label lists. Chance-corrected agreement."""
    n = len(a); cats = set(a) | set(b)
    po = sum(x == y for x, y in zip(a, b)) / n
    ca, cb = Counter(a), Counter(b)
    pe = sum((ca[c] / n) * (cb[c] / n) for c in cats)
    return (po - pe) / (1 - pe) if pe < 1 else 1.0

def fail_precision_recall(judge, human, fail="FAIL"):
    tp = sum(j == fail and h == fail for j, h in zip(judge, human))
    fp = sum(j == fail and h != fail for j, h in zip(judge, human))
    fn = sum(j != fail and h == fail for j, h in zip(judge, human))
    p = tp / (tp + fp) if tp + fp else 0.0
    r = tp / (tp + fn) if tp + fn else 0.0
    return p, r

def krippendorff_alpha_nominal(units):
    """units: one list of labels per item (any number of raters; items with < 2 votes are skipped)."""
    units = [u for u in units if len(u) >= 2]
    n = sum(len(u) for u in units)
    do = sum(sum(1 for i in range(len(u)) for j in range(len(u)) if i != j and u[i] != u[j]) / (len(u) - 1)
             for u in units) / n
    counts = Counter(l for u in units for l in u)
    de = sum(counts[c] * counts[k] for c in counts for k in counts if c != k) / (n * (n - 1))
    return 1 - do / de if de else 1.0

def swap_consistency(win_order1, win_order2):
    """Winner ids ('A', 'B', 'tie') for the same pairs judged in both display orders."""
    return sum(w1 == w2 for w1, w2 in zip(win_order1, win_order2)) / len(win_order1)

def position_bias(win_order1, win_order2):
    """order1 shows A first, order2 shows B first. P(first-shown wins) - 0.5 over decided pairs."""
    first = sum(w == "A" for w in win_order1) + sum(w == "B" for w in win_order2)
    decided = sum(w != "tie" for w in win_order1) + sum(w != "tie" for w in win_order2)
    return first / decided - 0.5 if decided else 0.0

def ece(conf, correct, bins=10):
    """conf: judge's stated P(verdict correct); correct: 1 if it matched the human label."""
    n = len(conf); total = 0.0
    for b in range(bins):
        lo, hi = b / bins, (b + 1) / bins
        idx = [i for i, c in enumerate(conf) if (lo < c <= hi) or (b == 0 and c == 0)]
        if idx:
            acc = sum(correct[i] for i in idx) / len(idx)
            avg = sum(conf[i] for i in idx) / len(idx)
            total += len(idx) / n * abs(acc - avg)
    return total

def wilson(p_hat, n, z=1.96):
    d = 1 + z * z / n
    centre = (p_hat + z * z / (2 * n)) / d
    half = z * sqrt(p_hat * (1 - p_hat) / n + z * z / (4 * n * n)) / d
    return centre - half, centre + half

def pass_at_k(n, c, k):  return 1 - comb(n - c, k) / comb(n, k)
def pass_hat_k(n, c, k): return comb(c, k) / comb(n, k)
