API rate limiter

A rate limiter is a shared gate in front of an API. It must answer “may this request pass?” in a millisecond, even when many gateway servers are checking the same client at once. The main choices are how to count, where to keep the count, and what to do if that store is unavailable.

core choice
token bucket for bursts · sliding-window counter for accuracy
where it runs
gateway middleware + a shared Redis counter store
the hard part
atomic check-and-increment across nodes
the policy question
fail open or fail closed when Redis is unreachable

Requirements and scale

Functional

  • Limit requests per client identity (API key, user id, IP) per rule, e.g. 100 requests per minute, 10 per second burst.
  • Multiple rules per endpoint and per tier; rules change without a redeploy.
  • Reject with 429 and tell the client when to retry (Retry-After, X-RateLimit-Remaining).
  • Weighted requests: an expensive call can cost more than one token.
  • Usage visibility for the client and for operators.

Non-functional

  • Latency: adds under 1–2 ms to the request path.
  • Availability: the limiter must never be the reason the API is down; explicit fail-open or fail-closed policy.
  • Accuracy: small over-admission under races is acceptable; large under-admission is not.
  • Distributed: hundreds of gateway nodes see one consistent count per client.
  • Memory-bounded: O(1) state per client-rule pair.

System design

Worked example

A client may send 100 requests per minute, with a burst of 10

Intuition: a bucket of tickets.The client starts with 10 tickets. Each request spends one; new tickets drip in over time. A request with no ticket gets rejected.

  1. The gateway identifies client acme and loads its cached rule.
  2. One Redis Lua call refills the bucket from the last timestamp and tries to spend one token atomically.
  3. If a token exists, Redis returns allowed and the gateway forwards the request.
  4. If the bucket is empty, the gateway returns 429 plus Retry-After.

What to notice: the atomic script prevents two gateway nodes from spending the same last token. Capacity controls the burst; refill rate controls the long-run average.

Algorithms, and what each one does

Token bucket

A bucket holds up to b tokens and refills at r per second; a request of cost c passes if c tokens are present. Stored as two numbers (tokens, last_refill); refill is computed lazily on access.

fits: user-facing API limits, bursts allowed up to b · remember: O(1) memory, allows a burst of b then r/s
Leaky bucket

A queue drained at a constant rate; arrivals beyond the queue are dropped. Smooths output to exactly r; used for traffic shaping rather than admission.

fits: shaping outbound calls to a third party · remember: smooth output, adds queuing delay
Fixed window counter

One counter per window (minute); reset at the boundary. Simple, but a client can do 2× the limit around the boundary (end of one window + start of the next).

fits: coarse quotas, logging · remember: boundary burst = 2× limit
Sliding window log

Store the timestamp of every request; count those within the last window. Exact, but memory grows with the rate.

fits: low-rate, high-value limits (login attempts) · remember: O(n) memory per client
Sliding window counter

Keep the previous and current fixed-window counts; estimate the sliding count as prev × (overlap fraction) + current. Two numbers per key, accurate to a fraction of a percent in practice.

fits: the default when accuracy at edges matters · remember: O(1), no boundary burst
GCRA

Generic cell rate algorithm: a token bucket expressed as a single “theoretical arrival time” timestamp. One number per key, no refill loop, used by Redis-based limiters.

fits: the same as token bucket, with less state · remember: one timestamp per key
Atomic Redis Lua script

Executes read-modify-write on the server as one step, so concurrent gateways cannot interleave between the read and the write.

fits: any distributed counter · remember: the fix for the lost-update race
Consistent hashing

Maps client keys to Redis shards so adding a shard moves only ~1/N of keys. See the KV database card for the full treatment.

fits: the counter store · remember: K/N keys move

Estimation lab: turn policy into machines

A limiter looks tiny because its decision is only yes or no. At scale, every protected request creates a state lookup, an atomic update, and often a metric. Estimation reveals whether one shared counter service is enough, whether hot keys dominate, and how much safety margin is needed. Keep units visible: requests per second become operations per second; keys multiplied by bytes per key become memory.

decision QPS

Usually equal to protected API QPS. If one request checks user, IP, and endpoint rules, multiply by three.

active key cardinality

Count identities seen during the state TTL, not registered users. This determines counter memory.

hot-key QPS

Average load can be safe while one API key saturates a single Redis shard or CPU core.

false-reject rate

The product metric. A technically available limiter that rejects legitimate traffic is still failing.

Scenario 1 — a consumer API at 200,000 requests/second

Assume 50 million registered users, 8 million daily active users, 200,000 requests/second at evening peak, and two checks per request: one per user and one per IP. The limiter sees checks, not business requests. Peak decision load is 200,000 × 2 = 400,000 checks/s. If each check is a Redis Lua call, the counter tier needs 400,000 operations/second before headroom.

  1. Add headroom for bursts and failover. Design to 60% steady utilization so a shard can absorb imbalance and one-node loss. Required demonstrated capacity is 400,000 / 0.60 ≈ 667,000 ops/s.
  2. Choose a conservative shard figure. Suppose benchmarking shows 80,000 Lua evaluations/second per instance at the desired p99. Raw capacity requires ceil(667,000 / 80,000) = 9 primary shards. Use ten or twelve, not nine: round numbers ease placement and leave growth room.
  3. Estimate state. Do not multiply by all 50 million accounts. Suppose 12 million users and 6 million IPs appear within the ten-minute maximum TTL: 18 million live keys. A compact value may hold tokens, last-refill time, version, and expiry—about 32 bytes—but Redis object, allocator, hash-table, and key overhead can make the real footprint 120 bytes. That is 18M × 120 B ≈ 2.16 GB. With replication and 50% safety margin, budget roughly 6.5 GB. CPU, not memory, is binding.
  4. Budget latency. If the gateway has a 100 ms p99 target, do not spend 20 ms on policy. Give the limiter perhaps 3 ms p99 in-region: 0.3 ms gateway work, 1 ms network, 1 ms Redis, and 0.7 ms queue/jitter. This forces regional stores; a cross-continent check cannot fit.
checks/s = API requests/s × rules checked/request
primary shards = peak checks/s ÷ (safe utilization × measured ops/s/shard)
memory = live keys × measured bytes/key × replicas × headroom

Decision: deploy a regional Redis cluster per traffic region, shard by a stable hash of rule plus identity, and run check-and-decrement atomically in Lua. One large node is risky even if it passes average-throughput benchmarks: every decision shares one failure domain, and failover has no reserve.

Sanity check: 200,000 requests/second is 17.3 billion requests/day. With 8 million daily users that implies roughly 2,160 requests per active user per day. That fits a chatty app, but not a once-a-day utility. If behavior sounds wrong, revisit the assumption before sizing hardware.

Scenario 2 — login protection where correctness matters more than availability

Now size a lower-throughput but sensitive rule: at most five failed logins per account per fifteen minutes and fifty attempts per IP per hour. Peak login traffic is 12,000 requests/second; 8% fail, so 960 failed attempts/second update the account window, while every attempt may update the IP window. Load is only 12,960 counter operations/second, but semantics are stricter. A fail-open outage creates an abuse window, and an approximate boundary can aid credential stuffing.

  1. Pick the algorithm from the error budget. A fixed fifteen-minute counter can allow ten failures around a boundary. A sliding timestamp log is exact and affordable because each account is capped at a handful of entries. Five 8-byte timestamps plus overhead might be 100–200 bytes per active failing account.
  2. Estimate keys from behavior. If 500,000 accounts see a failed login during the horizon, account state is 500k × 200 B = 100 MB. If 300,000 IPs are active during the hour at 150 bytes each, add 45 MB. With replicas and headroom, this remains below 1 GB.
  3. Make retries safe. A gateway timeout after commit can count the same failure twice. Include an attempt id and a short idempotency marker, or have authentication emit one failure event through an outbox. The extra state is worthwhile because false lockouts have direct support cost.
  4. Define degraded behavior. When the store is unavailable, do not just say “fail closed.” Existing sessions continue; new attempts use a tighter local allowance plus CAPTCHA or step-up verification. This protects accounts without turning a Redis incident into a total lockout.

Watch more than the 429 rate. Track failed attempts, unique targeted accounts, local-fallback decisions, challenge completion, lockout appeals, and legitimate rejection. Rising rejects with flat attack volume suggests a policy or clock defect rather than successful defense.

Interview insight: throughput did not drive this design; the cost of an error did. Estimation includes semantic precision. A 13k-op/s system can deserve stronger consistency and richer degradation than a 400k-op/s product API.

Scenario 3 — a global tenant with one extreme hot key

An enterprise tenant may call 100,000 requests/second globally, then launches a batch reaching 300,000/s from three regions. Hash partitioning sends its counter to one logical owner because all calls share a key. Adding normal shards does not split that key: average cluster load looks healthy while one owner queues. This is the difference between total capacity and per-key capacity.

  1. Quantify the ceiling. If one primary sustains 80,000 atomic checks/second at target latency, the 300,000-op/s key needs at least four fragments, and five at 75% utilization.
  2. Buy bounded inaccuracy. Give each of five fragments one fifth of the allowance and consistently hash gateways to fragments. Skew may cause one fragment to reject while another has tokens, so a background allocator rebalances quotas. The trade is exact global usage for low latency and bounded error.
  3. Use leases for hotter rules. A regional allocator can lease 10,000 tokens from a global budget. Requests consume locally. If a region disappears, at most its unspent lease is stranded; duplicate leases bound overshoot by lease size times allocators. Choose lease size from accepted overshoot.
  4. Model disaster traffic. An equal three-way split gives 33k/s each. If one region normally receives 60%, equal quotas falsely reject. A 60/25/15 split fits normal demand but handles failover poorly. Reserve capacity centrally, or deliberately allow bounded temporary overshoot.
minimum fragments = hot-key peak QPS ÷ safe per-fragment QPS
maximum lease overshoot ≈ lease tokens × allocators that can fail concurrently
global choice = exact limit + WAN latency, or regional speed + bounded inconsistency

What to say: “The cluster is not the unit constraining a hot key; one owner is. I detect keys above 20% of a shard’s safe capacity, move them to leased or striped limiting, and expose overshoot and false-reject metrics separately.”

TinyURL

A short URL is just a small key that points to a long URL. Creating links requires unique keys; opening them requires an extremely fast key lookup. Because redirects vastly outnumber creations, caching and redirect behavior matter more than clever encoding.

core choice
distributed ids (ranges or Snowflake) encoded in base62
read path
cache-aside Redis in front of a KV store
redirect code
302 if you want analytics, 301 if you want fewer hits
the hard part
unpredictable keys without collisions or a single counter

Requirements and scale

Functional

  • Shorten a long URL into a short key; optional custom alias; optional expiry.
  • Redirect the short URL to the long one.
  • Delete or disable a link; click analytics (count, referrer, country) for the owner.
  • Authenticated API for programmatic creation.

Non-functional

  • Redirect latency under 10 ms at the server; availability of reads above everything.
  • Read-heavy: about 100 reads per write.
  • Keys unpredictable (no enumeration), short (7 characters), unique.
  • Durable for years; links must not break.

System design

Worked example

Open /aZ91k and reach a long product URL

Intuition: a coat-check ticket.The short key is not compressed URL data. It is only a small claim ticket that looks up the full destination.

  1. The edge checks whether aZ91k is already cached; a hit can redirect immediately.
  2. On a miss, the API checks Redis, then the durable key-value store.
  3. It caches the mapping and returns a 302 with the long URL in Location.
  4. It publishes the click event asynchronously, so analytics cannot slow the redirect.

What to notice: the hot read path is one key lookup. Creation is separate: mint an id, Base62-encode it, and store the mapping with a conditional write.

Algorithms, and what each one does

Base62 encoding

Represent an integer id in digits [0-9a-zA-Z]: repeatedly divide by 62. 7 characters cover 3.5 trillion ids; URL-safe without + and /.

fits: any id-to-short-key mapping · remember: 62⁷ ≈ 3.5 × 10¹²
Leased id ranges

A coordinator (ZooKeeper or a DB row) hands each server a block of ids; the server increments locally. No coordination per request; a crashed server wastes at most one block.

fits: unique ids at scale without a hot counter · remember: block size trades waste for coordination
Snowflake ids

64-bit id = 41-bit millisecond timestamp + 10-bit machine id + 12-bit sequence. Time-sortable, no coordinator, 4,096 ids per ms per machine.

fits: TinyURL, tweets, messages · remember: 41 bits of ms ≈ 69 years
Hashing with collision handling

SHA-256 of the long URL, take 7 base62 characters, on collision append a salt and retry. Same URL gives the same key (dedup) but needs a check on every write.

fits: when identical URLs should share a key · remember: birthday collisions at √(key space)
Cache-aside with LRU

Read cache; on miss read the store and populate; evict least-recently-used. Reads of hot keys never touch the store; invalidate on delete.

fits: read-heavy key lookups · remember: 20% of keys take 80% of hits
Bloom filter

A probabilistic set: “definitely not present” or “probably present”. Screens custom aliases and missing keys before hitting the store.

fits: alias existence, 404 short-circuit · remember: ~10 bits per item for 1% false positives
HyperLogLog

Estimates the number of distinct items (unique visitors) in ~12 KB with ~1% error, regardless of cardinality.

fits: analytics uniques · remember: 12 KB per counter

Estimation lab: size the redirect path before the create path

Shortening a URL is a write; following it is a read. Estimate creations, redirects, record size, key space, cache working set, network egress, and analytics separately. A single “requests per second” figure hides the asymmetry that makes this design interesting.

read : write ratio

Determines whether caching dominates and whether write coordination can stay comparatively simple.

key-space occupancy

Keys must cover lifetime creations with reserve for blocked names, tests, and growth.

cache hit ratio

Each percentage point changes origin QPS by peak redirects × 1%.

redirect egress

Small per response, but meaningful across billions of TLS responses.

Scenario 1 — 100 million new links per month

Assume 100 million URLs are created monthly and each receives 100 redirects over its life. Creations average 100M / (30 × 86,400) ≈ 39 writes/s. Redirects average about 3,900 reads/s under steady behavior, a 100:1 ratio. Apply a peak factor of ten for diurnal and viral traffic: provision around 400 creates/s and 40,000 redirects/s. Say clearly that these are assumptions.

  1. Compute key length. Ten years gives 12 billion records. Base62 has 62⁶ ≈ 56.8 billion six-character combinations, so six fits numerically. Do not consume the whole space: reserved words, blocked keys, multiple environments, and growth argue for seven characters, or 62⁷ ≈ 3.5 trillion.
  2. Estimate database storage. Suppose destinations average 500 bytes. Add key, owner, timestamps, status, expiry, checksums, and index overhead; round to 1 KB/record. Annual logical data is 1.2B × 1 KB ≈ 1.2 TB; ten years is 12 TB. With three replicas, indexes, compaction slack, and 30% headroom, plan about 12 × 3 × 1.5 × 1.3 ≈ 70 TB.
  3. Estimate the hot cache. Traffic is Zipfian. If 20% of the latest 100 million links drive 80% of traffic, caching 20 million 1 KB records requires 20 GB before overhead. At 1.5 KB resident per entry and one replica, budget 60 GB. Split it for throughput and failure isolation.
  4. Translate hit ratio. At 40,000 peak redirects/s, 95% hits leave 2,000 database reads/s; 99% leaves 400. A cold-cache restart sends all 40,000 to origin. Use request coalescing, warm-up, and enough short-term origin headroom.
average writes/s = monthly creates ÷ seconds/month
peak redirects/s = average writes/s × redirects/link × peak factor
physical bytes = records × bytes/record × replicas × overhead × headroom
Sanity check: 100 redirects across 100 million monthly links means ten billion redirects/month, around 3,858/s average. If the product claims one billion daily redirects, then links receive more visits or creation volume is larger. Reconcile the behavior with the arithmetic.

Scenario 2 — one link goes viral during a live event

The service normally peaks at 40,000 redirects/s, but one link gets two million clicks in a minute: 33,000/s for one key. The database is safe if the value is cached; pressure moves to one cache owner, load-balancer routes, TLS termination, and egress. Separate aggregate load from the hottest object.

  1. Size response bandwidth. A compact 302 with headers may be 700 bytes on the wire. At 33,000/s that is 23 MB/s or 185 Mb/s for the viral key. Total peak at 73,000/s is about 51 MB/s. A fleet handles this; one small instance or cross-zone link may not.
  2. Prevent stampede. When the entry expires, thousands of misses could query storage. Serve stale for a grace period, refresh asynchronously, and use single-flight so one request reloads the value. Add TTL jitter so many popular keys do not expire together.
  3. Separate analytics. A synchronous click row adds 33,000 writes/s exactly when latency matters. Emit a 200-byte event to a partitioned log: 6.6 MB/s. Consumers batch and aggregate by link, minute, country, and referrer. If analytics lags, redirects continue.
  4. Choose status code consciously. A 301 moves repeats into browser caches, reducing load but hiding clicks and making edits sticky. A 302 or 307 preserves control at the cost of serving every visit. This is both capacity and product policy.

Dashboards should split redirect QPS by link and cache status. Overall p99 can look healthy while a viral key fails. Track hottest-key share, single-flight waiters, eviction rate, origin miss QPS, response bytes, and event-log lag.

Intuition: caching removes storage work, not front-door work. The load balancer, TLS terminator, application socket, and network still process each redirect unless a CDN or edge worker answers it.

Scenario 3 — expiring campaigns with detailed analytics

A marketing product creates 20 million links/day, retains destinations two years, expires most campaigns after ninety days, and records fifteen fields per click. Each link gets fifty visits. That is 20M × 50 / 86,400 ≈ 11,600 average redirects/s and perhaps 116,000 at a 10× peak. Creation averages only 231/s. Destinations remain modest; click events dominate.

  1. Destination retention. Two years is 14.6 billion records, or 14.6 TB logical at 1 KB each. If expiry permits deletion, compaction must actually reclaim disk; a TTL flag alone does not.
  2. Analytics volume. One billion clicks/day at 250 bytes/event makes 250 GB/day raw, 91 TB/year. Three log replicas with seven-day retention consume 5.25 TB. At 5:1 columnar compression, a year’s archive is about 18 TB.
  3. Partition the log. At peak, events are 29 MB/s. If one partition safely handles 10 MB/s and 10k events/s, event rate calls for twelve partitions. Choose perhaps twenty-four or forty-eight for growth and consumers. Hashing solely by link preserves order but traps a viral key; add a time bucket or suffix when click order is irrelevant.
  4. Follow byte flow into cost. If raw events cross zones three times, 250 GB/day becomes 750 GB/day of chargeable transfer. Aggregate near ingestion, keep brokers and consumers zone-aware, and retain raw events only as long as replay needs them.
analytics bytes/day = redirects/day × bytes/event
broker disk = ingress/day × retention days × replication factor
partitions = max(event-rate need, byte-rate need, consumer parallelism)

Redirects might target 99.99% availability while analytics targets 99.9% and fifteen-minute freshness. Give the paths different alerts. Measure consumer lag in records and wall-clock time: ten million messages can be benign at enormous throughput and catastrophic at low throughput.

Algorithms, and what each one does

Hybrid fan-out

Push the tweet id to followers’ caches when the author’s follower count is below a threshold; otherwise mark the author as pull-only and merge at read. Bounds write amplification while keeping reads cheap.

fits: any feed with a heavy-tailed follower graph · remember: threshold ~10k–100k followers
Snowflake ids

Time-ordered 64-bit ids: timestamp high bits, machine id, sequence. Sorting by id is sorting by time, so a chronological merge needs no timestamp lookup.

fits: tweets, comments, messages · remember: k-sorted across machines, exact within one
Keyset (cursor) pagination

“Give me items with id < cursor” instead of OFFSET n. Stable under inserts and O(log n) on an index; offsets drift and get slower with depth.

fits: every feed and list · remember: cursor = last id seen
Reddit hot ranking

hot = log10(max(|ups − downs|, 1)) · sign + (t − t0) / 45000: votes count logarithmically, and every 12.5 hours (45,000 s) of age costs one order of magnitude of votes. Newer posts rise, old ones sink regardless of score.

fits: front pages, trending lists · remember: log votes + linear time
Wilson score lower bound

The lower end of a confidence interval on the upvote proportion: (p̂ + z²/2n − z√(p̂(1−p̂)/n + z²/4n²)) / (1 + z²/n). A comment with 1 upvote and 0 downs ranks below one with 100 up and 5 down, because the first has no evidence.

fits: “best” comment sort, reviews · remember: rank by confidence, not ratio
Materialized path

Scenario 1 — ordinary authors and fan-out-on-write

Assume 50 million daily active users. Ten percent post two times/day: 10 million posts/day, or 116 posts/s average and roughly 1,160/s at a 10× peak. An ordinary author has 300 eligible followers. Pure push fan-out would create 1,160 × 300 = 348,000 peak timeline insertions/s. Each insertion only needs post id, author id, score/version, and timestamp; round to 40 bytes logical.

  1. Write bandwidth. Logical peak is 13.9 MB/s. With three replicas and protocol/index overhead near 2×, physical write flow can approach 84 MB/s. That is feasible across a sharded in-memory or log-backed timeline service, but not as row-by-row synchronous work on the post request.
  2. Queue capacity. If fan-out workers process 5,000 insertions/s each at safe utilization, 348,000/s needs seventy workers before failover reserve. Choose perhaps ninety. Partition by follower id so one user’s timeline has one owner and inserts distribute across the population.
  3. Timeline cache. Keep the newest 500 ids per daily user. 50M × 500 × 16 B is 400 GB logical before object overhead. At 30 bytes resident per entry, it is 750 GB; with one replica, 1.5 TB. The lesson is that “just ids” becomes large when multiplied by users and depth.
  4. Read QPS. If every daily user opens 8 sessions and refreshes 3 times, that is 1.2 billion feed requests/day, 13,900/s average, perhaps 139,000/s peak. Returning 20 posts means 2.78 million post hydrations/s without batching or cache locality. Batch multi-get and keep popular post bodies in cache.

Scenario 2 — celebrities force a hybrid design

Now one account has 80 million followers and publishes four times/day. Pushing a single post means 80 million inserts. Even at 500,000 insertions/s, one post takes 160 seconds and displaces ordinary traffic. Storing 40-byte entries creates 3.2 GB logical per celebrity post before replication. Yet pulling all authors at read time would make every feed request scan hundreds of sources. The hybrid threshold comes from cost comparison.

  1. Compare write and read work. For author A, push cost per post is follower count. Pull cost is active followers × feed opens while the post is relevant. If only 5% of 80 million followers open during the relevance window and open twice, pull does 8 million merge checks—ten times less than 80 million inserts.
  2. Choose a threshold dynamically. Do not label every verified account a celebrity. Estimate push_work = followers and pull_work = active_followers × expected_reads. Include latency: pulling 500 celebrity streams per read is worse than pulling twenty. A threshold around hundreds of thousands may be a starting point, then adapt from observations.
  3. Merge cheaply. Maintain a small cached head list for each pull-on-read author. At feed read, fetch the user’s pushed timeline plus heads for followed celebrities, then k-way merge by creation id before ranking. With twenty celebrity sources and fifty candidates each, the merge considers 1,000 ids—not millions.
  4. Handle mega-events. A sports final may make many celebrity posts hot simultaneously. Cache the merged result for cohorts where privacy allows, cap candidate depth, and degrade expensive ranking features before dropping the entire feed.
Intuition: the threshold is not fundamentally “one million followers.” It is the point where work performed for mostly inactive followers exceeds repeated merge work for active readers, subject to latency and freshness targets.

Scenario 3 — ranking, media, and failure budgets

Suppose peak feed reads are 150,000/s. The ranker retrieves 1,000 candidates to return 20, a 50× amplification. A feature service that receives one request per candidate would face 150 million calls/s, clearly absurd. Batch candidates and precompute cheap features. If a batched feature request handles 200 candidates, the load falls to 750,000 batch requests/s; still large, so cache author and post features and rank in stages.

  1. Stage the funnel. Use inexpensive eligibility filters and static scores to cut 1,000 candidates to 100, then run the expensive model on 100. At 150k reads/s, this is 15 million model item scores/s. Benchmark items per accelerator or CPU core to convert this into a fleet size.
  2. Do not count media in feed JSON storage. If twenty thumbnails average 40 KB, each response references 800 KB of media. At 150k/s that is 120 GB/s of edge delivery. The CDN absorbs it; origins see the miss fraction. At 98% hit ratio, origin media bandwidth is still 2.4 GB/s.
  3. Allocate the latency budget. For 300 ms p99: gateway/auth 20 ms, timeline retrieval 40, hydration 60, feature fetch 50, ranking 60, assembly 20, leaving 50 ms contingency. Parallelize independent calls; do not add budgets blindly because parallel branches contribute their maximum, not their sum.
  4. Set quality degradation. If feature service times out, return chronological or lightweight ranked results. Track fallback rate, not only HTTP success. A 99.99% endpoint serving empty or stale feeds is not a healthy product.

Worked example

Intuition: registered mail with a mailbox.The sender gets an acceptance receipt after durable storage; delivery is a later event. Repeated attempts are safe because the envelope has a unique id.

  1. A sends ciphertext with a client_msg_id; the conversation owner assigns the next sequence number.
  2. The service durably appends the message to B’s per-device queue, then acknowledges A.
  3. The registry says B is offline, so a push notification is sent and the message stays queued.
  4. When B reconnects, its gateway drains the queue. B deduplicates by id and acknowledges; A then sees “delivered.”

What to notice: accepted, delivered, and read are three different states. At-least-once delivery plus client dedup is simpler and safer than pretending the network offers exactly-once delivery.

  4. Reconnect storm. Losing gateways for five million connections and allowing instant retry can overwhelm authentication.   3. Ordering. A per-conversation sequencer, not a global one, assigns monotonic sequence numbers. At 500k sends/s spread across millions of conversations, most keys are cold. A single extremely active conversation is the hot-key case; ordinary hashing handles aggregate throughput.
  4. Offline queue. If 20% of recipient deliveries are offline and remain unacknowledged for an average six hours, Little’s Law gives 250k deliveries/s × 21,600 s = 5.4B queued items. At 100 bytes of queue metadata, that is 540 GB before replication; message bodies need not be duplicated if queues reference durable envelopes.
Correctness test: server acceptance means durable persistence, not recipient delivery. Use stable message ids so retries deduplicate. Recipients track highest contiguous sequence plus gaps; “exactly once” at the screen is achieved through idempotent application, not magical transport.

Scenario 3 — large groups, media, and encryption

A 100,000-member announcement group receives ten 1 KB messages per minute. Naively creating a per-user server copy means one million deliveries/minute, 16,700/s, for one group. That is manageable alone but dangerous across thousands of groups. If group membership is stable and messages are history-visible, store one ciphertext stream and per-user read cursors; gateways notify online members without cloning the body.

  1. Encryption changes fan-out. Pairwise encryption of one message for 100,000 users would be prohibitive. Sender keys let the sender encrypt once for the group epoch; membership changes rotate keys. Estimate key-distribution traffic separately from normal messages.
  2. Media is a different plane. If 5% of 8 billion daily messages attach a 1 MB object, uploads are 400 TB/day and downloads may be much larger. Send media directly to blob storage with pre-signed URLs, store a small encrypted reference in chat, and serve through a CDN. Do not proxy gigabytes through socket gateways.
  3. Presence is lossy. Broadcasting every online/offline transition to every contact explodes. If 35 million users change state twice/hour and have 200 contacts, naive notifications average 3.9 million/s. Publish presence only to active viewers, coalesce changes, use coarse last-seen, and accept eventual consistency.
  4. Allocate reliability. Target 99.99% for send acceptance and perhaps 99.9% for presence. During overload, drop typing indicators first, then presence; preserve message durability and acknowledgements. Priority queues make this policy executable.

Measure send-accept p99, online delivery p99, offline delivery age, duplicate-render rate, missing-sequence gaps, reconnect success, socket count, and media CDN hit ratio. A server-side latency metric that ends when the gateway writes bytes can miss a stalled mobile client; sample end-to-end client acknowledgements.

offline items (Little’s Law) = offline deliveries/s × average unacked seconds

System design

Worked example

Alice and Bob type at the same position

Intuition: merge intentions, not final pages.Send “insert X at position 5,” not the whole document. If another edit changes position 5 first, adjust the operation before applying it.

  1. Alice edits version 41 locally, so her UI responds immediately, then sends the operation.
  2. The server is already at 43 because Bob’s edits arrived first.
  3. It transforms Alice’s position against operations 42 and 43, applies the result, and records version 44.
  4. Version 44 is broadcast; every client transforms any still-pending local edits against it.

What to notice: the sequencer supplies one shared order. Transformation preserves what the user meant even though numeric positions moved.

Algorithms, and what each one does

Operational transformation (OT)

Given two ops a and b made against the same state, transform(a, b) returns a′ such that applying b then a′ equals applying a then b′ (property TP1). The server applies it to every late op; with a central order only TP1 is needed, which is why the sequencer matters.

fits: server-mediated collaborative text · remember: insert vs insert at the same index is tie-broken by site id
Delta ops: retain / insert / delete

An op is a walk over the document: skip n, insert text with attributes, delete n. Composition and transformation are defined on these three primitives, and formatting is an attribute change over a retained range.

fits: rich text · remember: three primitives, closed under compose
Sequence CRDTs (RGA, Yjs, Logoot)

Every character gets a unique, totally ordered id (site id + counter, or a position between neighbours); inserts reference the id they follow, deletes leave tombstones. Replicas converge without a server by merging commutatively.

fits: offline-first, P2P, E2EE editing · remember: metadata per character, tombstone GC
Version vectors

One counter per replica; an op carries the vector it was made against so receivers know what it has and hasn’t seen. The CRDT equivalent of the OT base version.

fits: CRDT sync, multi-master · remember: detects concurrency, not order
Snapshot + log compaction

Materialise the document at version n, then keep only ops after n hot. Loads become snapshot + short replay; old ops move to cold storage.

fits: event-sourced state anywhere · remember: snapshot every N ops or T minutes
Cursor transformation

A cursor is a position; when an op arrives, shift it by the inserts and deletes before it — the same arithmetic as transforming a retain.

fits: presence, comment anchors · remember: anchors are positions that move
Undo by inverse ops

Each op has an inverse (insert ↔ delete); undo appends the inverse transformed against later ops, so history stays append-only and collaborative undo stays local.

fits: restore, undo · remember: never rewrite history
diff-match-patch

Produces a minimal edit script between two texts; used to turn an offline client’s whole-document change into ops, or to show a diff between versions.

fits: history diffs, reconciling bulk edits · remember: Myers diff underneath

Estimation lab: collaborative editing is a hot-document problem

Document count determines storage, but simultaneously open documents determine the real-time fleet. Keystrokes are not database writes: clients batch edits into operations, servers sequence and transform them, and snapshots bound replay. Scenario 1 — ordinary office documents

Assume 20 million daily users, 2 million concurrent users at peak, and 1.3 open documents per connected user. Sessions cluster: average active document has 2.6 editors, so there are about one million open documents. Editors generate a batched operation every two seconds while actively typing, but only 40% are typing at any instant. Peak accepted rate is 2M × 0.4 × 0.5 = 400,000 ops/s.

  1. Session servers. If one collaboration server safely owns 5,000 open documents or 20,000 sockets, the document limit calls for 200 servers while sockets call for 100. Size on the tighter 200, then divide by 60% utilization for failover: roughly 334 server equivalents.
  2. Broadcast. With 2.6 editors/doc, each operation goes to 1.6 peers on average: 640,000 deliveries/s. At 250 bytes per transformed envelope, outbound collaboration traffic is 160 MB/s before transport overhead. The small messages make per-message CPU and syscalls as important as bandwidth.
  3. Operation log. At 400k ops/s × 200 bytes durable encoding, logs ingest 80 MB/s, 6.9 TB/day logical. Compression and idle periods reduce it; replication increases it. Retain the live log briefly, compact into snapshots, and archive only if product history needs it.
  4. Latency budget. Local echo should feel instantaneous because the client applies optimistically. Remote convergence might target 200 ms p99: 30 ms client/network, 30 gateway, 50 sequence/transform/persist, 30 broadcast, leaving 60 ms jitter. Acknowledgement after durable log append makes accepted edits recoverable.

deliveries/s = ops/s × average other sessions/document
log bytes/day = ops/s × bytes/op × 86,400
Sanity check: 400,000 ops/s sounds high, but it is only 0.2 ops/s averaged over two million connected editors. The behavioral assumption is plausible because most people pause more than they type.

Scenario 2 — a 5,000-person incident document

Average fan-out hides a pathological document. Five thousand viewers join an incident doc; two hundred can edit, and eighty are actively typing at 0.5 ops/s. Only 40 accepted ops/s enter, yet broadcasting each to 4,999 sessions creates nearly 200,000 deliveries/s for one document. Hashing by document sends all transformation work to one owner, so adding random servers does not split the hot key.

  1. Separate writers from viewers. Keep one authoritative sequencer for ordering but distribute broadcast through relay trees. The sequencer publishes each operation once to, say, twenty relay nodes; relays fan out to sessions. Ordering stays single-owner while network work scales.
  2. Batch presentation. Viewers do not need 40 rendering cycles/s. Relays can combine operations into 50–100 ms frames. That keeps collaboration under human perception thresholds while cutting per-message overhead.
  3. Protect the document. Admission limits, viewer mode, cursor sampling, and presence coalescing prevent ephemeral metadata from overwhelming edits. Cursor positions from 5,000 users at 5 updates/s would be 25,000 ephemeral events/s even before fan-out.
  4. Plan owner failure. A standby loads the latest snapshot and replays the tail. If snapshot is 10 MB and tail is 50,000 operations at 200 bytes, recovery reads 20 MB. At 100 MB/s this is fast; transform/rebuild CPU may dominate. Benchmark recovery, not just steady state.

The architectural lesson is that “one owner per document” does not mean “one process does all work.” Keep sequencing centralized per key while externalizing durable log, snapshot storage, and broadcast relays. Alert on per-document sessions, op rate, relay queue age, and transform CPU.

Scenario 3 — snapshots, history, and offline clients

Suppose an average document is 200 KB, receives 50,000 operations over its life, and snapshots every 1,000 operations or ten minutes while active. With 500 million documents, current snapshot storage is 100 TB logical. Three replicas make 300 TB before metadata and compression. Storing every historical snapshot would multiply this dramatically, so distinguish current recovery state from user-visible version history.

  1. Bound replay. At most 1,000 operations after a snapshot. At 200 bytes each, log tail is only 200 KB per doc. Recovery cost is roughly snapshot size plus tail; the snapshot interval can be chosen from a recovery-time target.
  2. Estimate snapshot writes. If one million docs are active and each snapshots every ten minutes, that is 1,667 snapshot writes/s. At 200 KB average, 333 MB/s logical. Incremental or content-addressed snapshots can reduce repeated bytes; staggering avoids synchronized spikes.
  3. Handle offline age. A client returning after thirty days should not replay a month of server ops from its old base. Download the current snapshot, then rebase the local offline changes. Put an explicit maximum transform window in the protocol and test conflicts beyond it.
  4. Version history economics. If product promises ninety days of point-in-time history, use periodic durable versions plus the operation log, not a full copy per edit. Compression works well because operations are small and snapshots share structure.
snapshot rate = active documents ÷ snapshot interval seconds
maximum replay bytes = max ops between snapshots × bytes/op
recovery time ≈ snapshot fetch + tail fetch + transform/rebuild CPU

Track local-edit latency, server-ack latency, remote convergence, transform conflicts, duplicate operations, owner moves, and recovery duration. A correct convergence algorithm can still provide a bad product if owner failover pauses one document for thirty seconds.

I size ordinary documents and the hottest document separately, keep one sequencer but scale broadcast with relays, and choose snapshot cadence from bounded recovery time rather than an arbitrary timer.”

Worked example

  2. Matching reads available drivers in that cell and neighboring rings until it has a small candidate set.
  3. The routing service computes ETA for roughly the best ten and the top driver gets a 15-second lease.
  4. Acceptance conditionally changes requested → matched; timeout tries the next driver without double-booking.

Algorithms, and what each one does

Geohash

Interleave the bits of latitude and longitude (a Z-order curve) and encode in base32; longer prefixes mean smaller cells, and nearby points usually share a prefix — except across cell boundaries, so always check the 8 neighbours.

fits: simple proximity indexes, Redis GEO · remember: 6 chars ≈ 1.2 km × 0.6 km
S2 cells

Project the sphere onto a cube and index each face with a Hilbert curve: 30 levels of cells with good locality, exact coverings of any region, used by Google Maps and Spanner’s geo features.

fits: planet-scale indexing, region coverings · remember: Hilbert curve, 30 levels
H3 hexagons

A hierarchical hexagonal grid (Uber’s): every cell has six equidistant neighbours, so rings are uniform and distance-by-cells is meaningful; resolution 9 cells are ~175 m across.

fits: supply/demand analytics, dispatch rings · remember: uniform neighbours, 16 resolutions
Quadtree

Recursively split a region into four until each leaf holds ≤ k points; dense areas get deeper. Adaptive, but rebalancing under constant movement is costly compared with fixed cells.

fits: static points (places), Yelp-style search · remember: adaptive depth, costly updates
Ring search for k nearest

Start at the query cell, add rings of neighbours until k candidates are found or a radius cap; then rank the candidates by road ETA.

fits: any cell index · remember: candidates by cells, ranking by roads
Haversine distance

Great-circle distance between two lat/lng points. Cheap coarse filter; never the final ranking in a city.

fits: pre-filtering, surge radii · remember: straight line, not road
Greedy dispatch vs batched assignment

Greedy: match each request to the best free driver immediately. Batched: every few seconds, solve all open requests × free drivers as an assignment problem (Hungarian algorithm, O(n³), or min-cost flow) minimising total ETA — a short wait buys a better global match.

fits: dense markets · remember: global optimum vs latency
Leases and conditional writes

An offer carries a token with a TTL; accept succeeds only if the token matches and the state is still requested. Prevents double assignment without distributed locks.

fits: any “one winner” race · remember: compare-and-set with expiry
Kalman filter / map matching

Smooth noisy GPS and snap positions to the road graph (HMM map matching) so ETAs and surge use real roads.

fits: location pipelines, Maps probes · remember: GPS is noisy in cities
Sagas

A multi-step transaction (complete trip → charge card → pay driver) as a sequence of local steps with compensating actions, instead of a distributed 2PC.

fits: payments, bookings · remember: compensate, don’t lock

  3. Use leases. Offering one driver to several riders raises acceptance but risks double assignment. A conditional write changes driver state from available to offered with a short lease and request id. Acceptance commits driver and rider together or via a carefully idempotent workflow.
  4. Estimate retry amplification. If 20% of offers time out and each request tries up to three drivers, average attempts might be 1.25, making 209 offers/s. During network trouble it may rise sharply. Dashboard attempts per successful match; this is an early warning for marketplace health.
Intuition: matching throughput is not the hard scale number. The hard part is making a fresh, globally sensible choice from rapidly changing local state while preventing two riders from owning one driver.

Scenario 3 — trip updates, ETA, surge, and regional failure

Suppose 2 million trips are active globally. Rider and driver apps each receive an update every four seconds, producing one million outbound updates/s. At 300 bytes each, that is 300 MB/s before TLS. Fan-out through regional gateways close to the clients; do not route every tick through a central trip database.

  1. Separate state from telemetry. Durable trip transitions—requested, matched, started, completed, cancelled—are tens of events/trip. GPS telemetry is hundreds or thousands. Persist transitions transactionally; stream telemetry to cheaper time-series storage.
  2. Surge cells need smoothing. Supply/demand counts over tiny cells are noisy. If a cell has two riders and one driver, the ratio is 2× but statistically weak. Aggregate neighboring cells and time windows, apply hysteresis, cap changes, and monitor realized wait time rather than the raw multiplier.
  3. Availability by function. If ETA service fails, matching can use straight-line estimates with wider error; if payment fails after completion, finish the trip and run an idempotent payment saga; if durable trip state is unavailable, prevent new matches in that shard rather than risk double assignments.
  4. Regional evacuation. Location and match ownership should follow geography, but metadata/control can span regions. If one region fails, another can accept new traffic only after fencing the old trip-state leaders. Network reachability alone must not create two authorities.
client updates/s = active trips × clients/trip ÷ update interval
offer amplification = offer attempts ÷ successful matches
marketplace quality = pickup ETA, acceptance rate, cancellation rate, and unfulfilled demand

Technical metrics need marketplace companions. A fast matching service can produce terrible outcomes if pickup ETA, acceptance, or cancellation worsens. Break down by cell and time: global averages conceal an airport queue or neighborhood with no supply.

System design

Worked example

Route across a city while one highway is congested

Intuition: precompute the road hierarchy.Do not explore every side street for a long trip. Move quickly onto important roads, cross the city, then descend to local streets near the destination.

  1. Snap both GPS points to nearby road-graph edges with a spatial index.
  2. Choose each edge’s weight from fresh live speed, then historical speed, then the speed limit.
  3. Run bidirectional contraction-hierarchy search over precomputed shortcuts.
  4. Unpack shortcuts into real roads, build turn instructions, simplify the polyline, and correct the ETA.

What to notice: topology changes slowly and is expensive to preprocess; traffic changes quickly and should update weights without rebuilding the whole graph.

Algorithms, and what each one does

Dijkstra

Expands nodes in order of distance from the source using a priority queue; O((V + E) log V). Correct and simple, but a continental query touches hundreds of millions of nodes — seconds to minutes.

fits: small graphs, the baseline to name · remember: too slow for planet routing
Bidirectional search & A* with landmarks (ALT)

Search from both ends and meet in the middle; A* adds a heuristic lower bound. Landmarks (a few dozen precomputed distance tables) give tight bounds via the triangle inequality: 10–100× faster than Dijkstra.

fits: medium graphs, dynamic weights · remember: heuristic must never overestimate
Contraction hierarchies (CH)

Preprocessing: order nodes by importance and contract them one by one, adding shortcut edges that preserve shortest paths. Query: bidirectional search that only goes “upward” in importance — it visits a few hundred nodes on a continental graph. Shortcuts are unpacked into the real path afterwards.

fits: Maps, OSRM, any static-weight routing · remember: hours to preprocess, ~1 ms to query
Customizable CH (CCH)

Split preprocessing into a metric-independent phase (the contraction order, once) and a cheap customization phase (compute shortcut weights for a given metric, seconds to minutes). Traffic updates re-run customization, not the contraction.

fits: routing with live traffic · remember: contract once, customize per metric
Time-dependent routing

Edge weights as functions of departure time (travel-time profiles); the search uses the arrival time at each node to pick the weight. Answers “leave at 5 pm” correctly.

fits: depart_at / arrive_by queries · remember: FIFO property keeps Dijkstra valid
Transit: RAPTOR / CSA

Public transport is not a plain graph: RAPTOR scans routes round by round (number of transfers); the connection scan algorithm sweeps a sorted list of trips. Both beat graph search on timetables.

fits: transit mode · remember: rounds = transfers
Web Mercator tiling

The world is a square at zoom 0, split into 4 per zoom level; tile (z, x, y) addresses a quadtree node. Keys are simple, caches are effective, and neighbours are arithmetic.

fits: any map UI · remember: 4ᶻ tiles at zoom z
Douglas–Peucker + encoded polylines

Simplify a path by dropping points within a tolerance of the line between their neighbours, then encode deltas as base64-ish text. A 2,000-point route becomes a short string.

fits: returning routes, drawing tracks · remember: tolerance scales with zoom
HMM map matching

Treat each noisy probe as an observation, each road segment as a hidden state; Viterbi finds the most likely sequence of segments. Turns GPS traces into road segments for traffic.

fits: traffic pipeline, trip reconstruction · remember: Viterbi over candidate segments
Spatial indexes: R-tree, k-d tree, S2

R-tree and k-d tree for nearest-edge snapping and nearby queries over static geometry; S2 cell coverings for region queries and sharding.

fits: snapping, places, reverse geocoding · remember: R-tree for rectangles, S2 for the sphere
Sliding-window speed aggregation

Per segment, an exponentially weighted or windowed mean of probe speeds over the last few minutes, with minimum sample counts for anonymity and confidence.

fits: live traffic · remember: minutes-old, falls back to history

Scenario 1 — global vector-tile viewing

Assume 100 million daily users, four map sessions/day, and thirty tile requests/session across initial view, pan, and zoom. That is 12 billion tile requests/day, 139,000/s average, perhaps 1.4 million/s peak. If an average compressed vector tile is 50 KB, uncached peak delivery is 70 GB/s—clearly an edge-distribution problem.

  1. Apply CDN hit ratio. At 99% hits, origin sees 14,000 requests/s and 700 MB/s. At 99.9%, it sees 1,400/s and 70 MB/s. One percentage point at this scale is a major fleet and egress difference.
  2. Make URLs immutable. Include dataset/version, style-relevant inputs, zoom, x, and y in the key. Long TTLs become safe because a changed map gets a new URL. Purge storms disappear; old clients can still fetch compatible tiles.
  3. Estimate catalog size. A full quadtree explodes at high zoom, but only populated land/road tiles exist. Suppose 500 million stored tiles average 50 KB: 25 TB logical. Multiple map styles should reuse geometry or render at the client, rather than duplicating every tile.
  4. Plan origin miss bursts. A new version invalidates cache keys. Prewarm major cities, roll versions gradually, and rate-limit fill. A 99.9% steady hit ratio says nothing about the first hour after worldwide release.

Scenario 2 — routing over a continental graph

Suppose the road graph has 500 million directed edges. A compact in-memory representation uses 24 bytes/edge including endpoints, weight, flags, and indexing: 12 GB. Contraction-hierarchy shortcuts and auxiliary structures may triple that to 36 GB. A routing server needs enough RAM for the graph plus live weights and working memory, perhaps a 64–96 GB instance.

  1. Convert latency to cores. Peak route traffic is 50,000 queries/s. If a point-to-point route consumes 8 CPU-ms, workload is 400,000 CPU-ms/s, or 400 fully busy cores. At 50% target utilization and 32 usable cores/server, need about 25 servers, then add replicas across zones.
  2. Multiple alternatives cost more. Three route options may not be exactly 3×, but assume 20 CPU-ms/query. The same 50k QPS becomes 1,000 cores before headroom. Product options—avoid tolls, waypoints, transit modes—change capacity.
  3. Shard carefully. Geographic shards reduce graph memory, but routes cross boundaries. A continental replica can be simpler for driving. Partition by product region for operational ownership while keeping overlapping border graphs or a higher-level inter-region graph.
  4. Cache by meaning. Exact start/end coordinates rarely repeat. Snap to road segments or coarse cells and cache popular origin-destination corridors for a short TTL, but include mode and avoidance options. Live traffic reduces safe cache life.
Sanity check: 50,000 queries/s × 8 ms equals 400 CPU cores only if the work is purely CPU and parallel. Memory bandwidth, cache misses, and NUMA behavior can dominate graph algorithms; benchmark the real representation.

Scenario 3 — live traffic from probe vehicles

Assume 20 million consenting active probes update every ten seconds: two million observations/s. A 60-byte compressed point creates 120 MB/s ingest before replication. Map matching each noisy point to a road segment is the expensive step; aggregating speeds afterward is comparatively simple.

  1. Partition for locality. Partition by geographic cell and time window so workers have nearby road geometry in memory. A downtown cell may be far hotter than rural cells; allow cell subdivision and monitor per-partition lag.
  2. Use windows with confidence. A segment with two probes should not instantly flip from green to red. Compute robust speed over recent minutes, weight by sample quality and recency, and expose confidence. Low-confidence segments fall back to historical speed.
  3. Budget freshness. For a two-minute p95 goal: device batching 15 s, ingest 10, map matching 25, window close 45, publish 15, leaving 10 s contingency. Long windows improve stability but violate freshness; the SLO forces the compromise.
  4. Update routing weights safely. Rebuilding the full routing hierarchy on every observation is impossible. Aggregate into segment overlays and periodically customize preprocessed structures. Routers atomically swap a versioned weight snapshot.

Metrics include tile edge/origin hit ratios, bytes by zoom, route p50/p99 and CPU-ms, no-route/error rates, graph version age, probe ingest lag, match confidence, segment sample counts, and traffic publish age. Always attach region and zoom/cell dimensions; worldwide averages erase the hot spots.

System design

Worked example

Edit one paragraph in a 1 GB file

Intuition: ship changed puzzle pieces, not the whole puzzle.Stable, content-based chunk boundaries mean a small insertion changes only nearby pieces.

  1. Laptop A rechunks the file and hashes every chunk after the local edit.
  2. It sends only the hash list; the server replies that two chunks are missing.
  3. A uploads those chunks, then conditionally commits the new ordered chunk list against the file’s base version.
  4. Phone B wakes, reads the change feed, and downloads only chunks it does not already have.

What to notice: immutable bytes and mutable metadata have different jobs. Blocks can be deduplicated and cached; the metadata commit is the small operation that needs consistency.

Algorithms, and what each one does

Content-defined chunking (Rabin fingerprint)

Slide a window over the file computing a rolling hash; cut a chunk where the hash matches a pattern (e.g. low 12 bits zero → ~4 KB average), with min and max sizes. Boundaries depend on content, so an insert shifts one boundary, not all of them.

fits: delta sync, backup systems · remember: rolling hash, boundaries follow content
Content addressing (SHA-256)

Name each chunk by its hash: identical data has one name everywhere, integrity is verifiable, and “do you have this?” is a key lookup.

fits: dedup, caches, git · remember: immutable blocks, refcount for GC
rsync-style delta transfer

Receiver sends block checksums (weak rolling + strong); sender finds matching blocks at any offset and transmits only literals and references. The ancestor of chunk-based sync.

fits: syncing an edited large file · remember: weak hash to find, strong hash to confirm
Merkle trees

Hash of hashes over a tree of files or chunks; two replicas compare roots, then only the subtrees that differ. Finds the differing files in O(log n) exchanges.

fits: comparing folder trees, anti-entropy · remember: compare roots first
Change feed with monotonic cursors

Every commit in a namespace gets the next sequence number; clients ask for everything after their cursor. Idempotent, resumable, and the push path can be a bare wake-up.

fits: sync, webhooks, CDC · remember: push says “something”, pull says what
Optimistic concurrency (base version)

A commit carries the version it was based on; if the current version differs, it is a conflict. Detects concurrent edits without locks.

fits: any multi-writer document · remember: compare-and-set on version
Vector clocks per file

When devices edit offline, a per-device counter vector tells whether two versions are ordered or concurrent — which decides “newer” versus “conflict”.

fits: multi-device offline sync · remember: concurrent ≠ newer
Bloom filter

A fast “probably have this chunk” filter in front of the block index, so the common case of an existing chunk skips a store lookup.

fits: dedup checks · remember: false positives only
Erasure coding

Split a block into k data + m parity fragments across failure domains; any k rebuild it. Durability of 3× replication at ~1.5× the storage.

fits: the blob store · remember: Reed–Solomon, e.g. 6+3
Exponential backoff with jitter

Sync clients retry failed calls at growing random intervals so a recovering server is not hit by every client at once.

fits: every client fleet · remember: jitter breaks synchronisation

Scenario 1 — one petabyte of user-visible files

Assume users see 1 PB of current logical data. Content-defined chunking and cross-file dedup reduce unique current blocks by 25%, leaving 750 TB. Compression saves another 20%, leaving 600 TB. But version history adds 35%, thumbnails/previews add 5%, metadata/indexes add 2%, and storage protection expands bytes. Compute in an explicit order so factors are not confused.

  1. Current unique compressed bytes. 1 PB × 0.75 × 0.80 = 600 TB.
  2. Add retained content. Versions and previews make 600 TB × 1.40 = 840 TB. Metadata at 2% adds about 17 TB, though it lives in a different store.
  3. Add durability coding. A 1.5× erasure-coding overhead yields 1.26 PB physical blocks, much better than three full copies at 2.52 PB. Hot recently uploaded blocks may temporarily use three replicas before background coding.
  4. Add operating headroom. At 70% maximum fullness, provision 1.26 / 0.70 = 1.8 PB. Fullness headroom is essential because repairs and rebalancing need free space.
physical = logical × dedup factor × compression factor × history factor × protection factor ÷ target fullness

These factors must be measured by cohort. Videos barely compress but may deduplicate; source trees deduplicate and compress well; encrypted client-side blobs may do neither. A global average is useful for budget, not for anomaly diagnosis.

Scenario 2 — block upload and commit

Suppose 20 million users synchronize 200 MB of changed logical content/day. That is 4 PB/day before dedup. Client hash comparison finds 50% of chunks already present, so 2 PB/day crosses the network: 23 GB/s average and perhaps 115 GB/s at a 5× peak. With average 4 MB chunks, peak is about 28,750 block uploads/s.

  1. Direct-to-blob upload. API servers issue pre-signed block URLs and do not proxy 115 GB/s. They handle authentication, block-existence checks, quotas, and final version commits.
  2. Count metadata calls. If a file averages twenty changed chunks, peak block traffic corresponds to about 1,440 file versions/s. Each version may request a batch existence check and one atomic commit. Batch hashes to avoid twenty metadata round trips.
  3. Make commit atomic. Blocks can arrive in any order and be retried. A final conditional transaction creates a file version referencing a complete block manifest and advances the namespace pointer. Orphan blocks are garbage-collected after a grace period.
  4. Detect corruption. Address blocks by cryptographic hash and verify on upload and periodic scrub. Track checksum failures separately from HTTP failures. Durability estimates assume latent corruption is discovered before too many fragments disappear.
Intuition: uploading bytes and publishing a file version are different operations. Immutable blocks make retries easy; the small metadata commit is the point that requires strong consistency and idempotency.

Scenario 3 — download, multi-device sync, and history

Assume 60 million active devices. Each performs twenty change-feed polls/day when push notifications are unavailable, about 14,000 average polls/s and 140,000 peak. Push should be only a wake-up; devices resume from a durable cursor and fetch all changes, so lost notifications do not lose data.

  1. Change-log storage. If users create 500 million metadata changes/day at 300 bytes each, raw change entries are 150 GB/day. Thirty-day cursor retention with three replicas is 13.5 TB before indexes. Older devices can fall back to a full reconciliation snapshot.
  2. Download egress. Suppose downloads total 8 PB/day and a CDN or edge cache serves 70%. Origin reads 2.4 PB/day, 27.8 GB/s average. At 5× peak, origin needs 139 GB/s. Popular shared files behave like hot objects and need stampede protection.
  3. Version economics. A 1 GB file edited in one 4 MB region should add roughly one chunk plus a new manifest, not another gigabyte. Content-defined boundaries keep insertions from shifting every later chunk. Track changed-byte ratio and dedup savings.
  4. Conflict policy. Two offline devices may edit the same base version. For binary files, preserve both as conflicted copies rather than silently choosing last-write-wins. For structured documents, hand off to an application-specific merge. Storage design must surface, not hide, semantic conflict.

Distributed message queue (Kafka-shaped)

A distributed queue is a set of durable, numbered logs. Producers append records; consumers remember how far they have read. Partitioning creates parallelism and per-key order, while replication keeps acknowledged records safe after a broker fails.

core choice
a log you read by offset, not a queue you pop
ordering
per partition, by key
durability
leader + in-sync replicas; acks=all; min.insync.replicas
delivery
at-least-once by default; exactly-once = idempotent producer + transactional offsets

Requirements and scale

Functional

  • Publish to topics; subscribe with consumer groups that share the work.
  • Ordered delivery within a partition; replay from any offset; retention by time or size.
  • Delivery guarantees: at-least-once by default; exactly-once as an option; dead-letter handling.
  • Admin: create topics, scale partitions, observe lag.

  • Throughput of millions of messages per second; latency of milliseconds end to end.
  • Durability: an acknowledged message survives the loss of a broker.
  • Availability through leader failover in seconds; horizontal scale by adding partitions and brokers.
  • Backpressure: slow consumers don’t break producers.

System design

Worked example

Publish three payment events for the same account

Intuition: a numbered notebook per partition.Producers append; consumers remember the last line they finished. Reading does not tear out the page, so another consumer or a replay can read it later.

  1. The account id hashes all three events to partition 0, preserving their order.
  2. The producer batches them to P0’s leader, which appends sequentially and assigns offsets.
  3. Followers replicate the bytes; the leader acknowledges only after the required in-sync replicas have them.
  4. The group member that owns P0 polls, processes the batch, then commits its next offset.

What to notice: ordering is only within a partition. Consumer position is separate from stored data, which is why replay and multiple consumer groups are possible.

Algorithms, and what each one does

Hash partitioning by key

partition = hash(key) mod N: every record with the same key lands on the same partition, which is what gives per-key ordering. Null keys round-robin.

fits: any sharded log or store · remember: adding partitions remaps keys
Leader-follower replication with ISR

Followers fetch from the leader; a follower that falls too far behind leaves the in-sync set. The high-watermark is the last offset present on all ISR members; acks=all means “wait for the ISR”.

fits: durable logs · remember: HW = min(ISR log end offsets)
Raft (controller quorum)

Leader election with majority votes and a replicated log of metadata changes; a majority must agree before a change is committed. Used for topic metadata and leader assignment, not for the data path.

fits: metadata, config stores (etcd), KV databases with strong consistency · remember: majority of 2f+1 survives f failures
Segmented log with sparse index

A partition is a sequence of segment files; each has a sparse index (every N KB: offset → file position). Finding an offset is a binary search in the index then a short scan — O(log n) with tiny indexes.

fits: any append-only store · remember: sparse index, sequential reads
Zero-copy and page cache

Segments live in the OS page cache; sendfile moves bytes from the cache to the socket without passing through user space. The broker rarely touches the data.

fits: high-throughput byte streaming · remember: the OS is the cache
Log compaction

Background rewrite of old segments keeping only the latest record per key (and tombstones for deletes): a changelog becomes a snapshot of current state that can rebuild a table.

fits: changelogs, offsets topic, CDC · remember: latest per key, not time-based
Consumer group rebalancing

A group coordinator assigns partitions to members (range, round-robin, sticky); cooperative rebalancing revokes only the partitions that move, so the rest keep consuming.

fits: parallel consumers · remember: partitions ≥ consumers
Idempotent producer & transactions

Producer id + per-partition sequence numbers let the broker drop retried duplicates; transactions write to multiple partitions and commit offsets atomically, with a coordinator writing commit/abort markers consumers honour.

fits: exactly-once stream processing · remember: inside the system only; sinks must be idempotent
Backpressure by pull

Consumers fetch what they can handle; lag grows instead of memory. Producers get backpressure via bounded buffers and max.block.

fits: every streaming pipeline · remember: lag is the health metric
Time index

Per segment, timestamp → offset entries so seek(timestamp) is a binary search instead of a scan.

fits: replay from a point in time · remember: second index beside the offset index

A message queue is a byte-moving system wrapped in ordering and durability promises. Size both messages/second and MB/second, because either may bind. Then multiply retention by replication, check the hottest partition, and ask how quickly consumers can recover after falling behind.

Scenario 1 — one million small events per second

Peak ingress is one million events/s, average event 800 bytes. Payload is 800 MB/s. With replication factor three, brokers receive leader traffic and send two follower copies, creating roughly 2.4 GB/s of cluster write flow before protocol overhead. Seven-day retention is 1M × 800 B × 86,400 × 7 ≈ 484 TB logical, or 1.45 PB replicated.

  1. Batch. Sending each 800-byte record as its own request makes one million broker requests/s. Batching 500 records creates 400 KB batches and only 2,000 produce requests/s, improving network and sequential disk efficiency at the cost of a few milliseconds of delay.
  2. Pick partitions from three constraints. Suppose one partition safely handles 20,000 records/s or 20 MB/s, and consumers need 100-way parallelism. Event count calls for fifty partitions, byte rate forty, consumers one hundred. Choose at least one hundred, then add growth headroom—perhaps 144 or 192.
  3. Size broker disk. If a broker safely holds 12 TB usable after reserve, 1.45 PB needs 121 broker-equivalents by disk alone. Throughput may require more. Keep utilization below roughly 70% so partition movement and repair have room.
  4. Account for egress. Five independent consumer groups each read the full stream: 4 GB/s application egress in addition to replication. Consumer count does not change stored bytes, but it changes broker/network capacity substantially.

retained physical bytes = ingress bytes/s × seconds retained × replication

Scenario 2 — a hot tenant and ordering boundaries

Hashing by tenant preserves per-tenant order, but one customer contributes 200,000 of the million events/s. If a partition safely handles 20,000/s, that key is ten times too hot and cannot be repaired by adding ordinary partitions. The product must decide what ordering it actually needs.

  1. Narrow the ordering domain. If order is only required per device or account, partition on tenant + entity. The tenant spreads while each entity remains ordered. If total tenant order is mandatory, one sequencer is an inherent throughput ceiling.
  2. Stripe with sequence reconstruction. Assign a monotonic tenant sequence number, then distribute records over N stripes. Consumers merge by sequence. This raises complexity and buffering; missing records can stall the merge. Use only when strict aggregate order is worth it.
  3. Isolate noisy neighbors. Give very large tenants dedicated topics or partition pools, quotas, and separate retention. Shared clusters need admission control so a producer cannot fill disks faster than operators can expand.
  4. Bound retry storms. If acknowledgements time out during a broker failover, producers retry. Idempotent producer ids and sequence numbers deduplicate at the partition. Backoff with jitter prevents all producers from retrying at once.
Interview insight: “ordered queue” is incomplete. Ask ordered relative to what key and for how long. The answer defines the maximum parallelism available to both brokers and consumers.

Scenario 3 — catch-up after a six-hour consumer outage

A consumer group normally receives 800 MB/s average and processes 1 GB/s, leaving 200 MB/s spare. After six hours down, backlog is 800 MB/s × 21,600 s = 17.28 TB. On restart, spare capacity of only 200 MB/s needs 86,400 seconds—24 hours—to catch up, even if new traffic stays average. “Consumer capacity exceeds producer capacity” is not enough; recovery time matters.

  1. Choose a recovery objective. To clear 17.28 TB in two hours while ingest continues, extra rate must be 2.4 GB/s. Total processing must reach 3.2 GB/s, over three times normal fleet capacity.
  2. Make scaling possible. Consumer instances cannot exceed useful partition parallelism. If the topic has one hundred partitions and one instance handles four, twenty-five instances are the normal concurrency ceiling. More partitions may be justified by recovery, not steady load.
  3. Measure lag two ways. Record lag shows remaining work; time lag shows user impact. One billion tiny events and one billion large events differ operationally, while a thirty-minute age directly expresses freshness.
  4. Protect live traffic. Unthrottled catch-up can saturate brokers and hurt producers. Reserve read bandwidth, throttle replay, or serve historical segments from tiered object storage. Recovery should not create a second incident.

Track produce/consume event and byte rates, batch size, request p99, under-replicated partitions, ISR changes, disk fullness, partition skew, leader imbalance, oldest lag age, rebalance duration, duplicate rate, and dead-letter volume. Alert on causes and user consequences, not merely broker CPU.

catch-up time = backlog bytes ÷ (consumer capacity − ongoing ingress)
required capacity = ongoing ingress + backlog bytes ÷ recovery objective seconds

System design

Worked example

Write a shopping cart while one of three replicas is down

Intuition: store three copies, wait for enough votes.The client does not need every replica to answer—only the chosen write quorum. A later overlapping read quorum is likely to encounter the new value.

  1. The coordinator hashes the cart key, finds its three replicas, and sends the timestamped write.
  2. Two live replicas append to their WAL and memtable; with W = 2, the client gets success.
  3. The coordinator holds a hint for the unavailable third replica and replays it when that node returns.
  4. A read with R = 2 compares two copies, returns the newest, and repairs any stale replica it observes.

What to notice: with N = 3, R = 2, and W = 2, read and write sets overlap. That improves freshness, but conflict resolution is still needed for concurrent writes.

Algorithms, and what each one does

Consistent hashing + virtual nodes

Hash nodes and keys onto a ring; a key belongs to the first node clockwise. Adding a node takes keys only from its neighbour (K/N expected). Virtual nodes give each physical node many ring positions, balancing load and spreading rebuild traffic.

fits: KV stores, caches, queues, gateways · remember: K/N keys move; ~256 vnodes per node
Quorums (N, R, W)

Write to N replicas, wait for W; read from R. If R + W > N every read overlaps the latest write; W = 1 is fastest and least durable; ALL is strongest and least available.

fits: any replicated store · remember: N=3, R=W=2 is the usual answer
Vector clocks

One counter per node per value; a write increments the coordinator’s counter. Two versions are ordered if one vector dominates, concurrent otherwise — concurrent versions are kept as siblings for the application to merge.

fits: no-lost-update stores (Dynamo, Riak) · remember: detects conflicts, doesn’t resolve them
Last-writer-wins + hybrid logical clocks

Each write carries a timestamp; the highest wins. HLCs combine wall clock and a logical counter so causality survives small clock skew.

fits: Cassandra-style simplicity · remember: can lose concurrent updates silently
Gossip

Every second, each node tells a few random peers what it knows (membership, tokens, health); information spreads epidemically in O(log N) rounds with no coordinator.

fits: membership, config dissemination · remember: O(log N) rounds, eventually consistent
Phi-accrual failure detector

Keeps the history of heartbeat intervals and outputs a suspicion level φ (how improbable the current silence is); callers pick a threshold instead of a fixed timeout.

fits: any heartbeat system · remember: adaptive to network conditions
Hinted handoff

If a replica is down during a write, another node stores a hint and replays it when the replica returns. Keeps writes available and repairs short outages.

fits: leaderless writes · remember: hints expire; not a substitute for repair
Merkle-tree anti-entropy

Each replica builds a hash tree over its key range; replicas compare roots, descend only into differing subtrees, and exchange just the keys that differ.

fits: periodic repair, Drive sync, blockchains · remember: O(log n) comparisons for small diffs
LSM tree

Writes go to a write-ahead log and an in-memory sorted memtable; when full it flushes to an immutable sorted file (SSTable). Reads check the memtable, then SSTables newest-first. Compaction merges SSTables (size-tiered or leveled) to bound read amplification.

fits: write-heavy stores (Cassandra, RocksDB, Kafka state) · remember: sequential writes, compaction cost
Bloom filter per SSTable

Before reading an SSTable for a key, check its Bloom filter: a “no” is certain and skips the disk read. ~10 bits per key for a 1% false-positive rate.

fits: LSM reads, dedup checks · remember: never a false negative
Paxos for compare-and-set

A lightweight transaction runs a Paxos round among the replicas to agree on a single value, giving linearisable conditional writes on an otherwise eventually consistent store.

fits: unique usernames, leases · remember: ~4 round trips; use rarely
Tombstones

A delete is a write of a marker that replicates like data and wins over older values; purged at compaction after a grace period long enough for every replica to see it — otherwise a lagging replica resurrects the key.

fits: every replicated store · remember: gc_grace must exceed repair interval

Scenario 2 — quorum latency and availability

With replication N=3, choose read quorum R and write quorum W. R=2, W=2 gives overlap because R+W>N, but both operations wait for two replicas. R=1, W=3 makes reads fast and writes sensitive to one slow replica. The arithmetic is simple; the latency distributions are not.

  1. Estimate tail latency. Waiting for the second-fastest of three replicas is usually better than waiting for the slowest. Hedged or speculative reads can send to multiple replicas and take the first valid response, trading extra load for tail reduction.
  2. State the consistency model. R+W>N only helps when quorums are drawn from the same current replica set and version resolution is sound. Sloppy quorums during partitions may write to substitutes, so read repair and hinted handoff are part of convergence.
  3. Quantify availability directionally. If each replica independently has 99.9% availability, requiring all three is roughly 99.7% before correlated failures; requiring any two is much higher. Independence is optimistic because rack, software, and network failures correlate—hence fault-domain placement.
  4. Match business semantics. Shopping-cart additions can merge siblings; account balance updates cannot casually use last-write-wins. If conditional transactions dominate, a leader-per-shard consensus design may be clearer than a Dynamo-style leaderless store.
Intuition: quorum numbers are not decorations. They choose which order statistic controls latency, how many simultaneous faults block progress, and what reconciliation work remains after partitions.

Scenario 3 — compaction and repair under growth

Logical writes are 500,000/s at 600 bytes, or 300 MB/s. If the LSM configuration has 8× write amplification, disks collectively write 2.4 GB/s during compaction before replication effects are interpreted at the node level. Add replication carefully: each replica’s LSM amplifies its own 300 MB/s-equivalent share, so cluster physical write work is about 7.2 GB/s.

  1. Provision compaction bandwidth. Foreground append is fast only while compaction keeps up. Track pending-compaction bytes. If it grows during steady traffic, the system is borrowing from the future and will eventually hit disk or read amplification limits.
  2. Estimate repair. Replacing a node with 4.8 TB used and streaming at a safe 200 MB/s takes at least 6.7 hours before validation and throttling. To recover in two hours requires about 667 MB/s plus source capacity. Recovery objectives influence node size: smaller nodes rebuild faster.
  3. Model tombstones. Deletes in an LSM are new writes; bytes disappear only after compaction and grace periods. A mass expiry can produce read amplification and disk pressure. Stagger TTLs and monitor tombstone scans.
  4. Check partition skew. Vnodes smooth random keys but cannot split a single hot key. Report top-key and top-partition QPS, not only node averages. Salt aggregatable keys, isolate tenants, or redesign the access pattern.
physical compaction write rate ≈ logical ingest × replication × write amplification
minimum repair time = bytes to stream ÷ safe repair bandwidth
headroom pays for compaction, repair, skew, and growth—not just future customers

Monitor p50/p99 by operation, timeouts, coordinator retries, cache hit ratio, bloom false positives, SSTables/read, pending compaction bytes, tombstones scanned, disk fullness, replica divergence, hint age, repair age, and per-partition skew. A low average latency with an ever-growing compaction backlog is not healthy.

Estimation answer“I compute node count independently from capacity, reads, writes, memory, and network, then take the maximum with failure reserve. I turn logical writes into physical compaction bandwidth, size rebuild time explicitly, and connect R/W choices to both latency order statistics and business conflict semantics.”

The chain that makes system design understandable

A design is not a collection of fashionable components. It is a chain of consequences. People behave in some way; that behavior creates reads, writes, bytes, concurrency, and hot spots; those loads meet latency and correctness promises; the resulting bottlenecks justify particular components. If you can narrate that chain, an interviewer can follow and challenge your reasoning.

1 · Start with a user action, not a database

Choose one concrete action: “Alice sends a message to a three-person group,” “Bob opens a home feed,” or “a driver sends a location update.” Follow it end to end. Name what must be durable before success, what may happen asynchronously, what data is read or written, who else is notified, and what the user sees during failure. Components emerge naturally. A durable acknowledgement implies replicated storage or a log. Notifications imply fan-out. Fast repeated reads suggest caching. Exclusive ownership suggests a conditional write, lease, or consensus group.

A common weak answer starts with “I’ll use Kafka, Redis, and Cassandra.” That gives no test for whether the pieces are necessary. A strong answer says, “The post request only needs to durably store the post and an outbox event; timeline insertion is asynchronous because a celebrity may have millions of followers.” Now the queue exists for a reason: it isolates a latency-sensitive write from large, variable fan-out.

2 · Keep four planes separate

requestAnswers an interactive user action.Low p99, bounded dependencies, graceful fallback.Open feed, redirect URL, accept message.
dataStores and moves authoritative product state.Durability, consistency, partitioning, recovery.Trip state, file manifests, post records.
asynchronousPerforms work not required before response.Backpressure, retry, idempotency, lag.Analytics, fan-out, thumbnails, indexing.

This separation prevents a background analytics outage from blocking a redirect, or a slow control-plane lookup from appearing on every request. It also enables different SLOs: the request path may need 99.99% availability, while analytics can be 99.9% with fifteen-minute freshness.

3 · Find the amplification factors

Most surprising capacity comes from multiplication after the front door. One feed post becomes follower inserts. One group message becomes device deliveries. One map session becomes thirty tile requests. One queue write becomes three replica writes and five consumer reads. One search request examines hundreds of candidates. Write every multiplier next to the user action.

backend work = user requests × fan-out × replicas × retries × candidate amplification
network bytes = operations × payload bytes × copies across boundaries
physical storage = logical data × replicas/coding × indexes × history × engine overhead

Not every factor applies, and some factors reduce work: cache hit ratio multiplies origin work by 1 − hit rate; dedup multiplies storage by the unique fraction; batching divides request count while leaving byte count similar. The point is to expose the transformations.

4 · Size average, peak, and pathological cases

Average checks basic plausibility and daily cost. Peak sizes the fleet and latency queueing. Pathological finds design discontinuities: one viral key, reconnect storm, mass expiry, zone failure, or celebrity account. A system can pass aggregate peak yet fail because one partition owns 30% of traffic.

Use a peak factor only when direct data is absent, and label it. Consumer products often have diurnal 3–10× average peaks; live events can be much higher. A better estimate comes from behavior: users concentrated into waking hours, regional time zones, launch events, and batch schedules. Ask what would make the factor wrong.

5 · Let the bottleneck choose the design

For every major component, compute at least four independent limits: CPU/operations, disk capacity, disk/network bandwidth, and memory/working set. Node count is the maximum, not the sum. Then add utilization headroom and failure reserve. If storage requires 80 nodes and throughput requires 30, deploy at least 80—but verify that those 80 meet network and repair requirements too.

required nodes = max(capacity nodes, QPS nodes, bandwidth nodes, memory nodes, recovery nodes)
safe per-node capacity = benchmarked capacity × target utilization
fleet size = workload ÷ safe per-node capacity, rounded up with fault-domain reserve

6 · Close the loop with measurement

Estimates are hypotheses. Name how production will validate them: bytes per stored record from a representative dataset, Redis bytes per key from MEMORY USAGE, CPU-ms per route from load tests, fan-out distribution from product analytics, compression ratio by file type, and p99 under a zone-failure exercise. Use ranges when uncertain and show which uncertainty matters.

Suppose record size could be 1–2 KB and traffic could peak at 5–8× average. Storage varies 2×; throughput varies 1.6×. If storage already dominates node count by 4×, refining peak traffic may not change the design. Spend interview time on decisions sensitive to the uncertainty.

A reusable answer frame

  1. Clarify: users, core actions, geography, retention, correctness, and what is out of scope.
  2. Quantify behavior: DAU, actions/user/day, concurrency, payload, fan-out, and peaks.
  3. Trace one request: sync boundary, async work, authoritative state, caches, and indexes.
  4. Calculate: QPS, bytes/s, stored bytes, connections, and hot-key load.
  5. Partition and replicate: key, ownership, fault domains, and consistency.
  6. Break it: dependency timeout, duplicate retry, node/zone loss, skew, backlog, cold cache.
  7. Observe it: user SLI, component saturation, correctness signals, and recovery objective.
Core intuition“Architecture is compressed reasoning. Every box should answer a stated workload, correctness requirement, or failure mode. If I cannot explain which assumption created a component, I probably do not need the component yet.”

When estimation should stay deliberately coarse

Do not spend five minutes multiplying precise decimals when the design choice is unchanged across a 10× range. If a dataset is somewhere between 50 and 200 GB, it fits comfortably in memory across a small replicated fleet either way; the more important questions may be update rate, hot-key skew, and recovery. Conversely, refine an input when crossing it changes the architecture—for example, whether one partition can preserve strict order, whether a working set fits memory, whether cross-region latency violates the SLO, or whether a rebuild finishes inside the recovery objective.

Use an order-of-magnitude ladder: tens, hundreds, thousands, millions; kilobytes, megabytes, gigabytes, terabytes. Carry a low/base/high range until a boundary appears. Then say which benchmark or product measurement will resolve it. This is not hand-waving. It is disciplined allocation of attention: uncertainty matters only when the system is sensitive to it.

Requirements and SLOs: convert adjectives into tests

“Fast, scalable, and reliable” is not a specification. A useful requirement names the user action, population, percentile, threshold, measurement boundary, time window, and failure policy. Only then can it guide architecture and capacity.

Functional requirements describe contracts

List the smallest end-to-end behaviors the system must support. For chat: send one-to-one text, receive on multiple devices, fetch missed messages, acknowledge delivery, and create groups. For a file system: upload chunks, atomically publish a version, download, list a folder, share, and synchronize changes. Avoid turning implementation details into requirements. “Use WebSockets” is a proposed mechanism; “online recipients see a message within 500 ms” is the requirement that may justify it.

Explicitly state exclusions. Not supporting full-text search, video calls, or real-time co-editing protects time and prevents contradictory choices. Exclusions are not evasive when the core problem is covered; they are prioritization.

SLI, SLO, and SLA are different

An SLI is the measured indicator: successful requests divided by valid attempts, or end-to-end delivery delay. An SLO is the internal target: 99.9% under 500 ms. An SLA is a customer contract with consequences. Design from the SLO, because operating exactly at an SLA boundary leaves no room for measurement error or incident response.

Choose the denominator carefully. Availability defined as successful responses divided by requests can improve when clients stop retrying during an outage; request-based and time-based views answer different questions. Exclude invalid requests consistently, but do not exclude internal overload or dependency failures simply because they are inconvenient.

Percentiles describe experiences averages hide

p50 is the median; half of samples are faster. p95 leaves one in twenty slower. p99 leaves one in one hundred slower. At one billion requests/day, one percent is ten million slow requests. Tail latency matters because one page may call many services: if twenty independent calls each meet a 99% threshold, the chance all twenty do is 0.99²⁰ ≈ 81.8%. Fan-out amplifies tails.

Do not average percentiles from hosts. Merge histograms or raw distributions. The average of per-host p99s is not fleet p99. Break latency down by region, operation, payload size, status, cache hit/miss, and dependency outcome to make it actionable.

Error budgets turn reliability into a decision

An availability target allows a bounded amount of failure. Over a 30-day month, 99.9% permits 43.2 minutes, 99.99% permits 4.32 minutes, and 99.999% permits about 26 seconds—if interpreted as continuous time. Request-based error budgets are often more useful: at one billion valid requests/month, 99.99% allows 100,000 errors.

error budget fraction = 1 − SLO
allowed failed requests = valid requests × error budget fraction
budget burn rate = observed error rate ÷ allowed error rate

A 14.4× burn rate exhausts a 30-day budget in roughly two days if sustained. Multi-window alerts combine a fast window for acute outages and a slow window for persistent degradation. The design implication is prioritization: when budget is exhausted, reliability work and risky-release controls take precedence over feature velocity.

Availability is not correctness or quality

A feed returning HTTP 200 with no posts is technically available but product-broken. A payment API returning success twice is worse than unavailable. Add correctness SLIs: duplicate charge rate, missing sequence gaps, stale-read rate, invalid state transitions, restore success, and permission leaks. Add quality SLIs: fallback ranking rate, no-route rate, pickup ETA error, or challenge completion.

Worked SLO decomposition

Goal: 99% of online chat messages render on the recipient within 500 ms. Allocate 60 ms sender-to-edge network, 40 ms authentication and gateway, 80 ms sequence plus durable append, 40 ms recipient lookup, 80 ms queue and gateway delivery, 100 ms recipient network/render, and 100 ms contingency. Independent steps add on the critical path; parallel lookups contribute approximately the slowest branch. This budget identifies where caches and co-location matter.

Also define the failure behavior. If presence is stale, try the last known gateway and queue durably. If push notification fails, message remains fetchable. If the durable log cannot meet acknowledgement semantics, return a retryable failure rather than claim success. The SLO is incomplete until degraded outcomes are named.

Self-check: For each requirement, can a test decide pass or fail? Does it name the user-visible boundary? Does it distinguish acknowledged durability from eventual processing? Does it specify percentile and time window? If not, refine it before drawing architecture.

Traffic math: derive load from behavior

Traffic estimates should be auditable. Begin with users and actions, convert time units, separate reads and writes, apply fan-out and cache effects, then create peak and hot-key cases. Round numbers aggressively but never drop units.

The basic conversions

seconds/day = 86,400 ≈ 100,000 for mental math
average QPS = actions/day ÷ 86,400
actions/day = daily active users × actions/user/day
peak QPS = average QPS × observed or assumed peak factor

Example: 40 million DAU each open a feed 12 times/day. That is 480 million reads/day, about 5,560 average QPS. A 7× peak gives 39,000 QPS. If each open loads two pages, peak becomes 78,000 page requests/s. State whether “open” already includes pagination; definitions prevent accidental double counting.

Use 100,000 seconds/day for fast arithmetic, then refine only if the decision is close. Forty million × twelve / 100,000 ≈ 4,800 QPS—within 14% of exact. Capacity estimates already have larger uncertainty. Precision is useful only when inputs are trustworthy.

Concurrency is a rate multiplied by time

Little’s Law says the average number in a stable system equals arrival rate times average time spent: L = λW. It sizes simultaneous requests, sockets, queued items, and work in progress.

At 20,000 requests/s and 200 ms average service time, about 20,000 × 0.2 = 4,000 requests are in flight. If an offline-message queue receives 50,000 items/s and items wait six hours, it contains 50,000 × 21,600 = 1.08 billion items on average. If a site has two million sessions/day averaging fifteen minutes and usage is uniform, concurrency is 2M × 900 / 86,400 ≈ 20,800; diurnal peaks raise it.

Little’s Law applies to a stable boundary with consistent units. It does not predict tail distribution or a system whose backlog grows without bound. When arrival exceeds service, there is no steady state; latency increases until shedding or failure.

Read/write ratio influences architecture

A short-link system with 100 redirects per create is read-heavy: cache aggressively, make redirect reads simple, and tolerate more coordination on rare writes. A telemetry stream can be write-heavy: sequential logs, batching, compaction, and asynchronous materialized views matter. Ratios alone do not choose a database, but they direct attention.

Calculate bytes as well as operations. One million 100-byte events/s is 100 MB/s and likely CPU/request-overhead bound. One thousand 100 MB uploads/s is 100 GB/s and bandwidth bound. “1M QPS” and “1k QPS” can reverse which system is harder.

Peak factor, burst, and seasonality

Average-to-peak factor captures predictable concentration; burst captures short-lived deviation from peak. A token bucket encodes both sustained rate and burst allowance. Capacity should survive expected peak at target utilization and absorb brief bursts via queueing, caching, or explicit shedding. Do not size an expensive permanent fleet for an unbounded event; define overload policy.

Separate global and regional peaks. Traffic across time zones may flatten globally but each regional fleet sees local evenings. Holidays, launches, sports finals, payroll batches, and notification campaigns produce correlated spikes. Use trace replay or a synthetic workload with the same skew, not only uniform random requests.

Hot-key math

Suppose total traffic is 1 million QPS across 100 shards: average 10k/shard. If one key owns 15%, its shard receives at least 150k QPS, no matter how many empty shards exist. The remedies are semantic: cache/replicate reads, split aggregatable state, lease local budgets, narrow ordering scope, isolate the tenant, or change the key. Consistent hashing smooths many random keys; it does not split one key.

hot shard QPS ≥ hottest key QPS + other keys assigned to that shard
effective capacity = min(total fleet capacity, hottest-owner capacity ÷ hottest traffic share)

Cache math

Origin load is total load times miss ratio. At one million reads/s, 99% hits still leave 10,000 origin reads/s; 99.9% leaves 1,000. A cache can reduce read load by 100× while making cold-start the dominant risk. Estimate entry count from the hot working set, resident bytes including object overhead, eviction rate, and fill bandwidth.

Hit rate must be segmented. A 99% global result may combine 99.9% for common objects with 0% for large, expensive rare objects. Byte hit ratio answers bandwidth savings; request hit ratio answers operation savings. Both matter for CDN and object caches.

Three-way worked example

A photo-sharing product has 10 million DAU. Each user opens five sessions/day, loads three pages/session, uploads 0.2 photos/day, and follows 300 accounts. First, feed reads: 10M × 5 × 3 = 150M/day ≈ 1,736/s average; at 8× peak, 13,900/s. Second, uploads: 2M/day ≈ 23/s average; at 10×, 230/s. Third, if each uploaded photo is pushed to 300 timelines, fan-out average is 6,900 inserts/s and peak 69,000/s.

If a feed page returns twenty 40 KB thumbnails, edge media is 800 KB/response. At 13,900 responses/s, edge delivery is 11.1 GB/s. With 98% byte hit ratio, origin serves 222 MB/s. The apparently modest feed QPS becomes a media system; the relatively tiny upload QPS becomes a timeline-write system through fan-out.

Traffic checklist: What counts as one request? Average and peak? Regional split? Reads versus writes? Bytes per operation? Fan-out? Replication? Retries? Cache miss fraction? Hottest key? Recovery or reconnect burst? If these are explicit, most hidden load is visible.

Storage math: follow each byte through its lifetime

Storage estimates fail when “record size” means only the visible payload. Real bytes include keys, metadata, indexes, allocator/block overhead, replicas or erasure coding, version history, tombstones, logs, snapshots, and free space for maintenance. Build the estimate as a multiplication chain and explain every factor.

Logical data begins with records and retention

records/day = writes/s × 86,400, or users × records/user/day
logical bytes = records × bytes/record
retained bytes = bytes/day × retention days + long-lived current state

Example: 200,000 events/s at 600 bytes produces 120 MB/s, 10.37 TB/day, and 311 TB over thirty days. At three replicas, raw replicated payload is 933 TB before indexes and reserve. Saying “about a petabyte” is more honest and useful than reporting 933.12 TB from uncertain inputs.

Estimate a record from fields

A message might contain: 16-byte message id, 16-byte conversation id, 16-byte sender id, 8-byte sequence, 8-byte timestamp, 4-byte flags, 500-byte ciphertext average, and perhaps 32 bytes envelope/checksum: 600 bytes rounded. Database encoding may add row headers, length prefixes, block indexes, and padding. Measure real serialized and resident sizes later.

Keys count too. A cache with a 40-byte string key and 16-byte value can occupy over 100 bytes after object headers, hash table buckets, allocator rounding, and expiry metadata. For in-memory systems, use measured bytes per key; payload size alone can miss by 3–10×.

Replication, erasure coding, and backups solve different problems

Replication keeps data online during hardware failure and supports reads. Erasure coding offers similar durability with less capacity but more CPU/network and slower small updates. Backups or version history protect against operator error, software bugs, malicious deletion, and correlated logical corruption. Three replicas faithfully replicate an accidental delete; they are not a backup.

Durability claims require detection and repair. If a silent bit error is never scrubbed, redundancy can decay unnoticed. Estimate the repair window after a disk, node, rack, or zone loss. A 10 TB node at a safe 200 MB/s needs at least fourteen hours to stream, before contention. Smaller failure domains can recover faster even with similar total capacity.

Write and read amplification

In an LSM tree, one logical write is appended quickly but rewritten through compaction levels. Write amplification of ten means 100 MB/s logical ingest causes around 1 GB/s disk writes per replica. In a B-tree, random-page updates and WAL writes create a different pattern. Read amplification counts how many files, indexes, or services are consulted per logical read. Bloom filters, caches, and compaction tune the trade.

Application amplification matters too: one profile page may fetch account, preferences, social counts, permissions, and recent activity. Batch or denormalize only after quantifying which joins or remote calls are expensive and how updates remain correct.

Retention, TTL, and deletion are physical processes

A TTL does not instantly free disk. In an append-only or LSM engine, expiry creates tombstones or makes segments eligible for compaction. A synchronized expiry wave can overload compaction. Add jitter, partition retention by time, and delete whole segments when possible. Track reclaim lag: expired logical bytes still occupying physical storage.

Legal deletion may require more than logical invisibility. Define how primary stores, search indexes, caches, analytics copies, backups, and derived models handle deletion, and the completion window. This is a data-lifecycle requirement, not an afterthought.

Worked example: event history plus current state

A delivery product stores 50 million current orders at 2 KB each: 100 GB logical. It also appends 500 million order events/day at 400 bytes: 200 GB/day. Ninety days of event history is 18 TB. Add 30% indexes/engine overhead and three replicas: current state is 390 GB; events are 70.2 TB. At 65% target fullness, provision about 109 TB. Event retention, not current state, dominates.

If analytics can archive events after seven hot days, hot replicated storage falls to 1.4 TB × 1.3 × 3 / 0.65 ≈ 8.4 TB, while the remaining 83 days move to cheaper compressed object storage. Tiering is justified by access pattern and recovery needs.

Latency, concurrency, queues, and backpressure

Latency is not just the sum of service times. It includes network, serialization, queue wait, locks, cache misses, retries, and fan-out tails. As utilization approaches saturation, queues grow nonlinearly. Good designs leave headroom, bound work, and shed lower-priority load before every request becomes slow.

Build a critical-path budget

Draw the calls that must finish before the response. Sequential calls add; parallel calls contribute roughly the slowest branch plus coordination. If an API has a 300 ms p99 target and uses gateway 20, cache 10, two parallel services at 70 and 90, assembly 20, network 40, the nominal path is 20 + 10 + max(70,90) + 20 + 40 = 180 ms, leaving 120 ms for jitter and retries. Without a budget, every dependency can claim 100 ms and the end-to-end target becomes impossible.

Place timeouts inside the caller’s remaining deadline. A downstream timeout longer than the upstream deadline only wastes work after the user has gone. Propagate deadlines and cancellation where supported. Retries need remaining budget and idempotency.

Utilization creates queueing

A simplified single-server queue shows the intuition: as utilization moves from 50% toward 90–100%, waiting time rises sharply. Real distributed systems have variable service time and multiple workers, but the shape remains. Operating a component at 95% average leaves no room for bursts, skew, garbage collection, or failure.

Target utilization depends on elasticity and recovery speed. A stateless service that adds instances in one minute can run higher than a database shard that takes hours to rebalance. Common interview starting points are 50–70% for stateful or latency-critical tiers and perhaps 60–75% for easily replicated stateless tiers, then justify with measurements.

Little’s Law connects latency and concurrency

in-flight requests = requests/s × average response seconds
queue depth = arrival rate × average wait seconds
required workers ≈ arrival rate × service seconds/worker ÷ target utilization

At 5,000 tasks/s and 40 ms CPU/task, workload is 200 CPU-seconds/second, or 200 busy cores. At 60% target, budget 334 cores. If each task instead waits 40 ms on remote I/O, asynchronous workers may multiplex it; CPU formula and connection/concurrency formula must be separated.

Tail amplification under fan-out

A request that waits for all 100 shards is likely to observe one slow shard. If each shard independently completes under threshold 99% of the time, all 100 do so only 0.99¹⁰⁰ ≈ 36.6% of the time. Independence is a simplification, but it shows why scatter-gather systems have difficult tails.

Mitigations include reducing fan-out, pre-aggregation, partial results, deadline-aware cancellation, hedged requests after a percentile threshold, redundant replicas, and isolating stragglers. Hedging increases load; only use it with spare capacity and cancel losers.

Backpressure protects the whole system

When consumers slow, unbounded queues convert overload into memory exhaustion and stale work. Use bounded queues, admission control, producer throttling, and priority. Define what is dropped: typing indicators before messages, analytics before payments, stale refresh work before new interactive requests.

Load shedding should happen early and cheaply. Rejecting at the edge after authentication may be better than letting requests consume database connections. Return retry guidance with jitter. Circuit breakers stop repeated calls to a known-bad dependency, but must probe recovery and avoid synchronized reopening.

Retries are multiplicative traffic

If 20% of calls fail and each failure gets two retries, extra offered load can be 40% before retry failures themselves are considered. When a dependency is overloaded, retries often make it worse. Use exponential backoff, random jitter, attempt limits, retry budgets, and idempotency keys. Prefer retrying at one layer; nested retries can multiply explosively.

A retry budget might allow retries to consume no more than 10% of normal request volume. When exceeded, fail fast or degrade. Track attempts per logical operation, because QPS dashboards can otherwise mistake retry amplification for genuine demand.

Batching trades latency for efficiency

Batching amortizes network, syscall, compression, and disk overhead. A queue producer can combine 500 800-byte events into a 400 KB request. Waiting five milliseconds to fill a batch may be invisible for analytics but unacceptable for an emergency alert. Bound both batch size and maximum wait.

Large batches reduce request count but can worsen tail latency, memory, retry cost, and fairness. A failed 10 MB batch retransmits more work. Choose from throughput measurements and product latency, not a universal number.

Worked overload example

A service normally receives 20,000 QPS and handles 30,000 at target p99. A dependency slows, doubling service time; capacity roughly halves to 15,000. Queue grows by 5,000 requests each second. In ten seconds, 50,000 wait. If clients time out after two seconds and retry once, offered traffic rises and much queued work finishes after clients have abandoned it.

A healthier policy admits 14,000 high-priority requests, sheds the rest immediately, cancels work on deadline, and enters a cheap fallback. Success rate is lower for the moment, but admitted requests remain responsive and recovery is faster. Availability is sometimes preserved by rejecting bounded work rather than pretending all work can complete.

Latency checklist: End-to-end boundary? p50/p95/p99? Critical path? Parallel fan-out? Queue wait versus service time? Target utilization? Deadlines? Retry budget? Bounded queues? Priority and shedding? Recovery traffic?

Reliability: design for faults, then prove recovery

Reliability is the ability to provide a correct, useful service despite expected faults. It includes prevention, isolation, graceful degradation, detection, repair, and learning. Replication is only one mechanism. A system with three replicas but an untested restore, shared credentials, or one bad deployment pipeline can still have a single failure domain.

Start with failure domains

Name what can fail together: process, host, disk, rack, availability zone, region, cloud control plane, software version, dependency, credential, configuration, operator action, and data model. Place redundancy across the domain you intend to survive. Three replicas on one rack do not survive rack power loss. Three regions running the same corrupt binary do not survive a software bug.

Correlated failures make naïve probability multiplication optimistic. If a node is available 99.9%, three independent copies look extraordinary; but they share networks, deploys, and traffic. Use probability as intuition, then build around explicit fault domains and test them.

Availability arithmetic

For independent components in series, multiply availability. A request that needs five 99.99% dependencies has about 0.9999⁵ ≈ 99.95% path availability before the application itself. Dependencies can therefore make a four-nines endpoint impossible unless calls are cached, optional, redundant, or degraded.

For independent redundant copies where any one suffices, unavailability multiplies. Two 99.9% replicas would theoretically be unavailable together only 0.001² = 0.000001, or 99.9999% availability. Failover is not free: detection delay, election, state divergence, and client retry reduce realized availability.

series availability = A₁ × A₂ × … × Aₙ
parallel availability when any copy works = 1 − Π(1 − Aᵢ)
monthly downtime approximation = (1 − availability) × 43,200 minutes

RPO and RTO make recovery concrete

Recovery point objective (RPO) is how much recent data may be lost, measured in time or acknowledged operations. RPO zero for acknowledged writes usually requires synchronous replication to a separate failure domain before success. Recovery time objective (RTO) is how long service can remain unavailable or degraded after the event.

A nightly backup gives up to 24-hour RPO even if restore takes ten minutes. Synchronous replicas can give near-zero RPO but still have a one-hour RTO if failover is manual. State both. Also distinguish component recovery from product recovery: a database may elect a leader in ten seconds while caches warm and consumers clear backlog for hours.

Acknowledgement defines durability

Ask what must be true before returning success. For a message, perhaps the record is fsynced or replicated to a quorum and assigned a sequence. For a file upload, blocks may exist but the version is not visible until an atomic manifest commit. For a payment request, an idempotent intent may be durable even though settlement is asynchronous.

If success is returned before the durable point, a crash can lose an acknowledged action. If success waits for every downstream side effect, latency and availability suffer. The usual pattern is to commit authoritative state plus an outbox event atomically, then perform derived work asynchronously.

Idempotency makes at-least-once delivery safe

Networks cannot always tell a client whether a timed-out operation committed. Retrying is necessary; duplicate effects are not. An idempotency key identifies the logical request. The server records the key and result within the same transactional boundary as the effect, then returns the original result on duplicates.

Define scope and lifetime. A key unique per customer may be sufficient; global uniqueness may be unnecessary. Retain keys at least as long as legitimate retries. Payload mismatch under the same key should be an error, not silent reuse. Downstream consumers also need event ids or natural idempotent state transitions.

Delivery semantics in plain language

At most once may lose work but does not retry duplicates—useful for ephemeral telemetry. At least once retries until acknowledged, so duplicates are possible—the common durable choice. Exactly once is scoped: a broker can make a consume-transform-produce transaction exactly once within its system, but an external email or card charge still needs idempotency. End-to-end exactly-once outcomes are composed from deduplication and transactional boundaries.

Timeout, retry, circuit breaker, and bulkhead

A timeout bounds waiting. A retry addresses transient failure. A circuit breaker stops calls when failure is persistent. A bulkhead limits how much of the caller can be consumed by one dependency or tenant. They work together but can also harm: overly short timeouts cause retries; retries amplify overload; breakers synchronize; shared pools let one slow dependency exhaust all threads.

Give each dependency a concurrency limit based on its safe capacity. Reserve pools for critical work. Use jittered backoff and retry budgets. During recovery, reopen gradually. Track rejected-by-bulkhead and short-circuited calls as product degradation, not invisible technical counters.

Graceful degradation is a product decision

List features in priority order. A feed can drop personalized features and return cached chronological posts. Chat can drop typing and presence while retaining durable sends. Maps can use historical traffic or straight-line ETA. A drive product can allow cached downloads while pausing new metadata mutations. Degradation should preserve correctness: serving slightly stale public data can be safe; serving stale permissions may be a security failure.

Test degraded paths regularly. A fallback invoked only during disaster often contains stale code, cold caches, expired credentials, or insufficient capacity. Dark-read or shadow traffic, controlled fault injection, and game days keep it credible.

Failure-detection tradeoff

Detecting failure too slowly extends downtime; detecting too aggressively mistakes delay for death and causes needless failover or split brain. Heartbeats, leases, and phi-accrual detectors turn observations into suspicion. The appropriate threshold depends on network variability and takeover cost. Fencing tokens ensure an old leader cannot continue writing after a new leader takes ownership.

Worked regional failure

A service receives 300,000 QPS split 50/30/20 across three regions. Each normally runs at 55% safe capacity. If the largest region fails and traffic redistributes proportionally, the others must absorb 150,000 extra QPS. Their combined normal load is 150,000; it doubles to 300,000, pushing 55% to 110%. “Three regions” did not provide regional failover capacity.

Options: provision N+1 capacity so any two regions carry all traffic; shed low-priority work; keep warm reserve; or recover only critical functions. Also consider state: synchronous global writes may block when a quorum region is lost; asynchronous failover risks RPO. State the chosen trade.

Recovery is a workload

After an outage, reconnects, cache fills, retries, replica repair, and consumer replay arrive together. Size recovery separately. If a consumer accumulates 20 TB and only has 200 MB/s spare, catch-up takes about 28 hours. If a cache normally offloads 99%, cold origin load can be 100×. Rate-limit recovery and prioritize current interactive work.

Reliability checklist: What is acknowledged? Which faults are in scope? Are replicas in separate domains? RPO and RTO? Backup restore tested? Idempotency scope? Retry budget? Fencing? Degraded product behavior? N+1 capacity? Recovery bandwidth and cache warm-up?

Consistency, partitioning, and distributed ownership

Consistency is not a single slider from weak to strong. Different guarantees answer different user questions: do I read my write, do observers agree on order, can two clients reserve the same driver, can offline edits merge, and what happens during a network partition? Choose per invariant and per data type.

Begin with invariants

An invariant is a truth the system must preserve: one driver cannot have two active trips; a file version references only existing blocks; a wallet cannot spend more than its allowed balance; a message sequence for one conversation never goes backward. Strong coordination is justified around invariants, not everywhere.

Derived views can usually lag: feed timelines, search indexes, analytics aggregates, presence, and thumbnails. Keep authoritative state small and strongly controlled, then rebuild or reconcile derived state from logs. This narrows the expensive consistency boundary.

CAP without the slogan

When a network partition separates replicas, a system cannot both guarantee every request receives a non-error response and guarantee linearizable agreement across the split. It must reject/delay some operations or allow divergent progress. Outside partitions, latency and consistency tradeoffs still exist, but CAP specifically frames partition behavior.

Choices can differ by operation. A social feed may continue serving slightly stale reads while rejecting privacy-setting changes if the authorization source is unreachable. A cart may accept additions in both partitions and merge; a scarce inventory reservation may require the owning quorum.

Leader-based ownership

One leader per shard serializes writes and replicates a log. It simplifies conditional updates, ordered sequences, and linearizable reads through the leader. Consensus elects the leader and commits entries to a majority. With 2f+1 voters, the group tolerates f failures while retaining a majority: three tolerates one, five tolerates two.

Leaders create hot-shard ceilings and failover pauses. Reads from followers scale but may be stale; use leader reads, leases, or version tokens when freshness matters. Reconfiguration itself must be committed safely so two memberships do not form disjoint majorities.

Leaderless quorums

A coordinator writes to W of N replicas and reads from R. With stable membership and R+W>N, read and write sets overlap. Concurrent writes still need versions and conflict resolution. Sloppy quorums may use substitute nodes during failure, improving availability but weakening immediate overlap.

Example with N=3: R=2/W=2 balances; R=1/W=3 favors reads but waits for every write replica; R=3/W=1 favors writes but makes reads fragile. Latency is determined by the required response order statistic. Business conflict semantics matter more than memorizing numbers.

Conflict resolution is domain logic

Last-write-wins is simple but can discard real work and depends on timestamp ordering. It may fit a profile picture; it is dangerous for balances. Multi-value registers preserve siblings for application merge. Sets and counters can use CRDTs when operations have suitable algebraic properties. Binary file edits often become conflicted copies because automated merge has no semantics.

Choose what concurrent means. Two updates based on the same version are concurrent even if wall-clock timestamps differ. Vector clocks or version vectors capture causality but metadata grows. Hybrid logical clocks help order events while reflecting physical time, yet do not magically turn conflicts into correct domain outcomes.

Transactions and sagas

A local ACID transaction protects invariants within one database boundary. Distributed two-phase commit can atomically coordinate participants but may block and creates operational coupling. A saga decomposes a long workflow into committed local steps with compensating actions. Compensation is not time travel: refunding a charge does not erase a completed ride.

The outbox pattern atomically writes business state and an event in one local transaction. A relay publishes the event at least once; consumers deduplicate. This avoids the dual-write failure where a database commit succeeds but queue publish fails, or vice versa.

Partitioning determines ownership

Hash partitioning spreads random keys well and supports point lookups. Range partitioning supports ordered scans but can create a hot latest range. Geographic partitioning provides locality but dense cities skew. Time partitioning makes retention easy but concentrates current writes. Composite keys combine goals, such as tenant + hash(entity) or region + time bucket.

A partition key also sets the transaction and ordering boundary. Data frequently updated together should often share ownership; data with independent high throughput should be separable. Cross-shard operations add coordination or asynchronous reconciliation. Model the hottest key and hottest tenant before declaring even distribution.

Consistent hashing and virtual shards

Consistent hashing maps keys around a ring so adding one node moves roughly 1/N of keys rather than remapping all. Virtual nodes improve balance and placement. Many systems instead use a fixed large number of logical shards mapped to physical nodes; ownership moves without changing the key-to-logical-shard mapping. This simplifies operations and range movement.

Neither mechanism fixes a hot key. They distribute many keys statistically. Hot objects need read replicas/caches; hot mutable counters need striping or leases; strict ordered hot streams may require a stronger single-owner machine or narrower ordering semantics.

Membership, failure detection, and fencing

Gossip spreads membership and health without one coordinator, but it is eventually consistent. Failure detectors report suspicion, not certainty. A lease gives ownership for bounded time under clock/renewal assumptions. A monotonically increasing fencing token lets storage reject an old owner even if it wakes after a pause. Without fencing, two processes may both believe they own a shard.

Worked invariant: reserve one driver

Two riders concurrently select driver D. An eventually consistent availability cache can recommend D to both; that is acceptable. The authoritative assignment performs a conditional transition available → offered(request_id, expiry). Only one compare-and-set succeeds. The loser chooses another candidate. If the offer expires, a newer fencing/version value returns D to available. The strongly consistent boundary contains one driver record, not the entire geospatial search.

Worked eventual view: feed timeline

Post P is durably written with an outbox event. Fan-out workers insert P’s id into follower timelines at least once. Duplicate inserts are harmless because timeline entries key by follower and post id. If a worker dies, queue replay completes missing work. A follower may see P seconds late but never loses the authoritative post. A repair job can compare author logs with timeline ranges. Here eventual consistency improves availability because the view is derivable.

Consistency checklist: What invariant must never break? What can lag? Ordering per what key? Read-your-writes needed? Conflict semantics? Partition behavior? Transaction boundary? Idempotency? Ownership and fencing? Repair source of truth?

Cost and capacity: money follows resource-seconds and byte-miles

A system-design estimate should identify the cost-shaped decisions even when no cloud price sheet is available. Compute units, stored byte-months, transferred bytes, provisioned headroom, and engineering complexity are the main levers. Use symbolic or relative cost when exact prices are unknown; the architecture decision often depends on ratios, not cents.

Capacity is workload divided by safe throughput

Benchmark a representative operation mix at the latency target, then discount to a safe utilization. If one service instance sustains 5,000 requests/s at target p99 and you operate at 60%, use 3,000 safe QPS. A 90,000-QPS peak needs thirty instances before fault-domain reserve. If losing a zone removes one third of capacity, provision forty-five across three zones so the surviving thirty still meet peak.

safe capacity/instance = measured capacity at SLO × target utilization
steady instances = peak workload ÷ safe capacity/instance
N+1 instances = steady need ÷ surviving fleet fraction after chosen failure

Autoscaling reduces long-term waste but does not eliminate reserve. Scale-up delay, connection warm-up, cache fill, data rebalancing, and quota limits determine how much warm capacity remains necessary. Stateful tiers often scale too slowly for sudden bursts.

Compute cost begins with work, not instance names

Convert operations to CPU-seconds. If ranking 100 candidates costs 6 CPU-ms and peak is 50,000 feeds/s, work is 300 CPU-seconds/s, or 300 busy cores. At 50% utilization and 16 usable cores/instance, need about 38 instances. Measure memory and accelerator needs separately; a model may be memory-bandwidth or GPU-bound rather than CPU-bound.

Batch workloads have a deadline instead of interactive QPS. Ten billion items at 2 ms CPU/item equal 20 million CPU-seconds, about 5,556 core-hours. To finish in six hours requires roughly 926 continuously busy cores; at 70% effective utilization, 1,323 cores. The same work can be cheap and slow or expensive and urgent.

Storage cost is provisioned physical capacity over time

Start with physical bytes after compression, dedup, replication/coding, indexes, and history. Divide by target fullness. A 500 TB physical requirement at 65% target fullness needs 769 TB provisioned. Then split hot SSD, warm HDD, and archival object tiers by access and recovery objectives.

Provisioned IOPS can dominate capacity. A 1 TB high-IOPS database may cost more than 100 TB of archival objects. Conversely, huge immutable media can dominate byte-months and egress while needing little compute. The cost model must name the constraining resource.

Network cost follows boundaries

Bytes moving within a host, across racks, across zones, across regions, and to the public internet may have different cost and latency. Draw byte flow: client upload, replication, consumer reads, CDN fill, cross-region copy, and download. A one-kilobyte event written once, replicated twice across zones, read by five consumer groups, and archived to another region can move many kilobytes.

Example: 250 GB/day analytics ingress, two additional broker replicas, three full-stream consumers in other zones, and one archive copy can create roughly 250 × (2 + 3 + 1) = 1.5 TB/day of additional boundary transfer, depending on placement. Co-locating consumers helps cost and latency but must preserve fault isolation.

CDN economics

If an app serves 10 PB/month of media and the CDN byte hit ratio is 95%, origin egress is 500 TB/month; at 99%, it is 100 TB. The four-point improvement cuts origin by 5×. Request hit ratio may differ: many small hits and a few large misses can produce high request hits but poor byte hits.

Immutable versioned URLs and long TTLs improve cacheability. Personalized or permissioned content may require signed URLs or edge authorization. A CDN is not just cost optimization; it moves latency and capacity near users and absorbs hot-object traffic.

Replication versus erasure coding

Three copies cost 3× raw bytes and make small reads/writes and repair straightforward. A 10+4 erasure code costs 1.4× and tolerates four fragment losses, but encoding, reconstruction, small updates, and repair network are more complex. Many systems replicate fresh hot data, then erasure-code cold immutable data. Estimate transition rate and temporary overlap.

Caching has a break-even point

A cache entry is worthwhile when avoided origin work exceeds cache memory, fill, invalidation, and operational cost. If a 2 KB object is read once, caching wastes memory. If read one million times, it is obvious. Popularity is usually skewed, so size the hot set rather than the full dataset and let eviction discover the boundary.

Negative caching can protect origin from repeated missing-key or invalid-id requests, but use short TTLs so newly created objects appear. Stampede control prevents many misses from duplicating fill work.

Denormalization buys reads with write/storage amplification

Copying author name into feed items saves profile lookups but makes rename propagation necessary. Materialized views make reads fast at the cost of update work and temporary inconsistency. Estimate both sides: if a profile is read ten billion times and renamed once, duplication may be excellent; if inventory price changes every second across a million cached product views, invalidation may dominate.

Managed service versus self-operated cluster

Unit infrastructure price is not total cost. Include on-call labor, upgrades, backups, security patching, capacity planning, incident risk, and opportunity cost. A managed database can be more expensive per node yet cheaper for a small team. Conversely, enormous stable workloads may justify specialized operation. In an interview, discuss operational complexity without inventing salary figures.

Multi-region choices

Active-active lowers user latency and can improve regional availability, but duplicates warm capacity, complicates writes, and creates cross-region transfer. Active-passive may be cheaper but requires tested promotion and enough standby capacity. A cold backup region has long RTO. Match topology to SLO, not prestige.

If three active regions each run at 40% and can absorb one-region loss, combined provisioned capacity is 2.5× normal work. If they run at 70%, regional loss overloads survivors. Redundancy cost is the price of the stated failure objective.

Cost per product action

Aggregate infrastructure bills are hard to reason about. Attribute units: cost per million redirects, per thousand feed loads, per gigabyte stored/month, per active socket-hour, per route, or per completed trip. Include shared services proportionally. When cost/action rises, decompose into request amplification, byte size, cache misses, model compute, and retry rate.

Worked comparative example

A redirect service receives 100,000 QPS and each miss costs one database read. Raising cache hit rate from 95% to 99% removes 4,000 reads/s. Suppose a database node safely serves 2,000 reads/s; that saves roughly two nodes plus replicas. Achieving it requires 200 GB additional cache. Whether it pays depends on relative node and memory cost, but the break-even variables are explicit.

Now imagine redirects are 800 bytes at the edge: 80 MB/s. Caching destination records does not reduce response egress. A CDN/edge worker could. The optimization target must match the resource dominating cost.

Uncertainty and sensitivity

Use low/base/high scenarios. If DAU is 50–100M, peak factor 5–10×, and payload 0.5–1 KB, throughput range spans 4×. Ask which variable changes architecture. If all cases fit one shard, do not over-design. If high case crosses a single-key or memory boundary, propose an incremental path and metric.

sensitivity of output to input ≈ percentage change in output ÷ percentage change in input
prioritize measuring inputs that are uncertain, sensitive, and architecture-changing

Saturation signals

For every resource track utilization, queueing, and rejection: CPU plus run queue and throttling; memory plus working-set misses, eviction, and OOM; disk capacity plus IOPS latency and compaction; network bandwidth plus packet loss/retransmit; thread/connection pools plus wait time; quotas plus denied requests. Utilization alone can lie—50% CPU with one single-threaded hot partition may already be saturated.

Reading metric combinations

  • Latency rises, CPU flat, concurrency rises: likely downstream or lock/I/O wait. Inspect queue wait and dependency spans.
  • Origin QPS rises, total QPS flat: cache hit ratio fell, keys churned, or a new version caused cold fill.
  • Queue depth flat, oldest age rises: event rate may have fallen while poison/hot partitions remain stuck; depth alone masked impact.
  • Disk grows, logical data flat: compaction/reclaim lag, tombstones, orphan blocks, snapshots, or index duplication.
  • Errors rise only at p99 payload size: request size or fan-out, not aggregate rate, is the likely driver.
  • Retries rise, successes flat: the same logical work costs more and may be causing feedback overload.
  • Global health green, one region poor: weighted averages hide a smaller population; alert per region and minimum volume.
  • Availability green, fallback high: transport works but product quality is degraded; spend error budget deliberately.

Metric design rules

Use counters for totals and derive rates; gauges for current state; histograms for distributions. Keep label cardinality bounded. Record stable identifiers in traces/logs rather than metric labels. Prefer event time for freshness and processing time for operational latency; capture both. Define metric ownership and a response playbook so an alert leads to action.

Alert on user impact and imminent exhaustion, not every fluctuation. SLO burn alerts detect real reliability loss; saturation alerts warn before it. Dashboards are for exploration, alerts are for urgent action, and logs/traces explain individual cases. One telemetry type cannot replace all three.

Metric checklist: User outcome, rate, latency distribution, errors by cause, saturation, freshness/lag, correctness, recovery, top-key skew, retry amplification, cache status, and cost unit. Every important asynchronous path needs an age metric, not only queue depth.

  2. Behavior: core actions/user/day, sessions/day, objects/session, writes versus reads, fan-out, retention, average and p99 object size.
  3. Traffic: average logical operations/s, peak factor, peak logical operations/s, attempts after retries, hottest tenant/key/partition.
  4. Amplification: replicas, followers/recipients, candidate set, cache miss fraction, index updates, consumer groups, retries, background derivations.
  5. Bytes: ingress and egress bytes/s, logical bytes/day, retention bytes, physical multipliers, memory working set, repair/replay bytes.
  6. Promises: latency percentile, availability, durability/ack boundary, consistency invariant, freshness, RPO/RTO, overload behavior.
  7. Capacity: measured safe capacity/unit, target utilization, node count by CPU/storage/memory/network, N+1 failure reserve.
  8. Validation: most sensitive assumption, production metric, benchmark needed, pathological test, and incremental growth path.

Say units aloud: “fifty thousand requests per second times twenty items per request equals one million item hydrations per second.” Dimensional narration catches mistakes and makes reasoning easy to follow.

Drill 1 — push notification service

Prompt: Design a service that sends transactional and marketing push notifications to 200 million daily devices. Estimate peak send load, provider calls, queue storage, and overload priority.

Work it: Assume two transactional and one marketing notification/device/day: 600 million logical deliveries/day, about 6,900/s average. Marketing campaigns concentrate: use a 20× burst, roughly 138,000/s. Five percent of tokens are invalid or providers transiently fail; with 1.1 attempts/delivery, provider offered load is 152,000 calls/s. At 500 bytes/envelope, queue ingress is 76 MB/s during burst.

If the provider outage lasts thirty minutes at 138k logical/s, backlog is 248 million notifications, 124 GB raw. Recovery in one hour while current traffic continues needs extra 69k/s capacity; total consumer ability should exceed 207k/s. Marketing messages have expiry and may be dropped when stale; password-reset and security alerts get separate priority and reserved capacity. Partitioning only by campaign can create one hot partition; include recipient hash while preserving per-user order where needed.

Measure: accepted-to-provider and accepted-to-device latency, provider result codes, invalid-token rate, attempts/delivery, oldest queue age by priority, expiry drops, and campaign skew. The design lesson is that daily average is nearly irrelevant; campaign burst and provider outage recovery dominate.

Drill 2 — search autocomplete

Prompt: Suggest terms under 100 ms while users type. Estimate query rate, index size, cache behavior, and freshness.

Work it: Fifty million DAU perform ten searches/day, averaging six prefix keystrokes. That is three billion suggestion requests/day, 34,700/s average and perhaps 250,000/s peak. Client debounce at 100 ms and cancellation of superseded requests can cut traffic materially; measure instead of assuming. With 100 million indexed phrases averaging 30 bytes plus weights and trie/FST overhead, an optimized in-memory index might be several gigabytes to tens of gigabytes and can be replicated per serving cluster.

Cache full prefix plus locale, safe-search, and user cohort. Popular prefixes are extremely skewed, so edge/application caches offload most traffic. Personalization can merge a small user-history list with global candidates rather than creating a unique global-cache key per user. Rebuild a base index periodically and overlay trending deltas every minute. If trend updates fail, serve a slightly stale base rather than fail suggestions.

Budget: 20 ms network, 10 gateway, 25 prefix lookup, 20 personalization/merge, 10 serialization, 15 contingency. Track request cancellation, empty-result rate, cache hits, index version age, trend freshness, and click-through—not just latency. A fast but irrelevant suggestion system fails its product goal.

Drill 3 — flash-sale inventory

Prompt: Sell 10,000 limited items to millions of users without overselling. Estimate the hot-key problem and choose consistency.

Work it: Suppose five million purchase attempts arrive in two minutes: 41,700/s average during the event, perhaps 150,000/s in the first seconds. All contend on one SKU; ordinary hash sharding does not distribute it. Inventory is an invariant, so a strongly consistent reservation owner or partition must serialize decrements, but it need not run payment synchronously.

Create short reservation leases. Admission can use a fast queue or token allocation that releases at most the remaining inventory plus a small buffer. The owner conditionally decrements available count and records reservation id. Payment runs as a saga; expiry returns stock exactly once. If one owner safely commits 20k reservations/s, front-door traffic must be shed or queued; most of five million attempts cannot succeed anyway. A waiting room turns uncontrolled retries into bounded admission.

Metrics: attempts, admitted rate, reservation p99, oversell/undersell, expired reservations, payment completion, queue position age, retries/logical attempt, and bot/challenge results. Availability does not mean accepting all traffic; correctness and fair bounded rejection are the goal.

Drill 4 — webhook delivery

Prompt: Deliver customer webhooks reliably even when customer endpoints are slow or broken.

Work it: Ten million events/hour at peak is 2,780/s. Each event targets 1.4 subscriptions, so 3,900 logical deliveries/s. If 10% need two additional attempts, offered load is 4,680/s. Payload averages 4 KB: under 20 MB/s, so concurrency and hostile latency matter more than bandwidth.

Partition by destination or customer to preserve ordering where promised and apply per-destination concurrency limits. One endpoint taking 30 seconds should not occupy the global worker pool. Use exponential backoff with jitter, signed payloads, stable event/delivery ids, and an attempt log. Suppose 5% of endpoints are down for an hour: 195 deliveries/s × 3,600 ≈ 702,000 delayed items. Retain events for a product-defined window and offer replay. Move exhausted attempts to a visible failure state, not a forgotten queue.

Metrics: delivery success by attempt, endpoint latency, oldest pending age, attempts/delivery, per-tenant backlog, signature errors, disabled endpoints, and customer-visible time to delivery. “Exactly once webhook” is unrealistic across external HTTP; promise at-least-once with deduplication identifiers.

Drill 5 — top-100 leaderboard

Prompt: Maintain global and regional game leaderboards with 500,000 score updates/s and ten million reads/s.

Work it: Reads are 20× writes and the returned set is tiny. A sorted set can maintain rank, but one global mutable index is a hot key. If scores are monotonic best scores, shard players by id, maintain a local top-K per shard, and merge shard top-Ks into a global materialized top 100. For 100 shards and K=100, the merge examines only 10,000 candidates.

Update each shard at 5,000/s average. Global aggregator need not process every noncompetitive score: shards publish when their top-K changes, greatly reducing work. Cache the global top 100 at edges for seconds; at ten million read QPS, even 99.9% hits leave 10,000 origin QPS. For “rank around me,” maintain approximate quantile/rank structures or query the owning ordered index; it is a different access pattern.

Correctness: scores need anti-cheat validation and idempotent event ids. Decide whether a few seconds of ranking lag is acceptable. Track freshness, shard skew, top-K change rate, duplicate updates, cache hit ratio, rank error, and rejected suspicious scores.

Drill 6 — video upload and transcoding

Prompt: Accept user videos, transcode several renditions, and publish only when required outputs are ready.

Work it: One million uploads/day averaging 500 MB means 500 TB/day or 5.8 GB/s average direct to object storage; peak may be 5×. API servers issue multipart upload URLs and manage metadata, not byte proxying. Each upload creates perhaps six renditions totaling 1.5× source bytes plus thumbnails. Daily derived output is 750 TB before replication/coding.

Compute is measured in video-minutes. If average video is five minutes, five million source minutes/day. Suppose total rendition work is 8× real time on one CPU core: 40 million core-minutes/day, 27,800 cores continuously busy. Specialized hardware changes the benchmark. If the product promises publish within fifteen minutes, autoscaling must handle peak arrival and backlog; Little’s Law gives work in progress.

Use a durable job DAG with idempotent stages, leases, retry limits, and a final conditional publish when required renditions exist. Optional high-resolution output may lag. Track upload completion, queue age, transcode real-time factor, failure by codec, cost/video-minute, orphan objects, publish latency, and playback start/error by rendition.

Drill 7 — API analytics counters

Prompt: Show per-customer request counts by minute, endpoint, and status for one million events/s.

Work it: Writing every event to one counter row causes contention. Stream events through partitions keyed by tenant plus bucket, aggregate locally for one-second windows, and emit partials. If 10,000 workers each combine 100 events into one update, downstream write rate falls from one million/s toward 10,000/s, depending on key distribution.

Cardinality matters: 100,000 tenants × 500 endpoints × 20 statuses × 1,440 minute buckets/day could imply 1.44 trillion theoretical cells, but only observed combinations should exist. Retain fine-grained minutes seven days, hourly aggregates a year, and approximate sketches for unique users or high-cardinality dimensions. Late events update still-open windows or adjustment records.

Storage: raw 200-byte events are 200 MB/s, 17.3 TB/day; seven raw days with replication are enormous. If replay is needed, compress/tier. Aggregated rows are far smaller. Track event lag, aggregation reduction ratio, active-key cardinality, late-event fraction, estimate error for sketches, and query scan bytes.

Drill 8 — authentication sessions

Prompt: Support 100 million active sessions, quick validation, logout/revocation, and regional outages.

Work it: Stateless signed access tokens make validation local but revocation delayed until expiry. Opaque sessions require a lookup but revoke immediately. A hybrid uses fifteen-minute signed access tokens and longer refresh tokens stored/revocable server-side. If protected APIs run at 500,000 QPS, local signature verification avoids 500,000 session-store reads/s; refresh traffic is far lower.

At 100 million refresh sessions and 200 bytes/session before overhead, logical state is 20 GB; resident database/cache cost may be far larger. Replicate regionally with an ownership policy. Sensitive global logout can publish revocation version or maintain a deny set until access tokens expire. Clock skew affects expiry; allow a small bounded leeway and use trusted server time.

Failure: if the refresh store is unavailable, existing access tokens continue briefly while new refreshes fail safely. Protect login/refresh from abuse with exact-enough limits. Track validation failures, refresh success, revoked-token acceptance samples, clock-skew errors, key-rotation progress, active sessions, and suspicious reuse.

Drill 9 — IoT telemetry

Prompt: Ingest readings from 50 million devices, query recent history, and trigger alerts.

Work it: Devices report every minute: 833,000 readings/s. At 100 bytes/read, ingest is 83 MB/s and 7.2 TB/day raw. Thirty hot days is 216 TB logical before replication; a year is 2.6 PB. Partition by tenant/device and time bucket so writes distribute and retention deletes entire old partitions. Compress columnar history and tier older data.

Disconnected devices may reconnect with hours of buffered data. Mark event time separately from ingest time and cap per-device catch-up so storms do not delay current alerts. Alert evaluation should process fresh streams, keep small per-rule/window state, and deduplicate alert notifications. A global “device id” partition can hot-spot a tenant with millions of devices; isolate large tenants or hash within them.

Metrics: readings/s and bytes/s, event-time lag, late/out-of-order fraction, active devices versus expected, partition skew, compression ratio, alert evaluation delay, duplicate alerts, retention reclaim, and query scan bytes. “All data eventually arrived” is not enough if safety alerts were hours late.

Drill 10 — calendar free/busy

Prompt: Find common availability for up to 100 participants while calendars change concurrently.

Work it: The authoritative calendar stores events per user, often range-partitioned by user and time. A free/busy query fans out to participant shards, fetches busy intervals over the requested horizon, and intersects them. One request for 100 participants is 100 backend reads; at 5,000 front-door QPS, naïve fan-out reaches 500,000 reads/s and tail latency waits for stragglers.

Precompute compact free/busy bitmaps for common horizons and granularity, such as 5-minute slots for the next ninety days: 25,920 bits, only 3.2 KB/user before metadata. Updates modify affected slots; recurring events need expansion/versioning. Privacy responses reveal busy/free only. For large meetings, return partial/unknown or async results if a participant shard misses the deadline.

Creating the meeting needs conflict policy. Free/busy is advisory; an atomic event write per participant across organizations may be unavailable. Use organizer event plus invitations and attendee acceptance, or reserve within one organization transactionally. Track fan-out count, straggler rate, bitmap freshness, scheduling conflicts after suggestion, and privacy-policy denials.

Drill 11 — product search indexing

Prompt: Search 500 million products while price and inventory change frequently.

Work it: Product documents average 2 KB indexed: 1 TB logical before inverted index, stored fields, replicas, and merge slack; physical search clusters may need several times that. Search peak is 100,000 QPS. If one shard query costs 15 CPU-ms and each request fans to twenty shards, work is 30,000 CPU-seconds/s before caching—far too high. Partition or route so requests touch fewer shards, cache popular queries, and replicate for read throughput.

Catalog metadata can update through a change log. Inventory and price need fresher treatment than description: overlay a fast availability service or publish small partial updates rather than rebuild full documents. Search results are derived; the checkout service revalidates price and stock transactionally. This prevents a stale index from becoming the source of truth.

Metrics: query p99 by fan-out, shards/request, cache hits, zero-result and click-through rates, index freshness by field, rejected/stale documents, segment merge backlog, CPU-ms/query, checkout mismatch rate, and hot-query share.

Drill 12 — image thumbnail service

Prompt: Generate multiple thumbnail sizes for two billion source images and serve them globally.

Work it: Existing sources average 3 MB, six derivatives average 100 KB total, so derivative storage is 200 TB logical. New images arrive at 20 million/day: 231/s average, perhaps 2,000/s peak. If processing one image takes 500 CPU-ms, peak needs 1,000 busy cores; at 60% target, 1,667 cores, unless image accelerators improve the benchmark.

Generate common sizes asynchronously after upload and less common transforms on demand with single-flight. Content-address output by source hash, transform spec, and implementation version. Immutable CDN URLs allow long caching. A new algorithm version can trigger a catastrophic full rebuild; regenerate lazily or roll through a controlled queue with separate capacity.

If derivative requests peak at one million/s and average 20 KB, edge egress is 20 GB/s. At 99% byte hits, origin serves 200 MB/s. Track generation queue age, CPU-ms/image, failures by format, duplicate coalescing, CDN request/byte hits, origin fill, derivative storage by version, and stale-version share.

Drill 13 — audit log

Prompt: Store tamper-evident administrative events for seven years and support investigations.

Work it: Peak 100,000 events/s, 1 KB/event: 100 MB/s and 8.64 TB/day raw. Seven years is roughly 22 PB before compression/protection. At 5:1 compression and 1.5× erasure coding, about 6.6 PB, plus indexes. Keep recent weeks in searchable hot storage and older immutable partitions in object archive. Build sparse indexes/catalogs so investigations fetch narrow time/tenant ranges.

Append events with chained hashes or signed segment manifests, trusted timestamps, strict access control, and write-once retention where required. Replication alone does not prove an administrator did not rewrite history. Late arrival and clock skew need both event time and trusted ingest time. Deletion policy may conflict with retention; requirements must be legally clarified.

Metrics: accepted versus source-emitted counts, sequence gaps, ingest lag, signature verification, immutable-retention policy status, archive age, catalog freshness, restore/retrieval duration, and access audit. Test retrieval from the oldest tier, not only writes.

Drill 14 — collaborative whiteboard

Prompt: Support infinite-canvas drawing with 200 active participants and offline edits.

Work it: Strokes are larger and burstier than text. Suppose each active drawer generates twenty point updates/s at 30 bytes, but clients batch 20 points into one operation. With fifty simultaneous drawers, the server accepts 50 ops/s, each about 600 bytes. Broadcasting to 199 peers creates 9,950 deliveries/s and roughly 6 MB/s for one hot board. Cursor updates may exceed drawing traffic and should be sampled/coalesced.

Partition board content spatially into tiles/layers so clients subscribe to visible regions and snapshots do not grow without bound. Use a sequencer/OT or CRDT suited to object operations; raw pixel merge is poor. Persist append-only operations and compact into tile snapshots. Offline operations carry stable ids and causal/version context; deleted objects need tombstones until all relevant replicas advance.

Metrics: local echo and remote convergence, ops and deliveries per board, hottest-board sessions, snapshot/replay time, merge conflicts, tombstone volume, dropped cursor updates, and reconnect catch-up. The hot document—not total board count—drives real-time architecture.

Drill 15 — coupon redemption

Prompt: Enforce one use per customer and a global campaign cap across regions.

Work it: The invariant has two dimensions: unique customer-campaign use and remaining global inventory. A conditional unique key prevents repeat customer redemption. A single global counter is a WAN-latency and hot-key bottleneck. Allocate regional token leases from the global cap; each redemption atomically consumes a regional token and inserts the user key.

If campaign cap is one million and acceptable temporary overshoot is 1,000, lease size and concurrent allocators must keep worst-case duplicate/unreported allocation under 1,000. Regions request smaller leases near exhaustion. If a region fails, unused leased tokens are stranded until expiry/reconciliation, causing undersell; letting tokens be reissued too soon risks oversell. Choose explicitly.

At 200,000 attempts/s with only 5,000 successful redemptions/s, reject invalid/expired/exhausted cases cheaply and rate-limit abuse before the transaction store. Track attempts, unique successes, duplicates, lease utilization, stranded tokens, overshoot/undersell, conditional conflicts, latency, and reconciliation difference.

A ten-minute speaking script

Minute 0–1: restate scope and ask about population, core action, geography, retention, and strongest correctness promise. Minute 1–3: estimate average/peak QPS, bytes, fan-out, concurrency, and hot-key case. Minute 3–5: trace one request and identify the synchronous durability boundary versus asynchronous work. Minute 5–7: choose storage, partition key, replication, caching, and queues with explicit reasons. Minute 7–9: break it with retry, dependency failure, zone loss, skew, backlog, and cold cache. Minute 9–10: name SLOs, metrics, sensitive assumptions, and growth path.

If interrupted, welcome the new constraint and update the calculation. System design is collaborative reasoning, not a memorized speech. Preserve the chain: “If strong global ordering is now required, the single sequencer becomes the ceiling; at the estimated hot-key rate it will not fit, so we must either narrow the ordering key or accept a more expensive partitioned merge.”

Mistake clinic: repair the reasoning

  • “There are 100 million users, so 100 million QPS.” Users are a population; QPS is a rate. Multiply active users by actions/user/day and divide by seconds/day, then apply a peak model.
  • “We need 10 TB, so two 8 TB nodes are enough.” Apply replicas/coding, indexes, compaction and fullness reserve. Then check throughput and failure capacity; storage is only one constraint.
  • “Redis does 100k QPS.” For what command, value size, pipeline, persistence, network, CPU, and p99? Use it as a placeholder and demand a representative benchmark.
  • “Kafka gives exactly once.” State the boundary. Broker transactions can deduplicate and atomically move offsets/output; an external email or payment still needs its own idempotency contract.
  • “Three replicas means no data loss.” Replicas can share failure domains and replicate deletes or corruption. Define acknowledgement, placement, backup, checksum detection, and tested restore.
  • “The cache hit rate is 99%, so origin is safe.” At huge traffic one percent may still be large, and cold start is 100% misses. Compute origin QPS, byte hits, and refill rate.
  • “We can add shards for the celebrity.” Hash sharding distributes keys, not one key. Split or replicate the celebrity’s workload, change fan-out timing, or isolate it.
  • “The average latency is 20 ms.” Averages hide tail and workload mix. Report percentiles by operation, region, payload, and hit/miss, with an end-to-end measurement boundary.
  • “The queue has only one million events.” Without event rate and age, count is ambiguous. Report bytes, oldest-event age, partition skew, consumer throughput, and catch-up time.
  • “Retries improve reliability.” Only for transient failures with idempotency and spare capacity. Bound attempts, back off with jitter, enforce a retry budget, and avoid retries at many layers.
  • “Eventual consistency is fine.” For which invariant and staleness window? Name what can lag, conflict resolution, read-your-writes needs, repair source, and partition behavior.
  • “We use multi-region for availability.” Show traffic evacuation capacity, data quorum during region loss, RPO/RTO, fencing, DNS/routing convergence, and tested failover.
  • “Autoscaling handles peaks.” Compare peak rise time to metrics, decision, provisioning, startup, connection, and cache-warm time. Maintain reserve for demand faster than the loop.
  • “The write is done when the API returns 200.” Define what is durable at that exact moment: local memory, disk, quorum, outbox, or final external side effect. User expectations follow the acknowledgement.
  • “We will monitor CPU and errors.” Add the user SLI, saturation and queueing, correctness, freshness, top-key skew, retries, recovery progress, and cost per product action.
  • “A 50% buffer should be enough.” Name what it covers: zone loss, skew, burst, growth until next expansion, compaction, repair, and safe deployment. Reserve follows failure model.
  • “Deletes free storage immediately.” In logs/LSMs, tombstones and expired segments persist until reclaim. Estimate compaction and legal deletion across caches, indexes, backups, and analytics.
  • “We need strong consistency everywhere.” Identify the invariant and keep its coordination boundary small. Derived views can often lag and be rebuilt, improving latency and availability.
  • “We need no downtime.” Translate to an SLO, error budget, excluded/valid events, degraded success, RPO/RTO, and cost. Infinite reliability is neither testable nor free.
  • “These estimates prove the exact fleet size.” They identify order of magnitude and bottleneck. Final capacity comes from load tests with real payloads, skew, failure, and latency goals.

Capstone — size a photo-sharing home feed from a blank page

Step 1: state the product contract. Users upload photos with captions, follow accounts, and open a reverse-chronological home feed. Photos should be durable after upload completes; feed metadata should load under 300 ms p99 in-region; an ordinary new post should appear for 99% of eligible active followers within five seconds. We exclude comments, stories, video, recommendations, and editing. The feed can be a few seconds stale, but privacy changes must be enforced immediately on read.

Step 2: invent behavior transparently. Assume 50 million DAU. Each user opens six feed sessions/day and requests two pages/session. Five percent upload two photos/day. Average source photo is 4 MB. Average author has 400 followers, but 0.1% of authors have more than 500,000 and will use pull-on-read. A page returns twenty items with 30 KB thumbnails. Use an 8× read peak and 10× upload peak until product telemetry replaces them.

Step 3: derive front-door traffic. Feed pages/day are 50M × 6 × 2 = 600M, about 6,940/s average and 55,500/s peak. Uploads/day are 50M × 0.05 × 2 = 5M, about 58/s average and 580/s peak. The read/write QPS ratio is almost 100:1, but upload bytes are much larger than feed metadata.

Step 4: expose byte traffic. Peak source upload ingress is 580 × 4 MB = 2.32 GB/s. Clients should upload directly to object storage with multipart, checksums, and pre-signed authorization; API servers should not proxy these bytes. If thumbnails total 120 KB/photo across sizes, derived storage grows 600 GB/day. Current source growth is 20 TB/day before compression or coding.

Each feed page references 600 KB of thumbnails. Peak edge delivery is 55,500 × 600 KB ≈ 33.3 GB/s. At 98% CDN byte hits, origin serves about 666 MB/s. A one-point hit drop to 97% raises origin to 1 GB/s. Track byte hit ratio and cold fills after a new derivative version.

Step 5: derive fan-out. Ordinary uploads peak at roughly 580/s. If the pushed subset averages 400 eligible followers, fan-out is 232,000 timeline inserts/s. A timeline entry with post id, author id, timestamp, and version may be 40 bytes logical, only 9.3 MB/s, but per-operation overhead and replication matter. Queue the work; upload success waits for photo metadata, object references, and an outbox event—not every follower insertion.

Keep 1,000 timeline ids for 50 million daily users: 50 billion entries. At 24 resident bytes/entry after a compact representation, that is 1.2 TB and 2.4 TB with one replica. If actual object overhead is 60 bytes, the same design becomes 6 TB replicated. Benchmark representation before committing to cost.

Step 6: isolate celebrities. Pushing one post to ten million followers creates ten million writes and long freshness lag. For a celebrity, store the post once in the author stream. At read time, merge the user’s pushed timeline with recent posts from followed pull-on-read authors. The threshold compares inactive-follower push waste against active-reader merge cost. Cache celebrity heads and bound sources/candidates per read.

Step 7: size metadata reads. At 55,500 page requests/s and twenty results, naïve hydration is 1.11 million item fetches/s plus author/privacy data. Batch multi-get by storage shard, cache hot public post metadata, and embed immutable small fields in timeline entries where update cost is acceptable. Privacy is checked against current relationship or an efficiently versioned authorization state; never rely solely on stale fan-out copies for access control.

Step 8: choose stores by access pattern. Store immutable photo bytes and derivatives in blob storage/CDN. Store photo metadata and ownership in a replicated key-value or relational store keyed by photo id. Store follow graph adjacency lists partitioned by user id. Store ordinary timeline id lists in a sharded, log-backed cache/service. Use an append-only event stream for fan-out, thumbnail jobs, moderation, and analytics, with idempotent consumers. Keep authoritative upload state plus outbox atomic.

Step 9: allocate latency. For 300 ms p99: gateway/auth 20 ms; timeline ids 40; parallel post/author/privacy hydration 80; lightweight ranking/filtering 50; response assembly 20; network 40; contingency 50. Media loads separately from CDN and should not block initial feed metadata. Timeouts use the remaining deadline; if optional author enrichment fails, return a simpler card rather than fail the page.

Step 10: break it. A viral post stresses CDN and one metadata key; use edge caching and request coalescing. A fan-out backlog violates freshness; autoscale workers, prioritize recent active followers, and pull missing author posts as read-time repair. A cold timeline cache should rebuild from durable event/post sources without sending every user to origin simultaneously. A zone loss requires enough surviving feed and metadata capacity; thumbnail processing can lag while uploads remain durable.

Step 11: define correctness and retry behavior. Upload session id makes multipart completion idempotent. A photo version becomes visible once all required blocks and metadata commit. Fan-out keys by follower plus post id, so replay does not duplicate. Delete/privacy events take priority and reads enforce current authorization. Object deletion follows a lifecycle after references and retention requirements are cleared.

Step 12: close with metrics. User SLIs: feed p99, nonempty/fallback rate, post-to-feed freshness, image load success, upload completion, and privacy violations. Cause metrics: page QPS, candidate/hydration amplification, cache request and byte hits, CDN origin bandwidth, fan-out oldest age, worker throughput, celebrity merges/read, hottest post share, upload bytes, thumbnail queue age, retries/logical operation, and storage growth. Capacity signals: CPU, connection pools, disk fullness, compaction, network, queue partitions, and N+1 headroom.

Step 13: identify sensitivity. Average follower count is misleading because distribution determines hybrid fan-out. Thumbnail bytes and CDN hit ratio dominate bandwidth. Resident bytes/timeline entry determine terabytes of memory. Peak factor affects stateless fleet but can be validated quickly. Those are the first measurements to request. If DAU doubles, the design scales horizontally; if one author reaches a billion followers, it remains a pull/edge hot-object problem rather than a reason to push a billion entries.

What the rubric looks for, in the interviewer’s words

  • Drives the conversation. You propose; they probe. Silence while you think is fine; silence while you wait for direction is not.
  • Chooses, then justifies. “It depends” is only acceptable if followed by “on X, and here I assume X, so Y.”
  • Knows the numbers. Latency of a disk seek, QPS of one server, bytes in a tweet — and uses them to decide, not to decorate.
  • Handles failure. Every component gets the question “and when this dies?” before they ask it.
  • Depth in one place. A shallow sweep of twelve boxes scores lower than eight boxes and one deep component.

Phrases that signal seniority, and the traps

Say

  • “The hot path is X; everything else can be asynchronous.”
  • “I’m choosing availability over consistency here because a stale feed is fine and a failed post is not.”
  • “This store is keyed by Y, so every query must include Y; the one that doesn’t gets its own table.”
  • “Reads are 100× writes, so I move the work to write time — except for the celebrity case.”
  • “When this component dies, clients see Z; recovery is W seconds because of V.”
  • “At 10× the first thing to break is the counter; I’d shard it.”
  • “I’ll make this idempotent so retries are safe.”

Avoid

  • Drawing twelve boxes before saying what the system is for.
  • “We’ll use Kafka” without saying what goes in it and who reads it.
  • “NoSQL for scale” — name the access pattern that rules out SQL.
  • A number without a derivation, or a derivation without a conclusion.
  • Designing for 10 billion users when they said 10 million.
  • Ignoring the hint: when the interviewer steers, that is the deep dive they want.
  • Finishing without naming a failure mode.
