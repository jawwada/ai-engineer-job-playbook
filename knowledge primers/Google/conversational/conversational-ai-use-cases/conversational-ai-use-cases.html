1 · The building blocks: what an agent is made of, and what the pieces are called in 2026

A Conversational Agents (Dialogflow CX) agent is a small object model: flows made of pages, pages made of a form and handlers, handlers that match intents or conditions and run fulfilment, fulfilment that speaks or calls a webhook, and, since 2024, playbooks that let a model run a stage of the conversation from instructions and tools. Everything an interviewer asks about — routing, state, identity, generative placement, cost — is a question about which object holds what. The inventory is the first artefact of a design review: if intents outnumber pages by three to one, the agent is modelling steps as intents; if a flow has forty pages, it is three flows; if the webhook has one tag, the back end is deciding the conversation.

From tasks to objects

  1. List the tasks the product owner wants done by conversation, with the parameters each needs, the validation rules, and the system that fulfils it. One row per task; this is the backlog and the test plan.
  2. Group tasks into flows by family (orders, account, support) and by the stage of a conversation (authenticate, then act). A flow that would exceed twenty pages is two flows.
  3. Draw the pages: one page per step that collects something or waits for something. Write the entry message, the form (required parameters, prompts, reprompts), and the exits (routes) before any training phrase exists.
  4. Write intents as goals (“dispute a charge”, “cancel my card”), with twenty to fifty phrases each from real transcripts; page-scope the ones that only make sense in one place (“yes”, “the second one”).
  5. Build the entities: custom with synonyms for the vocabulary, regex for codes and amounts, composites for “$40 on Tuesday”, session entities for the user’s own things (cards, charges, appointments).
  6. Define the webhook contract as an OpenAPI document: tags, parameters in, parameters and messages out, error shapes. Build the back end to it; build the flows against a mock.
  7. Add the generative objects last: one task playbook for the open questions with a data store, generative fallback where a no-match is usually a question, generators only where the text is free and the numbers are not (card 4).
  8. Record test cases from day one, one per arrow in the page map; pin versions into draft, test and prod; export to git on every change (card 6).

How the object model gets misused

  • Steps as intents. give_card_number, give_reason: the classifier is asked to recognise where the user is instead of what they want. Pages are steps; forms collect; intents are goals.
  • One flow for everything. Sixty pages, routes that cross the whole agent, nobody can test a change. Flows by task family; END_FLOW to return.
  • Global session state. Every parameter kept forever, a flow reads a value another flow left behind. Clear parameters on entry to a task; pass what a flow needs explicitly; treat flows as black boxes (the Agent Studio guidance says the same).
  • Private data in the definition. Customers’ card names or merchants as static entity values, in git. Session entities, written per session by the API and gone with it.
  • A webhook with one tag. handle, with the back end inspecting the page to decide what to do: the conversation policy has moved out of the console. One tag per action.
  • Versions by hand. The prod environment pointing at draft. Versions per flow, pinned in environments, promoted by test results.
  • The old names. “Dialogflow ES contexts”, “the Dialogflow CX console”, a suite name from 2024. Flows and playbooks in Conversational Agents; CX Agent Studio as the successor; Gemini Enterprise for CX as the suite.
  • Agent Studio treated as Dialogflow with a new skin. Its agents are ADK agents: a steering model with tools and handoff rules, where flow-based agents are the deterministic parts. The mapping is real but not one-to-one (card 2).

def detect(session_id: str, text: str, id_token: str, params: dict | None = None):
    payload = struct_pb2.Struct(); payload.update({"id_token": id_token, "channel": "app"})
    qp = cx.QueryParameters(payload=payload, time_zone="America/New_York")

Saying it

Thirty secondsA Dialogflow CX agent is flows made of pages. A page has an entry fulfilment, a form that collects parameters, and routes and event handlers that decide where to go next. Intents and entities are the understanding; fulfilment speaks or calls a webhook by tag; playbooks and data stores are the generative half, where a model runs one stage from instructions and tools. The session is the only state. In 2026 the console calls this Conversational Agents, CX Agent Studio is the ADK-based successor that wraps those flows as deterministic sub-agents under a steering model, and Gemini Enterprise for Customer Experience is the suite around both.
Two minutesStart from the session: an id, a bag of parameters, the current flow and page, and a stack of flows that were called and will return. Everything else is the structure that moves the session along. Flows group a task family or a conversation stage; each has a start page and flow-level handlers. Pages are steps: an entry fulfilment that speaks or calls the webhook, a form whose required parameters are prompted one by one with reprompt handlers for no-match and no-input, and routes and event handlers with a fulfilment and a transition target. Intents are what the user wants, trained on phrases with annotated parameters, and they are consumed by the first matching route; entities type the parameters, from system entities through custom synonyms and regex to session entities the API writes per session so that the user’s own cards and charges never enter the agent definition. Fulfilment is the only place the agent acts: messages, parameter presets, a webhook call selected by a tag, with the webhook returning parameters and messages so the flow keeps the policy. Playbooks are the generative objects: a goal, instructions, examples and tools, with routine playbooks for stages and task playbooks that take inputs and return outputs; data stores are tools over documents. Environments pin one version of each flow and playbook, and the export is a folder of JSON you keep in git. The names matter in the room: Conversational Agents is the product with flows and playbooks; CX Agent Studio, GA since February 2026 and built on the Agent Development Kit, is the successor where the outer agent is a model with tools and handoff rules and the deterministic parts are flow-based agents it hands to; Gemini Enterprise for Customer Experience is the suite that also carries Agent Assist, Insights and the Food Ordering agent.

Likely questions

  • What is the difference between a flow and a page? A flow is a task family with its own start page and handlers, called and returned from through a stack; a page is one step inside it, with a form and its exits.
  • Why not one intent per step? Intents are classified from the utterance alone; a step is known from the session. Pages hold the step; intents hold the goal; page-scoped routes keep “yes” from meaning yes everywhere.
  • Where does state live? Only in the session: parameters, current page, the flow stack; thirty minutes after the last request it is gone. Anything longer-lived is in the back end behind the webhook.
  • How does this map to CX Agent Studio? Flows become flow-based agents called by a steering model; intents become the model’s routing; webhooks become tools (OpenAPI, MCP, code); session parameters become variables; routes become handoff rules. Same discipline, different outer manager.
  • What do you version? Each flow and playbook has versions pinned into environments; the whole agent exports to git; the webhook URL and the test suite are per environment.

2 · The dialogue manager: what happens on one turn, and whether the playbook is it

In the classic split of a conversational system into understanding, dialogue management and generation, the dialogue manager is the part that owns the state and decides the next action. Conversational Agents has two of them. In a flow, it is a deterministic state machine: it loads the session, takes the understanding result or an event, evaluates handlers in a fixed order, runs fulfilment, applies the transition and drives the form-filling loop. In a playbook, it is the model acting as a policy under the goal, instructions and examples: each turn it decides whether to reply, call a tool, hand to another playbook or flow, or finish. The playbook is a dialogue manager, but a delegated one; which of the two is outermost decides what you can read, test, bill and defend.

one turn (playbook)
prompt = system + tools + goal + instructions + examples + conversation → the model picks one step (reply, tool, transition, finish) → repeat until it replies
nesting
in CX the flow is outermost and routes into a playbook that returns; in CX Agent Studio the steering model is outermost and flows are black boxes it hands to
the rule
structure for anything that must be read by an auditor or asserted by a test; a model for anything open-ended; never let the delegated manager hold the money

So, is the playbook the dialogue manager?

Yes, within its scope: once a route hands the session to a playbook, the model decides every next action from the instructions and the tools until it returns or transitions, and nothing in the flow engine is consulted in between. No, for the conversation as a whole, when the flow is outermost: the flow engine decided when to enter the playbook, holds the session the playbook reads, and takes control back when a task playbook returns its outputs or a routine playbook transitions or ends. In CX Agent Studio the roles invert: the outermost manager is a steering agent (a model with handoff rules), and an imported flow runs as an encapsulated black box until END_SESSION hands control back. The design question is therefore not “which one is the dialogue manager” but “which one is outermost for this conversation, and what does the inner one hold”. The five designs on this page keep the flow outermost in CX and give the playbook the open questions and read-only tools; in Agent Studio they would make the steering agent outermost and keep the money and the gate inside flow-based agents.

Designing the handlers

  1. Flow-level defaults first. sys.no-match-default and sys.no-input-default with limits and a hand-off; agent.human and help.* as flow-level intent routes so they work on every page; webhook.error with an honest message.
  2. One page per step, exits explicit. Every page lists its intent routes (what the user may want here), its FINAL condition route, and its event handlers; a page with no exit for “no” or “stop” is a dead end.
  3. Scope deliberately. Page-scope the intents that are ambiguous elsewhere (confirm.yes); keep goal intents at flow level; remember that condition-only flow routes fire only on the start page.
  4. Parameters: set early, clear explicitly. Preset identity and context parameters on the first page; clear task parameters on a task’s entry; never let one flow depend on what another left behind.
  5. Decide the nesting. Flow outermost in CX; task playbooks for questions that return an answer; a routine playbook only for a stage that is open end to end; in Agent Studio, the steering agent outermost with flow-based agents for data collection, validation and authentication.
  6. Give the playbook structure where it matters. Instructions as numbered steps naming the tools, four to ten examples including the refusals, input and output parameters declared, a pinned GA model, banned phrases.
  7. Test the order. A test case per arrow: the expected current page, matched intent, parameters and text after each turn; a test that the same-turn traversal lands where the design says.
  8. Budget the turn. Webhook timeout at half the channel’s window (the default is 5 s with one retry); long work asynchronous; a playbook turn costs a model call per step, so cap the steps.

How dialogue management goes wrong

  • Expecting flow-level condition routes to fire off the start page. They are in scope only on the start page; put the condition on the page, or give the flow route an intent requirement.
  • Conditions that fire twice. A condition is not consumed; two condition routes both true, the first without a transition, both speak. Order them; give the first a transition or make them exclusive.
  • A route without a transition that keeps the user on a page forever. It adds a message and evaluation continues; nothing moves. Every route that completes a step transitions.
  • Intent propagation surprises. A flow-level route on cancel transitions into a flow whose start page also routes on cancel; both fire. Know the exception; test it.
  • Deep stacks. Flows calling flows calling flows; beyond 25 the stack pops and END_FLOW lands somewhere else. Two levels, three at most.
  • The playbook decides about money. A tool that places or pays inside a playbook, so the read-back and the yes are model behaviour. Money is a page with a confirmation and a webhook; playbooks get read-only tools.
  • A routine playbook that never exits. No transition step, no end condition; the user is trapped in a chat. A task playbook with declared outputs, or an explicit ${FLOW: …} step.
  • Playbook-first by accident. A playbook calls a flow and the whole conversation is billed as playbook, and the SLA no longer covers it. Flow outermost in CX unless the stage is open end to end.
  • Agent Studio flows used as intent classifiers. The docs say to classify with the model and use flows for deterministic logic; a flow that only routes adds a hop for nothing.
  • Testing text instead of state. A test that asserts the sentence and not the current page passes when the policy is wrong. Assert the page, the intent and the parameters.

A twenty-line model of the evaluation order, and a playbook instruction that hands off

The first snippet is the mental model, written as code so it can be argued with: scope, three phases, consumption, a transition that stops evaluation, same-turn traversal. It is not the product.

# dm_model.py — the flow engine's turn, as the documented rules read (a model for reasoning and for unit-testing a design)
from dataclasses import dataclass, field

@dataclass
class Handler:
    kind: str                  # "intent" | "condition" | "event"
    key: str                   # intent name, condition expression, or event name
    level: str                 # "param" | "page" | "page_group" | "flow" | "flow_group"
    messages: list[str] = field(default_factory=list)
    webhook_tag: str | None = None
    target: str | None = None  # page, flow, playbook or symbolic target

ORDER = {"intent": ["page", "page_group", "flow", "flow_group"],
         "condition": ["page", "page_group", "flow", "flow_group"],      # flow levels only on the start page
         "event": ["param", "page", "flow"]}

def in_scope(h: Handler, on_start_page: bool, filling: str | None) -> bool:
    if h.level == "param": return filling is not None
    if h.level.startswith("flow") and not on_start_page: return h.kind == "intent"   # flow routes off the start page need an intent
    return True

def turn(session: dict, handlers: list[Handler], matched_intent: str | None, event: str | None, evaluate_condition) -> dict:
    queue: list[str] = []; intent_consumed = False; event_consumed = False
    for kind in ("intent", "condition", "event"):
        for level in ORDER[kind]:
            for h in (x for x in handlers if x.kind == kind and x.level == level):
                if not in_scope(h, session["on_start_page"], session.get("filling")): continue
                fires = ((kind == "intent" and not intent_consumed and h.key == matched_intent) or
                         (kind == "condition" and evaluate_condition(h.key, session)) or
                         (kind == "event" and not event_consumed and h.key == event))
                if not fires: continue
                if kind == "intent": intent_consumed = True
                if kind == "event": event_consumed = True
                queue += h.messages
                if h.webhook_tag: queue += call_webhook(h.webhook_tag, session)        # returns messages; writes session params
                if h.target:
                    session = transition(session, h.target)                          # push/pop the flow stack; symbolic targets
                    queue += entry_fulfilment(session)
                    return turn(session, page_condition_handlers(session), None, None, evaluate_condition) | {"messages": queue + ["…"]}
    return {"session": session, "messages": queue}                                    # no transition: stay; the form may prompt next

Saying it

Thirty secondsConversational Agents has two dialogue managers. In a flow it is a state machine: load the session, take the intent and entities or a form fill, evaluate handlers in a fixed order (intent routes, then condition routes, then event handlers, page level before flow level), run the fulfilment, apply the transition, and keep going through the new page’s entry and conditions in the same turn. In a playbook it is the model: the prompt is the goal, instructions, examples, tools and the conversation, and each step it decides to reply, call a tool, hand off or finish. The playbook is the dialogue manager inside its scope; the flow decides when it is entered and gets control back. I keep the flow outermost where a step must be read, tested or billed as deterministic.
Two minutesA turn begins with the session: the current flow and page, the parameters, and the stack of flows that were called. If the page is filling a form, the input is first tried as the parameter being prompted; otherwise, and in any case, the intent classifier and the entity extractors run. Then the handlers are evaluated in a documented order. First the intent routes, page level before page groups before flow level before flow groups, and an intent is consumed by the first route that matches; then condition-only routes, page level first and flow level only on the start page, where conditions are not consumed, so several can fire and a route without a transition just adds its messages; then event handlers, the parameter’s reprompt handlers before the page’s before the flow’s, for no-match, no-input, invalid parameter, webhook errors and custom events. The first handler with a transition target ends evaluation; the target is a page in the active flow, a flow’s start page, a playbook, or a symbolic target like END_FLOW, which pops the stack and resumes the calling page, or END_SESSION. Fulfilment is where the agent acts: messages, parameter presets and a webhook call selected by a tag, which returns parameters and messages so the policy stays in the flow. After a transition the new page’s entry fulfilment runs and its condition routes are evaluated again, all within the same turn, which is how an account gate takes three regulated decisions on one request and leaves three page names in the log. When a route hands the session to a playbook, the model becomes the manager for that scope: the prompt is assembled from the goal, numbered instructions that can name tools, flows and other playbooks, examples and the conversation; the model picks one step at a time, tool results are appended, and it stops when it replies; a task playbook then returns its declared outputs to the caller and a routine playbook transitions or returns to the last active flow. Two consequences decide the design. Billing follows the manager, so a flow turn that touches anything generative is a playbook turn and a playbook that calls a flow makes the whole conversation playbook-priced; and the SLA excludes playbooks. So the flow is outermost in CX, and the playbook gets the open questions and read-only tools. CX Agent Studio inverts the nesting: a steering agent is outermost and an imported flow runs as a black box until END_SESSION; there the regulated steps live inside the flow-based agents and the model does the routing.

Likely questions

  • Is the playbook the dialogue manager? Inside its scope, yes: the model decides every action from the instructions and tools. For the conversation, only if it is outermost; in CX I keep the flow outermost, so the playbook is a delegated manager that returns.
  • What happens on a no-match while filling a form? The parameter’s reprompt handler first (sys.no-match-1), then the page’s, then the flow’s; page-scoped intents still match, so “talk to a person” escapes the form.
  • How do you stop a playbook taking over? Make it a task playbook with declared outputs, give it read-only tools, name the exit in an instruction step, and never let it call a flow unless you intend the whole conversation to be playbook-priced.
  • How does control come back from a flow? END_FLOW pops the stack and resumes the calling page, whose remaining handlers are evaluated; the cancellation and failure variants raise events the caller can handle.
  • How does CX Agent Studio change this? The outermost manager is a model with tools and handoff rules; flows become flow-based agents called with explicit variable mappings and returning at END_SESSION; the docs want intent classification done by the model and flows kept for deterministic logic.

Building the webhook and the identity path

  1. Contract first. One OpenAPI document: tags, parameters in, parameters and messages out, error shapes, versions. The back end builds to it; the flows are built against a mock that returns the documented shapes.
  2. One handler per tag, named verb.noun. otp.send, otp.verify, charge.lookup, dispute.open; a tag does one thing and returns parameters the flow can route on.
  3. Authentication. Service-agent ID tokens verified for audience and principal; mTLS where the client requires it; one URL per environment; secrets only through Secret Manager references.
  4. Identity. The channel proves (JWT, step-up); the webhook verifies and exchanges for an opaque reference; parameters carry level and timestamp; every money or health action checks the level again inside the handler, not only in the flow.
  5. Validation both ways. Mark a just-collected parameter INVALID rather than inventing a transition; validate the whole form once on FINAL.
  6. Timeouts and async. Budget half the window; return a job id for anything slower; push an event or a message back into the session when the job finishes.
  7. Redaction and retention. Mark every sensitive parameter redact-in-log; Sensitive Data Protection templates on history; audio export with its own retention; the audit log in the back end, keyed by user and session.
  8. Test the contract. Contract tests on the webhook; CX test cases that assert parameters after each call; a chaos case for a timeout that must land on the error handler.

  • Access tokens or API keys in the export. A key in git. Service-agent ID tokens; Secret Manager references for headers.

  • The audit in the transcript. Compliance asks for the record and gets a chat log with redactions. The audit log is the back end’s, append-only, keyed by user and session.
  • A card number through the bot. “Please read me your card number.” Never: last four digits only; the PAN through DTMF masking at the telephony partner or the app’s tokenizer.
  • Identity checked only in the flow. A webhook that trusts auth_level without re-reading its own record. The handler checks the level and its age before acting.

Saying it

Thirty secondsFulfilment is where a flow acts, and the webhook is a contract: the tag selects the action, the session parameters are the inputs, and the response is messages and parameters, never a transition, so the policy stays in the flow. It is authenticated with the service agent’s ID token per environment and bounded by a five-second budget with one retry, so anything slower is a job with an event back. Identity rides the same path: the channel proves who the user is, the webhook verifies it and exchanges it for an opaque reference, and the flow routes on a level and a timestamp held in redacted parameters. A secret never becomes a parameter.
Two minutesEvery fulfilment that calls the webhook sends the tag, the session with its typed parameters, the page and the state of each form parameter, the matched intent with its confidence, the text and language, and the channel’s payload. The webhook answers with messages, parameters to set or clear, and optionally a form parameter marked invalid, which makes the flow reprompt. It can also name a target page, and the design rule is that it never does, because a conversation whose transitions are decided in code cannot be read in the console or asserted by a test. Authentication is the service agent’s ID token, verified for audience and principal, with mutual TLS where the client requires it and Secret Manager references for any header value; access tokens are discontinued and keys never enter the export. The budget is five seconds per attempt with one automatic retry, so the practical rule is half the channel’s window and asynchronous work for everything else: a job id now, a worker, and an event injected into the session when the job finishes. Identity has levels. Anonymous is a visitor, a car or an unknown caller; caller id is a hint, not proof. Known means the operator’s app signed the user in and sends a short-lived JWT in the payload, which the webhook verifies and exchanges for an opaque reference with a short life, writing the user id, the reference, the level and the eligibility flags as parameters marked redact-in-log. Strong means a step-up on a page: a one-time code sent and verified by the webhook, kept as a redacted form parameter and cleared immediately, or a passkey in the app reached by a deep link, after which the level carries a timestamp that expires. Every handler that moves money or touches a medication re-checks that level inside itself. Privacy is a set of controls you can name: redact-in-log on parameters and entity types, Sensitive Data Protection on the history, retention and audio export you own, regionalisation, customer-managed keys and VPC Service Controls; HIPAA, ISO, SOC and FedRAMP High cover the product including generative features, and PCI is not on the list, which is why a card number never enters the agent. In CX Agent Studio a token broker with OAuth 2.0 lets a tool act with the user’s own delegated token, which is the same principle one layer deeper.

Likely questions

  • How does the agent know who the user is? The channel proves it (a JWT from the app; a step-up on a page), the webhook verifies and exchanges it, and the flow routes on redacted parameters carrying a level and a timestamp.
  • Why can’t the webhook decide the next page? It can; it must not. The policy would leave the console and the tests. Return a parameter; a condition route decides.
  • What about a thirty-second job? Return a job id inside the timeout; finish in a worker; inject an event into the session with the result.
  • How do you handle card numbers? Never through the agent: last four digits only; the PAN through DTMF masking at the telephony partner or the app’s tokenizer; PCI is not in Dialogflow’s compliance list.
  • How is the webhook secured? Service-agent ID tokens verified for audience and principal, one URL per environment, mTLS where required, secrets by reference, a private endpoint through Service Directory where the client needs it.

4 · Playbooks and the generative features: what goes generative, what never does, and how each is kept honest

Conversational Agents has four generative objects. A playbook is a model running a stage of the conversation from a goal, numbered instructions, examples and tools; a data store is indexed documents the model can cite; a generator is a prompt that produces one response inside a fulfilment; generative fallback answers when no intent matches. Adding the generative features, last and deliberately

  1. Run the ladder on every step of the page map; write the placement next to each arrow. Money, records, identity and the regulated steps are pages before anything else exists.
  2. Documents before models. Collect the terms, FAQs, rules and menus the answers should come from; make the owner sign them; index them as a data store; decide the no-answer behaviour.
  3. One task playbook per family of open questions. A goal, five to eight numbered instructions including the refusals and the exit, four to ten examples, declared inputs and outputs, read-only tools scoped to the user.
  4. Generators only where the facts arrive as parameters. Tool output in, one parameter out, a numeric check before it is spoken; static text where the check fails.
  5. Generative fallback where the no-match is usually a question. Grounded, first miss only, banned phrases; never on a confirmation page.
  6. Pin and guard. A GA model pinned at agent level; banned phrases and safety settings; redaction still applies to what the model sees.
  7. Evaluate before and after. A refusal suite with a rubric and a judge, a numeric-fidelity script, injection cases hidden in documents and tool results, and the deterministic test cases that assert the flow still lands where it should; re-run on every prompt, document or model change.
  8. Measure in production. Playbook share of turns, fallback rate per page, answer citations, the weekly listen; the cost model of card 6.

How generative features go wrong

  • A money tool in a playbook. The model decides when the read-back happened. Money is a page; the playbook’s tools are read-only.
  • A routine playbook as the whole agent. Natural, fast to build, impossible to audit, and the SLA does not apply. Flows outermost; the playbook for the open stage.
  • Instructions as an essay. Three paragraphs the model paraphrases. Numbered steps, each one action, the refusals and the exit as steps.
  • No examples with refusals. The model learns the happy path only. Four to ten examples, a third of them refusals and hand-offs.
  • A generator fed the conversation. It repeats a number the user said wrongly, or invents one. Parameters and tool output only; the fidelity check.
  • Fallback everywhere. A confirmation page that answers a question instead of hearing “no”. Fallback where no-match means a question, never where it means a value.
  • Documents nobody owns. A data store of last year’s terms. An owner, a refresh cadence, citations in the log.
  • A preview model in production. Behaviour changes with the release notes. A pinned GA model; the suite re-run on change.
  • Injection through documents and tool results. A merchant name or a market’s rules text telling the model to ignore its instructions. Tool results rendered as data; injection cases in the suite; banned phrases.
  • Measuring the model and not the design. “The playbook answered well” while the flow never regained control. Test cases that assert the page after the playbook returns.

Likely questions

  • When is a playbook the right choice? When the input is open-ended and the output is information: questions over documents, explanations, the user’s own data read through scoped tools. Not when the step moves money, needs a record, has an SLA, or uses DTMF.

Building a voice agent

  1. Choose the channel: a partner telephony integration when a contact centre exists (queueing, agents, DTMF masking come with it); a custom audio channel when the device is yours.
  2. Pick the STT model per language and force it where the integration would choose otherwise; build the speech adaptation phrase sets from the entities and the alias lists; regenerate them with the data.
  3. Tune endpointing on recordings, not by feel: collect two hundred utterances per page type, sweep the sensitivity, measure cut-offs and dead air; set per page where answers are long.
  4. Write prompts for the ear: under twelve words, the question last, digits through SSML, a pause before a number, a holding sentence as a partial response where the webhook is slow.

  7. Log audio for the first month to a bucket you own; listen to twenty calls a week; fix the speech layer before touching the flows.

What goes wrong with voice

  • Chat prompts spoken aloud. Forty words, three questions, the user forgot the first. Twelve words, the question last.

Thirty secondsVoice wraps the same dialogue manager in a pipeline with a clock. Two minutesThree things change with voice. The first is the clock: a user hears silence after they stop speaking, and the budget that feels natural is under a second and a half to the first syllable. Endpointing takes most of it, which is why the sensitivity is tuned on two hundred recordings per page type rather than set once; then the final transcript, the intent and entities, the webhook, and synthesis to the first byte. Conversational Agents names the settings: end-of-speech sensitivity, timeout-based endpointing for all languages, smart endpointing for numbers in English, the no-speech timeout that fires no-input, barge-in at agent, flow or fulfilment level, partial responses that play a holding sentence while the webhook runs and can be cancelled by the final message, the speech model per language, speech adaptation from phrase sets, DTMF with finish digits and timeouts, and an audio export bucket. Audio is kept for the first month and twenty calls a week are listened to, because the errors are heard, not read.

Likely questions

  • How do you hit the latency budget? Endpointing tuned on recordings, a telephony model with adaptation, a webhook under 400 ms or a partial response over it, streaming synthesis with a short first sentence; measured per step.
  • Where is barge-in off? The read-back, disclosures, and any prompt whose whole content matters; on everywhere else, knowing that listening during playback is billed.
  • How do you take a card number by phone? Not through the agent: DTMF masking at the telephony partner or the app’s tokenizer; the agent sees the last four digits as a redacted parameter.
  • Phone gateway, partner or custom? Gateway for pilots; a partner when a contact centre exists; custom audio when the device is yours and the adapter must own the speech policies.
  • What does a call cost? About twenty cents of agent time for a four-minute call on flows, a bit more with a playbook stage, plus the partner’s minutes; prompts and barge-in decide the seconds.

-- completion, containment, fallback and p50 duration per flow, last 7 days (illustrative columns of the interaction export)
WITH s AS (
  SELECT session_id, ANY_VALUE(entry_flow) AS flow,
         MAX(IF(page_name IN ('Done', 'Result', 'Booked', 'Dispute opened', 'Rebooked'), 1, 0)) AS completed,
         MAX(IF(live_agent_handoff, 1, 0)) AS handed_off,
         COUNTIF(match_type = 'NO_MATCH') / COUNT(*) AS no_match_rate,
         TIMESTAMP_DIFF(MAX(request_time), MIN(request_time), SECOND) AS duration_s,
         SUM(IF(billed_as = 'PLAYBOOK', 0.012, 0.007)) AS chat_cost
  FROM `bank-cx.dialogflow.interactions`
  WHERE request_time >= TIMESTAMP_SUB(CURRENT_TIMESTAMP(), INTERVAL 7 DAY) AND channel = 'chat'
  GROUP BY session_id)
SELECT flow, COUNT(*) AS sessions, ROUND(AVG(completed), 3) AS completion, ROUND(1 - AVG(handed_off), 3) AS containment,
       ROUND(AVG(no_match_rate), 3) AS fallback_rate, APPROX_QUANTILES(duration_s, 100)[OFFSET(50)] AS p50_s, ROUND(AVG(chat_cost), 4) AS cost_per_session
FROM s GROUP BY flow ORDER BY sessions DESC;

Running an agent in production

  1. Record the first test cases before the first release, one per arrow of the page map, with injected parameters standing in for the webhook; add a case for every bug after it.
  2. Wire CI: export on change, run the test suite by API against the test environment, run the generative checks and the audio replays, block promotion on failure, commit the export with the ticket.
  3. Pin versions into environments; promote by re-pinning; keep the previous versions one click away; one webhook URL per environment.
  4. Export conversations to BigQuery and build the four dashboards: completion and abandonment per flow and page, containment, fallback per page, latency per step and cost per conversation.
  5. Alert on webhook p95 and error rate, fallback spikes after a release, confidence drift, and cost per conversation drifting with the playbook share.
  6. Review weekly: the no-match utterances become training phrases or new intents; twenty calls are listened to; the playbook evaluation set grows from saved conversations; the refusal suite re-runs if a prompt changed.
  7. Model the cost with the formula on the Example tab before every design decision that moves turns into playbooks or lengthens prompts; check the price list, which changes.
  8. Keep an incident playbook: a wrong version (re-pin), a webhook outage (the error handler’s message, a status page), a model regression (pin the previous model, re-run the suite), a data store with stale documents (refresh, re-index).

# cost/model.py — the agent-fee model behind the chart; prices are the October 2026 list and are parameters, not constants
def agent_cost(conversations: int, *, chat_turns=0.0, voice_seconds=0.0, playbook_share=0.0,
               p_flow_req=0.007, p_pb_req=0.012, p_flow_sec=0.001, p_pb_sec=0.002) -> float:
    per_turn = (1 - playbook_share) * p_flow_req + playbook_share * p_pb_req
    per_sec = (1 - playbook_share) * p_flow_sec + playbook_share * p_pb_sec
    return conversations * (chat_turns * per_turn + voice_seconds * per_sec)

How it is built and reviewed

  1. Menu file first. Items, sizes, modifiers, combos, prices, aliases and upsell rules as versioned JSON; a resolver and a pricer with unit tests; a nightly job that regenerates entities and the speech-adaptation list from it.
  2. The channel adapter. Streaming STT and TTS, endpointing, barge-in policy, silence policy, the yes/no matcher, the thread id per car; test it with recorded audio before any understanding exists.
  3. Understanding. CX pages and intents with list parameters, or the Turn/Op schema and the small model; measure cart accuracy on a labelled set of fragments and corrections.
  4. Read-back, POS, crew. Idempotent submit; the hand-off with the partial order; a test that every spoken price equals the computed price.
  5. Pilot on one lane with a crew member listening; log everything; fix the speech layer first.
  6. Metrics. Order accuracy at the window (items, sizes, modifiers as made), seconds from arrival to confirmed order, intervention rate, upsell acceptance; a weekly listen to twenty recordings.
  7. The design review asks four questions. Can a two-item order with one modifier be placed in two turns? Does a mid-order “actually make that large” change the right line? Does the agent ever say a price not computed from the menu file? Is there a human within two misses?

What goes wrong in a drive-through

  • A price from the model. Fluent, wrong, and charged. Every number comes from the pricer over the menu file; a test asserts it.
  • Improvised offers. “Would you like our new shake?” when there is no shake. Upsell is a rule in the menu file, once, before the read-back.
  • Per-item modifiers in list parameters. “Two burgers, one without pickles” cannot be annotated as intents; apply modifiers only for single items in CX, or move understanding to the structured call.
  • Barge-in during the read-back. The customer talks over the total and nobody heard it. Barge-in off for that one prompt.
  • Endpointing by feel. 400 ms cuts people off mid-order; 1,500 ms feels broken. 700 ms, tested with recordings.
  • Silence treated as an error. “I didn't catch that” after a complete order. Silence after items means done.
  • Restart on ambiguity. “Let's start over” after two misses loses the customer. The crew gets the partial order.
  • No speech adaptation. “A one combo” becomes “a wine combo”. Boost the alias list from the menu file.
  • A large model in the loop. Three seconds of silence per turn. The small, fast model; the budget is 1.5 s.
  • No audio logged. A month of “the AI misheard” with nothing to listen to. Log transcripts with audio from day one.
  • Ordering as a playbook. A model turn per item, tool calls the model chooses, and offers it invents. Flows for the order; the one task playbook answers menu questions and returns.

def cart(req, params):
    cart = params.get("cart") or []
    intent = req["intentInfo"]["displayName"]
    p = {k: v["resolvedValue"] for k, v in (req["intentInfo"].get("parameters") or {}).items()}
    items = p.get("menu_item") or []
    if isinstance(items, str): items = [items]
    sizes = p.get("size") or []; mods = p.get("modifier") or []; qty = p.get("quantity") or []
    problems = []
    for i, name in enumerate(items):
        line = resolve(MENU, name, size=(sizes[i] if i < len(sizes) else None),
                       modifiers=mods if len(items) == 1 else [], quantity=int(qty[i]) if i < len(qty) else 1)
        if line is None: problems.append(name); continue
        if intent == "order.add": cart.append(line)
        elif intent == "order.remove": cart = [c for c in cart if c["id"] != line["id"]]
        elif intent == "order.modify": cart = [line if c["id"] == line["id"] else c for c in cart]
    if intent == "order.start_over": cart = []
    msgs = []
    if problems: msgs.append(say(f"I don't have {problems[0]}. Anything else?"))
    elif intent == "order.add": msgs.append(say(f"Got it, {speak_cart(cart[-len(items):])}. Anything else?"))
    upsell = next((u for u in MENU["upsell"] if not params.get("upsold") and u["matches"](cart)), None)
    out = {"cart": cart, "cart_spoken": speak_cart(cart), "total": price_cart(MENU, cart)}
    if upsell: msgs = [say(upsell["say"])]; out["upsold"] = True; out["pending_upsell"] = upsell["adds"]
    return response(msgs, params=out)

# drive_thru/graph.py — the LangGraph version: one structured call returns typed ops; code owns the cart
from typing import Annotated, Literal, TypedDict
from langchain.chat_models import init_chat_model
from langchain_core.messages import AIMessage, AnyMessage, SystemMessage
from langgraph.graph import END, START, StateGraph
from langgraph.graph.message import add_messages
from langgraph.types import Command, interrupt
from pydantic import BaseModel, Field

class Op(BaseModel):
    action: Literal["add", "remove", "set_size", "add_modifier", "remove_modifier", "set_quantity"]
    item: str = Field(description="menu item or combo as the customer said it")
    size: Literal["small", "medium", "large"] | None = None
    modifiers: list[str] = []
    quantity: int = Field(1, ge=1, le=20)
    target_index: int | None = Field(None, description="which existing line this changes, 0-based")

class Turn(BaseModel):
    ops: list[Op] = []
    done_ordering: bool = False
    start_over: bool = False
    wants_human: bool = False
    answered_upsell: Literal["yes", "no"] | None = None

class State(TypedDict, total=False):
    messages: Annotated[list[AnyMessage], add_messages]
    cart: list[dict]; upsold: bool; pending_upsell: dict | None; misses: int
    phase: Literal["ordering", "readback", "done"]

model = init_chat_model("gemini-2.5-flash-lite", temperature=0)      # small and fast: latency is the product

def understand(state: State) -> dict:
    t = model.with_structured_output(Turn).invoke([
        SystemMessage("You convert a drive-through customer's latest utterance into cart operations. "
                      f"Known items: {MENU_WORDS}. Current cart lines: {speak_cart(state.get('cart', []))}. "
                      "If they answer a yes/no offer, set answered_upsell. Do not invent items."),
        state["messages"][-1]])
    cart = [] if t.start_over else list(state.get("cart", []))
    unknown = []
    if t.answered_upsell == "yes" and state.get("pending_upsell"): cart.append(resolve(MENU, **state["pending_upsell"]))
    for op in t.ops:
        line = resolve(MENU, op.item, size=op.size, modifiers=op.modifiers, quantity=op.quantity)
        if line is None: unknown.append(op.item); continue
        if op.action == "add": cart.append(line)
        elif op.action == "remove": cart = [c for c in cart if c["id"] != line["id"]]
        elif op.target_index is not None and op.target_index < len(cart):
            cart[op.target_index] = {**cart[op.target_index], **{k: v for k, v in line.items() if k in ("size", "modifiers", "quantity")}}
    progress = bool(t.ops or t.done_ordering or t.start_over or t.answered_upsell)
    return {"cart": cart, "pending_upsell": None, "misses": 0 if progress else state.get("misses", 0) + 1,
            "phase": "readback" if t.done_ordering and cart else state.get("phase", "ordering"),
            "messages": [] if not unknown else [AIMessage(f"Sorry, I don't have {unknown[0]}.")], "wants_human": t.wants_human}

def route(state: State) -> Literal["human", "readback", "respond"]:
    if state.get("wants_human") or state.get("misses", 0) >= 2: return "human"
    return "readback" if state.get("phase") == "readback" else "respond"

def readback(state: State) -> Command[Literal["submit", "respond"]]:
    cart = state["cart"]
    ok = interrupt({"kind": "confirm", "text": f"So that's {speak_cart(cart)}, {price_cart(MENU, cart):.2f} total. Is that right?"})
    return Command(goto="submit") if ok else Command(goto="respond", update={"phase": "ordering", "messages": [AIMessage("What should I change?")]})

def submit(state: State, config) -> dict:
    order = submit_order(state["cart"], idempotency_key=config["configurable"]["thread_id"])
    return {"phase": "done", "messages": [AIMessage(f"{order.total:.2f} at the first window, please. Thank you!")]}

b = StateGraph(State)
for n, f in [("understand", understand), ("respond", respond), ("readback", readback), ("submit", submit), ("human", human)]: b.add_node(n, f)
b.add_edge(START, "understand")
b.add_conditional_edges("understand", route, {"human": "human", "readback": "readback", "respond": "respond"})
for n in ("respond", "submit", "human"): b.add_edge(n, END)
graph = b.compile(checkpointer=checkpointer)

async def lane_session(audio_in, audio_out, thread_id):
    stt = StreamingSTT(model="telephony", boost=MENU_ALIASES, endpointing_ms=700)
    tts = StreamingTTS(voice="en-US-Neural2-F", speaking_rate=1.1)
    await tts.say("Welcome to Harbor Burger, what can I get you?", audio_out, barge_in=stt)

        if reply.done: break

Saying it

Thirty secondsA drive-through is a speech-and-state problem. The menu is versioned data, the understanding step produces deltas — Dialogflow CX intents with list parameters, or one structured-output call that returns typed cart operations — and code resolves, prices and speaks the cart. A channel adapter owns the three things no framework gives you: endpointing at 700 milliseconds, barge-in everywhere except the read-back, and a silence policy where silence after items means done. One rule-based upsell, a read-back with an explicit yes, an idempotent POS submit, and a crew hand-off with the partial order after two misses.
Two minutesThe reason several chains withdrew AI order-taking is that they treated it as a language problem. The language is trivial; the channel is brutal: engine noise, fragments, mid-sentence corrections, and a time budget where every second at the window is lost throughput. So the design starts with the budget: under 1.5 seconds from end of speech to start of reply, every prompt under twelve words, streaming speech-to-text with the menu aliases boosted so “a one combo” is not “a wine combo”, and streaming text-to-speech that starts on the first sentence. The menu is a versioned JSON file — items, sizes, modifiers, combos, prices, aliases and the upsell rules — and nothing about it lives in a prompt. Understanding returns deltas: in Dialogflow CX, one Order flow with three pages, Ordering with list-parameter intents and a cart webhook, Read-back with no barge-in and an explicit yes, Done with the total and the lane, a crew hand-off page, and one task playbook for menu questions over the menu as a data store — the only generative turn, because the order path cannot afford a model call — with no customer identity anywhere, the lane session being the id; in LangGraph, the same structure with one call on a small fast model that returns typed operations, which handles “two burgers, one without pickles” natively, and an interrupt at the read-back. Code resolves operations against the menu and prices the cart, so a price can never be hallucinated; the upsell is one rule, fired once, before the read-back, never after a no. The POS submit uses the lane session as its idempotency key, and the crew gets the partial order on their screen after two misses or the word “person”. We log every transcript with its audio for the first month because the errors are in the speech layer, and the review asks four questions: two items with one modifier in two turns, a mid-order “make that large” changing the right line, no price not computed from the file, and a human within two misses.

Likely questions

  • CX or LangGraph? CX when the chain already runs a telephony partner and operations must read the flow; LangGraph when per-item modifiers and free-form corrections dominate. The adapter, the cart code and the read-back are the same.
  • Where do playbooks and the generative features fit in a drive-through? One task playbook for menu questions, with the menu and the allergen sheet as a data store and a lookup tool, returning an answer to the Ordering page; generative fallback for off-menu questions at the first miss; no generators on the order path. A playbook turn is a model turn and chooses its own tools, so orders stay in the flow.
  • What identity does the agent have? None for the customer; the session is store, lane and menu version, which doubles as the thread id and the POS idempotency key; the webhook is authenticated with the service agent’s ID token.
  • Why not a bigger model for better understanding? Latency is the product; the small model with a typed schema and a menu vocabulary is accurate enough, and code does the rest.
  • How do you stop it inventing items or prices? Deltas, not prices, from the model; the resolver rejects unknown items; the pricer is the only source of numbers; a test asserts spoken equals computed.
  • What about noise and accents? A telephony STT model, speech adaptation from the alias list, 700 ms endpointing tuned on recordings, and a crew hand-off that never makes the customer repeat the order.
  • How is it measured? Order accuracy at the window, arrival-to-confirmed seconds, intervention rate, upsell acceptance, and twenty recordings a week listened to by a person.

B · The prediction-market assistant for Kalshi and Polymarket: information, never advice; money only through code and a human yes

A prediction-market assistant answers “what is the market saying about X, what would it cost me to take a position, and can you place it?” over a regulated exchange API. It is the opposite of the drive-through: the channel is easy (text, usually inside the operator’s app), the language is open-ended, and the risk is concentrated in one action — placing an order with real money. So everything open-ended goes to the model and everything about money goes into code, with a human confirmation in between. The agent explains prices as implied probabilities and positions as cost, payout and maximum loss; it never says whether a bet is good. This is the design from the Conversational AI primer.

How it is built, in order

What goes wrong

  • Advice leakage. “This looks like good value.” The prompt rule, the refusal suite and a judge on every change; the reply explains the implied probability and declines.
  • A generated number. A fee or a payout the model rounded in its head. Every number from quote_position or market_details; the fidelity script catches the rest.
  • An order without the read-back. The model calls place_order on an implied instruction. The middleware pauses regardless; the discipline traces assert the six fields were read back.
  • Silent retries. ok=false and the model tries 0.63 instead. Rule 4; the audit log shows every attempt.
  • Price units. 64 cents sent as 64 dollars, or 0.9 typed for 0.09. Units in the adapter only; the deviation check against the book.
  • Duplicate orders. A retried confirmation after a timeout. client_order_id and the 409.
  • A key where the model can reach it. Injection in a market’s rules text asks for it. Keys live in the adapter or the user’s wallet; injection cases in the suite.
  • Trading into resolution. An order a minute before close. The close window in policy.
  • Eligibility assumed. The venue’s identity and jurisdiction checks skipped because the chat is friendly. The account gate first; policy checks the flag on every order.
  • The order inside a playbook. The model decides when to call the money tool and how to phrase the read-back; nobody can audit a page that does not exist. Orders are a flow; the playbook’s tools are read-only.

# pm_agent/policy.py — limits, the quote arithmetic and the check that runs inside place_order even after approval
from dataclasses import dataclass
from datetime import datetime, timedelta, timezone

@dataclass
class Limits:
    max_contracts_per_order: int = 100
    max_notional_per_order: float = 100.0
    max_notional_per_day: float = 500.0
    min_minutes_before_close: int = 30
    max_price_deviation: float = 0.05          # vs best ask/bid; catches 0.9 typed for 0.09

class PolicyError(Exception): ...

def cost_and_payout(side, action, contracts, price, fee_fn):
    cost = contracts * price; fee = fee_fn(contracts, price)
    return {"cost": round(cost + fee, 2), "fee": round(fee, 2), "max_payout": contracts * 1.0,
            "max_profit": round(contracts * (1 - price) - fee, 2), "max_loss": round(cost + fee, 2), "implied_probability": round(price, 3)}

def check(req, market, account, limits: Limits, spent_today: float) -> dict:
    if not account.eligible: raise PolicyError("Account is not eligible to trade (identity or jurisdiction check incomplete).")
    if market.status != "open": raise PolicyError(f"Market is {market.status}.")
    close = datetime.fromisoformat(market.close_time.replace("Z", "+00:00"))
    if close - datetime.now(timezone.utc) < timedelta(minutes=limits.min_minutes_before_close):
        raise PolicyError("Market closes too soon to accept new orders through the assistant.")
    if req.contracts > limits.max_contracts_per_order: raise PolicyError(f"Order exceeds the per-order limit of {limits.max_contracts_per_order} contracts.")
    ref = market.yes_ask if req.side == "yes" else (None if market.yes_bid is None else 1 - market.yes_bid)
    if ref is not None and abs(req.limit_price - ref) > limits.max_price_deviation:
        raise PolicyError(f"Limit price {req.limit_price:.2f} is far from the market ({ref:.2f}); please confirm the price you meant.")
    notional = req.contracts * req.limit_price
    if notional > limits.max_notional_per_order or spent_today + notional > limits.max_notional_per_day:
        raise PolicyError("Order exceeds your notional limits for this order or for today.")
    return {"notional": round(notional, 2)}

# eval/checks.py — numeric fidelity and order discipline from the run trace; refusals go to a judge with the rubric
import re
NUM = re.compile(r"(?<![\w.])\$?(\d+(?:\.\d+)?)%?")

def numeric_fidelity(turn):
    said = {float(n) for n in NUM.findall(turn.reply)}
    allowed = set()
    for r in turn.tool_results:
        allowed |= {float(n) for n in NUM.findall(str(r))}
        allowed |= {round(100 * v, 0) for v in allowed if 0 < v < 1}          # 0.64 may be said as 64%
    return said <= allowed, said - allowed

def order_discipline(trace):
    for i, step in enumerate(trace):
        if step.kind == "tool_call" and step.name == "place_order":
            prior = [s.text for s in trace[:i] if s.kind == "assistant"]
            fields = ("venue", "market", "side", "buy", "contracts", "limit")
            if not prior or not all(f in prior[-1].lower() for f in fields): return False, i
            if not any(s.kind == "interrupt" for s in trace[:i]): return False, i
    return True, None

Saying it

Thirty secondsA prediction-market assistant has one dangerous action, so the design pushes everything open-ended to the model and everything about money into code with a human pause in between. Exchange adapters normalise Kalshi and Polymarket into one schema and own keys, idempotency and price units; a policy layer in code enforces eligibility, caps, price sanity and market state and writes an audit log; the conversation layer is a create_agent whose lookup and quoting tools need no approval and whose place_order sits behind human-in-the-loop middleware with a six-field read-back. It gives information, never advice, and a four-part evaluation suite — refusals, numeric fidelity, order discipline, jailbreaks — gates every change.
Two minutesThe user wants three things: what is the market saying about X, what would it cost me to take a position, and can you place it. The first two are language and arithmetic; the third moves real money on a regulated venue, and the regulatory picture itself moves — Kalshi as a CFTC-regulated US exchange, Polymarket relaunched for eligible US users in late 2025 with state exclusions — so counsel reviews eligibility, disclosures and advertising before anything ships. The architecture is three layers. Adapters give both venues one Market and one OrderRequest schema with prices in dollars between zero and one; Kalshi quotes cents, so the conversion lives there and nowhere else; the Kalshi adapter signs requests with the operator’s key, Polymarket orders are signed by the user’s own wallet or custody through the official client, and the conversation layer never holds a key. Policy is code between the agent and the adapters: eligibility, per-order and per-day notional caps, a contract cap, a price-deviation check against the book that catches 0.9 typed for 0.09, market state and a close window, a cooling-off rule, and an append-only audit log of every quote shown and every order attempted. The conversation layer is a create_agent with tools for search, details, quoting and positions that need no approval, and place_order wrapped in human-in-the-loop middleware: the run pauses, the channel reads back venue, market, side, buy or sell, contracts and limit price, and the user approves, edits or rejects; the policy check still runs inside the tool after approval, so a confirmed order that breaches a limit is rejected with a plain reason and both decisions are logged. The quote is computed, not generated — cost, fees, payout, maximum loss, implied probability — and the model only phrases it, with an explicit “not a forecast by us”. Five prompt rules, PII blocking, a call limit and a durable checkpointer. For an operator with a Dialogflow CX support agent, the regulated steps are pages: Start verifies the app’s JWT and sets the eligibility flags as redacted session parameters, an account-gate flow walks Eligibility, Disclosures and Limits, the order is a four-page flow whose Quote webhook issues a quote id and whose Confirm webhook places by that id, advice requests land on a static Decline page, and the open-ended market questions go to a task playbook with read-only tools and a rules data store — a playbook that cannot place anything, so order discipline is structural rather than prompted. The evaluation suite runs on every prompt or model change: fifty advice-fishing prompts that must all produce explanation-plus-decline, a script that traces every number in a reply to a tool result, order-discipline traces with zero tolerance, and injection cases hidden in market rules text.

Likely questions

  • How do you keep it from giving advice? A prompt rule, tools that return explanations and numbers rather than opinions, fifty fishing prompts judged against a rubric on every change, and a human spot-check; the reply explains what the price implies and declines.
  • What stops a wrong order? The pause with a six-field read-back, the policy check inside the tool after approval, idempotent client order ids, price sanity against the book, and an audit log of every attempt.
  • Why one schema for two very different venues? Both settle at one or zero; the differences are units, authentication and signing, which belong in adapters so the policy and the agent never see them.
  • Where does Dialogflow CX fit? In front, for the regulated steps an auditor must read: account gate, disclosures, trading-enabled, confirmation; the agent handles the open-ended market questions behind a tool.
  • Flows or a playbook for the order? A flow. A playbook chooses its own tool calls, so the read-back and the yes would be model behaviour; as pages they are structure, with a quote id that ties the confirmation to exactly what was read back. The playbook gets read-only tools and the questions.
  • How does the agent know who it is talking to? The operator’s app sends a short-lived JWT in the request payload; the Start webhook verifies it, exchanges it for an opaque reference and sets eligibility, trading-enabled and limits as redacted session parameters; venue keys stay in the backend; every webhook and tool call carries the service agent’s ID token.
  • How is it evaluated? Refusal rate on the suite, numeric-fidelity rate, order-discipline violations at zero, injection cases, and median latency; all re-run on every change.

How it is built and reviewed

  1. Compliance first. The policy table (Reg E and Reg Z timelines, the notice window, the account-age variants), the approved wording of the Confirm and Window pages, the data retention, the UDAAP review of every prompt; the table is versioned and owned.
  2. The webhook contract as OpenAPI: fourteen tags, the identity parameters, the idempotency rule, the error shapes; built against the core-banking and case-system sandboxes.
  3. Identity: the app’s JWT and the partner’s token verified in account.check; the Step-up page with OTP and DTMF; the level re-checked in every money handler; the deep links for address changes and passkeys.
  4. The flows, thin: Card, Transactions and Dispute with the forms per type, the Window and Freeze-offer pages, the hand-offs; session entities from tx.list.

What goes wrong in a bank bot

  • A card number through the bot. “Read me the 16 digits.” Last four as a redacted session entity; the PAN at the partner or the tokenizer.
  • Caller id as identity. A spoofed number freezes or, worse, unfreezes a card. The partner’s token or an OTP; a step-up page.
  • A model deciding liability. “You’ll probably get it back.” Nothing about outcomes anywhere; the refusal suite; banned phrases.
  • Discouraging the claim. “Have you contacted the merchant first?” as a gate. State, offer, file; log abandonment, never induce it.
  • Timelines in a prompt. A generator that says 30 days. The policy table; the Confirm page speaks parameters.
  • Business days by calendar. A provisional-credit date on a Sunday. Business-day arithmetic with the bank’s holiday calendar, in code.
  • Not freezing first. Seven questions while the card is being used. fraud.now freezes at the known level immediately.
  • Duplicate disputes. A retried yes opens two cases. An idempotency key per confirmation; dispute.context checks prior disputes.
  • A stale strong level. Verified at 9:00, replacing a card at 9:40 after the phone changed hands. The handler checks auth_at; the level expires.
  • Fallback on the Type page. “Not mine” misheard, answered with an essay about disputes. Fallback only on Hub and List.
  • The transcript as the record. The regulator asks for the case. The case system holds it; the chat is redacted history.
Weak answer“A chatbot that lets customers report lost cards and raise disputes, with GPT for natural conversation.”
Strong answer“Identity as pages, with a step-up before any card control or dispute and the level re-checked in every handler; freeze first for fraud; a dispute as a form per type with Reg E or Reg Z timelines read from a policy table and spoken from parameters; the PAN never in the agent; a task playbook with read-only tools for the questions, and a refusal suite that proves the bot never predicts an outcome or discourages a claim.”

# bank/policy.py — the regulated timelines as data, owned by compliance and versioned; paraphrased for design, counsel owns the rules
from dataclasses import dataclass
from datetime import date, timedelta

@dataclass(frozen=True)
class Timelines:
    regime: str; notice_window_days: int; investigate_bdays: int; provisional_credit_bdays: int | None; extended_days: int | None; result_notice_bdays: int

POLICY = {                                                                                 # version 2026-09
  ("debit", "standard"):  Timelines("REG_E", 60, 10, 10, 45, 3),
  ("debit", "new_account"): Timelines("REG_E", 60, 20, 20, 90, 3),
  ("debit", "pos_or_foreign"): Timelines("REG_E", 60, 10, 10, 90, 3),
  ("credit", "standard"): Timelines("REG_Z", 60, 30, None, 90, 2),                        # acknowledge within 30 days; resolve within two cycles, ≤ 90 days
}

def timelines(card_product: str, account_age_days: int, charge) -> Timelines:
    if card_product == "credit": return POLICY[("credit", "standard")]
    if account_age_days < 30: return POLICY[("debit", "new_account")]
    if charge.pos or charge.foreign: return POLICY[("debit", "pos_or_foreign")]
    return POLICY[("debit", "standard")]

def add_business_days(d: date, n: int, holidays: set[date]) -> date:
    while n > 0:
        d += timedelta(days=1)
        if d.weekday() < 5 and d not in holidays: n -= 1
    return d

Saying it

Thirty secondsCard conversations are short transactions with regulated tails, so the design keeps every tail on a page. Identity is pages: known from the app’s token, strong after a step-up with a one-time code or a passkey, re-checked inside every handler. Fraud freezes first and asks later. A dispute is a form per type whose questions are the ones the network and the regulation need, with Regulation E or Z timelines read from a policy table and spoken from parameters on a confirmation page. The card number never enters the agent. A task playbook with read-only tools answers the questions, and a refusal suite proves the bot never predicts an outcome or discourages a claim.
Two minutesThe bank has three families of card conversations: controls, transactions and disputes, and they become three flows behind a Start page that verifies identity. Start takes the app’s JWT, or the telephony partner’s authenticated-caller token, from the request payload and sets the user, an opaque reference, the level and the cards as a redacted session entity; a Step-up page with a one-time code as a redacted form parameter, entered by keypad on voice, raises the level to strong with a timestamp, and every handler that freezes, replaces or files re-reads that level and its age, because the flow is not trusted to protect the back end. The one exception is fraud: “someone is using my card right now” freezes at the known level immediately, since a freeze is reversible and minutes matter, and steps up afterwards. The Transactions flow loads the last thirty days through a webhook that also writes them as a session entity with merchant, amount, date and ordinal synonyms, so “the parking one” resolves deterministically and nothing about the customer enters the agent definition; a hold or pending charge is explained by a generator that only sees the tool output. The Dispute flow identifies the charge, asks the type among six, and runs a form per type with exactly the questions the case needs: did you have the card, when did you notice, did you contact the merchant, what did you expect. A context webhook returns the regime from the card product, debit under Regulation E and credit under Regulation Z, the notice window and the timelines from a versioned policy table that compliance owns; the Confirm page reads the claim back with those timelines as parameters, barge-in off on voice, and an explicit yes opens the case with an idempotency key, computing the provisional-credit date in business days with the bank’s calendar. The bot never states an outcome, a liability amount or a refund, never gates a claim on contacting the merchant, and when a charge is outside the notice window it states the rule and still files. The card number never passes through: last four digits as a redacted entity, the PAN at the partner’s DTMF masking or the app’s tokenizer, because PCI DSS is not in the product’s compliance list. The Explain task playbook, with the terms data store and read-only tools for the user’s own cards and dispute status, takes the questions and returns; fallback is grounded and only on the Hub and List pages. In CX Agent Studio the same design is a steering agent with flow-based agents for step-up, cards and disputes.

Likely questions

  • How do you authenticate on the phone? The partner’s authenticated-caller token in the payload when the IVR already verified the caller; otherwise an account lookup plus a one-time code by keypad on a Step-up page; caller id is a hint only.
  • Where do the regulatory timelines live? In a versioned policy table the context webhook reads; the Confirm page speaks them from parameters; no prompt contains a number of days.
  • How is PCI handled? The agent never sees a PAN: last four digits only, the PAN captured by DTMF masking at the partner or the app’s tokenizer, replacements to the address on file.
  • Why six dispute types? Because the questions differ and the case quality depends on them; a generic narrative produces cases that need a call-back.
  • Where is the playbook? Explaining how things work and reading the user’s own data; never filing, freezing, or saying what will happen to a claim; the refusal suite tests that on every change.

What goes wrong in a clinic bot

  • Helpful triage. “A fever for three days is usually viral.” The nurse line; a refusal suite built with clinicians.
  • An emergency gated by identity. “Please sign in first.” The Emergency page from any state, no token needed.
  • A result read aloud. “Your A1c was 8.1.” Never; the Results page says the clinician explains.
  • Proxies by claim. “This is for my husband” accepted. The proxy list from the portal; never extended by the bot.
  • Diagnosis in a prompt. A generator told the visit reason. No generators; templates over FHIR fields; the reason stays in the EHR.
  • Double booking. Two confirmations for one slot. A hold with an expiry; the booking by hold id.
  • A refill “approved” by the bot. “Your refill is on its way.” Requested, never promised; the turnaround from the table.
  • Controlled substances in the list. The patient asks and the bot files. Flagged by meds.list; the clinician page.
  • Drug names misheard. “Lisinopril” becomes something else. Speech adaptation from the patient’s own eligible list; a read-back.
  • One language tested. Spanish prompts that drift into English. Both language sets in every test case.
  • The PHI in the transcript. A redaction audit that finds names in history. Redact-in-log, Sensitive Data Protection, ids in the audit, a monthly check.

@handler("slots.search")

    top = pick_three(slots, params.get("time_pref"))

    return say(spoken_slots(top, lang=params["language"]), {"slots_offered": [s.id for s in top]})

@handler("slot.hold")
def slot_hold(body, params):
    hold = fhir.create("Appointment", status="proposed", slot=params["slot"], minutes_valid=5)         # or the vendor's hold API
    return say(None, {"hold_id": hold.id, "hold_expires": hold.expires_iso, **readback_fields(hold, lang=params["language"])})

@handler("appt.book")
def appt_book(body, params):
    user = auth.resolve_ref(params["auth_ref"]); patient = entitled(user, params["patient"])
    hold = fhir.read("Appointment", params["hold_id"])
    if hold.status == "booked": return say(booked_message(hold, params["language"]), {"appointment_id": hold.id})   # a retried yes
    if hold.expired: return say(t("hold_expired", params["language"]), {"hold_expired": True})                     # the flow returns to Slots
    appt = fhir.update(hold, status="booked", participants=[patient.ref, hold.practitioner_ref])
    audit(user.id, "appointment_booked", appt.id, hold=hold.id, read_back_version=params.get("read_back_version"))
    return say(booked_message(appt, params["language"]), {"appointment_id": appt.id, "telehealth_url": appt.telehealth_url})

@handler("meds.list")
def meds_list(body, params):
    user = auth.resolve_ref(params["auth_ref"]); patient = entitled(user, params["patient"])
    if not auth.is_strong(user, params.get("auth_level"), params.get("auth_at"), max_age_s=600): return say(t("verify_first", params["language"]), {"needs_step_up": True})
    reqs = fhir.get("MedicationRequest", patient=patient.id, status="active")
    rows = [(r.id, med_synonyms(r, patient), refill_policy.classify(r)) for r in reqs]                      # eligible | controlled | visit_needed | pharmacy_has_refills
    write_session_entity(body, "medication", [(mid, syn) for mid, syn, cls in rows])
    eligible = [mid for mid, _, cls in rows if cls == "eligible"]
    return say(spoken_meds(rows, params["language"]), {"med_classes": {mid: cls for mid, _, cls in rows}, "eligible_count": len(eligible)})

@handler("refill.request")
def refill_request(body, params):
    user = auth.resolve_ref(params["auth_ref"]); patient = entitled(user, params["patient"])
    cls = params["med_classes"].get(params["medication"])
    if cls != "eligible": return say(t(f"refill_{cls}", params["language"]), {"refill_blocked": cls})           # the flow routes controlled → clinician page

Saying it

Thirty secondsEverything a clinic bot touches is protected health information, so identity, minimisation and redaction come first, under the BAA. Scheduling and refills are thin flows over FHIR: a slot search that writes the options as a session entity, a five-minute hold before the read-back, a booking keyed on the hold so a retried yes cannot double-book; refills only for eligible prescriptions, controlled substances to the clinician, a turnaround stated and never a promise. The bot never triages: an Emergency page is reachable from every state without identity, symptom talk goes to the nurse line, results to the clinician. One task playbook answers pre-visit questions from signed documents and returns clinical flags the flow routes on.
Two minutesStart takes the patient portal’s token from the request payload and sets the user, an opaque reference, the language, and the list of people this account may act for, which the portal decided and the bot inherits as a session entity; on voice the clinic’s telephony partner verifies the caller with date of birth and a one-time code and produces the same token. Known is enough to book, move and cancel; refills and any health detail spoken on voice need a step-up on a page, a one-time code by keypad, valid for ten minutes and re-checked inside the handlers. The Scheduling flow asks the visit type among those the clinic lets this patient self-book, an optional provider from the care team and a preference, searches FHIR Slots, writes the first three as a session entity so “the Tuesday one” resolves deterministically, holds the chosen slot for five minutes as a proposed Appointment, reads it back with the cancellation policy and barge-in off, and books on an explicit yes using the hold id as the idempotency key. The Refills flow lists only eligible prescriptions by the names the patient uses, flags controlled substances to a clinician page, confirms the pharmacy on file, reads the request back with the prescriber’s turnaround from a policy table, and files a Task to the prescriber queue; the bot requests, the prescriber decides, and nothing is ever promised. Three things override everything: a high-priority emergency intent on every flow, backed by a keyword net in the adapter, that sends the user to an Emergency page with the instruction to call 911, needing no identity; a nurse-line hand-off for anything that sounds like advice; and a Results page that only says results are released by the clinician. Minimisation is a rule per channel: first names and visit types on voice, medications by the patient’s own words, no diagnosis, result or dosing in any prompt or message, ids in the audit log, redact-in-log on every parameter and Sensitive Data Protection on the history. The one playbook is Pre-visit: preparation, logistics and how visits work from documents the medical director signed, in English and Spanish, with emergency and needs-clinician flags as outputs that the Hub routes on. The design review asks whether an emergency reaches the page from every state, whether any message contains clinical content, whether a user can act for someone not on the list, whether a controlled substance can be requested, and whether a slot can be booked twice.

Likely questions

  • How do you stay inside HIPAA? The product under the BAA with the covered-services check, regional agent, CMEK, redaction on parameters and history, minimisation on voice, ids in the audit, retention the clinic sets, and a monthly redaction audit.
  • What happens when a patient describes chest pain mid-booking? The emergency intent on every flow (and the adapter’s keyword net) interrupts to the Emergency page, which needs no identity, logs the event and ends; the nurse lead reads every hit.
  • How do you avoid double bookings? A hold on the slot before the read-back and a booking keyed on the hold; an expired hold returns to the slot list.
  • How are proxies handled? The portal’s entitlements become the patient session entity; the bot never extends them; a child past the confidentiality age drops off in the portal and therefore here.
  • Where is the model used? Only in the Pre-visit playbook over signed documents, with clinical flags as outputs, and in grounded fallback on the Hub; nothing generative touches a slot, a medication or a symptom.

E · The airline disruption agent: rebooking inside the policy, refunds and compensation from a table, and nothing paid through the bot

When a flight is cancelled or delayed for hours, every passenger on it wants the same three things at once: what is happening, what are my options, and what am I owed. The airline wants them rebooked before they reach the desk. The design is a proactive conversation that opens from the disruption notification with the booking already in context, offers the rebooking options its own systems rank inside the irregular-operations policy, commits the choice with a hold and a read-back, and handles refunds, compensation and duty-of-care vouchers as entitlements computed by a policy engine from rules that change: the US automatic-refund rule, EU261 as it stands and as it is being revised, and the airline’s own customer-service plan. The bot states entitlements; it never estimates them, and no card ever passes through it.

How it is built and reviewed

  1. Legal and customer relations first. The policy engine’s rule set: the US refund rule, EU261 in force and the revision with its application date, the airline’s plan; the cause categories; the approved wording for Status, Refund and Compensation; the languages.
  2. The reservation-system contract. Lookup, disruption feed, ranked options inside the IROPS policy, hold, commit, refund to origin, vouchers; built against the vendor sandbox with synthetic disruptions.
  3. Identity. The app JWT; the record-locator path with rate limits and lockout; the booking-scoped reference; the deep links for anything that changes money or contact details.
  4. The flows, thin: Status, Rebooking with hold-then-confirm, Entitlements with the engine’s parameters, Care, the hand-offs by location; session entities for passengers, options and trips.
  5. The generative objects last: the contract and the plan as a data store, the Travel-questions playbook with the refusals in its examples, the Options generator with the fidelity check, fallback on Status.
  6. Test cases per arrow and per rule: a controllable cancellation, weather, an EU departure, a partner rebooking, an expired hold, a double yes, a compensation-fishing prompt in five languages, a refund where the passenger is not entitled.
  7. Storm-day rehearsal: replay a real disruption day against the test environment at ten times the rate; cache and throttle paths exercised.
  8. Pilot on one hub for app users, then web and phone; customer relations reads every compensation denial for the first month.
  9. The design review asks five questions. Can the bot state an amount the engine did not return? Can anything of value leave the booking? Can a hold be committed twice? Does a storm day degrade to a static path rather than a timeout? Is every assessment logged with its rule version?

What goes wrong in an airline bot

  • A compensation figure from the model. “You should get €600.” The engine returns the amount and the regime; the playbook refuses to estimate; banned phrases.
  • The law in a prompt. A fallback that still says three hours after the revision applies. A versioned rule set with application dates; nothing legal in any prompt.
  • Arguing the cause. “It was the weather” to a crew-shortage cancellation. The cause category from the operations record; the bot states it and offers the review.
  • Refunds to a new account. “Where should we send the money?” Original form of payment only; vouchers to the booking’s contact.
  • Bank or card details in the chat. A fare difference typed to the bot. The app’s payment sheet as a function tool.
  • Searching fares in the conversation. A model proposing routings. The reservation system ranks inside the policy; the bot phrases.
  • Double commits. Two passengers, two seats, one retried yes. A hold with expiry; commit by hold id.
  • A record locator over a bad line. “Q as in Quebec” misheard three times. Speech adaptation with the phonetic alphabet; the app path; the desk.
  • Timeouts on the storm day. The reservation system at ten times load and the webhook at five seconds. Cached options, a short budget, the static degraded path.
  • A voluntary change in the disruption flow. “While you’re here, move me to next week.” The app’s fare rules by deep link; this agent is for the involuntary case.
  • Hand-off to the wrong place. A passenger at the gate sent to a phone queue. at_airport decides the desk.

The policy engine, the options handler with the fidelity check, and the hold-commit pair

# air/rights.py — the entitlement rules as versioned data; paraphrased for design, legal owns the rule set and its dates
from dataclasses import dataclass
from datetime import date

RULES_VERSION = "rights-2026-10"

@dataclass(frozen=True)
class Assessment:
    regime: str; eligible: bool; amount: float | None; currency: str | None; reason_category: str; escalation: bool; rule_version: str = RULES_VERSION

def us_refund_entitled(seg) -> bool:
    # cancellation, or a significant change: ≥ 3 h domestic / ≥ 6 h international, airport change, added connection, downgrade
    if seg.status == "cancelled": return True
    threshold = 180 if seg.domestic else 360
    return (seg.schedule_change_minutes >= threshold or seg.airport_changed or seg.connection_added or seg.downgraded)

def eu261_amount(distance_km: float) -> int:
    return 250 if distance_km <= 1500 else (400 if distance_km <= 3500 else 600)        # in force; the 2026 revision applies from 2027 per its own text

def eu261_delay_threshold_minutes(distance_km: float, on: date) -> int:
    if on >= EU261_REVISION_APPLIES_FROM:                                                  # set by legal when the revised regulation is published; not before
        return 240 if distance_km <= 3500 else 360
    return 180

def assess_compensation(seg, pax, on: date) -> Assessment:
    if seg.eu261_applies:
        if seg.cause_category in EXTRAORDINARY: return Assessment("EU261", False, None, None, seg.cause_category, escalation=True)
        late = seg.status == "cancelled" and seg.notice_days < 14
        delayed = seg.arrival_delay_minutes >= eu261_delay_threshold_minutes(seg.distance_km, on)
        if late or delayed or seg.denied_boarding: return Assessment("EU261", True, eu261_amount(seg.distance_km), "EUR", seg.cause_category, escalation=False)
        return Assessment("EU261", False, None, None, "below_threshold", escalation=False)
    # US: no fixed cash compensation for delays; the airline's own customer-service plan governs care and goodwill
    return Assessment("US_PLAN", False, None, None, seg.cause_category, escalation=seg.cause_category == "controllable")

Saying it

Thirty secondsA disruption conversation opens from the notification with the booking in context and answers the three questions in order: what happened, from the operations record; what are my options, ranked by the reservation system inside the irregular-operations policy and phrased by a generator that only sees the JSON; and what am I owed, from a versioned policy engine that carries the US refund rule, EU261 as in force and as revised, and the airline’s own plan. Rebooking is a hold, a read-back and a commit keyed on the hold. Refunds go to the original payment only, money moves through the app’s own sheet, and a playbook with read-only tools answers the questions without ever stating an amount.
Two minutesThe notification that a flight is cancelled carries a link that opens the chat with the booking and the segment already known, so the first thing the passenger reads is the status: the flight, the new schedule if any, and the cause category from the operations record, never argued. Identity is the app’s token or, on web and phone, the record locator and last name, which is weak, so the design removes the attack surface instead of defending it: a booking-scoped reference, the same passengers on any rebooking, vouchers to the booking’s contact, refunds only to the original form of payment, and anything that changes money or contact details only in the app behind strong authentication. Rebooking is a flow: the reservation system returns at most three options ranked inside the irregular-operations policy, own metal first and partners where allowed; a session entity makes “the 18:40” and “tomorrow morning” resolve; a generator phrases the options from the JSON alone and a check compares every time, flight number and price to it before the text is spoken; the chosen option is held for ten minutes, read back with barge-in off, and committed on an explicit yes with the hold id as the idempotency key. Entitlements are a second flow fed by a policy engine, not a prompt: the US rule gives a full refund to the original payment for a cancellation or a significant change when the passenger declines alternatives, within seven business days for cards; EU261 gives fixed amounts by distance for short-notice cancellations and long delays unless the circumstances were extraordinary, with care regardless, and its June 2026 revision raises the thresholds from 2027, which is a date in the rule set and nothing the bot explains; the airline’s customer-service plan decides meals, hotels and transport. The engine returns the regime, the amount, the reason category and whether a review is open, the bot states exactly that, and every assessment is logged with its rule version. A fare difference opens the app’s payment sheet as a function tool. The Travel-questions playbook answers from the contract of carriage, the plan and the FAQ with read-only tools for trip and bag status, and refuses to estimate an entitlement for this passenger. On a storm day the options are cached per flight, the webhook budget is short, and the flow degrades to a static path rather than a timeout; the hand-off goes to the airport desk queue when the app says the passenger is at the airport and to the contact centre otherwise.

Likely questions

  • Isn’t record locator plus last name too weak? For what this agent does, it is enough, because nothing of value can leave the booking: same passengers, original payment, the booking’s contact; everything else happens in the app behind strong authentication.
  • How do you keep compensation answers right? A versioned policy engine assessed per route, cause and delay returns the amount and regime; the bot speaks parameters; the playbook refuses to estimate; the revision’s application date is a field in the rule set.
  • Why a generator on the options? Three ranked options in a sentence is language, not policy; the generator sees only the JSON and a check verifies every number before it is spoken, with a static fallback.
  • What happens on a storm day? Options cached per flight, a short webhook budget, a static degraded path when the reservation system throttles, and a rehearsal against a replayed disruption day at ten times the rate.
  • Where does the model sit in Agent Studio? As the steering agent that routes and answers travel questions; rebooking and entitlements stay flow-based agents the model hands to and gets back from.

The stack, in two lengths

Thirty secondsGoogle’s conversational stack in 2026 is Conversational Agents, the product once called Dialogflow CX, with flows for deterministic conversation and playbooks for generative stages, and CX Agent Studio, its ADK-based successor, inside Gemini Enterprise for Customer Experience. A flow is pages with forms, routes and handlers, driven by a state machine with a documented evaluation order; a playbook is a model running one stage from a goal, instructions, examples and tools. Fulfilment calls a webhook by tag that returns data, never the next page. I put money, identity and regulated steps on pages, open questions in task playbooks with read-only tools, documents in data stores, and I keep the flow outermost in CX because billing and the SLA follow the nesting.
Two minutesStart with the session: an id, parameters, the current flow and page, and a stack of called flows, alive for thirty minutes. The deterministic dialogue manager moves it: on each turn the input is matched to an intent with entities or used to fill a form parameter, then handlers are evaluated in a fixed order, intent routes before condition routes before event handlers, page level before flow level, with intents and events consumed by the first match and conditions not; the first handler with a transition ends evaluation, the new page’s entry fulfilment and condition routes run in the same turn, and symbolic targets like END_FLOW pop the stack. Fulfilment is the only place the agent acts: messages, parameter presets and a webhook call selected by a tag; the webhook receives the tag, the session parameters, the form state, the intent and the channel payload, and returns messages and parameters under a five-second budget with one retry, authenticated with the service agent’s ID token per environment. Identity rides the payload: the channel proves, the webhook verifies and exchanges for an opaque reference, the flow routes on a level and a timestamp held in redacted parameters, and a step-up page raises the level before money or health actions, which the handlers re-check. The generative half is four objects: playbooks, routine for stages and task for questions that return outputs, with tools of four kinds and a pinned GA model; data stores of indexed documents; generators inside fulfilments; and generative fallback on no-match. I place them with five questions: money or a record means a page; an open input means a task playbook with read-only tools; documents mean a data store; a question-shaped no-match means grounded fallback once; free wording over fixed facts means a generator fed only the facts. Voice wraps all of this in a pipeline with a clock: a telephony partner or a custom audio channel, speech-to-text with a model and adaptation phrases, an endpointer tuned on recordings, barge-in set per prompt and off on the read-back, synthesis streamed with a short first sentence, under a second and a half from end of speech to the first syllable, billed per second. Operations are test cases that assert pages and parameters, versions pinned into environments with the export in git, a BigQuery export measured by completion and abandonment before intent accuracy, and a cost model where any generative turn bills at the playbook rate and a playbook calling a flow prices the whole conversation. CX Agent Studio inverts the nesting: a steering model with tools and handoff rules is outermost, imported flows are black boxes for data collection, validation and authentication, and a token broker lets tools act with the user’s own token. The five designs on this page are the same rules applied five times.

If asked to pick one design and defend it

Pick the bank. It has every ingredient: strong identity as pages with a step-up re-checked in handlers, a regulated process with timelines from a policy table, a PCI boundary that keeps the card number out of the agent entirely, voice through a telephony partner with DTMF, a task playbook with read-only tools and a refusal suite, and an audit that lives in the case system rather than the transcript. Then offer the airline as the contrast: a weak identity made safe by removing what could be stolen, and entitlements that change on a legal timetable.

Likely questions, by theme, with the shape of a good answer

The platform

  • Flows or playbooks? Both, by placement: flows for anything that must be read, tested, billed deterministically or covered by the SLA; task playbooks with read-only tools for open questions; the flow outermost in CX.
  • What is the dialogue manager? In a flow, the state machine with the documented evaluation order; in a playbook, the model under instructions; the playbook manages its scope, the flow decides when it is entered and takes control back.
  • How does Agent Studio change your design? The outer manager becomes a steering model with handoff rules; the regulated steps become flow-based agents called with explicit variables; tools replace webhooks; the token broker handles delegated identity.
  • What does a webhook return? Messages and parameters, a form parameter marked invalid when needed, never a target page.

Identity and compliance

  • How does the bot know who it is talking to? The channel proves (a JWT in the payload, a step-up on a page), the webhook verifies and exchanges, the flow routes on a redacted level and timestamp the handlers re-check.
  • How do you handle a card number, a diagnosis, a record locator? The card number never enters the agent; the diagnosis never enters a prompt; the record locator is a redacted regex parameter scoped to the booking.
  • Which compliance programmes cover it? HIPAA, ISO, SOC and FedRAMP High for Dialogflow CX including generative features; PCI DSS is not on the list, which shapes the card design.

Generative features

  • How do you keep a model from inventing numbers? Generators fed only tool output with a fidelity check; playbooks with read-only tools and refusal examples; entitlements and timelines from policy tables; the suite on every change.
  • When is generative fallback appropriate? On pages where a no-match is usually a question, once, grounded; never on a confirmation or a form that collects a value.
  • How do you evaluate a playbook? A refusal suite with a rubric and a judge, a numeric-fidelity script, injection cases hidden in documents and tool results, and the deterministic test that the flow regained control after it returned.

Voice

  • What is your latency budget and how do you meet it? 1.5 s to the first syllable: endpointing tuned on recordings, a telephony model with adaptation, a webhook under 400 ms or a partial response, streaming synthesis with a short first sentence.
  • Where is barge-in off? The read-back and the disclosures; on elsewhere, knowing that listening during playback is billed.

Operations and cost

  • How do you test and release? Test cases asserting pages and parameters, run by API in CI; versions pinned into environments; the export in git; rollback by re-pinning.
  • What does it cost? Per request for chat and per second for voice, double at the playbook rate; the playbook share and the prompt length are the levers; a bank at half a million conversations a month runs about sixty thousand dollars of agent fees.
  • What do you measure? Completion and abandonment per page first, containment with completion, fallback per page, latency per step, cost per conversation.

The designs

  • Why does the drive-through have no identity and the clinic so much? Because nothing personal is captured at a speaker box, and everything is protected health information at a clinic; the identity design follows the data, not the channel.
  • Why is the airline’s weak identity acceptable? Because the design removed what could be stolen: same passengers, original payment, the booking’s contact; the rest lives in the app.
  • What is common to all five? The money and the regulated steps are pages with a read-back and a yes; the open questions are a task playbook with read-only tools; the rules are tables; the audit is the back end’s.
