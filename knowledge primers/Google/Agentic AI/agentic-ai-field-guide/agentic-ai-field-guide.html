Agentic AI Field Guide

A production agent is five problems wearing one trench coat: it spends money every time it thinks, it fails in ways no log line explains, its behaviour depends on how its loop, tools and reasoning are arranged, nobody can say whether a change made it better without a judge, and it touches data on someone’s behalf. This page takes the five problems in turn — FinOps, observability, agentic design, evaluation, security and identity — with the definitions, the actual schemas and numbers, and the code that implements the answer, with Google Cloud as the reference platform and Langfuse, OpenTelemetry, the Deep Agents SDK and Google’s Agent Development Kit as the reference tooling. The five parts share one spine, the trace: cost is measured per step on it, a failing tool call is found on it, reasoning and plans become visible on it, evaluation samples come from it, and an unauthorised data access would show up on it.

1 · What a token costs, and why agent loops are quadratically expensive

A model bill is a sum of token counts multiplied by per-token prices, and the prices differ by an order of magnitude depending on which kind of token it is. Knowing the kinds is the whole of FinOps literacy; everything else is arithmetic. The arithmetic that matters most in an agent is that the model is stateless between calls, so every turn re-sends everything that came before it: an agent that takes ten turns does not cost ten times one turn, it costs closer to fifty.

the four counts
input · cached input · output · thinking (billed as output, shown or not); plus tool schemas on every call and multimodal inputs at fixed token rates
the ratios (Oct 2026)
cached input ≈ a tenth of base input; output four to eight times input; thinking at the output rate; batch about half; Agent Runtime’s deferred tier 50% off for background work (preview, Sep 2026)
the loop
input per turn = P + g·n; total over N turns = N·P + g·N(N+1)/2 — the second term is the bill
the rule
the cheapest token is the one you stop re-sending: a tool result trimmed before it enters the history is saved on every later turn

Two facts hold across vendors at the time of writing and shape every optimisation that follows: reasoning tokens are billed at the output rate even when only a summary is returned (Gemini’s documentation states that response pricing is the sum of output and thinking tokens), and cached input is roughly a tenth of the base input rate across Gemini, Anthropic and OpenAI, with Anthropic charging a premium on cache writes and Gemini and OpenAI charging none for implicit caching.

Definitions

token

the unit a model reads and writes; sub-word pieces, roughly four characters or three-quarters of an English word, with code, numbers, non-Latin scripts and whitespace-heavy formats such as JSON costing more tokens per character; images, audio and video convert to fixed token budgets per unit of input.

context window

the maximum number of tokens a request may contain, input plus output plus thinking; a ceiling, not a target — cost scales with what you send, not with what you could send.

prefix P and growth g

P is the fixed prefix (system prompt, tool schemas, retrieved documents); g is roughly the tokens added per turn (the previous model output plus the tool result it triggered); input at turn n is P + g·n.

carry cost

tokens a tool result introduces into the history multiplied by the turns that follow; the quadratic multiplier made visible, and the number that reorders the fix list (card 3).

How to read a bill, and what each line lets you edit

  1. Store all four counts per call. Input, cached input, output and thinking, under the vendor’s names (Gemini: prompt_token_count, cached_content_token_count, candidates_token_count, thoughts_token_count). Instrumentation that keeps only input and output cannot explain the bill: it misses the cache discount on one side and the thinking surcharge on the other, and in an agent each can be larger than the visible answer.
  2. Price them separately. A cost function with four rates (card 3’s Budget.charge), applied per call, so cost per step exists before anyone asks for it.
  3. Estimate P and g for each workload. P from the first turn’s input; g from the slope of input across turns. The two numbers predict the bill for any N and say which family of fix applies.
  4. Edit the line that is largest. Input: trim prompts, prune history, send fewer tool definitions. Cached input: order the prompt stable-first (card 2). Output: length limits, structured outputs, stop sequences. Thinking: the effort or budget setting, per step. Multimodal: resolution and sampling. Anything that can wait: the batch endpoint or the deferred tier.
  5. Attack the quadratic term before the linear one. Caching makes P nearly free after the first turn; context control shrinks g; attribution (card 3) finds which turns and tools dominate. A tool result trimmed from 10,000 tokens to 1,000 before it enters the history saves 9,000 tokens on every remaining turn, not once.
  6. Track two distributions per workload. Steps per run and input tokens per run, medians and 95th percentiles, before and after any change. The tail is where loops live and where the money goes.

What makes the loop worse

  • Large tool results. A tool that returns a 10,000-token document, or a search that returns twenty results, is paid for on every subsequent turn, not once. Tool output is the most common reason g is far larger than teams assume.
  • Verbose tool schemas. Thirty tools with long descriptions are part of P on every call; catalogues of several thousand tokens are routine.
  • Sub-agents that inherit history. A supervisor that forks its full context into each sub-agent multiplies the quadratic cost by the number of sub-agents.
  • Reasoning on every turn. Thinking tokens are billed as output on every step, and each step’s visible output then becomes input for the next.
  • Retries. A failed tool call retried with the same context pays the full context again.
  • Two-count instrumentation. Input and output only: the cache line and the thinking line are invisible, so the bill doubles “for no reason” when a reasoning model is switched on.
  • Capping thinking with max_output_tokens. A cap that cuts off thinking still bills the thinking and returns an incomplete result; lower the thinking level instead (card 3).
what the bill looks likeone number per month per project, split by model at best; nobody can say what a document costs, so the only lever anyone pulls is “use a cheaper model”.
what it should look likecost per step per workload from the trace, with the cache share and the thinking share visible, so the lever pulled is the tool result, the prompt order or the effort setting that actually moves it.

Pricing a call, and predicting a loop

from dataclasses import dataclass

@dataclass(frozen=True)
class Prices:            # $ per million tokens; illustrative, read from the vendor's price page
    input: float = 1.25
    cached: float = 0.125
    output: float = 10.0  # thinking is billed at this rate

def call_cost(u, p: Prices) -> float:
    """u carries the four counts; cached is a subset of input, so it is priced instead of, not on top of."""
    uncached = u.input - u.cached
    return (uncached * p.input + u.cached * p.cached + (u.output + u.thinking) * p.output) / 1e6

def loop_input_tokens(P: int, g: int, N: int) -> int:
    """Total input tokens over N turns when turn n sends P + g*n: the linear term plus the quadratic term."""
    return N * P + g * N * (N + 1) // 2

assert loop_input_tokens(8_000, 1_500, 10) == 162_500
assert loop_input_tokens(8_000, 1_500, 20) == 475_000

def carry_cost(introduced_tokens: int, step: int, total_steps: int) -> int:
    """Tokens a tool result at `step` is re-sent across the remaining turns: 5,000 at step 2 of 12 beats 20,000 at step 11."""
    return introduced_tokens * (total_steps - step)

assert carry_cost(5_000, 2, 12) == 50_000 and carry_cost(20_000, 11, 12) == 20_000

2 · How prompt caching works, and how to order a prompt so it does

Prompt caching lets a provider skip re-processing the part of a request it has already seen, and charge a fraction for it. It works on prefixes: the cached part must be byte-identical and must come first. Everything about using it well follows from that one constraint — the prompt is assembled from most stable to least stable, dynamic content goes last, tools are serialised in a fixed order, and history is compacted at checkpoints rather than on every call.

The mechanism, in one paragraph

When a transformer reads a prompt it computes, for every token, a pair of vectors per layer, the keys and values that later tokens attend to. That computation, the prefill, is the expensive part of processing input, and its result, the KV cache, depends only on the tokens read so far. If two requests begin with the same 12,000 tokens, the KV cache for those 12,000 tokens is identical, and a provider that kept it from the first request can start the second at token 12,001. The saved compute is what the discount reflects.

When explicit caching wins

An explicit cache earns its storage cost when the same large context is reused many times over a long window by many requests: a document corpus every agent in a session reads, a code repository under analysis, a long video. The break-even is the storage cost per hour against the input cost saved per request times requests per hour.

break-even requests per hour = storage price per token-hour ÷ (input rate − cached rate) · e.g. $4.50 ÷ ($1.25 − $0.125) per million ≈ 4 requests per hour illustrative rates

Below a few requests per hour against a moderate context, implicit caching or no caching is cheaper; the numbers are easy to compute from the trace data, which already carries the context size and the request rate per workload.

Making the cache hit, and proving it

  1. Assemble the prompt stable-first. System instructions, then tool definitions, then shared reference documents, then the history, then the latest tool result or user message. Anything dynamic (date, user id, request id, locale) goes into the last segment or into a message, never into the system prompt.
  2. Serialise tools in a fixed order. Sort by name once; never let a dict’s iteration order or a feature flag reorder the catalogue between calls.
  3. Stay above the minimum. Gemini’s implicit cache needs 2,048 tokens on 2.5 models and 4,096 on 3.x; a workload with a large system prompt and a hit ratio near zero is either below the minimum or rebuilding the prompt differently per call.
  4. Compact at checkpoints. Pruning and summarising history changes the prefix, so do it every k turns or at a context threshold, then let the cache rebuild once; never rewrite earlier turns on every call.
  5. Send similar requests close together. Implicit caches live minutes and are refreshed on use; a session’s turns naturally qualify, nightly batch jobs do not, which is where an explicit cache with a TTL belongs.
  6. Record the hit on every generation. cached_content_token_count into the span, cost priced at the cached rate, and the hit ratio per workload on the dashboard with an alert when it drops after a deploy.
  7. Decide explicit versus implicit from the trace. Context size × requests per hour against storage per token-hour; create a CachedContent only for the corpora that clear the break-even.

How caches are defeated

  • Dynamic content early. A date, a user id or a request id in the system prompt turns the whole prompt into a miss on every call; the hit ratio reads zero and the team concludes caching “does not work”.
  • Reordered tool definitions. Same tools, different order, different tokens; a miss from token 2,000 onward.
  • Mutating history. Summarising or rewriting earlier turns on every call rebuilds the prefix every call.
  • Below the minimum. Prompts under the provider’s threshold are never cached, whatever their order.
  • Expecting caching to halve the bill. It attacks the input line only; output and thinking are untouched, and in a reasoning-heavy step those are the bill.
  • Explicit caches for everything. Storage per token-hour on a corpus used twice an hour costs more than it saves.
  • Invisible hits. Instrumentation that does not record the cached count cannot price the discount or alert on its loss.

Assembling the prompt stable-first, with a fixed tool order

def build_request(system: str, tools: dict, docs: list[str], history: list[dict], latest: dict, *, now: str) -> dict:
    """Order: [1] system  [2] tools (sorted by name)  [3] shared documents  [4] history  [5] the new message with anything dynamic."""
    tool_decls = [tools[name].schema for name in sorted(tools)]           # never a dict's iteration order
    contents = [{"role": "user", "parts": [{"text": d}]} for d in docs] + history
    contents.append({"role": "user", "parts": [{"text": f"[{now}] {latest['text']}"}]})   # the date lives here, not in `system`
    return {"system_instruction": system, "tools": [{"function_declarations": tool_decls}], "contents": contents}

3 · Shortening reasoning loops, and finding what consumes the most

A loop is shortened in two directions, fewer turns and less context per turn, and the levers are ordered by how much they usually save: budgets the runtime enforces, thinking effort set per step, a plan written once, tool results compacted before they enter the history, history pruned at checkpoints, smaller outputs, routing by difficulty, parallel tool calls and a stop condition that fires. Cost is then found the way latency is found: attributed to the span that incurred it and sorted. The precondition is that every model call is its own span with its usage recorded.

The carry cost is the quadratic multiplier made visible, and it reorders the fix list: a 5,000-token result at step 2 of a 12-step run costs more than a 20,000-token result at step 11.

The detection recipe

  1. Sort yesterday’s traces by total cost; open the top ten.
  2. List each trace’s generations in order with input, cached, output and thinking tokens. The pattern names the problem: input growing by a large constant each step means a large tool result in the history; thinking dominating means the effort level is too high for the step; many generations with small inputs means a loop.
  3. For the generation with the largest uncached input, find which message segment is large. The tool observation immediately before it, with its output token count, is the usual answer.
  4. Compute the cache hit ratio per generation. Zero after the first turn means the prefix is not stable (card 2).
  5. Compute, per tool, tokens introduced × turns that followed: the carry cost. Fix the tools in that order.
  6. Compare steps per run and input tokens per run against the workload’s 95th percentile. Runs beyond it are candidates for a tighter budget or a missing stop condition.

Recording cost where it happens

Each model call becomes an observation carrying the model name, the four token counts and the dimensions needed to roll it up: workload, agent, sub-agent, step index, the tool that preceded it and the prompt version. In Langfuse these are generation observations with usage_details and, if the model is in its pricing table, computed cost_details; the model name must match a model definition for the price to apply. In OpenTelemetry the same data is a span with gen_ai.usage.input_tokens and gen_ai.usage.output_tokens plus the gen_ai.client.token.usage metric split by token type, which Cloud Monitoring or any Prometheus-compatible backend aggregates. The attribute most teams forget is the size of each tool result: without it, “which tool is inflating the history?” cannot be answered from the trace.

Alerts that catch it early

Three alerts cover most cost incidents: a workload’s daily spend exceeding its moving average by a threshold; steps per run or input tokens per run crossing the workload’s 95th percentile for a sustained period; and the cache hit ratio dropping after a deployment. Each names the workload owner and links to the sorted-traces view, because the alert says that something changed and the trace says what.

Where loops and bills go wrong

  • Budgets in the prompt. “Use at most ten steps” is a request; a counter in the runtime is a rule. An agent that usually stops is an agent that sometimes does not.
  • Effort per agent, not per step. The planner’s high effort applied to tool-argument extraction; thinking becomes the bill.
  • Capping thinking with max_output_tokens. The thinking is billed anyway and the result comes back incomplete; lower the level instead.
  • Unbounded reflection. The most common source of loops that run to the budget; one self-review, capped, with explicit criteria.
  • Compaction on every call. It rebuilds the cache prefix every turn (card 2); compact at checkpoints and emit the event so a confused agent can be traced to a lossy summary.
  • Observation names that vary. tool:search:2026-10-19T09:14 cannot be grouped; verb-first stable names can.
  • No tool output sizes. The carry-cost cut is impossible and the biggest lever is invisible.
  • Retrying with the full context. A failed call retried unchanged pays the whole context again; retry only idempotent operations, bounded.

The budget, and the script that ranks carry cost

A budget the runtime enforces

from dataclasses import dataclass, field
import time

@dataclass
class Budget:
    max_steps: int = 12
    max_cost_usd: float = 0.50
    max_seconds: float = 120.0
    steps: int = 0; cost: float = 0.0; started: float = field(default_factory=time.monotonic)

    def charge(self, usage, prices):
        self.steps += 1
        self.cost += (usage.input * prices.input + usage.cached * prices.cached
                      + (usage.output + usage.thinking) * prices.output) / 1e6
        if self.steps > self.max_steps or self.cost > self.max_cost_usd \
           or time.monotonic() - self.started > self.max_seconds:
            raise BudgetExceeded(steps=self.steps, cost=self.cost)   # caught by the loop: partial result + status + trace event

from collections import defaultdict

Designing the trace before the first production run

  1. One trace per turn or per autonomous run, rooted in an invoke_agent span carrying gen_ai.agent.name and gen_ai.conversation.id; sub-agents as nested invoke_agent spans.
  2. One span per model call, tool call, retrieval and hand-off, named operation-first (chat gemini-2.5-pro, execute_tool retrieve_documents) with stable, verb-first step names that never embed runtime values.
  3. Usage on every generation: input, output, and the cached and thinking counts under one documented mapping; the prompt version and the step index as attributes.
  4. Size and status on every tool span: error.type on failure, output token count on success, the input the model actually sent.
  5. Content as events, gated by data tier. gen_ai.input.messages and gen_ai.output.messages only where the workload’s classification allows, never globally.
  6. Events for what nothing records for you: budget breaches with the counts at the time, compaction and pruning with before and after, retrieval filters and the number of results trimmed by access control, the human-approval decision and who made it, the cache hit ratio.
  7. Propagate context into every remote tool so its spans join the trace; put the trace id in the audit log of every data access.
  8. Aggregate from the two metrics for dashboards and alerts; keep traces for the questions aggregates cannot answer.

Traces that cannot answer the question

  • Content capture on everywhere. The backend becomes a store of user data; the flag is set per workload tier, never globally.
  • No error.type on tool spans. A failure caught and returned as a string produces a span with status OK and a confident wrong answer after it (card 6).
  • No conversation id. The wrong identifier was introduced three turns earlier and the session view cannot be assembled.
  • Names that vary at runtime. Step names with timestamps or ids in them cannot be grouped, so cost by step and latency by step are impossible.
  • High-cardinality attribute keys. One key per user or per document; keys are low-cardinality, values are free.
  • Thinking and cached counts in three different places. The mapping lives in one module or nobody can reconcile the bill.
  • A remote tool outside the trace. Without traceparent on the request, the tool’s database and HTTP children are invisible and its latency is a black box.
  • Reconstructing outputs later. If the span never recorded the tool’s output and size, no trace tool can show it afterwards.

Instrumenting an agent, in order

  1. Decide content capture per workload tier first. It decides whether the trace store holds user data, and it is set in one place: OTEL_INSTRUMENTATION_GENAI_CAPTURE_MESSAGE_CONTENT true for low-tier workloads, false otherwise.
  2. Initialise the tracer provider once (Langfuse’s client does it; or a TracerProvider with a BatchSpanProcessor and the exporter of choice) and auto-instrument the model SDK (GoogleGenAiSdkInstrumentor, the Vertex AI instrumentation) so every model call is a generation span.
  3. Wrap the loop in an agent span and each tool in a tool span. Stamp user, session, tags and the prompt version with propagate_attributes; record the four counts on each generation; record error and output size on each tool.
  4. Propagate context into remote tools with propagate.inject(headers) so their spans join the trace, and accept it on the way in.
  5. Add a redaction span processor before the exporter where content capture is on: regex plus a DLP client for the classes that matter; the model saw the real data, the trace store never does.
  6. Emit the events nothing emits for you: budgets, compaction, approvals, retrieval filters, cache ratio.
  7. Choose the exporter: Langfuse’s endpoint, the Google telemetry endpoint, or a Collector sidecar that holds the credentials and fans out to both.
  8. In production replace bearer tokens with the Google Cloud OTLP exporter’s auth or the Collector; the application exports plain OTLP to the sidecar.

What goes wrong between the code and the dashboard

  • Keys in code. LANGFUSE_SECRET_KEY or a bearer token in a file; they come from the secret store, and in production the exporter’s auth or a Collector sidecar holds them.
  • Capture decided globally. One flag for every workload means the trace store holds data from the one that should never have been captured.
  • Swallowed tool errors. except Exception: return "Error: …" produces OK spans and a wrong answer; re-raise after recording.
  • No output size on tools. Truncation and carry cost become invisible.
  • Model names that do not match a model definition. Langfuse cannot price the generation; cost reads zero and nobody notices.
  • Large or multimodal content in log entries. Google’s guidance is Cloud Storage for those, with a reference on the span.
  • Telemetry turned on, conventions not opted in. Old attribute names in the spans and an empty generative-AI view in Trace Explorer.
  • Treating the backend choice as a rewrite. It is an exporter line; the decision can be revisited and both can run.

6 · Troubleshooting case: the dataset exists, the agent says it does not

The agent answers “I could not find a dataset called finance_2026”, and the dataset is right there in the console. The temptation is to edit the prompt. The right move is to open the trace, because the model’s sentence is the last step of a chain, and the fault is almost never in the last step. Six checks, each a span attribute, each with its fix; most cases end at check one or two.

the durable fixes
a resolver tool that returns ids the system produced; typed exceptions that distinguish “could not check” from “found nothing”; output sizes on every tool span; the case added to the evaluation set

Six checks read off the trace, each with its fix

Why a trace tool is the right instrument

Every check is a query over spans: existence of a span by name, an attribute value, an input, an output size, a flag. In Langfuse the trace view shows the tree with each observation’s input, output, metadata and level, and the session view shows the turns before the failure, which matters when the wrong id was introduced three turns earlier. The Google Cloud equivalent is Trace Explorer with the span details panel (card 5). What neither can do is reconstruct a tool’s output after the fact if the span never recorded it, which is why card 5’s instrumentation records outputs and sizes even when content capture is off for prompts.

What the model should be told, by outcome

what the wrapper said"Error: dataset not found" — the same string for a 403, a 404, a timeout and an empty page; the model relays it faithfully and the trace reads OK.
what it should sayLookupFailed(kind="permission", retryable=False) → “I could not check whether finance_2026 exists because this agent lacks access; escalating”. NotFound → “no dataset with that id in proj-eu/EU; candidates: finance_2026”.

The procedure

  1. Reproduce with the trace open. Content capture on for this one trace, in a test environment if production forbids it. Find the invoke_agent span.
  2. Check 1: did the agent call the tool at all? Look for an execute_tool span for list_datasets or get_dataset. None means the model answered from its sense of what exists. The fixes are structural, not prompt wording: the tool description as the only source of truth, instructions that forbid answering about data without it, a forced tool call on the first step where it matters, a trimmed tool list, and the case in the evaluation set.
  3. Check 2: did the tool fail, and how? error.type on the span. 403 is identity (the service account lacks bigquery.datasets.get, the dataset’s IAM omits it, or a VPC Service Controls perimeter rejects the call from where the agent runs); 404 is address (project, location, id). The agent’s identity is in gen_ai.agent.id or the runtime’s logs; the request parameters are in the span’s input.
  4. Check 3: were the arguments right? The span’s input shows what the model actually sent: display name for id, wrong case, wrong project, a defaulted region. The durable fix is a resolver tool so the lookup is always called with an id the system produced.
  5. Check 4: was the result empty or cut off? Read the output and its size: the first page of fifty, a wrapper truncation, an empty list where a raise was due.
  6. Check 5: was the error swallowed? A successful tool call followed by a confident wrong answer is the signature. The rule: tools raise typed exceptions, the runtime records them with error.type, and the message to the model distinguishes “the lookup failed because of permissions” from “the lookup succeeded and found nothing”.
  7. Check 6: was the result stale? A cache-hit flag or a timestamp on the entry. A time to live appropriate to the data and a cache key that includes the identity.
  8. Then the prompt. If every check passes, it is a reasoning failure; the fix is usually to reduce what the model had to read rather than to add instructions. Record the case in the evaluation set either way.

How the investigation goes wrong

  • Editing the prompt first. The most common cause is the model not calling the tool, and the fix for that is the tool’s description, a forced call and a smaller catalogue, not another paragraph of instructions.
  • Reading the 403 as a bug in the tool. BigQuery does not reveal the existence of resources the caller may not read; “does not exist” is what correct security looks like from the agent’s side.
  • Letting the model spell identifiers. It saw the display name in prose and typed it; identifiers come from a resolver.
  • Trusting a status-OK span. The error was turned into a string two layers down; the trace needs error.type to tell failure from absence.
  • A cache keyed without identity. One user’s empty listing served to another is both a correctness and a confidentiality bug.
  • No output sizes recorded. Truncation at exactly the wrapper’s cap is invisible without output_tokens.
  • Fixing the case without a test. Card 11’s trajectory check (“did it call read_contract?”) is check 1 turned into a gate.

def find_dataset(name_fragment: str, creds=None) -> list[dict]:
    """Candidate datasets across the projects this agent serves, with project and location: the only input get_dataset accepts."""
    out = []

Typed errors, and what the model is told

class ToolError(Exception):
    kind: str = "unknown"; retryable: bool = False

class LookupForbidden(ToolError):  kind = "permission"     # 403: could not check
class LookupNotFound(ToolError):   kind = "not_found"      # 404: checked, nothing at that address
class LookupTimeout(ToolError):    kind = "timeout"; retryable = True

def get_dataset(dataset_id: str, project: str, creds=None) -> dict:
    try:
        d = bigquery.Client(project=project, credentials=creds).get_dataset(f"{project}.{dataset_id}")
    except Forbidden as e:      raise LookupForbidden(str(e)) from e
    except NotFound as e:       raise LookupNotFound(str(e)) from e
    return {"id": d.dataset_id, "project": project, "location": d.location, "tables": len(list(d.list_tables()))}

7 · Agentic patterns of interaction, and the Agent2Agent protocol

An agentic system is a small number of patterns composed. Naming them matters because each has a known cost profile, a known failure mode and a known test strategy, and because the first design decision, workflow or agent, is a decision about how much control flow the model owns. When agents are separately hosted, by different teams, in different runtimes or organisations, they need a wire protocol; A2A is that protocol, and the split is worth stating plainly: MCP connects an agent to tools and data, A2A connects an agent to other agents.

if you can draw the flow on a whiteboard, build the workflow; if you cannot, build the agent and bound it; a single agent before a multi-agent system

Workflows versus agents

workflowcontrol flow written by an engineer in which model calls are steps: predictable, testable step by step, cheap, because each step sees only the context it needs rather than the whole history.
agentcontrol flow chosen by the model at runtime from the tools it has: handles inputs the engineer did not anticipate, at the price of being tested statistically rather than deterministically and costing more per task.

Operations are SendMessage and GetTask, over JSON-RPC, gRPC or HTTP+JSON bindings that are functionally equivalent. SendMessage blocks until a terminal or interrupted state unless returnImmediately is set. Clients send an A2A-Version header; an absent header is treated as version 0.3.

The supervisor’s rules, applied

isolate worker context

a worker receives a task description and the inputs it needs, not the supervisor’s history; Deep Agents runs sub-agents isolated by default, with a fork mode that inherits history for the cases that need it.

narrow worker tools

each worker has the tools its job needs and no others: a cost and a security measure.

structured reports

workers return a schema the supervisor reads cheaply, not prose it re-reads every turn.

budget the supervisor separately

supervisor loops are the expensive ones; cap its steps and treat a worker’s failure as a reportable event, not a reason to retry blindly.

co-locate by default

workers in the same process share state cheaply; split one into its own hosted agent only for independent scaling, a separate security boundary or reuse by other applications, then talk to it over A2A.

Choosing, one addition at a time

  1. Start with a single agent or a workflow. Draw the flow; if it can be drawn, it is a workflow.
  2. Add routing when requests are heterogeneous. A small model, a fixed label set, cost tiering falls out.
  3. Add workers when tool sets or contexts naturally separate, co-located, with isolated context and structured reports.
  4. Add an evaluator loop when there is an objective acceptance test, capped at one or two rounds.
  5. Add a human interrupt wherever a side effect’s blast radius warrants it (card 8, principle 10).
  6. Add A2A when an agent must be reused across applications, scaled independently or operated by someone else. The remote agent authenticates with the scheme its card declares, gets its own identity and quota on the receiving side, and is reached through the gateway so the policies that govern model and tool calls govern agent calls too (card 13).
  7. Across the A2A boundary, run it like any remote dependency. Trace context in the request so its spans join the trace; timeouts; retries only for idempotent messages; INPUT_REQUIRED and AUTH_REQUIRED handled as first-class states rather than errors.
  8. Test each pattern the way it fails. Workflows step by step; agents statistically against a golden set; routers on a labelled set; evaluator loops on round counts; supervisors on hand-off counts and worker failures.

The failure modes, by pattern

  • Multi-agent first. A supervisor and five specialists for a task a single agent with six tools would do; every hand-off is a place to fail and a line on the bill.
  • Context inheritance. A supervisor that forks its history into each worker multiplies the quadratic cost by the number of workers.
  • Prose reports. Workers that return paragraphs the supervisor re-reads on every turn.
  • Uncapped evaluator loops. Refinement forever, or an evaluator that agrees with the generator because the criteria are vague.
  • Stale plans. A planner-executor that follows the plan after the world changed; revise at failures and checkpoints.
  • Approval fatigue. A human interrupt on every action trains the human to click approve.
  • A2A as the default. Separately hosted agents for workers that could share a process; discovery, trust and partial failure added for nothing.
  • Treating INPUT_REQUIRED as an error. The remote agent asked a question; that is the protocol working.
  • A remote agent outside the gateway. It is an external caller and callee; it needs its own identity, quota, sanitisation and trace propagation like any client.

Running the review

  1. Ask where each rule is enforced. For every principle, point at the code, schema, identity or gate. A sentence in a prompt is a request, not a rule.
  2. Classify every tool. Read-only, reversible, irreversible-internal, external-or-money; write the class into the registry and let the runtime derive the gate from it.
  3. Trace one failing run before approving. If the trace cannot show the tool’s input, error type and output size, principle 6 is not met and principles 7 and 9 cannot be checked.
  4. Find the state. Everything the agent knows that is not in the prompt should have a name and a place; if a crash loses it, principle 3 is not met.
  5. Check the identity chain. The agent’s own identity, the user’s identity carried downstream where entitlements differ, no credential in a prompt, environment file or tool argument.
  6. Demand the golden set. Even twelve cases; it grows from production. A change with no evaluation evidence is a change that does not ship.
  7. Read the user’s side. Is it told it is an agent, does it see progress and citations, can it reach a person.

Where designs fail the principles

  • The prompt as the runtime. Budgets, allow-lists and stop conditions written as instructions; the sometimes they are ignored is where incidents and bills live.
  • Hidden state in a long prompt. State that cannot be inspected, resumed or trimmed.
  • Silent degradation. A plausible answer after a failure the agent did not surface: the worst outcome, and the one most designs permit by default.
  • Retrying non-idempotent tools. A second notice filed, a second charge made.
  • Credentials in tool arguments. The model is now a party to the secret and the trace is too.
  • Model changes by alias with no evidence. “We moved to the new model” with no golden-set run before and after.
  • Approval on everything. The interrupt that fires on every action trains the approver to click through; the gate belongs above the threshold only.
  • Confident fabrication to the user. No citation, no uncertainty, no path to a human; a governance obligation in regulated settings and bad product everywhere.

def gate(spec: ToolSpec, call) -> None:
    """Runs before every tool call; the runtime decides, the prompt never does."""
    if spec.blast == Blast.EXTERNAL_OR_MONEY:
        raise ToolRefused("prepared for a person, never taken by the agent")
    if spec.blast == Blast.IRREVERSIBLE_INTERNAL:
        approval = request_approval(call, timeout_s=24 * 3600)       # the runtime's interrupt; the run checkpoints and waits
        if not approval.granted:
            raise ToolRefused(f"declined by {approval.by}")
        trace_event("approval", by=approval.by, tool=spec.name, args=call.args)
    if not spec.idempotent and "idempotency_key" not in call.args:
        raise ToolRefused("non-idempotent tool called without an idempotency key")

9 · Latent reasoning for agentic workflows, built with the Deep Agents SDK and Google ADK

Latent reasoning is the reasoning an agent does that the user never sees: the model’s internal thinking before it answers or acts, the plans and notes it keeps in working memory, and the self-critique it runs before committing. It is latent in the sense of hidden, not absent; it is where most of an agent’s quality and most of its hidden cost come from. Three kinds, each with a place it lives, a cost and a control, and the same portfolio-review agent built twice to show where each kind goes.

thinking tokens
inside the model, before the visible output of one call; billed as output; controlled per call by thinking_level (Gemini 4: LOW · MEDIUM · HIGH) or a numeric thinking_budget on 2.5 models; thought summaries for debugging, read from the trace
plan and scratchpad
the agent’s state: a numbered plan, notes, intermediate results; input tokens on later turns, once written; controlled by the planning tool and the state design
reflection
a separate pass that critiques a draft or a trajectory against concrete criteria; a second generation plus a judge; a capped evaluator-optimiser loop
the fourth kind
reasoning carried in continuous latent vectors rather than tokens exists in research and trades interpretability for efficiency; not something an application developer builds today

When each pays

thinking: the few steps that need judgement

high for planning and for steps that synthesise across many inputs; low or minimal for classification, extraction and tool-argument formation; off for steps that are deterministic in all but name. Thought summaries are the best debugging aid an agent has when a step goes wrong.

plans: reasoning that happens once

fewer turns because the agent does not re-decide what to do; cheaper turns because execution needs low effort; a progress indicator for humans; a checkpoint structure for resumability. The cost is a plan that goes stale, so it is revised at failures and checkpoints rather than followed blindly.

reflection: reasoning about the result

works when the criteria are concrete: tests that must pass, a rubric, a schema, a citation requirement; fails, by looping or by agreeing with itself, when they are vague. One pass, explicit criteria, capped, is the production setting.

Choosing the mix

  1. Set thinking per step, not per agent. High on the planner and on synthesis across many inputs; low or minimal on classification, extraction and tool-argument formation; off where the step is deterministic in all but name. Lower the level rather than cap max_output_tokens.
  2. Use a plan whenever a task has more than a handful of steps or a human will watch it. Numbered steps in state with pending, in-progress and completed; revise at failures and checkpoints.
  3. Put findings in working memory, not in the conversation. Files or state the agent reads back selectively; the history carries references.
  4. Use reflection when there is an objective check to reflect against, once, capped: a LoopAgent with max_iterations, an evaluator that can escalate, or one more todo item (“review findings against the rubric before filing”).
  5. Isolate sub-agents. Fresh context and a narrow tool set per worker; fork only when inheriting history is the point.
  6. Gate the side effect. interrupt_on for the one tool that files, sends or applies.
  7. Measure all three in the trace. Thinking tokens per step, plan revisions per run, reflection iterations per run; thought summaries for debugging, read from the trace and never shown to users.

Where hidden reasoning turns into hidden cost

  • High effort everywhere. The planner’s setting applied to twelve extraction calls; the thinking line becomes the bill (card 1).
  • Re-deriving the plan every step. A loop that decides what to do next on every turn pays thinking tokens each time and takes more turns.
  • A plan followed blindly. The world changed at step four; the plan is revised at failures and checkpoints, not obeyed.
  • Reflection against vague criteria. “Is this good?” loops or self-agrees; “does every finding cite a clause?” converges.
  • Uncapped loops. The reflection cap is the stop condition; without it the run ends at the budget.
  • Findings in the conversation. Sixty contracts of findings re-sent on every turn instead of read back from files when needed.
  • Showing thought summaries to users. They are a debugging aid read from the trace; the user gets progress and citations instead.
  • Mistaking the research kind for the production kind. Continuous latent-vector reasoning is not something to build today; in production the term means the three kinds above.

10 · LLM-as-a-judge: purpose, construction, criteria, scoring, and the maintenance manual

An LLM-as-a-judge is a model prompted to assess another model’s output against stated criteria and return a verdict. Its purpose is to scale human judgement: a few hundred expert labels teach a judge that then scores a hundred thousand outputs, every day, consistently. It is not a replacement for human judgement; it is a compression of it, and it is only as good as the human judgement it was calibrated against. A judge is a measurement instrument: biased in known ways, drifting, and calibrated against something more trustworthy than itself.

anatomy
task definition · the inputs the criterion needs · a precise rubric with the hard cases · a reasoning instruction · a structured output with reasoning first and verdict last
the contract
temperature zero · one criterion per judge · binary where possible · a different model family from the one under test · a fixed prompt version on every score · agreement with human labels measured and published
three deployments
offline in the pipeline against a golden set (gates a release) · online asynchronously over sampled traces (drift) · inline synchronously in the request path (one failure that must never ship: small, fast, binary, a timeout)
the loop
calibration set with critiques → accuracy, Cohen’s κ, FAIL recall → read every disagreement → edit the rubric, not the verdicts → re-measure → version and re-baseline

Scales, and sync versus async

Binary pass/fail is the default: easiest to label consistently, to aggregate (a pass rate) and to act on (a gate). Likert scales with anchored descriptions per level are used when degrees matter, but judges cluster at the top and humans disagree on the middle, so a 5-point scale is often reported as a pass rate at a threshold anyway. Pairwise preference with a tie option is the scale for ranking. Probabilities route borderline cases to human review. Whatever the scale, scores are aggregated per criterion, reported with the sample size and the judge’s measured agreement, and compared against the previous version’s baseline, not an absolute number alone. Asynchronous judging is the default and can use the strongest judge; synchronous judging sits in the request path for the one failure that must never ship, with a small fast model, one criterion, a binary verdict and a strict timeout. A groundedness check before returning a cited answer is a typical synchronous judge; a style score is never one.

Several bodies of practice converge: the MT-Bench and Chatbot Arena work found that strong models agree with human preferences at roughly the rate humans agree with each other and named the biases to control for (position, verbosity, self-preference); G-Eval established reasoning before a form-filled score; Anthropic’s and OpenAI’s published guidance both favour many small, binary, criterion-specific judges over one holistic score, with rubrics written by the people who own the task; Google’s evaluation service formalises pointwise and pairwise metrics, adds rubric-based evaluation, and ships tooling to evaluate the judge itself against a human-rated benchmark.

Judging a conversation, at two levels

A conversation is not a list of answers. Each turn is correct or not relative to everything before it, and the conversation as a whole succeeds or fails at a goal no single turn contains.

turn level, in contextthe judge receives the history and the latest turn and judges the latest turn only, against the usual criteria plus two conversational ones: did it correctly use what the user said earlier (context use), and was it the appropriate next move (a clarifying question when the request was ambiguous, not when it was clear).
conversation levelthe judge receives the whole transcript and judges the outcome: goal achieved (task completion); turns taken against turns needed (efficiency); persona and policy held throughout (consistency); escalated when it should and not when it should not (escalation correctness); repetition or looping; anything unsafe at any turn.

Simulated users, and sampling production

Multi-turn evaluation needs conversations, and real ones are scarce and sensitive. A simulated user, a model given a persona, a goal and a behaviour profile (cooperative, vague, frustrated, adversarial), drives the system through a conversation, and the transcript is judged. Simulations cover the long tail production has not produced yet; they are generated from the same scenario list the golden set uses, and reviewed by humans before they are trusted, because a simulator that is too agreeable makes every assistant look good. Online, whole sessions are sampled rather than individual turns, redacted and judged at both levels; the session is the unit of drift. Langfuse’s sessions and Agent Runtime’s session view make that sampling possible, and the evaluation service supports multi-turn inputs for its model-based metrics.

Building, improving, and embedding expert knowledge

  1. Write the five parts. Task definition; exactly the inputs the criterion needs and nothing else; a rubric with pass and fail stated and the subtle boundary illustrated; an explicit instruction to analyse before deciding; a structured output with reasoning and evidence first, the verdict last.
  2. Sign the contract. Temperature zero; one criterion per judge; binary where possible; a different model family from the one under test; the prompt version on every score.
  3. Build the calibration set. A few hundred items labelled by the people who own the task, each with a one-line critique; the critique is what makes labels teachable.
  4. Measure. Accuracy against the labels, Cohen’s κ to correct for chance, precision and recall of FAIL specifically. Report these numbers with the judge’s scores forever after.
  5. Read every disagreement. They cluster: a rule the rubric did not state, a boundary the humans handle one way and the judge another, a formatting pattern that confuses it.
  6. Edit the rubric, not the verdicts. Add the missing rule, a worked example of the boundary case, a tighter definition; two or three few-shot examples per failure mode from the critiques is usually enough.
  7. Re-measure; version; re-baseline. If agreement does not rise, the criterion may be one humans do not agree on, which step 3’s inter-rater agreement reveals. Old scores are not compared with new.
  8. Embed the experts. Experts write the rubric in their words before an engineer edits it for the model; worked examples carry the tacit rules; checklists for completeness; reference answers where they exist; inter-rater agreement as the ceiling; active learning (low-confidence and disagreement cases route to experts); production feedback (escalations, corrections, deserved thumbs-down) becomes calibration items with the reason attached.

Pairwise with the position swap: a preference counts only if it survives

def judge_pairwise(question: str, a: str, b: str) -> str:
    """Returns "A", "B" or "tie". Each order is judged once; disagreement between the orders is a tie."""
    first  = _pairwise_once(question, a, b)          # "first" | "second" | "tie"
    second = _pairwise_once(question, b, a)          # swapped
    if first == "first" and second == "second": return "A"
    if first == "second" and second == "first": return "B"
    return "tie"                                     # position bias, or a real tie: either way, not a preference

Standing up the gate

  1. Build the dataset from traces. Sample whole sessions from Cloud Trace or Langfuse, redact, have the task’s owners label with a critique; columns prompt, context, reference, and for pairwise runs the production version’s answers as baseline_model_response.
  2. Pick metrics per criterion. Google’s pointwise templates where they fit, your own template with card 10’s rubric where they do not, computation metrics for references, rubric-based for instruction following, trajectory metrics for the agent.
  3. Record scenarios as an evalset. From the developer UI’s recorded sessions or by hand; one scenario per arrow of the design, with the expected trajectory, and card 6’s case among them.
  4. Tie the run to an experiment. EvalTask(experiment=…) with a run name carrying the prompt version; runs compared across versions, never against an absolute number alone.
  5. Put the thresholds in the workload’s manifest. Blocking asserts after task.evaluate; adk eval --config_file_path for the trajectory and response thresholds; both from pytest so the same gate runs on every pull request.
  6. Calibrate the judge with the service’s tooling. The human-labelled set as the benchmark; refine the judge prompt or bring a tuned judge; publish the agreement with the scores.
  7. Backfill when the rubric changes. Batch evaluation over the golden set with the new rubric version, then re-baseline.

Evaluation that does not gate anything

  • A golden set with no critiques. Labels without reasons cannot teach a judge or settle a disagreement.
  • Response-only metrics on an agent. The right sentence produced without the lookup passes; the trajectory metric is what catches it.
  • Absolute thresholds with no baseline. 4.2 means nothing without the production version’s 4.31 beside it; pairwise against the baseline is the honest comparison.
  • Google’s templates used unread. They are a starting point; the rubric still needs the hard cases the task owners know.
  • Calibration items in the evaluation set. Agreement inflated; keep them disjoint.
  • Evalsets that never grow. The twelve scenarios from launch week; every incident should add one.
  • Rubric edits without a version. Old and new scores compared as if the instrument had not changed.
  • The gate on a laptop. If it is not in CI on every pull request, it is a demo.

12 · Authorisation for agents: who the agent is, and what it may touch

Authorisation for an agent answers two questions on every tool call: as whom is this call made, and what may that identity see or change. The model never answers either; the runtime and the data platform do. On Google Cloud the answers are built from IAM, BigQuery’s row- and column-level controls, VPC Service Controls, and a disciplined choice between the agent’s own identity and the user’s. The question to ask of any design is the same: if the model is tricked into asking for everything, what does the infrastructure allow it to get?

Confining an agent, in order

  1. Give the agent its own identity. Workload Identity on GKE, the service identity on Cloud Run, identity_type=AGENT_IDENTITY on Agent Runtime; no key files, no long-lived credentials.
  2. Decide the model of acting per tool. Autonomous work runs as the agent; anything serving people with different entitlements runs on behalf of the user, with the user’s token or impersonation under an IAM condition that scopes what can be impersonated.
  3. Grant dataset-scoped roles, dataViewer on the datasets served and jobUser on the project; nothing project-wide, nothing that writes.
  4. Write the row access policies: one for the service account’s slice, one keyed to SESSION_USER() for users.
  5. Tag the sensitive columns and do not grant the Fine-Grained Reader role; add masking where the row is needed without the value.
  6. Expose authorised views for shaped subsets and grant the view, not the table.
  7. Draw the perimeter and write the ingress and egress rules by name.
  8. Bound the tool: SELECT only, maximum_bytes_billed, max_results, a timeout, a dataset allow-list, job labels for cost and audit.
  9. Test it adversarially in CI. A cross-tenant test: a prompt that asks for everything, run as each identity, asserting the rows and columns that come back; and a test that the agent cannot see the dataset it must never see.

How agents end up seeing too much

  • Project-wide roles. dataViewer on the project because it was quicker; every dataset is now one injection away.
  • Acting as the agent for everyone. The agent’s permissions become the union of its users’ needs instead of the intersection; the account manager sees the region.
  • Key files and long-lived tokens. In an environment file, in a prompt, in a tool argument; short-lived tokens from the metadata server are the only form.
  • Row policies without the service account. A principal outside every policy sees no rows, which reads as “the dataset is empty” to the agent (card 6).
  • Trusting the tool to filter. A filter in the SQL the model writes is not a control; a row access policy is.
  • A cache keyed without identity. One user’s result served to another.
  • No labels on jobs. The audit log names the principal but not the run; the join to the conversation is lost.
  • No cross-tenant test. The design is correct until the next grant; the CI test is what keeps it correct.

from google.cloud import bigquery
from google.oauth2.credentials import Credentials

def query_bigquery(sql: str, user_access_token: str | None, max_bytes: int = 2_000_000_000) -> list[dict]:
    creds = Credentials(token=user_access_token) if user_access_token else None   # None -> ambient agent identity
    client = bigquery.Client(project=PROJECT, credentials=creds)
    if not sql.lstrip().upper().startswith("SELECT"):
        raise ToolRefused("read-only tool")                       # DML/DDL never reaches the warehouse
    job = client.query(sql, job_config=bigquery.QueryJobConfig(
        maximum_bytes_billed=max_bytes,                              # a cost budget per query
        use_query_cache=True, labels={"workload": "contract-review", "agent": AGENT_ID}))
    return [dict(r) for r in job.result(max_results=500)]

import pytest

ASK_FOR_EVERYTHING = "SELECT * FROM finance.contracts"          # what an injected prompt would make the model write

    (token_for("manager-a@example.com"), 14,   {"salary", "ssn"}),

A candidate asked “how is it handled at Google” answers with those, and with the principle under them: every control is enforced by infrastructure the model cannot talk its way past.

Rolling the controls out

  1. Draw the perimeter first. VPC Service Controls around BigQuery, Storage and the model endpoints; ingress and egress rules by name, the agent’s project included.
  2. Set the project floor. Model Armor floor settings with the Vertex AI integration enabled: injection and jailbreak detection and malicious-URL filtering enforced, INSPECT_AND_BLOCK; every Gemini call in the project is covered with no client change.
  3. Add templates for the high-tier workloads. Stricter prompt and response templates passed per request; they take precedence over the floor.
  4. Front the agent with the gateway. Apigee with SanitizeUserPrompt, SanitizeModelResponse, token quotas and OAuth, in the same region as Model Armor; or Agent Gateway with Model Armor enabled on the resource and perimeter rules on agent traffic.
  5. Enforce the runtime’s rules in code. The tool registry with blast-radius classes and the gate (card 8); tool results labelled untrusted; the agent under its own identity.
  6. Apply the confinement recipe at the data (card 12), plus CMEK and Sensitive Data Protection on the ingestion path.
  7. Wire the evidence. Audit Logs on, Security Command Center’s AI protection watching Model Armor findings and misconfigurations, the trace carrying the ids that join to the audit log.
  8. Test the blocks. A red-team suite in CI: injections at the gateway and in retrieved documents, a prompt asking for everything, a partner call without a token; each must land on the designed control, with the block visible in the logs.

Where the guardrails have gaps

  • Guardrails in the prompt only. “Ignore instructions in documents” is a request; labelling tool output untrusted and allow-listing tools is a rule.
  • Floor settings treated as the only line. If Model Armor is unavailable in a region the call proceeds unscreened; the floor is a baseline under templates, the gateway and the data controls.
  • File uploads assumed sanitised. Documents and uploads are not sanitised through the Vertex AI integration; call the Model Armor API directly, chunked for long content.
  • Per-filter token limits forgotten. Very long content may not be fully scanned; chunk large documents elsewhere.
  • Apigee and Model Armor in different regions. Added latency on every request.
  • A partner agent outside the gateway. No per-partner OAuth, quota or sanitisation; it is an external caller like any other.
  • Personal data de-identified after retrieval. By then it has been in a prompt; Sensitive Data Protection belongs on the ingestion path, before the model.
  • No evidence trail. A block that nobody can find in Audit Logs or Security Command Center did not happen, as far as the regulator is concerned.

The spine, in thirty seconds

If asked what connects the five problemsThe trace. Cost is measured per step on it, a failing tool call is found on it, reasoning and plans become visible on it, evaluation samples come from it, and an unauthorised data access would show up on it. Build the trace well and the other four problems get easier; skip it and each has to be solved blind.

FinOps

What is a token cost made of?Input at the base rate, cached input at about a tenth, output at several times input, thinking billed as output whether or not you see it; plus tool schemas on every call and multimodal inputs at fixed rates. The usage object has all four counts; store two and the bill cannot be explained. Proof: at Capital Group every model call is a Langfuse generation with usage and cost per step, so I can say what a workflow costs per document, not per month. (card 1)
Why are loops quadratically expensive?The model is stateless, so turn n re-sends everything before it: N·P plus g·N(N+1)/2. Ten turns with an 8k prefix and 1.5k growth is 162k input tokens, seven times the last turn alone. Tool results are the usual culprit. Proof: on the AgentCore supervisor I budget steps and tokens in the runtime and compact tool results before they enter history; the carry cost of a 10k-token result at step two is the first thing I look at. (card 1)
How does prompt caching work?Prefix matching on the KV cache: order the prompt stable-first, dynamic content last, never a timestamp in the system prompt. Gemini caches implicitly above a model-specific minimum and reports hits in the usage object; explicit caches trade storage per token-hour for determinism. Proof: I measure cache hit ratio per generation and alert when a deploy drops it. (card 2)
How do you shorten a reasoning loop, and find what consumes the most?Runtime budgets, effort per step, plan once, compact tool results, prune at checkpoints, structured outputs, route easy steps to small models, parallel tool calls, an explicit finish with one capped reflection. Then cost by step name, the most expensive traces read end to end, and carry cost per tool. (card 3)

Likely follow-ups, with the shape of a good answer

FinOps

  • We switched on a reasoning model and the bill doubled with no traffic change. Why?Thinking tokens are billed as output on every step, and the output becomes input on the next; the fix is effort per step, not per agent, and a cost line that shows thinking separately.
  • Caching is on and the hit ratio reads zero.Something dynamic sits early in the prompt, tools are reordered, history is rewritten every call, or the prompt is below the provider’s minimum; the trace’s cached count per generation says which.
  • Where would you look first for a cost spike?The most expensive traces of the day sorted, then the generation with the largest uncached input and the tool just before it with its output size.

Observability

  • Content capture: on or off?Per workload tier, never globally; off gives structure, timing and tokens; on makes the trace store a store of user data, so a redaction processor runs before the exporter.
  • Langfuse or Cloud Trace?An exporter line; native when traces must stay in the project and Agent Runtime hosts the agents, Langfuse for the LLM-shaped single view; often both.
  • What does auto-instrumentation miss?Tool output sizes, budget breaches, compaction events, prompt versions, approvals, the cache hit ratio: each an attribute or event you add.

Design

  • When is a multi-agent system wrong?When a single agent with six tools would do; every hand-off adds a failure point and a bill line, and context inheritance multiplies the quadratic cost.
  • How do you stop an evaluator-optimiser loop?A cap on rounds and concrete criteria; vague criteria loop or self-agree.
  • Which principle is a process, not code?Evaluated before and after every change; it is the one that keeps the others alive.

Evaluation

  • Why not one score from 1 to 10?It collapses correctness, tone and safety into a number nobody can act on; many small binary judges, aggregated separately, with the judge’s agreement published.
  • How do you know the judge is right?Accuracy, κ and FAIL recall against a human-labelled calibration set, with expert-to-expert agreement as the ceiling.
  • How do you evaluate an agent rather than an answer?Trajectory metrics against an expected tool sequence, plus the response; ADK evalsets in CI; the dataset case from card 6 as a scenario.

Security

  • What stops an injected document from acting?Tool output labelled untrusted, the allow-list, read-only defaults and the approval interrupt; it can ask, it cannot widen what IAM and the perimeter permit.
  • Why does the agent see a 403 as “does not exist”?BigQuery does not reveal resources the caller may not read; the fix is the grant or the perimeter rule, and a message to the model that says “could not check”.
  • How would you prove the confinement to an auditor?The cross-tenant test in CI, the audit log by principal with job labels, and the trace that joins the access to the conversation.

The recipes, as checklists

Finding the cost (card 3)

  1. sort yesterday’s traces by cost; open the top ten
  2. list generations in order with the four counts; name the pattern
  3. largest uncached input → the tool just before it and its output size
  4. cache hit ratio per generation; zero after turn 1 = unstable prefix
  5. carry cost per tool; fix in that order
  6. steps and input tokens per run against the p95; tighten budgets

The six checks (card 6)

  1. an execute_tool span for the lookup at all?
  2. error.type: 403 identity · 404 address
  3. the arguments the model sent
  4. the output and its size: paged, truncated, empty
  5. status OK then a confident wrong answer: swallowed
  6. a cache-hit flag or old timestamp: stale
  7. then, and only then, the prompt

The judge contract (card 10)

  1. task definition · the inputs the criterion needs · a precise rubric with the hard cases · reason before deciding · structured output, verdict last
  2. temperature 0 · one criterion · binary where possible · a different model family · versioned prompt
  3. calibration set with critiques · accuracy, κ, FAIL recall · read every disagreement · edit the rubric · re-measure · version and re-baseline

Instrumenting (cards 4, 5)

  1. content capture decided per workload tier
  2. tracer provider once; auto-instrument the model SDK
  3. an agent span around the loop; a tool span around each tool
  4. the four counts on every generation; error and output size on every tool
  5. traceparent into every remote tool
  6. a redaction span processor before the exporter
  7. events for budgets, compaction, approvals, retrieval filters, cache ratio
  8. the exporter: Langfuse, the Telemetry API, or a Collector to both

Confining the agent (card 12)

  1. its own identity; no key files
  2. as the agent, or on behalf of the user, per tool
  3. dataset-scoped roles; jobUser on the project; nothing that writes
  4. row access policies, including SESSION_USER()
  5. policy tags without the Fine-Grained Reader role; masking
  6. authorised views for shaped subsets
  7. the perimeter and its rules
  8. the tool: SELECT only, bytes, rows, timeout, allow-list, labels
  9. the cross-tenant test in CI

Guardrails (card 13)

  1. perimeter first
  2. Model Armor floor settings, inspect-and-block
  3. templates for the high-tier workloads
  4. the gateway: sanitise, quota, OAuth, same region
  5. the runtime’s rules in code; tool output untrusted
  6. the data controls; CMEK; de-identify on ingestion
  7. Audit Logs, Security Command Center, the trace join
  8. the red-team suite in CI

The design-review questions

  • What does one conversation cost, per step, and which line is largest?If the answer is a monthly number, the trace is missing the four counts.
  • What is P, what is g, and what happens at twenty turns?The quadratic term should be known before the first production run.
  • Where in the prompt is the first dynamic token?It should be in the last segment.
  • Which tool introduces the most tokens, and at what step?Carry cost ranks the fixes.
  • Show me the trace of a failing run.Tool input, error type, output size, the model’s next step.
  • Where does the budget live?In code that counts; a finish tool; a cap on reflection.
  • Can this flow be drawn?Then it is a workflow; if not, one agent, bounded, before many.
  • What does a worker receive, and what does it return?A task and its inputs; a schema.
  • Which tool is irreversible, and what gates it?Blast-radius class in the registry; the runtime’s interrupt.
  • What is in the golden set, and what is the judge’s agreement rate?Cases from traces with critiques; κ and FAIL recall published.
  • As whom does each tool call run, and what does it see if tricked into asking for everything?The identity chain and the seven layers.
  • Where would a regulator find what happened?Audit Logs by principal, the trace by conversation, job labels joining them.
