Agentic AI · knowledge primer

Self-Improving Agents

How an agent gets better at a job when its model never changes: the benchmarks that measure it, the gyms it practises in, and the five mechanisms — prompts, memory, critique, discovery, tools — that carry the improvement, with the pitfalls that come with each.

Thesis. With the weights frozen, every gain has to live in the harness: in what the model is told, what it can remember, what it can call, how it checks itself, and who gets to say no. The harness is the thing you engineer, the gym is where you measure it, and pass^k on a frozen task set is the number that tells you whether it worked.

0 · THE LOOP

One picture: where improvement comes from when the model is frozen

Every section below is one part of this picture. Sections 1 and 2 are where you measure it (τ-bench, the gyms). Section 3 is the claim that frozen weights still leave room to improve, and the taxonomy of where. Sections 4 and 5 are two inputs the loop depends on — reference trajectories and correct tool use. Section 6 is the five mechanisms. Section 7 is what goes wrong. Section 8 puts the parts in one architecture.

1 · τ-BENCH

What τ-bench is, and how to read a τ-bench number

τ-bench (Sierra, 2024) is a benchmark for tool-agent-user interaction. An agent has to complete a customer-service task by talking to a simulated user and calling tools against a database, while following a written policy. It was the first widely used benchmark where all four things an agentic deployment needs are present at once — and the first to report reliability rather than ability.

A policy document

The rules the agent must follow — which changes are allowed, what fees apply, what needs confirmation. Written like a real SOP. Violating it fails the task even if the user is happy.

airline_policy.md §4.2 change fees

Tools over a database

About a dozen functions per domain (look up a reservation, change flights, issue a refund) that read and write a seeded database. The database is the ground truth the grader inspects.

update_reservation_flights(...)

A simulated user

An LLM given a persona, a goal, constraints and hidden information. It plays the customer; it reveals the loyalty tier only if asked; it refuses to pay more than it said.

goal: move the return flight; max fee $150

State-based grading

Success is decided by comparing the final database state to the expected one, plus checks on the final answer the user received. Not by reading the transcript.

reservations.R7K2PQ.flights[1].date == 2026-11-03

Two domains, one reliability metric

The original release has an airline domain (on the order of 50 tasks) and a retail domain (on the order of 115 tasks). τ²-bench (2025) added a telecom domain with dual control: the user also acts in the environment and has to follow the agent’s troubleshooting instructions, so the simulator becomes an actor the agent must direct.

The metric that made the benchmark matter is pass^k — the probability that all k of k independent trials on the same task succeed — rather than pass@k, the probability that at least one does. Run a task n times with c successes:

pass@k = 1 − C(n − c, k) / C(n, k)    # at least one of k succeeds  — ability   (rises with k)
pass^k = C(c, k) / C(n, k)            # all k succeed               — reliability (falls with k)

# n = 8 trials, c = 6 successes:
#   pass@1 0.75   pass@2 0.964   pass@4 1.0
#   pass^1 0.75   pass^2 0.536   pass^4 0.214   pass^8 0.0

The gap between the two curves is the variance you would ship to customers. Frontier agents that score well on pass@1 fall off steeply on pass^k, which is the honest statement of how far they are from a deployment that behaves the same way every time. Three things follow for anyone building or buying a gym: pass^k only means something when the environment is deterministic (same seed, same simulator); a simulator that fails 5% of the time by itself caps every agent near 0.95k; and improving pass^k — the same task, every time — is exactly what the self-improvement mechanisms in section 6 are for.

How to read a τ-bench result. Ask four questions: which domain; pass@1 or pass^k and at what k; was the simulator pinned (which model, which prompt version); and what fraction of failures were policy violations versus wrong end state versus simulator breakdown. A number without those four is a headline, not a measurement.

2 · AGENT GYMS

Agent gyms: the environments agents practise and are measured in

A gym is an environment with a reset, a step, and a reward, built so an agent can run thousands of episodes against it. τ-bench is one; so are Terminal-Bench and SWE-bench (tasks in Docker with tests as the grader), WebArena and OSWorld (self-hosted sites and real OS VMs with state checks), AppWorld (apps with unit tests on state), and the bespoke environments labs commission for their own domains. They all have the same six parts.

tasks
Initial state + goal + expected end state + forbidden actions. Frozen for evaluation; generated in volume for training.
state
A database, a filesystem, a VM snapshot — restored on every reset so episodes are comparable.
tools / action space
What the agent can do: API calls, a shell, a browser. Mocked and deterministic in a gym; real in production.
simulator / world
Whatever answers back: a user simulator, a mocked API with failure modes, a container.
grader / reward
Tests, a state diff, forbidden-action checks, and a rubric judge for the parts only text can show.
runner
The loop that resets, steps, enforces caps, records the trace and calls the grader.

Evaluation gyms versus training gyms

EvaluationTraining (RL, or the harness loop in this page)
tasksFrozen, secret, a few hundred, calibratedThousands, generated from templates, with a curriculum
determinismRequired — pass^k is meaningless without itRequired for reproducibility; seeds vary across episodes
rewardBinary pass, reported with intervalsBinary plus penalties; partial credit is dangerous (it gets hacked)
throughputHundreds of episodes per runHundreds of thousands; parallel resets, cheap simulators
what it feedsA decision about a model or a harness versionWeights (RL) — or, with weights frozen, the prompt, memory and tool stores in section 6

The second column is the point of this page. A gym built for RL is exactly the gym you need to run the frozen-weight loop: the reward that would have become a gradient becomes a signal that decides whether an episode’s lesson is worth storing. Scoping and pricing one is covered in the companion Scoping & Pricing Playbook; the trace every episode produces is dissected in Agent Trace Anatomy.

3 · IMPROVING WITHOUT FINE-TUNING

Where improvement can live when the weights cannot change

Fine-tuning moves knowledge into the parameters. Everything else moves it into the context the model sees at inference time, the tools it can reach, or the loop around it. That gives five places a frozen agent can get better, and each has its own signal, store and failure mode.

LeverWhat changesSignal that drives itWhere it is storedMain risk
promptInstructions, rubric, few-shot exemplars, output formatPass rate on a dev set of tasksA versioned prompt storeOverfitting the dev set; silent regressions
memoryPast situations and what worked; facts learned about this environmentGrader-verified success on an episodeA case store with embeddings (RAG)Poisoned or stale cases; retrieval of the wrong one
critiqueThe agent’s own second look before acting or after failingA grader or judge verdict, or a self-checkNothing persistent — the loop itself; reflections may be storedSelf-rationalising; cost per step
discoveryWhich tools, resources and environment facts the agent knows existFinding a tool that fits; a dry run that succeedsThe tool registry; a skills libraryTrusting a discovered tool; capability creep
control loopRetries, budgets, routing, approval gatesCost and failure statisticsHarness configurationLoops that never terminate; approvals that get rubber-stamped
Why this works at all. Most agent failures on a fixed job are not capability failures. They are missing context (the model did not know the Docker socket needs a group), missing procedure (it did not know to check --help first), or missing a check (it did not run the tests). All three are fixable by changing what the model is shown and what it is allowed to do — which is why pass^k on the same task set rises without a single gradient step.

The discipline that makes it safe is the same in every case: a lesson enters a store only when a grader said the episode succeeded, every store is versioned, and a frozen eval split is re-run before a new version of any store is promoted. Improvement that is not measured on a frozen set is drift with good intentions.

4 · GOLDEN TRAJECTORIES

Golden trajectories: the reference runs everything else is measured against

A golden trajectory is a complete, verified run of a task: every observation, every tool call with its arguments, every result, the final state and the reward. It is the agentic equivalent of a reference answer. In a gym it is also the proof that the task is valid — if no trajectory reaches the expected end state within the policy, the task is broken, not the agent.

How they are produced

  • Human demonstration through the same tool interface, recorded as a trace. Expensive, highest trust.
  • Verified agent runs: a strong agent’s episode that the grader passed and a human audited for policy and reward hacking.
  • Oracle scripts written by the task author (the solve.sh in a terminal task).
  • Filtered rollouts: many runs, keep the ones that pass, dedupe by action sequence, audit a sample.

What they are used for

  • Validity oracle: the task is accepted only once a golden trajectory passes the grader.
  • Exemplars: the best few become few-shot demonstrations in the prompt, or the seed cases in episodic memory.
  • Trajectory evaluation: precision, recall and in-order match of an agent’s tool calls against the reference.
  • Targets for distillation or SFT later, if fine-tuning ever enters the picture.

The trap. There is rarely one right trajectory. Grading an agent by exact match to the golden path punishes a valid different route (look up the flight before the reservation). Grade the end state and the constraints; use the golden trajectory for validity, exemplars and diagnostics, not as the answer key.

5 · RIGHT TOOL, RIGHT API

Right tool usage: selection, arguments, contracts

Most agent episodes are a sequence of tool calls, so “did it use the right tool, with the right arguments, in a sensible order” is a metric on its own — the Berkeley Function Calling Leaderboard measures exactly that with syntax-tree and execution matching — and it is the single most improvable thing in a frozen-weight system, because tool descriptions are prompts.

Selection

The model picks a tool from its descriptions. A description that says what the tool is for, when not to use it, and what it returns, is worth more than any instruction elsewhere in the prompt.

"Use for one reservation by id. For search, use find_reservations."

Arguments

Typed schemas with enums and examples; required fields; units in the name (amount_usd); ids not names. Validate before calling; return the validation error to the model, not an exception.

"payment_id": {"pattern": "^card_"}

Contracts

Idempotent writes with a request key; explicit error types the model can act on; pagination and limits stated; side effects declared so the HITL gate can key on them.

side_effect: "financial" → requires approval

Least privilege

The right tool is also the narrowest one that does the job: a get_reservation tool over a raw SQL tool, a read-only shell over a root shell.

prefer read tools; gate write tools

The metric and the loop that improves it

# tool-call accuracy against a golden trajectory (order-insensitive form)
expected = {("get_reservation_details", "R7K2PQ"), ("update_reservation_flights", "R7K2PQ")}
actual   = {(c.name, c.args["reservation_id"]) for c in trace.tool_calls}
precision = len(expected & actual) / len(actual)      # did it call things it shouldn't have?
recall    = len(expected & actual) / len(expected)    # did it miss a required call?
in_order  = is_subsequence([e[0] for e in golden_order], [c.name for c in trace.tool_calls])

When precision is low, the fix is usually in a description (the model reached for a tool it should not have); when recall is low, in the instructions or an exemplar (it did not know a step was required); when arguments are wrong, in the schema. All three are prompt-store changes, measured on the dev set, versioned — the first mechanism of section 6.

Two patterns from the large-catalog world are worth knowing. Deferred tool loading: with hundreds of tools, only names are in context and the agent searches for and loads the schema it needs — the harness this page was written in does exactly this. Result validation: a tool result is data; a schema check on the way back catches a broken mock or an injected payload before the model reads it (section 7).

6 · THE MECHANISMS  ·  6.1 DYNAMIC PROMPT OPTIMISATION

Dynamic prompt optimisation: the prompt as a parameter

Treat the instructions, the few-shot exemplars and the output format as parameters, and optimise them against a metric on a development set — by a program, on a schedule, with a held-out set to catch overfitting. Four families exist, and production systems usually combine the first and the last.

FamilyHow it worksKnown asBest for
exemplar bootstrappingRun the agent on the dev set; keep traces the grader passed; select the most informative as few-shot demonstrations.DSPy BootstrapFewShotFormat and procedure errors; cheap; first thing to try.
instruction searchAn LLM proposes instruction variants; each is scored on the dev set; the best survive and are mutated again.OPRO; DSPy MIPROv2 (joint instructions + demos, Bayesian search)Ambiguous task definitions; rubric wording.
textual gradientsA critic writes natural-language feedback on each failure; an editor applies the feedback to the prompt; execution traces are the evidence.TextGrad; DSPy GEPA (reflective evolution over traces, Pareto frontier of candidates)Agentic tasks where the failure is visible in the trace.
failure-driven rulesCluster the failures, write one rule per cluster, add it to the prompt, re-measure — the same loop as improving a judge’s rubric.the manual version of the aboveEvery system, every week.
 
# a minimal evolutionary prompt optimiser; grader(task, output) -> 0/1 is the gym's grader
def score(prompt, tasks, k=3):
    # pass^k-style: a task counts only if all k runs pass — optimise reliability, not luck
    return sum(all(grader(t, run_agent(prompt, t, seed=s)) for s in range(k)) for t in tasks) / len(tasks)

def optimise(base_prompt, dev, holdout, rounds=6, beam=4):
    pool = [(score(base_prompt, dev), base_prompt)]
    for r in range(rounds):
        parents = sorted(pool, reverse=True)[:beam]
        children = []
        for s, p in parents:
            failures = [(t, run_agent(p, t)) for t in dev if not grader(t, run_agent(p, t))]
            feedback = critic_llm(p, failures)                 # "the agent never checks --help before running a CLI"
            children.append(editor_llm(p, feedback))           # returns a revised prompt
        pool = parents + [(score(c, dev), c) for c in children]
    best_s, best = max(pool)
    assert score(best, holdout) >= score(base_prompt, holdout)    # promote only if it generalises
    return register_prompt_version(best, dev_score=best_s)
What goes wrong. Overfitting the dev set (keep a held-out split and a frozen eval); gaming the metric (a grader that checks output format gets prompts that produce format and nothing else); prompt bloat (every round adds a sentence; prune); non-determinism (score with several seeds, as above); and silent regressions when a new prompt version is promoted without re-running the frozen split.

6.2 · EPISODIC MEMORY IN RAG

Episodic memory: successful patterns stored and retrieved

The most direct way a frozen agent learns is the way a support engineer does: remember what worked last time. An episode that the grader passed is distilled into a case — the situation, what was tried, what fixed it, how it was verified — embedded, and stored. The next time a similar situation appears, the case is retrieved into context as evidence. Three kinds of memory come out of this, and they are stored differently.

Episodic

What happened: a situation and its resolution, with the evidence. Retrieved by similarity of the current error or state.

"docker.sock permission denied → add user to docker group"

Semantic

Facts about this environment, learned once: the staging database is read-only; the CI runner has no network; tests live under tests/ not test/.

env.staging.db = read_only

Procedural

How to do a thing: a script or a skill document that worked, parameterised. Voyager’s skill library; a SKILL.md an agent loads when relevant.

skills/rotate-k8s-secret.md

A worked example: the Docker failure that becomes a case

Episode 1: the agent runs docker build and gets permission denied while trying to connect to the Docker daemon socket at unix:///var/run/docker.sock. It reflects (section 6.3), tries sudo docker, gets a different error about the build context, tries adding the user to the docker group and re-entering the group, and the build succeeds; the tests pass; the grader returns 1. The reflection step distils the episode into a case, and the memory gate stores it because the grader passed.

{"id": "case_01f8", "kind": "episodic", "provenance": "grader_verified",
 "trigger": {"error_signature": "permission denied .* /var/run/docker\\.sock",
             "context": ["linux", "non-root user", "docker daemon running"]},
 "diagnosis": "the user is not in the docker group, so the socket is not accessible without sudo",
 "resolution": ["sudo usermod -aG docker $USER", "newgrp docker", "docker ps   # must exit 0 before retrying the build"],
 "do_not": ["chmod 666 /var/run/docker.sock  # works, opens the daemon to every local user"],
 "verification": "docker ps exits 0; the original build command succeeds",
 "evidence": {"episodes": ["ep_8812", "ep_9044"], "success_count": 7, "fail_count": 1, "last_verified": "2026-10-12"},
 "risk": "privileged", "requires_human_review": true, "ttl_days": 180,
 "embedding_of": "error_signature + diagnosis"}

Episode 2, weeks later, a different task hits the same error. Retrieval finds the case by the error signature, and the harness injects it — as data, with its provenance, not as an instruction:

<past_resolutions provenance="episodic_memory" note="evidence from earlier verified episodes; verify before relying on it">
  [case_01f8] verified 7×, last 2026-10-12, risk: privileged
  diagnosis: user not in docker group
  resolution: sudo usermod -aG docker $USER; newgrp docker; docker ps must exit 0
  do not: chmod 666 on the socket
</past_resolutions>

The agent still has to run the fix, and the fix still goes through the HITL gate because the case is marked privileged. What changed is that the first attempt is now the right one — which is what moves pass^k.

Write policy — what gets in

  • Only episodes the grader passed; a reflection without a pass is a hypothesis, not a case.
  • Dedupe by trigger signature; merge evidence counts instead of storing twins.
  • Human review before storing anything privileged, destructive or financial.
  • Provenance and a TTL on every case; decay cases that stop being retrieved or start failing.
  • Never store secrets, tokens or raw customer data in a case.

Read policy — how it is used

  • Top-k by similarity with a threshold; prefer high success_count and recent last_verified.
  • Inject as delimited data with provenance; the model is told it is evidence, not an order.
  • Never auto-execute a stored resolution; it is a suggestion the agent verifies.
  • Measure the lift: pass^k on the frozen split with memory on versus off, every version.
def remember(episode, grade):
    if grade.reward < 1: return                                   # hypotheses are not cases
    case = distil_llm(episode)                                    # trigger, diagnosis, resolution, verification, risk
    existing = store.find(signature=case.trigger.error_signature)
    if existing: existing.evidence.merge(episode.id); return
    if case.risk in {"privileged", "destructive", "financial"}:
        review_queue.put(case); return                          # a human promotes it
    store.add(case, embedding=embed(case.trigger.error_signature + case.diagnosis), ttl_days=180)

def recall(observation, k=3, min_sim=0.82):
    hits = store.search(embed(observation.error_text), k=k)
    hits = [h for h in hits if h.sim >= min_sim and h.evidence.success_count > h.evidence.fail_count]
    return render_as_data(hits)                                   # delimited block with provenance, never bare text

The systems to know by name: Reflexion’s episodic buffer of reflections; Voyager’s skill library of verified programs; ExpeL, which turns experiences into reusable insights; the Generative Agents memory stream with recency, importance and relevance scoring; MemGPT/Letta for paging memory in and out of context; and the production stores — LangGraph’s store, Mem0 — that give an agent a namespaced, searchable memory across threads.

6.3 · AUTOMATED CRITIQUE AND REFLEXION

Automated critique and Reflexion: the second look

Reflexion (Shinn et al., 2023) is the pattern most harness loops descend from: an actor attempts the task, an evaluator scores the attempt, a self-reflection step writes, in words, what went wrong and what to do differently, and that reflection is placed in memory for the next attempt. It was called verbal reinforcement learning because the reflection plays the role a gradient would — and it works when, and only when, the evaluator is trustworthy.

PatternWho critiquesGrounded inHelps withFails when
ReflexionThe model, after an external verdictA grader: tests, exact match, a state diffMulti-attempt tasks with a real signalThe verdict is noisy; the reflection then rationalises noise
Self-RefineThe same model, on its own outputNothing externalStyle, format, completeness checklistsCorrectness — a model that was wrong is wrong again, confidently
CRITICThe model, using toolsRunning the code, searching, calculatingAnything verifiable with a toolNo tool can check the claim
Judge in the loopA separate model, different familyA rubric calibrated against humansPolicy adherence, tone, process qualityThe judge is unmeasured; the agent learns to please it
 
def reflexion(task, max_attempts=3):
    reflections = []                                               # episodic buffer for this task
    for attempt in range(max_attempts):
        episode = run_agent(task, context=render_as_data(reflections))
        grade = grader(task, episode)                              # tests / state diff first ...
        if grade.reward == 1:
            remember(episode, grade)                               # ... then the case goes to memory (6.2)
            return episode
        verdict = judge(task, episode) if grade.reason is None else grade  # ... judge only where the grader is blind
        reflections.append(reflect_llm(task, episode, verdict))    # "I edited the test instead of the code; next time ..."
    return escalate(task, episode, reflections)                   # HITL after the budget is spent

Three rules keep critique honest. Ground it: a critic with a tool or a test beats a critic with an opinion. Separate it: the judge is a different model family and is itself measured against humans. Budget it: two or three reflections, then a human — an unbounded reflect-retry loop is the most expensive way to fail.

6.4 · DYNAMIC DISCOVERY

Dynamic discovery of tools and environments

An agent that only knows the tools it was launched with cannot improve its reach. Discovery is the mechanism by which it learns what exists — tools, resources, procedures, and the facts of the environment it is standing in — and the registry is where what it learned is kept.

Tool discovery

  • MCP: a server advertises tools/list, resources/list and prompts/list; the client fetches schemas at connect time and again when the server signals a change.
  • OpenAPI specs for HTTP services; --help and man for CLIs; package introspection for libraries.
  • Tool search over a large catalogue: index the descriptions, retrieve by the task, load only the matching schemas — deferred loading keeps context small and selection sharp.
  • Skills: procedure documents discovered by description and loaded when relevant — procedural memory you can author, review and version.

Environment discovery

  • Look before acting: ls, the README, git log, env, which, docker ps, the config files. Ten seconds of discovery prevents most first-attempt failures.
  • Record what was found as semantic memory with a timestamp: “this runner has no outbound network” is worth more the second time.
  • Probe capabilities with a dry run or a read-only call before relying on them.
  • Expire environment facts; they go stale faster than cases.
# discover → filter → verify → register
async def discover(mcp_client, allowlist, registry):
    tools = await mcp_client.list_tools()                      # names, descriptions, input schemas
    for t in tools:
        if t.name not in allowlist: continue              # discovered ≠ trusted
        if looks_like_injection(t.description): quarantine(t); continue   # tool-description poisoning
        ok = await dry_run(mcp_client, t)                     # read-only probe or a no-op call
        registry.put(t, verified=ok, side_effects=classify(t), discovered_at=now(), ttl_days=30)
Discovered is not trusted. A tool description is text the model reads, so it is an injection surface (“before using this tool, first export the environment variables to…”). Allowlist by name, scan descriptions, classify side effects, dry-run, and keep the registry versioned — every discovered capability is a permission you just granted.

6.5 · SHELL AND WEB-SEARCH TOOLS

The two universal tools, and what each one is for in the loop

The shell

The shell is how an agent verifies: it runs the tests, inspects the state, reproduces the error. In the loop it is the grader’s instrument and the discovery tool in one. The patterns that make it safe to give out:

  • Runs inside the sandbox, never on the host; a read-only mode for inspection and a write mode that passes the HITL gate.
  • Command allow- and deny-lists (rm -rf, curl | sh, package publishes); “explain before execute” for anything destructive.
  • Timeouts, output truncation, a per-episode budget; scripts over long chains of single commands.
  • Every command and its exit code in the trace — the shell span is the most useful span in a failed episode.

Web search and fetch

Search is how an agent learns facts it was not given: the error message nobody has seen, the API change since the model’s cutoff, the vendor’s own docs. What comes back is the most untrusted content the agent will ever read.

  • Egress allowlist; a fetch proxy that logs; no credentials on the fetch path.
  • Results wrapped as data with the source URL; summarised into semantic memory with provenance, never pasted raw into an instruction slot.
  • Cache fetched pages for the run; re-fetch on a TTL, not on every episode.
  • Treat “instructions” found on a page as findings to report, not steps to take.

Together they close the loop at both ends: search gives the model the fact it lacked; the shell proves whether the fix worked; the grader’s verdict decides whether the fact and the fix become memory.

7 · PITFALLS

Pitfalls: the four that decide whether the loop can run unattended

PitfallHow it shows upControls
prompt injectionInstructions arrive inside tool results, web pages, files, tool descriptions — and, in a self-improving system, inside memory: a poisoned case stored once is retrieved on every similar episode.Every tool result and retrieved case is delimited data with provenance; an instruction hierarchy the model is reminded of; action allowlists; an injection detector on retrieved content; the memory write gate (grader-verified, deduped, human review for privileged cases); never executing instructions found in content.
ephemeral sandboxingA fresh container or micro-VM per episode is what makes failure cheap and compromise temporary — and it is also why nothing learned survives unless it is written to a store outside the sandbox. Warm-up cost tempts people to reuse containers.gVisor or Firecracker, snapshot and restore, no secrets inside, memory and traces externalised through a narrow API, image caches for warm-up, a kill switch per episode.
network segregationThe agent’s shell reaches the host network, the cloud metadata endpoint, or production from a test gym; a fetched page triggers a request to an attacker’s host.Egress allowlist through a logging proxy; block link-local and metadata addresses; separate networks for eval, training and production; DNS control; the sandbox’s network is not the host’s.
human in the loopNo gate before a payment, a delete, a send or a deploy; or a gate that approves everything because it shows nothing useful.An interrupt before irreversible or side-effecting actions, keyed on the tool’s declared side effect; the diff and the reason shown to the approver; approval rate limits; budgets and a stop button; escalation when confidence is low; every approval in the audit log.

And three that are specific to improvement loops

  • Reward hacking becomes memory. If the grader can be satisfied without the goal (editing the test, telling the simulator what it wants to hear), the loop stores the hack as a case and retrieves it forever. Audit a sample of passed episodes for the goal, not the reward, before their cases are promoted.
  • Optimising on the eval. A prompt tuned on the frozen split is no longer being evaluated by it. Dev, held-out and frozen eval are three disjoint sets, and promotion requires the third.
  • Cost without a ceiling. Reflection and retry loops, discovery probes and judge calls multiply tokens per task. Budget per episode, per task and per day; report cost next to pass^k.

The one-sentence version. A self-improving agent is a frozen model plus four versioned stores — prompt, memory, tools, and the critic that guards them — in a loop where a grader decides what gets stored, a human decides what gets executed, and a frozen gym split decides what gets promoted.
