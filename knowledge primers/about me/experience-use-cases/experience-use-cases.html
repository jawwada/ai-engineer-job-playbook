1 · The legal agent: the right metadata, the guidelines, and disclosures through a knowledge graph

Capital Group’s marketing incubator wanted content review faster without making legal nervous. Every piece of marketing content — fund commentary, web pages, emails, social posts, advisor decks — passes editorial and legal review before it can be used. The legal agent is the pre-check: it resolves the metadata that decides which rules apply, extracts the claims a draft makes, maps each claim through a knowledge graph to the rules and the disclosure texts it requires, checks that each disclosure is present, current and close enough to the claim, and hands the legal reviewer findings with evidence. The reviewer decides; the agent never publishes.

Why a knowledge graph rather than a long prompt

  • Rules change. A disclosure version is a node with an effective date; the prompt never changes when counsel changes the wording. Nothing is approved against a stale version because the check reads the current one.
  • Applicability is relational. A performance claim about fund X for a retail web page in the US requires a different set of texts from the same claim in an institutional deck; the graph answers that with one query across product, audience, channel and jurisdiction.
  • Explainability. A finding is a path: claim type → rule → disclosure → placement rule. Counsel can read the path, dispute a node and fix it in one place.
  • Ownership. Legal edits the graph through a reviewed change process; engineering owns extraction and checks. No one has to ask an engineer to change a rule.

Multi-LLM orchestration and structured outputs

Three model roles with different budgets: a small model extracts claims from every block (thousands a month), a strong model handles low-confidence or novel claims and writes explanations, and a judge model (card 2) scores the rewritten text. Every model call returns JSON validated against a schema; a failed validation is retried once and then routed to the strong model; a second failure becomes a finding of its own (“could not parse block 7”) rather than a silent skip. Model names are configuration, not code; the trace records which model answered.

What stays human

Principal approval of retail communications, any change to the rules or disclosure library, any finding the agent marks as uncertain, and the decision to reuse content in a new jurisdiction. The agent proposes; the reviewer disposes; the log records both.

How it is built, in order

  1. Sit with legal before the model. Inventory what a review actually checks: the rule families, the disclosure texts, the placement conventions, the exceptions. Write them as nodes and edges on a whiteboard; that drawing becomes the graph schema and the acceptance criteria.
  2. Build the disclosure library as versioned data. Every text with an id, a version, effective dates, applicable products, audiences, channels and jurisdictions, and the rule that mandates it. Load it into the graph; counsel reviews the load.
  3. Annotate the past. Take 300 completed reviews, label the claims in each draft and the findings the reviewers made. This is the golden set; agreement between two annotators on claim type above κ 0.8 before it is used.
  4. Extraction first, with a schema. Prompt and few-shot the extractor; measure claim recall and type precision on the goldens; add the strong-model fallback for low confidence. Gate: recall of blocker-class claims ≥ 0.95.
  5. Resolution and checks as code. Graph queries for applicability; unit-tested checks for presence, proximity, currency and audience. Gate: on the goldens, missing-disclosure recall ≥ 0.95 and finding precision ≥ 0.8, so reviewers see few false alarms.
  6. Pilot on one content type. Fund commentary for the web, one team, four weeks, the agent’s findings shown next to the human review; measure agreement, time to first feedback, and reviewer trust in their own words.
  7. Human-in-the-loop UI and the decision log. Accept, reject with reason, edit; every decision stored with the finding, the versions and the reviewer id. The log is the evaluation set from now on.
  8. Roll out by content type, then by team. Social and email next (link-form disclosures), decks last (tables and footnotes). Each step gated on the same metrics.
  9. Operate the rules. A change process for the graph (proposal, counsel approval, effective date), re-run of checks on in-flight items when a version bumps, dashboards for findings by rule, acceptance rate by finding type, cycle time, and drift in extraction confidence.

What goes wrong, and what to defend

  • The model decides applicability. A prompt that says “check compliance” produces confident, unreproducible findings. Applicability is a graph query; the model extracts and explains.
  • Presence without proximity. A legend buried in a footer twelve blocks away “exists”; reviewers reject it. Placement rules are part of the graph and the check measures distance.
  • Stale versions. A disclosure updated in November, content approved in December against the old text. Versions with effective dates, and re-runs on version bumps.
  • Audience leakage. An institutional paragraph reused in a retail email with its projections intact. Audience is metadata the checks read, not a prompt hint.
  • Over-flagging. Precision below 0.7 and the reviewers stop reading the agent. Tune severity, suppress duplicates, show precedent.
  • Silent failures. A block that fails to parse is skipped and the item looks clean. Every failure becomes a finding.
  • Rubber-stamping. If the agent is usually right, reviewers click accept; the decision log shows acceptance in seconds. Sample reviews with the agent hidden, and keep the principal approval a separate act.
  • Prompt-only rules. Counsel asks for a change and an engineer edits a prompt; nobody can say what the rule was last quarter. The graph is the rulebook with history.
  • No audit trail. A regulator asks why a piece was approved: the trace must show model, prompt version, graph version and the human decision.
  • PII and confidential data in prompts. Drafts can quote client situations; redaction before any model call and a content-capture policy in tracing.

Extraction, resolution, checks and the review interrupt

Python with LangChain on Bedrock for structured extraction, Neptune openCypher for resolution, plain functions for the checks, and a LangGraph with a human node. Module paths and parameter names change; verify against current docs before running.

# claims.py — structured extraction with a schema; small model first, strong model on low confidence
from pydantic import BaseModel, Field
from typing import Literal, Optional
from langchain_aws import ChatBedrockConverse

ClaimType = Literal["performance_claim", "rating_mention", "comparison", "forward_looking",
                    "aum_fact", "testimonial", "award", "fee_claim", "other"]

class Claim(BaseModel):
    id: str
    type: ClaimType
    span: tuple[int, int] = Field(description="character offsets in the block")
    product: Optional[str] = None
    period: Optional[str] = None
    comparator: Optional[str] = None
    as_of: Optional[str] = None
    strength: Optional[Literal["promissory", "hedged", "neutral"]] = None
    confidence: float

class Claims(BaseModel):
    claims: list[Claim]

SMALL = ChatBedrockConverse(model="small-model-id", temperature=0).with_structured_output(Claims)
STRONG = ChatBedrockConverse(model="strong-model-id", temperature=0).with_structured_output(Claims)

def extract(block_text: str, task_meta: dict) -> Claims:
    prompt = PROMPT.format(text=block_text, products=task_meta["products"], audience=task_meta["audience"])
    out = SMALL.invoke(prompt)
    if any(c.confidence < 0.7 or c.type == "other" for c in out.claims):
        out = STRONG.invoke(prompt)             # ~10% of blocks go to the strong model
    return out
# graph.py — what does this claim require for this task?  (Neptune, openCypher)
import boto3, json
neptune = boto3.client("neptunedata", endpoint_url="https://<cluster>:8182")

REQUIRED = """
MATCH (ct:ClaimType {name: $claim_type})-[r:REQUIRES|PROHIBITED_FOR]->(x)
OPTIONAL MATCH (x)-[:APPLIES_TO]->(a:Audience {name: $audience})
OPTIONAL MATCH (x)-[:APPLIES_TO]->(c:Channel {name: $channel})
OPTIONAL MATCH (p:Product {id: $product})-[:HAS_DISCLOSURE]->(pd:Disclosure)
WHERE (x:Disclosure AND x.current = true AND x.effective_from <= date($today))
   OR (x:Audience AND x.name = $audience)
RETURN type(r) AS relation, labels(x) AS kind, x.id AS id, x.version AS version,
       r.placement AS placement, r.max_distance_blocks AS max_distance, collect(DISTINCT pd.id) AS product_disclosures
"""

def requirements(claim, task):
    params = {"claim_type": claim.type, "audience": task["audience"], "channel": task["channel"],
              "product": claim.product or task["products"][0]["fund_id"], "today": task["run_date"]}
    res = neptune.execute_open_cypher_query(openCypherQuery=REQUIRED, parameters=json.dumps(params))
    return res["results"]
# checks.py — deterministic, unit-tested; the reviewer relies on these
from rapidfuzz import fuzz

def find_disclosure(blocks, disclosure_text, threshold=92):
    for i, b in enumerate(blocks):
        if fuzz.partial_ratio(disclosure_text, b.text) >= threshold:
            return i
    return None

def check(claim, block_index, req, blocks, library):
    if req["relation"] == "PROHIBITED_FOR":
        return dict(status="prohibited", severity="blocker")
    text = library.current_text(req["id"])            # current version only
    at = find_disclosure(blocks, text)
    if at is None:
        old = library.any_version(req["id"], blocks)      # an old version present? still a finding
        return dict(status="outdated" if old else "missing", severity="blocker")
    if abs(at - block_index) > (req["max_distance"] or 1):
        return dict(status="present_not_proximate", severity="major", found_block=at)
    return dict(status="ok", severity=None)
# flow.py — LangGraph: extract → resolve → check → explain → human review (interrupt) → log

Saying it

Thirty secondsAt Capital Group I built the legal pre-check for marketing content. The rules and disclosure texts live in a versioned knowledge graph that legal owns; a model extracts the claims a draft makes and explains findings; code checks that each required disclosure is present, current and close to the claim; and the legal reviewer decides. We measure it against past reviews: recall on missing disclosures, and precision because reviewers stop reading below about seventy percent.
Two minutesThe incubator’s problem was cycle time: drafts took days or weeks to get through editorial and legal. I did not start with a model. I sat with legal and editorial and asked what a review actually checks: disclosures, claims, tone, conflicts with existing content. That became a graph: claim types, rules, disclosure texts with versions and effective dates, products, audiences, channels and jurisdictions, with edges for what requires what and what is prohibited for whom. Workfront stayed the system of record; the agent reads the task metadata, which decides which rules apply, and the draft, normalised into blocks with offsets so every finding points at a span. A small model extracts claims into a schema and a strong model handles the ambiguous ten percent. Applicability is a graph query, not a prompt. The checks are deterministic: presence by fuzzy match against the current version, proximity in blocks, currency of as-of dates, audience and channel allowed. Findings come with the rule, the disclosure text and a precedent from a prior approved piece. The legal reviewer accepts, rejects or edits, and every decision is logged with the model, prompt and graph versions, which is both the audit trail and the training data for the judges and the rewriter. We gated on a golden set of three hundred past reviews: missing-disclosure recall at or above ninety-five percent and finding precision at or above eighty before the pilot. The thing that made it ship in a regulated workflow was that the people who owned the risk designed the acceptance criteria.

Likely questions and answer shapes

  • Why a knowledge graph and not retrieval over the policy documents? Retrieval finds text; it does not decide applicability. Applicability is relational and versioned: product × audience × channel × jurisdiction × date. The graph answers that deterministically and explains the answer as a path; retrieval still supplies the wording and the precedent.
  • How do you know the extractor is good enough? A golden set of annotated past reviews with inter-annotator agreement above 0.8; recall by claim type, with a hard gate on the blocker types; the strong-model fallback on low confidence; and the live acceptance rate per finding type as the ongoing measure.
  • What did legal push back on? Autonomy. The agreement was explicit: the agent proposes, writes into the task, never changes status, never publishes; principal approval stays a human act; and the rulebook changes only through their process.
  • What happens when a rule changes? A new disclosure version with an effective date supersedes the old one in the graph; in-flight items are re-checked; dashboards show findings by rule version so counsel can see the effect.
  • Hallucination? The model never asserts a rule; it cites a rule id and a disclosure id that the checks resolved. If an explanation references something not in the finding’s path, a validator rejects it before the reviewer sees it.
  • How did you handle cost at thousands of claims a month? Two model tiers, structured outputs that fail fast, caching of the task context, and the strong model only on low confidence. Cost per item in cents; the trace records tokens per item.

2 · Rewriting and the four judges: creative, brand, editorial and legal criteria, digital twins, conflicts and resolution plans

A draft that fails the pre-check needs a rewrite that satisfies four reviewers who want different things. Each reviewer has a digital twin: a judge configured with that reviewer’s guideline, calibrated against that reviewer’s past decisions, returning scored findings with evidence. The twins disagree by design — legal wants the full disclosure next to the claim, editorial wants a forty-word opening, brand wants the firm’s voice — so a conflict detector finds the collisions and a planner resolves them into an ordered plan before a word is rewritten. The rewriter executes the plan, the twins re-score, and the human reviewer sees a diff with the scores and the evidence.

Why “digital twin” and not “LLM-as-a-judge”

Both are judges. The twin is the version that stands in for a named reviewer: configured with that person’s guideline, fed that person’s past decisions, measured against that person, and used to pre-check before the person reads. The organisational point is ownership: the editorial lead owns the editorial twin’s checklist the way legal owns the graph. When the reviewer changes their mind, the twin changes with the next calibration, not with a prompt edit by an engineer.

How it is built

  1. Turn each guideline into a checklist. Brand guide, house style, creative principles, legal content standards: each a list of criteria with a type, a scale with anchors, and a statement of what counts as evidence. Candidate-based drafting: write criteria while scoring real drafts, not in the abstract.
  2. Assign gates and weights with the owners. Legal and factual criteria gate; the owners agree the weights for the rest and sign the scoring rule.
  3. Build the four twins with retrieval over their guideline and examples from their reviewer’s history; JSON outputs with evidence.
  4. Calibrate. 50 items per reviewer; agreement per criterion; fix the checklist where the twin and the reviewer disagree because the guideline was ambiguous; fix the prompt where the guideline was clear.
  5. Conflict table and precedence. Enumerate fix types and their incompatibilities; set precedence in configuration with the owners; write the plan validator.
  6. Planner and rewriter. Prompt the planner with the closed strategy set; the rewriter with the plan; validate candidates (gates, verbatim texts, facts unchanged by a fact-consistency check against the source).
  7. Pilot with the diff UI on one content type; measure acceptance of candidate B over the reviewer’s own rewrite, edits per accepted candidate, rounds to convergence, and reviewer time.
  8. Operate: monthly calibration, drift alerts when a twin’s acceptance rate moves, guideline version bumps re-run calibration, and every decision captured for card 3.

Judge and rewrite failure modes

  • A judge that rates style when asked about law. Without typed criteria and required evidence, the legal twin returns impressions. Binary criteria, evidence spans, rule ids.
  • Self-preference. The rewriter’s model family judging its own prose scores it higher. Different family for the judge where possible, position swap, and the human.
  • Verbosity and position bias. Longer candidates and first-shown candidates win pairwise comparisons. Length-controlled prompts, swap, consistency check.
  • Oscillation. Twins rewriting each other’s rewrites. The plan is fixed per round; only wording changes; three rounds then the human.
  • The rewrite changed a fact. A fluent candidate with a wrong period or number. A fact-consistency check against the source document is a gate.
  • Twins that encode a reviewer’s bad habits. Calibration against the reviewer can teach the twin to be inconsistent; where the reviewer and the guideline disagree, the guideline owner decides and the guideline is fixed.
  • Approved text paraphrased. A disclosure rewritten in plain language is no longer the approved disclosure. Verbatim flag on texts; the validator compares strings.
  • Scores without evidence. A 4/5 with no span is not reviewable. Evidence is required by the schema; missing evidence invalidates the criterion.
  • Calibration once. Guidelines and reviewers change; monthly re-calibration and drift alerts on acceptance rate.

# twin.py — one judge with typed criteria and required evidence
from pydantic import BaseModel
from typing import Literal, Optional

class Verdict(BaseModel):
    id: str                                  # criterion id from the guideline checklist
    type: Literal["binary", "ordinal"]
    verdict: Optional[Literal["pass", "fail"]] = None
    score: Optional[int] = None              # 1–5 with anchors, ordinal only
    evidence: str                            # span or rule id; the schema makes it mandatory

class TwinOutput(BaseModel):
    judge: str
    guideline_version: str
    criteria: list[Verdict]
    proposed_fix: Optional[str] = None
    confidence: float

def run_twin(name, block, context, judge_llm, checklist, examples):
    prompt = TWIN_PROMPT.format(name=name, checklist=checklist, examples=examples, text=block.text, context=context)
    out = judge_llm.with_structured_output(TwinOutput).invoke(prompt)
    for v in out.criteria:                      # evidence must point at something real
        if v.type == "binary" and v.verdict == "fail" and v.evidence not in block.text and not v.evidence.startswith(("rule:", "ED-", "BR-", "LG-")):
            v.verdict = None                  # invalid finding, dropped and logged
    return out
# conflicts.py — deterministic detection on overlapping spans
INCOMPATIBLE = {("insert", "shorten"), ("replace", "verbatim"), ("remove", "keep"), ("expand", "shorten")}
PRECEDENCE = ["legal", "factual", "editorial", "brand", "creative"]

def overlaps(a, b):
    return a["block"] == b["block"] and a["range"][0] < b["range"][1] and b["range"][0] < a["range"][1]

def conflicts(findings):
    out = []
    for i, a in enumerate(findings):
        for b in findings[i + 1:]:
            if overlaps(a["span"], b["span"]) and ((a["fix_op"], b["fix_op"]) in INCOMPATIBLE or (b["fix_op"], a["fix_op"]) in INCOMPATIBLE):
                first = min((a, b), key=lambda f: PRECEDENCE.index(f["judge"]))
                out.append({"findings": [a["id"], b["id"]], "span": a["span"], "dominant": first["judge"]})
    return out
# plan.py — the planner picks a strategy from a closed set; the validator checks the plan before any prose
STRATEGIES = ["dominate", "relocate", "merge", "rephrase"]

def validate_plan(plan, findings, library):
    gate_ids = {f["id"] for f in findings if f["gate"]}
    addressed = {t for s in plan["steps"] for t in s.get("addresses", [])}
    assert gate_ids <= addressed, f"gate findings not addressed: {gate_ids - addressed}"
    for s in plan["steps"]:
        if s["op"] == "insert" and "text_id" in s:
            assert s.get("verbatim") is True and library.is_current(s["text_id"])
    return True

def rewrite(draft, plan, writer_llm, k=3):
    return [writer_llm.invoke(REWRITE_PROMPT.format(draft=draft, plan=plan, seed=i)).content for i in range(k)]
# choose.py — pairwise with position swap; inconsistent pairs go to the human
def prefer(a, b, judge_llm):
    v1 = judge_llm.invoke(PAIR_PROMPT.format(first=a, second=b)).content.strip()   # "first" | "second"
    v2 = judge_llm.invoke(PAIR_PROMPT.format(first=b, second=a)).content.strip()
    w1 = a if v1 == "first" else b
    w2 = b if v2 == "first" else a
    return w1 if w1 is w2 else None        # None = inconsistent under swap → tie

Saying it

Thirty secondsContent rewriting at Capital Group has four reviewers who want different things, so we built four digital twins: judges with typed criteria and evidence, each calibrated against its reviewer’s past decisions. Their findings conflict on purpose; code detects the conflicts and a planner resolves them by precedence, legal first, into a plan the rewriter executes. Candidates are re-judged, gates block, a swap-consistent pairwise pick chooses, and the reviewer sees a diff with the scores and the evidence.
Two minutesThe hard part of rewriting marketing content is not the prose, it is that editorial, brand, creative and legal pull in different directions and a naive loop oscillates: the editorial pass shortens the opening and drops the legend, the legal pass puts the legend back in the first paragraph, the brand pass changes its voice. We modelled the reviewers as digital twins. Each twin is a judge built from that reviewer’s own guideline turned into a checklist, with binary gates and ordinal criteria with anchors, retrieval over the guideline, and a few of the reviewer’s own past comments as examples; every verdict must cite evidence, a span or a rule id, or it is dropped. We calibrated each twin against fifty items its reviewer had judged and fixed the checklist where the twin and the human disagreed because the guideline was ambiguous. Legal and factual criteria are gates; the rest are weighted. Then conflict detection is deterministic: two findings on overlapping spans with incompatible fixes, insert versus shorten, replace versus verbatim. The planner is where the thinking happens: precedence is configuration, legal over factual over editorial and brand over creative, and the model chooses a strategy per conflict from a closed set — dominate, relocate, merge, rephrase — and writes a plan that a validator checks before any prose: every gate addressed, approved texts verbatim. A separate writer executes the plan into three candidates, the twins re-score, gated candidates are dropped, and a pairwise judge with a position swap picks the best; inconsistent pairs go to the human. Three rounds at most. The reviewer gets a diff with per-twin scores and evidence, and every accept, edit and reject is captured, which is what card 3 learns from.

Likely questions

  • How do you know the twins are not just agreeing with each other? They are measured against their own reviewer, criterion by criterion, not against each other; agreement with the human is the metric, and the human still reads.
  • What is “resolution-based planning”? Resolving the conflicts into an ordered plan before writing: precedence fixed, a strategy per conflict, a validator on the plan. The rewrite then has nothing to negotiate.
  • Why not one judge with all four guidelines? One prompt averages them; the owners lose ownership; the evidence becomes vague. Four twins keep four owners and four calibrations.
  • What about the judge’s biases? Named and handled: self-preference with a second model family, position with the swap, verbosity with length control; the pairwise consistency rate is monitored.
  • Could the rewriter change a fact? Yes, which is why fact consistency against the source is a gate and the approved texts are verbatim by flag.

3 · Learning from reviewers: annotation, rubrics, reward models, RLHF and RLAIF

Every accept, reject, edit and comment a reviewer makes is a label. Where it runs, and what governance asks

At Capital Group the stack is AWS: Bedrock for inference, and for fine-tuning either Bedrock custom models or SageMaker training jobs with LoRA on an open model, with artefacts in a model registry. Governance asks for a model-risk record per version (data lineage, evaluation results, limitations, approver), no client PII in training data (the drafts are marketing copy, but comments can mention clients, so redaction runs before anything is stored), retention rules on the event log, and a rollback path. The frozen-weight loop ships inside the application change process; a fine-tuned model is a model release with its own approval.

The constitution for RLAIF, in practice

Not a philosophy document: a numbered list derived from the four guidelines and the graph — C1 approved disclosure texts verbatim; C2 facts only from the source; C3 no promissory language; C4 opening within the editorial limit; C5 the firm’s lexicon; and so on — plus tie-break rules in the same precedence as the planner. The labeler must cite clauses in its rationale; labels without clauses are discarded. Its agreement with the 500-pair human slice is a release gate for the labeler itself.

How the loop is run

  1. Instrument the review UI so every decision carries the versions of the judge, prompt, graph and guidelines, and a reason code on rejects. Without versions the data cannot be attributed.
  2. Write the annotation guideline as a decision procedure (what counts as a substantive edit, how to code a comment, when a pair is valid), pilot it on 30–50 items with three annotators, and measure α; 0.8 is reliable, 0.67–0.8 tentative. Fix the guideline before scaling.
  3. Build the datasets with splits by task and by reviewer so the evaluation set never shares items with training; freeze goldens per version.
  4. Calibrate the judges first. Agreement per criterion; fix checklists; only then use the judges as graders for anything else.
  5. Start with the frozen-weight loop: prompt optimisation against the goldens, better examples, better retrieval. Measure win rate on held-out pairs with a Wilson interval.
  6. Add RLAIF when labels are the bottleneck, with the constitution, the swap, and the human slice gate (κ ≥ 0.8).
  7. Fine-tune when governance allows: SFT, then DPO on pairs; GRPO with rubric rewards if pairs are scarce. Each run gets a model-risk record.
  8. Gate every version: twin agreement κ ≥ 0.7, legal gate recall ≥ 0.95, held-out win rate up with the interval clear of 50%, no regression on the frozen goldens; canary to one team; rollback by configuration.
  9. Watch for reward hacking and drift: length distributions, disclosure counts per item, reviewer edit distance over time; a guideline change re-baselines the goldens (major version) and re-calibrates the twins.

The formulas in use

Bradley–Terry: P(a ≻ b) = σ(r(a) − r(b)); loss = −log σ(r(chosen) − r(rejected))
DPO: loss = −log σ( β·[log π(y_w|x)/π_ref(y_w|x) − log π(y_l|x)/π_ref(y_l|x)] )
GRPO advantage for candidate i of G: A_i = (r_i − mean(r)) / std(r); objective = clipped policy ratio × A_i − β·KL(π ‖ π_ref)
rubric reward: R = gates × Σ_j w_j·v_j / Σ_j w_j (v_j ∈ {0,1} or scaled ordinal; gates ∈ {0,1})
agreement: κ = (p_o − p_e) / (1 − p_e); win rate CI: Wilson interval on k wins of n pairs

How learning from reviewers goes wrong

  • Reward hacking. The rewriter learns that more disclosures and longer text pass the legal gate and score higher; readers suffer. Length terms, “exactly the required disclosures” as a check, and the editorial twin in the reward.
  • Teaching the model to override. A reviewer overrides a legal gate once; if that becomes a pair, the model learns the override. Overrides are escalations, never training data.
  • Label leakage between eval and training. Pairs from the same draft on both sides; the win rate looks great. Split by task and reviewer.
  • Learning a reviewer’s idiosyncrasies. One reviewer hates semicolons; the model learns it as law. Calibrate per reviewer, train on the guideline owner’s view, and code comments against the guideline.
  • Distribution shift after a rule change. Pairs labelled under disclosure v6 train a model for v7. Version everything; retire pairs whose rule versions are superseded.
  • RLAIF agreeing with itself. Labeler, judge and rewriter from one model family produce a closed loop that is confident and wrong. Different families, the swap, the human slice.
  • Too few pairs, too much optimisation. DPO on 200 pairs overfits to wording. Thresholds on data size before training; otherwise stay in the frozen-weight loop.
  • Rubrics that reward keywords. “Mentions risk” is satisfied by the word “risk”. Criteria must describe the behaviour and require evidence; lint the rubric.
  • No re-baselining. Goldens that never change hide drift. Major version on criteria changes; re-run and re-publish the baseline.

def rubric_reward(text, items, checks):
    """items: [{id, weight, gate, verdict∈{0,1}}] from the judge; checks: code-verified items."""
    gates = all(i["verdict"] == 1 for i in items + checks if i["gate"])
    num = sum(i["weight"] * i["verdict"] for i in items + checks)

Saying it

Thirty secondsThe self-improving part is a data loop, not a magic model. Reviewer decisions are logged with every version; edits become preference pairs, rejects carry reason codes, comments become rubric candidates. We calibrate the judges first, ship prompt-level improvements inside the app, and when governance allows we fine-tune the rewriter with SFT and DPO, or GRPO with rubric rewards. RLAIF labels are produced under a written constitution and checked against a human-labelled slice. Every version is gated on agreement with humans, held-out win rate and legal recall.
Two minutesIn a regulated firm the question is not whether to do RLHF, it is what you are allowed to change and how you prove it got better. So the design starts with the data. The review UI records every accept, reject, edit and comment with the versions of the judge, the prompt, the graph and the guidelines; a substantive edit is an implicit preference pair, a pairwise choice is an explicit one, a reject carries a reason code, a comment is coded by an annotator against the guideline, and an override of a legal gate is an escalation that never becomes training data. The annotation guideline is a decision procedure piloted on thirty to fifty items with three annotators until Krippendorff’s alpha is above 0.8. Datasets are split by task and reviewer; goldens are frozen per version. Then the learners, in order of what governance allows: the frozen-weight loop first — prompt optimisation, examples, retrieval, judge checklists — which is where most of the first year’s gain came from; then, as a model release with its own model-risk record, SFT on accepted rewrites and DPO on two to five thousand pairs, or GRPO with the rubric as the reward when pairs are scarce, which is the Rubrics-as-Rewards recipe. Rewards are rubrics plus verifiable checks: approved texts verbatim, facts from the source, banned terms absent; the Bradley–Terry model is the implicit alternative for holistic preferences. RLAIF enters when human labels are the bottleneck: a labeler from a different model family follows a numbered constitution derived from the guidelines and the graph, cites clauses, is position-swapped, and must agree with a five-hundred-pair human slice at kappa 0.8 before its labels count. Every version passes three gates: twin agreement with humans, held-out win rate with the interval clear of fifty percent, and legal gate recall; then a canary and a rollback switch.

Likely questions

  • RLHF or RLAIF, which did you use? Both, in order: human labels from ordinary reviewer decisions first; an AI labeler under a constitution once the human slice showed it could be trusted; the human slice never went away.
  • Why rubrics rather than a reward model? The criteria are known, owned and auditable, and legal items are gates; a scalar reward hides all of that. We kept a Bradley–Terry model for the holistic part and used the rubric as the primary reward.
  • How much data did you need? Hundreds of goldens to evaluate, thousands of pairs to fine-tune; below that, stay in the frozen-weight loop. Edits produce most pairs for free.
  • What stopped reward hacking? Length control, the editorial twin inside the reward, “exactly the required disclosures” as a check, and watching the edit distance reviewers apply over time.
  • How did governance fit? Prompt-level changes inside the application change process; a fine-tuned model as a model release with a risk record, evaluation results, approver and rollback.

What “information, not advice” means in code

Outputs describe what happened, who said it, who is exposed and what history shows, with citations. They do not say buy, sell, overweight, target price, or “we expect the stock to”. A term list catches the obvious; a judge scores each output for recommendation language and forward-looking claims about returns; either rejects the sentence and the trace records it. The same rule that keeps the marketing content compliant (card 1) keeps the brief compliant.

How it is built

  1. Decide the products with the analysts: a brief, alerts, Q&A. Write the acceptance criteria in their words: “nothing in my brief is about the wrong company”, “I can click to the source”.
  2. Settle data access with compliance first: which feeds are licensed for this use, which internal views the agent may read (aggregated exposure yes, trades no), retention, and the recommendation-language policy.
  3. Build the security master alias table and the resolver; measure link accuracy on 1,000 labelled mentions; threshold and a human queue for the rest.
  4. Define the taxonomy and the schema with the analysts; label 1,000 documents; measure extraction precision and recall by type; gate at recall ≥ 0.9 on the material types.
  5. Compute the event-study priors from history; show them as history; never as a forecast.
  6. Stand up the stores and the tools as governed views; the semantic layer for run_sql with named metrics and row limits.
  7. Build the agent with a citation checker and a compliance guard; every sentence must map to a source id; outputs without a citation are rewritten or dropped.
  8. Pilot with ten analysts: brief at 06:30, alerts in the day, Q&A; collect useful / not useful / wrong-entity ratings; measure timeliness.
  9. Operate: feed health, link accuracy drift, alert precision, cool-downs, cost per brief; taxonomy reviews when “other” grows.

How news agents fail

  • Wrong entity. “Apple” the grower, “Meta” the word, a subsidiary mapped to the wrong parent. Alias tables, context disambiguation, a confidence threshold, a human queue.
  • Duplicates as momentum. Fourteen outlets repeating one wire story look like a developing situation. Cluster first; novelty against the cluster.
  • Look-ahead in the event study. Using the close of day 0 when the event hit after the close. Event time, not publish time, and a careful window.
  • Hallucinated figures. A guidance number that is not in the source. Figures carry spans; the citation checker compares.
  • Advice leakage. “This looks like a buying opportunity.” Term list, judge, zero tolerance, trace.
  • The agent seeing too much. A tool over raw holdings or the blotter turns a research aid into an information-barrier incident. Governed, aggregated views; read-only; logged.
  • Over-alerting. Every rating change pages the analyst. Materiality thresholds, novelty, cool-downs per entity.
  • Backtesting the agent as alpha. Someone builds a strategy from the alerts and calls it a signal. Out of scope; say so in the charter.
  • Licensing. Storing or displaying feed content the licence does not allow. The source registry is enforced in code, not in a policy document.
  • Latency as an afterthought. A brief that is right at 09:30 and useless. Streaming, not batch; the strong model only on material clusters.

import numpy as np

def car(ret, mkt, event_idx, est=(-250, -30), win=(0, 1)):
    e0, e1 = event_idx + est[0], event_idx + est[1]
    beta, alpha = np.polyfit(mkt[e0:e1], ret[e0:e1], 1)            # market model on the estimation window
    w0, w1 = event_idx + win[0], event_idx + win[1] + 1
    abnormal = ret[w0:w1] - (alpha + beta * mkt[w0:w1])
    return float(abnormal.sum())

The knowledge graph: UCS and what sits around it

The Universal Category System is the sound-effects industry’s taxonomy: 82 main categories from Air to Wood and more than 750 subcategories, with a filename convention (category id, effect name, creator id, source id) that most libraries now follow. The graph holds the taxonomy as nodes with synonyms and typical durations, and adds edges the taxonomy does not have: SOUNDS_LIKE (a door creak and a wooden chair creak), CO_OCCURS_WITH (footsteps on gravel and a car door outside), MATERIAL_OF (wood, metal, glass across categories), PERSPECTIVE_VARIANT, and RIGHTS (licence, territory, attribution). Retrieval uses it to constrain (category), to expand (synonyms, neighbours) and to exclude (rights). Each library clip carries an audiocard: structured metadata grounded in acoustic attributes and sonic descriptors, generated by an LLM from the clip, its filename and its existing tags, which Adobe Research showed in February 2026 improves retrieval and captioning over single-sentence captions.

What the reranker learns from, and what the judge is held to

The reranker optimises a pairwise objective: for each event, the clip the editor kept beats each shown clip the editor passed over, weighted by slot propensity; swaps within the top five are the most informative pairs because the alternatives were seen. The judge is a classifier of fit with typed reasons; its calibration set is the editor’s keep / reject decisions on the judge’s own verdicts, and its threshold is set where precision on “fit” reaches the level the editors asked for. Both retrain weekly on a fixed schedule, and both are evaluated on a frozen set of 500 events from finished projects before a version replaces the previous one.

How it is built, and what the loop buys

  1. Library first. Normalise filenames to UCS, generate audiocards for every clip with an LLM from audio, filename and tags, QA a sample with a sound designer, compute CLAP and text embeddings, load rights.
  2. The graph. UCS categories and subcategories as nodes with synonyms; add the relations editors use (sounds like, co-occurs, material of, perspective variant, rights); validate with two designers.
  3. Scene detection and annotation. TransNetV2 plus grouping; annotate 1,000 scenes with a frontier model, correct 300 by hand, fine-tune the annotator (card 6); measure field-level F1 and JSON validity.
  4. Events and queries. Prompt the proposer with the schema and the existing-sounds suppression; check duplicate rate against the mix on 100 scenes.
  5. Retrieval and the first reranker. Hybrid search; recall@50 against editor picks from past projects; a first fit model on heuristics (duration ratio, loudness, UCS match) before any clicks exist.
  6. The judge. Typed criteria; calibrate on 300 editor decisions; set the threshold for the precision editors want on “fit”.
  7. Placement. Motion-peak onset; transient alignment; level rules per category; fades; verify sync on 50 events by eye and ear.
  8. The editor UI and the feedback store. Five options, one-click actions, slot logging, 5% randomised sessions.
  9. The loop. Weekly retraining of the reranker on pairs and recalibration of the judge; a frozen 500-event evaluation set; a version ships only if nDCG@5 and judge precision do not regress and top-1 acceptance holds.

What goes wrong

  • Doubling sounds already in the mix. The annotator never heard the recording; the pipeline adds a second glass clink. Audio-visual annotation or an audio tagger on the existing track, and an existing-sounds suppression list.
  • Shots mistaken for scenes. Ambience restarts at every cut. Group shots into scenes before proposing ambiences.
  • Material and perspective confusion. CLAP finds “drawer” but not “wooden, close, sticky”. Audiocards with materials and perspective, graph constraints, and the fit model’s features.
  • Position bias in the training data. Slot 1 is chosen because it is slot 1; the reranker learns to agree with its past self. Log slots, randomise 5%, weight by propensity.
  • A judge that rubber-stamps. If the top-1 is usually fine, the judge says fit to everything. Calibrate on rejects as well as keeps; monitor precision on “fit” and the reject rate.
  • Variety collapse. The loop keeps recommending the 200 clips editors picked last month. Diversity in the top-5 (at most two clips from one source), exploration slots, an editor prior with decay.
  • Sync drift. Variable frame rates, dropped frames, timecode offsets. Work in sample positions from the decoded stream; verify onset alignment per event.
  • Rights. A beautiful clip the project may not use in that territory. Rights as a hard filter before retrieval, not a warning after.
  • Long videos and cost. A feature film is thousands of events; audio in prompts is expensive. Scenes in parallel, the judge only on the top-5, the frontier model only when the open model’s confidence is low.
  • Generated audio passed off as library. Flag it, store its provenance, and never retrain the reranker on generated clips as positives.

# rerank.py — a text cross-encoder for semantic fit plus a pairwise GBDT fit model; combined by a learned weight
import lightgbm as lgb

def features(event, clip):
    return [clap.cos(event["clap_q"], clip["clap"]), clip["duration_s"] / max(event["dur"], 0.1),
            abs(clip["audiocard"]["loudness_lufs"] - target_lufs(event)), clip["transient_density"],
            float(clip["ucs"]["id"] == event["ucs"]), clip["editor_prior"]["selections"] / (clip["editor_prior"]["impressions"] + 20),
            float(clip["audiocard"]["perspective"] == event["perspective"])]

def train_fit_model(pairs):            # pairs: (query_id, pos_features, neg_features, weight)
    X, y, g, w = [], [], [], []
    for qid, pos, neg, wt in pairs:
        X += [pos, neg]; y += [1, 0]; g.append(2); w += [wt, wt]
    ds = lgb.Dataset(X, label=y, group=g, weight=w)
    return lgb.train({"objective": "lambdarank", "metric": "ndcg", "eval_at": [5], "learning_rate": 0.05, "num_leaves": 31}, ds, 400)

def rerank(event, cands, ce, fit, alpha=0.6):
    s_text = ce.score([(event["desc"] + " | " + event["scene_context"], c["audiocard_text"]) for c in cands])   # cross-encoder
    s_fit = fit.predict([features(event, c) for c in cands])
    score = alpha * zscore(s_text) + (1 - alpha) * zscore(s_fit)
    return sorted(zip(cands, score), key=lambda t: -t[1])[:5]

def log_action(session, event_id, shown, chosen, action, edits, randomised):
    store.insert("feedback", dict(session=session, event_id=event_id, shown=shown, chosen=chosen, action=action,
                                  edits=edits, slot_randomised=randomised, ts=now()))

def pairs_from_feedback(rows, propensity):        # propensity[slot] = P(examined | slot), from the randomised 5%
    out = []
    for r in rows:
        if r["action"] not in ("keep", "swap"): continue
        for slot, clip in enumerate(r["shown"]):
            if clip != r["chosen"]:
                out.append((r["event_id"], r["chosen"], clip, 1.0 / propensity[slot]))
    return out

Saying it

Thirty secondsAt Noctal the sound-design pipeline turns an uploaded video into a timeline with effects placed and five alternatives per event. Scene detection, then an annotator that sees the picture and hears the existing mix, then sound events with times, hybrid retrieval over structured metadata, CLAP and a UCS knowledge graph, a reranker trained on editors’ choices, a judge that hears the candidate on the picture, and placement from motion peaks. Every keep, swap and trim is logged and retrains the reranker and recalibrates the judge weekly.
Two minutesThe product promise was a first cut in minutes instead of an afternoon, with the editor in charge. The pipeline is a LangGraph of stages, each narrowing. TransNetV2 finds the cuts and we group shots into scenes by CLIP similarity and audio continuity, because ambiences and perspective belong to scenes. The annotator fills a JSON schema — setting, actions with times, sounding objects and materials, camera distance, mood — and crucially lists what is already audible, so we never propose a second door slam. A proposer turns that into sound events: what needs a sound, when, how salient, from what perspective. For each event we retrieve fifty candidates with hybrid search: BM25 over audiocards, structured metadata per clip with source, action, material, texture, envelope and perspective; CLAP text-to-audio vectors; and the knowledge graph of the UCS taxonomy with the relations editors think in — sounds like, co-occurs with, material of — plus rights as a hard filter. A reranker cuts fifty to five: a text cross-encoder for semantic fit and a gradient-boosted fit model on audio features and the editor prior, trained pairwise on what editors kept over what they were shown, with slot randomisation in five percent of sessions so it does not learn its own position bias. A multimodal judge then hears each candidate muxed under the scene and answers typed questions: same object, material, sync plausible, perspective, tone. Placement aligns the effect’s transient to the nearest motion peak, sets duration and gain by category. The editor gets five options per event, and every action is logged with what was shown. Weekly, the reranker retrains and the judge recalibrates, gated on a frozen set of five hundred events: recall at five, nDCG at five, judge precision and top-one acceptance must hold. When nothing fits, a video-to-audio model generates a candidate, flagged as generated.

Likely questions

  • Why a knowledge graph when you have embeddings? Constraints and exclusions embeddings cannot express: category, rights, perspective variants, and the editor’s own relations; it also gives explanations (“retrieved through sounds-like from DRWRWood”).
  • How does the reranker avoid learning position bias? Impressions logged with slot; 5% randomised sessions estimate examination propensity; pairs weighted by inverse propensity.
  • How is the judge different from the reranker? The reranker orders by learned preference from text and audio features; the judge hears the actual result on the picture and answers typed criteria; it is calibrated against editor keeps and rejects, with a threshold set for the precision editors asked for.
  • What about sync? The annotation’s time is approximate; the onset comes from the motion peak in the frames and the effect’s transient; sync error is measured in frames on a sample every week.
  • Where does generation fit? As a labelled fallback when the library has nothing that passes; library sound is licensed, consistent and editable.
  • What did editors change your mind about? Five options rather than one, the duplicate problem, and that explanations mattered as much as rank.

How the models are built, in order

  1. Freeze the evaluation sets first. 300 human-corrected scenes, 2,000 held-out library clips with editor-kept labels, 300 judge verdicts; all from projects after a cut-off date; nobody trains on them.
  2. Audiocards and AST on the library. Generate structured metadata for every clip, QA 500 with a designer, fine-tune AST on UCS classes to catch mislabelled clips; fix the library before any retrieval model sees it.
  3. CLAP fine-tune. Pairs from audiocards, hard negatives within subcategory, replay; train until held-out R@10 stops improving; compare against the base model on the same set.
  4. CLIP fine-tune or probe. Scene-grouping agreement and zero-shot tag accuracy decide whether the probe is enough.
  5. Annotator. Frontier labels on 1,000 scenes, 300 corrected; LoRA SFT of the video-language model; field F1 and JSON validity; iterate on the schema where F1 is low because the schema was ambiguous.
  6. Omni annotator and judge. Add the existing-audio field and the judge task; LoRA on the Thinker; gates on existing-sound recall and judge precision.
  7. Serving. Export encoders to TensorRT, deploy on Triton with dynamic batching; vLLM for the Omni model; load test per scene and per video; set autoscaling on queue depth.
  8. Register and gate. Every artefact in the registry with its data snapshot, hyperparameters and metrics; promotion requires no regression on the frozen sets and a canary on one editor team.
  9. Loop. Weekly data refresh from the feedback store; monthly retrains for encoders, on demand for the language models; drift alerts on retrieval recall and judge precision.

The arithmetic that comes up

InfoNCE (one direction): L = −(1/N) Σ_i log [ exp(s_ii / τ) / Σ_j exp(s_ij / τ) ], s_ij = cos(a_i, t_j); the symmetric loss averages both directions
LoRA parameters per adapted matrix: r × (d_in + d_out); r = 16 on a 4096 × 4096 projection = 131,072 vs 16.8 M full
throughput: scenes / hour / GPU = 3600 ÷ (batch latency ÷ batch size); cached embeddings remove the encoder term for repeat clips
memory for a 30B-A3B MoE in bf16 ≈ 2 bytes × 30 B ≈ 60 GB + KV cache; fp8 ≈ 30 GB

What goes wrong in multimodal training and serving

  • Leakage by clip or by shot. Random splits put the same footage on both sides; reported F1 is fiction. Split by project and by date.
  • Catastrophic forgetting in CLAP. Fine-tuned on the library, it forgets general sounds and the next client’s library suffers. Replay and a general held-out set in the gate.
  • Small contrastive batches. In-batch negatives are too few and easy; the model learns nothing about materials. Large batches, gradient caching if memory is short, mined hard negatives.
  • Noisy teacher labels. Frontier labels with wrong times or invented objects train a confident student. Human correction on a sample, up-weighted; time errors measured, not assumed.
  • Schema drift. The annotator trained on schema v2 serves a pipeline on v3. Schema versions in the registry; constrained decoding against the served version.
  • Over-fitting the judge to one editor. Judge SFT on one editor’s rejects learns that editor’s taste. Balance across editors; evaluate per editor.
  • Cold starts and fragmentation on GPUs. Replicas that take minutes to load and pools fragmented across models. Warm pools, model-per-pool, autoscaling on queue depth with minimums.
  • Long inputs. A five-minute scene at 2 fps blows the context or the memory. Chunk by shot, sample adaptively, pass the annotation of the previous chunk as context.
  • Licences. Research-only weights in a commercial product, or client footage in a training set without consent. A licence field on every model and dataset in the registry; consent recorded per project.
  • Timestamps. Frame indices from one decoder, seconds from another, variable frame rate in between. One time base per pipeline, in samples, derived from the decoded stream.

import torch, torch.nn.functional as F
from transformers import ClapModel, ClapProcessor

model = ClapModel.from_pretrained("laion/clap-htsat-fused")
proc = ClapProcessor.from_pretrained("laion/clap-htsat-fused")
for p in model.text_model.parameters(): p.requires_grad = False      # stage 1: freeze the text tower
opt = torch.optim.AdamW([p for p in model.parameters() if p.requires_grad], lr=1e-5, weight_decay=0.01)

def step(audios, texts, hard_neg_texts):
    inputs = proc(text=texts + hard_neg_texts, audios=audios, sampling_rate=48000, return_tensors="pt", padding=True)
    out = model(**inputs)
    a = F.normalize(out.audio_embeds, dim=-1)                        # [B, d]
    t = F.normalize(out.text_embeds, dim=-1)                         # [B + H, d]: positives then hard negatives
    logits = a @ t.T / model.logit_scale_a.exp()                     # learnable temperature
    labels = torch.arange(len(audios))
    loss = F.cross_entropy(logits, labels)                            # audio → text over positives + hard negatives
    loss = loss + F.cross_entropy(logits[:, :len(audios)].T, labels)  # text → audio
    loss.backward(); opt.step(); opt.zero_grad()
    return loss.item()

Saying it

Thirty secondsThe Noctal model is a stack, not a model: CLIP for frames, CLAP for audio, a video-language model for structured scene annotation — Video-LLaVA first, now the Qwen Omni family so it can hear the existing mix and judge fit — AST for tagging what is already audible, ViT for shot classes, diffusion for previews. Encoders are fine-tuned contrastively with hard negatives and replay; the language models get LoRA SFT on a few thousand corrected examples; everything is gated on frozen sets split by project and served on GKE with Triton and vLLM, with Vertex AI for training jobs and endpoints.
Two minutesWhen people ask how to build the Noctal model I start with the jobs. Grouping shots into scenes and tagging settings is a CLIP job; we fine-tuned it contrastively on keyframes paired with annotation phrases, with thirty percent replay so it kept its general knowledge, and measured scene-grouping agreement with editors. Finding sounds is a CLAP job; we built audiocards for forty thousand clips, trained with hard negatives from the same UCS subcategory so the model learned materials and perspective, and measured text-to-audio recall on held-out clips; the 2026 option is Text-Prompted CLAP, which conditions the audio features on the query. Annotating a scene into a schema was Video-LLaVA at the start: LoRA SFT on three to five thousand short clips labelled by a frontier model and corrected by editors, loss on the JSON tokens, constrained decoding at inference, field-level F1 as the gate. Its successors are Qwen3-VL and then Qwen3-Omni, which hears the existing audio track, so the annotator lists what is already there and the pipeline stops doubling sounds; the same model with a second LoRA task is the judge that hears a candidate on the picture. The frontier Omni models — Qwen3.5-Omni, Qwen3.8-Omni-Flash — are teachers for labels and the judge for hard cases through the API. AST tags the uploaded mix in batch, ViT classes shots for perspective, diffusion draws previews behind a scale-to-zero endpoint. Serving matched each model’s shape: encoders as TensorRT fp16 engines on Triton with dynamic batching and cached embeddings on an L4 pool; the Omni model on vLLM with continuous batching on A100 or H100; scenes processed in parallel. The eighty percent throughput uplift on the resume came from that class of lever, and the engagement lift from first cuts arriving in minutes. Every fine-tune was gated on frozen evaluation sets split by project, registered with its data snapshot, and canaried with one editor team.

Likely questions

  • Why not one big multimodal model for everything? Cost and control: encoders are tiny and hot; the language model is large and bursty. One model that sees and hears (Qwen3-Omni) replaced two steps, not six.
  • What did Video-LLaVA get wrong that made you move? Timing of actions and anything audible; it could not hear. Qwen3-VL improved the picture; Qwen3-Omni added the audio.
  • How did you fine-tune CLAP without breaking it? Replay, freezing the text tower first, large batches with mined hard negatives, and a general held-out set in the release gate.
  • How many examples does a LoRA need? A few thousand corrected examples for a schema and a vocabulary; the frontier teacher makes the first thousand cheap, humans make three hundred of them right.
  • Where did the throughput come from? Batching and fp16 engines on the encoders, cached embeddings, continuous batching for the language model, and scenes in parallel; measured in scenes per hour per GPU.
  • TPU or GPU? TPU v5e for batch inference over a whole library with the ViT and CLIP towers; GPUs for the interactive path and for the language model.

How it is built

  1. List the tasks and their parameters with the product team; write each flow as a table of pages, parameters, validation rules and the webhook tag that fulfils it.
  2. Define the webhook contract first as an OpenAPI document: tags, parameters in, parameters and messages out, error shapes, versions. The backend team builds to it; the designers build against a mock.
  3. Build the entities: UCS categories with synonyms from the knowledge graph, regex time ranges with unit tests, session entities fed by the backend.
  4. Build the flows thin: forms, re-prompts, no-match and no-input handlers with limits, confirmations where money or files move.
  5. Record test cases from the first week; run them in CI on every agent change; block promotion on failures.
  6. Add generative features last: generators for summaries, fallback with the docs, one playbook for open asks; measure fallback rate before and after.
  7. Export conversation history to BigQuery; dashboards for completion per flow, containment, fallback, p50 duration; weekly review of no-match utterances to add training phrases.
  8. Operate: version per flow, environments, webhook SLOs (p95 and error rate), alerting on fallback spikes after releases.

What goes wrong

  • The backend drives page transitions. targetPage from the webhook makes the console lie; nobody can read the conversation policy. Policy in the flow, data from the webhook.
  • Overlapping intents. “download” for a clip, a video and a segment as three intents with similar phrases; the classifier guesses. One intent with a parameter, or route by flow context.
  • Giant forms. A page that asks seven questions before doing anything. Defaults, session entities, and ask only what the task needs.
  • Synchronous long jobs. A cut that takes forty seconds inside a webhook with a thirty-second timeout. Job id, async worker, push event.
  • Files through the chat. Size limits, timeouts, no resumability. Signed URLs.
  • Refunds decided by a model. Generative features near money. Policy in code; the bot explains the policy; the human decides the exceptions.
  • No test cases. Designers change a page, a parameter disappears, fulfilment breaks on Friday. Record from week one; run in CI.
  • Measuring intent accuracy and calling it success. Users understood and then abandoned at a bad confirmation step (the E.ON lesson). Completion first; classifier metrics as diagnostics.
  • Private data in the agent definition. Project names and charges as static entities. Session entities, scoped to the user and the session.
  • Old names in the room. “Dialogflow ES” thinking, or not knowing the 2026 console names. Flows and playbooks, Conversational Agents, Customer Engagement Suite.

Where pricing systems go wrong

  • Elasticity from promotions. A coupon week looks like price sensitivity and the model recommends permanent markdowns. Controls, exclusion of promo weeks, pooling.
  • Stock-outs read as zero demand. The forecast learns that a SKU sells nothing in the weeks it was unavailable. Mask stock-out weeks; impute from sessions.
  • Winning on price, losing the Buy Box. A rise that clears the competitor median by a few percent loses the box and most of the sales. The cap, and the Buy Box share in the outcomes.
  • Per-SKU models. Thousands of noisy models for slow movers. One global model; hierarchical pooling for elasticity.
  • Fees that depend on price. Referral fees are a percentage; margin per unit is not constant. The fee-aware margin in the objective.
  • Markdowns deep enough to cause the next stock-out. The optimiser must simulate inventory, not just this week’s profit.
  • Identity. ASIN, SKU, Linnworks id and marketplace variants mapped wrong; the SKU with 17 weeks of cover is actually two. The mapping table owned by operators.
  • Text-to-SQL over raw tables. The copilot invents a column and a number. A semantic layer with named metrics; answers cite definitions.
  • Recommendations without reasons. Operators ignore a number; they argue with a reason and then accept it. The binding constraint, in their units, on every row.
  • Attribution after the fact. Claiming $1.5M with no holdout invites a fight. Agree the measurement with finance before the first run.

# elasticity.py — log-log with controls per SKU, shrunk toward the family estimate
import numpy as np, pandas as pd, statsmodels.formula.api as smf

def sku_elasticity(df):                      # weekly rows: units, price, promo, season, stockout, comp_index
    d = df[(df.units > 0) & (~df.stockout)]
    m = smf.ols("np.log(units) ~ np.log(price) + promo + C(season) + np.log(comp_index)", data=d).fit()
    return m.params["np.log(price)"], m.bse["np.log(price)"]

def pooled(eps_sku, se_sku, eps_family, tau=0.3):
    """precision-weighted shrinkage toward the family value; tau = family spread"""
    w = (1 / se_sku**2) / (1 / se_sku**2 + 1 / tau**2)
    return w * eps_sku + (1 - w) * eps_family
# optimise.py — grid search over a 12-week inventory simulation with guardrails; returns price, profit and the binding constraint
def simulate(p, sku, weeks=12, h=0.12, penalty_per_unit=8.0):
    D = sku.D0 * (p / sku.p0) ** sku.eps
    margin = (1 - sku.fee_rate) * p - (sku.landed + sku.fulfilment)
    inv, profit, hold = sku.on_hand, 0.0, 0.0
    for t in range(1, weeks + 1):
        sold = min(D, inv)
        profit += sold * margin
        inv = inv - sold + sku.inbound.get(t, 0)
        hold += h * inv
        if t == sku.capacity_week:
            profit -= penalty_per_unit * max(0.0, inv - sku.capacity_limit)
    return profit - hold, D, margin

def recommend(sku, guard):
    best = None
    for p in np.arange(guard.p_min(sku), guard.p_max(sku) + 0.01, 0.5):
        if abs(p / sku.p0 - 1) > guard.max_step: continue                  # ±10% per week
        if p < sku.map_price or p > guard.buybox_cap * sku.comp_median: continue
        if ((1 - sku.fee_rate) * p - sku.landed - sku.fulfilment) / p < guard.margin_floor: continue
        profit, D, margin = simulate(p, sku)
        if best is None or profit > best["profit"]:
            best = {"price": round(p, 2), "profit": round(profit), "units_wk": round(D, 1), "margin": round(margin, 2)}
    best["binding"] = guard.binding_constraint(sku, best["price"])      # which rule or stock check decided it
    return best

-- overstock and understock lists from the semantic layer's definitions (Databricks SQL)
WITH pos AS (
  SELECT sku, on_hand, landed_cost, forecast_4wk_avg, on_hand_week9, capacity_check,
         on_hand / NULLIF(forecast_4wk_avg, 0) AS weeks_of_cover, inbound_before_stockout
  FROM gold.stock_position WHERE as_of = CURRENT_DATE())
SELECT sku, weeks_of_cover, on_hand * landed_cost AS tied_up_value,
       CASE WHEN weeks_of_cover > 12 OR on_hand_week9 > capacity_check THEN 'overstock'
            WHEN weeks_of_cover < 3 AND NOT inbound_before_stockout THEN 'understock' END AS status
FROM pos WHERE weeks_of_cover > 12 OR on_hand_week9 > capacity_check OR (weeks_of_cover < 3 AND NOT inbound_before_stockout)
ORDER BY tied_up_value DESC;

What goes wrong

  • Training–serving skew. A feature computed one way offline and another way online; the model is right in the notebook and wrong in production. One feature definition, parity tests, skew checks before training.
  • Feedback loops. The model trains on what it showed; new creatives never get shown; the model confirms itself. An exploration slice with logged propensities.
  • Position and placement bias. Clicks depend on where the ad sat; the model learns the slot. Position as a feature at training, fixed at inference, or inverse propensity weighting.
  • Delayed conversions. Labels arrive days later; yesterday’s negatives are tomorrow’s positives. Observation windows, importance weighting, or a delayed-feedback model.
  • Calibration drift. The ranker ranks well and prices everything wrong. Calibration as a guardrail; recalibrate per placement.
  • Index recall. The ANN quietly drops the best candidates after a rebuild. Recall@k against brute force on every build.
  • Peeking at the A/B test. Significance found by looking every hour. Sequential tests with fixed looks, or a fixed horizon with power computed in advance.
  • Metric conflict. CTR up, revenue down, advertisers concentrated, users annoyed. Primary metrics plus guardrails, and the commercial owners decide the frontier.
  • Censoring ignored in bid landscapes. Losing bids with no clearing price treated as missing at random. Survival models or censored regression.
  • Consent treated as a checkbox. Profile features used where the purpose was not consented. Consent gates in the feature store, not in a policy document; contextual fallback.

A two-tower model, the index, the gate and a bid landscape

# two_tower.py — context tower and ad tower; in-batch softmax with logQ correction; PyTorch
import torch, torch.nn as nn, torch.nn.functional as F

class Tower(nn.Module):
    def __init__(self, vocab_sizes, dense_dim, d=128):
        super().__init__()
        self.embs = nn.ModuleList([nn.Embedding(v, 32) for v in vocab_sizes])
        self.mlp = nn.Sequential(nn.Linear(32 * len(vocab_sizes) + dense_dim, 512), nn.ReLU(), nn.Linear(512, 256), nn.ReLU(), nn.Linear(256, d))
    def forward(self, cats, dense):
        x = torch.cat([e(c) for e, c in zip(self.embs, cats.unbind(1))] + [dense], dim=1)
        return F.normalize(self.mlp(x), dim=-1)

class TwoTower(nn.Module):
    def __init__(self, ctx_vocabs, ctx_dense, ad_vocabs, ad_dense, temp=0.05):
        super().__init__()
        self.ctx, self.ad, self.temp = Tower(ctx_vocabs, ctx_dense), Tower(ad_vocabs, ad_dense), temp

    def loss(self, ctx_cats, ctx_dense, ad_cats, ad_dense, log_q):
        """log_q: log sampling probability of each in-batch ad (its frequency in the stream) for the logQ correction"""
        u = self.ctx(ctx_cats, ctx_dense); v = self.ad(ad_cats, ad_dense)
        logits = u @ v.T / self.temp - log_q[None, :]            # popular ads are not easy negatives
        labels = torch.arange(len(u), device=u.device)
        return F.cross_entropy(logits, labels)
# index.py — ANN over ad embeddings; recall@500 against brute force on every build
import faiss, numpy as np

def build(ad_vecs: np.ndarray):
    index = faiss.IndexHNSWFlat(ad_vecs.shape[1], 32, faiss.METRIC_INNER_PRODUCT)
    index.hnsw.efConstruction = 200; index.add(ad_vecs); index.hnsw.efSearch = 128
    return index

def recall_at_k(index, ad_vecs, queries, k=500):
    exact = np.argsort(-(queries @ ad_vecs.T), axis=1)[:, :k]
    _, approx = index.search(queries, k)
    return np.mean([len(set(a) & set(e)) / k for a, e in zip(approx, exact)])    # gate: ≥ 0.95
# gate.py — primary metric test with a fixed daily look (a simple z-test on rates; use a sequential method for multiple looks)
from math import sqrt
from scipy.stats import norm

def rate_test(c_clicks, c_n, t_clicks, t_n, alpha=0.05):
    p_c, p_t = c_clicks / c_n, t_clicks / t_n
    p = (c_clicks + t_clicks) / (c_n + t_n)
    se = sqrt(p * (1 - p) * (1 / c_n + 1 / t_n))
    z = (p_t - p_c) / se
    rel = (p_t - p_c) / p_c
    half = norm.ppf(1 - alpha / 2) * sqrt(p_c * (1 - p_c) / c_n + p_t * (1 - p_t) / t_n) / p_c
    return {"rel_lift": rel, "ci": (rel - half, rel + half), "p": 2 * (1 - norm.cdf(abs(z)))}

def decide(primary, guardrails):
    if any(not g["ok"] for g in guardrails): return "rollback"
    return "ship" if primary["ci"][0] > 0 else "hold"
# landscape.py — win probability against bid with censoring handled by a survival model (lifelines)
from lifelines import CoxPHFitter
# rows: duration = our bid; event = 1 if we won (clearing price ≤ bid observed), 0 if we lost (clearing price censored above our bid)
cph = CoxPHFitter().fit(df[["bid", "won", "placement_ctr", "hour", "device_ctv"]], duration_col="bid", event_col="won")
def win_prob(bid, row):
    return 1 - cph.predict_survival_function(row, times=[bid]).iloc[0, 0]

# floors.py — choose the floor per placement from recent auctions, with a bandit for drift
def floor_grid(auctions, floors):
    out = {}
    for f in floors:
        bids = auctions[auctions.max_value >= f]                  # bidders with value ≥ f participate
        paid = np.maximum(f, bids.shaded_bid)                      # shaded bids are lifted to the floor
        out[f] = {"fill": len(bids) / len(auctions), "rev_per_1000": paid.sum() / len(auctions) * 1000}
    return max(out.items(), key=lambda kv: kv[1]["rev_per_1000"])

Why the LLM ranks and narrates but does not decide

The graph walk produces candidate causes with numbers; the model’s job is to weigh them (a floor gap on the placement that carries half the bids outranks a creative rejection from three days ago), write the explanation an account manager reads, and hand a proposal to the policy. A model that acts directly on auction data is a model that one day raises every bid by twenty percent because a feed was late. The policy acts within limits; the human owns the rest; the log makes every version measurable.

How it is built

  1. Label incidents first. Two hundred past failing campaigns with the cause the account managers found; this is the evaluation set for detection and explanation.
  2. Ontology and ingestion. Model the campaign hierarchy and its dependencies; sync hourly from the ad server, DSP and SSP; store config diffs as versioned properties.
  3. Detectors. Plan-vs-actual rules and rate anomalies; tune thresholds on the labelled set for precision ≥ 0.8 at recall ≥ 0.9 on high-severity faults.
  4. Traversal. Implement the dependency walk with an evidence record per hop; measure top-1 and top-3 cause accuracy on the labelled incidents.
  5. Agent. Tools behind MCP; the narration prompt with the evidence; the grounding validator; a pilot with account managers reading the reports next to their own diagnosis.
  6. Action space and limits agreed with the commercial owners; the approval queue and the undo path.
  7. Policy. Start with the account managers’ actions as the logged policy; train the bandit on the decision log; evaluate off-policy; go live within the limits; expand limits as reversal rate stays low.
  8. Operate. Weekly review of incidents the agent missed or misdiagnosed; retrain detectors on new labels; monthly OPE report on the policy.

What goes wrong

  • A stale graph. The ad server changed the floor at 14:00 and the graph says 2.00 until 16:00; the diagnosis is wrong and confident. Hourly sync with change events, and the sync lag shown in the report.
  • Correlation narrated as cause. Delivery fell on Sunday; the agent blames a creative. The walk requires a dependency path and a number; seasonality is a detector baseline, not a hypothesis.
  • Alert fatigue. Every pacing wobble becomes an incident. Severity by plan deviation and money at risk; cool-downs; weekly precision review.
  • The policy changes the data it learns from. Raising bids changes win rates; the next model sees its own effect. Propensities logged, bounded actions, OPE before every version.
  • Reward hacking. A composite reward that favours eCPM makes the policy starve delivery. Guardrails in the reward, delivery as a hard term, reversal rate as a stop signal.
  • The model touches money. An LLM with the ad-server API is one feed outage from a disaster. The model has read tools and a proposal tool; only the policy acts, within limits.
  • Hypotheses without evidence. Fluent reports that cite nothing. The validator rejects claims without evidence ids; the account managers were told to distrust any report without numbers.
  • Labelled incidents never refreshed. The detectors are tuned to last year’s faults. Weekly review of misses; new labels; versioned detectors.
  • Permissions. The agent’s service identity can do everything the ad-server admin can. Least privilege: read, propose, and a separate identity for the bounded apply path.

# policy.py — contextual Thompson sampling (linear-Gaussian per arm) and doubly-robust off-policy evaluation
import numpy as np

class LinTS:
    def __init__(self, arms, d, v=0.5):
        self.arms, self.v = arms, v
        self.A = {a: np.eye(d) for a in arms}; self.b = {a: np.zeros(d) for a in arms}
    def choose(self, x, n_samples=200):
        draws = {a: np.random.multivariate_normal(np.linalg.solve(self.A[a], self.b[a]), self.v**2 * np.linalg.inv(self.A[a]), size=n_samples) @ x for a in self.arms}
        wins = np.argmax(np.stack([draws[a] for a in self.arms]), axis=0)
        probs = np.bincount(wins, minlength=len(self.arms)) / n_samples      # estimated propensity of each arm
        a = self.arms[wins[np.random.randint(n_samples)]]                     # act on one posterior draw
        return a, float(probs[self.arms.index(a)])
    def update(self, x, a, r):
        self.A[a] += np.outer(x, x); self.b[a] += r * x

def doubly_robust(logs, new_policy_probs, reward_model):
    """logs: (x, a, r, p_logged); new_policy_probs(x) → {arm: prob}; reward_model(x, a) → r̂"""
    vals = []
    for x, a, r, p in logs:
        pi = new_policy_probs(x)
        direct = sum(pi[b] * reward_model(x, b) for b in pi)
        vals.append(direct + pi[a] / p * (r - reward_model(x, a)))
    return float(np.mean(vals)), float(1.96 * np.std(vals) / np.sqrt(len(vals)))

Saying it

Thirty secondsTwo agents on the auction data. The fault-detection agent absorbs campaign metadata into a knowledge graph with history, joins hourly metrics, detects deviations with code, walks the dependencies from symptom to cause with a number at every hop, and the model ranks and narrates under a validator that rejects anything without evidence. The next-best-action agent is a bounded contextual bandit with logged propensities, evaluated off-policy before it goes live, acting within limits and handing anything larger to a human with the diagnosis attached.
Two minutesA failing campaign is almost always a relationship problem: a bid below a placement’s floor, a creative rejected by a placement’s policy, a cap too tight for a segment’s reach, a deal not activated on the other side. So the metadata — campaigns, flights, line items, creatives, targeting, placements, deals, pacing plans — lives in a graph with validity times, synced hourly with config diffs, and the hourly metrics are joined by id from a time-series store. Detection is code: plan-versus-actual rules, rate anomalies against same-hour-last-week baselines, and config-change triggers, tuned on two hundred labelled incidents. Explanation is a dependency walk: from the symptom node through targeting filters with eligible counts, placements with floor gaps and wins, creatives with status timelines, caps with hit rates, budgets, deals; each hop yields an evidence record with a number. The language model ranks those hypotheses and writes the report, through MCP tools that are read-only, under a validator that rejects any claim without an evidence id; it never calls the ad-server API. Action is a separate thing: a bounded action space agreed with the commercial owners — bid and floor steps, pacing profile, budget shifts, creative rotation, audience changes — with limits per action. A contextual Thompson-sampling policy chooses within those limits, logs its propensity, and anything above a limit becomes a ticket with the diagnosis attached. Because every decision has a propensity, a new policy version is evaluated on the log with doubly robust estimation before it touches money, and the live measures are approval rate and reversal rate. Four parts, four numbers: detector precision and recall, top-k cause accuracy, off-policy value, reversal rate. The lesson from this work is that an agent earns autonomy limit by limit, and that the graph is what makes the explanation reproducible.

Likely questions

  • Why a graph and not a few SQL joins? History and dependencies: “what changed for this line item in the last day” and “what does it depend on” are one query over versioned edges; the explanation is the path.
  • Why not let the LLM act? A late feed or a stale graph turns a fluent diagnosis into a bad bid change on every line item; the policy is bounded and measurable, the model is not.
  • How do you evaluate the policy without an A/B test on money? Logged propensities and doubly robust off-policy evaluation on the decision log; an A/B test only after OPE says the version is better, and only within the limits.
  • What was the hardest part? Labelling two hundred incidents with the account managers and keeping the ontology honest when three systems disagree about a line item’s state.
  • What does “next best action” mean here? The action with the highest expected composite reward — delivery recovery, eCPM, performance guardrails — given the context, within limits, including “do nothing”.

Likely questions, by theme, with the shape of a good answer

Human in the loop and evaluation

  • Where does the human sit in your systems, and why there? Where the risk owner is: the legal reviewer on findings, the editor on five options, the operator on prices, the account manager above action limits. The human decides; the system proposes, logs and learns.
  • How do you evaluate an LLM system? A frozen golden set from real decisions, typed criteria with evidence, judges calibrated against humans (κ), gates for the things that must never fail, win rates with intervals, and live acceptance rates as the ongoing measure.
  • How do you stop a judge from being gamed? Evidence requirements, gates plus weights, length control, position swaps, a second model family, and watching the edit distance humans still apply.

Knowledge graphs and retrieval

  • When is a knowledge graph worth it? When the answer is relational, versioned and owned by someone who is not an engineer: rules and disclosures, campaign dependencies, a sound taxonomy. Otherwise retrieval is enough.
  • Hybrid retrieval: what and why? Keyword on structured metadata, dense on embeddings, graph constraints and expansions, fused by reciprocal rank; each covers what the others miss, and the graph gives explanations.

Multimodal

  • What are CLIP, CLAP and Video-LLaVA for, and what did you fine-tune? CLIP for frames and scene grouping, CLAP for audio retrieval, Video-LLaVA as the first structured annotator; contrastive fine-tuning with hard negatives and replay for the encoders, LoRA SFT on a few thousand corrected examples for the annotator; then the Qwen Omni family because it hears.
  • How did you serve them? Encoders as TensorRT engines on Triton with dynamic batching on an L4 pool; the language model on vLLM on A100/H100; scenes in parallel; Vertex AI for training and the registry.

Ad tech and pricing

  • Design a ranking system for ads. Cascade with budgets; two-tower retrieval with logQ-corrected negatives and a measured index; calibrated cross-feature ranker with sequence and multi-task heads; auction with bid landscapes; exploration slice; harness with gates and rollback.
  • How do you set floors? As an elasticity question per placement: fill and revenue against the floor from recent auctions, interior because bidders shade; a bandit for drift; the owners choose on the yield-vs-volume frontier.
  • How did you price a retailer’s catalogue? Forecast, price sensing, stock position, one optimiser over an inventory simulation with guardrails, a reason per recommendation, holdout SKUs for attribution.

Agents

  • When should an agent act on its own? Within limits agreed with the owner, with propensities logged and off-policy evaluation before each version, with a reversal rate as the stop signal; above the limits, a human with the diagnosis attached.
  • What kind of agent for market news? Event-driven and portfolio-aware with entity resolution to the security master, a fixed event schema, a temporal graph, read-only tools and a compliance guard; information, never advice.

Behavioural

  • A time you changed your design because of the users. Editors wanted five options and explanations, not one answer; CX designers needed the policy in the flows, not in the webhook; operators needed the binding constraint in their units.
  • A number you could not defend at first. The retailer’s revenue impact before the attribution rules existed; the fix was to agree the measurement with finance before the next run.

What transfers between a bank, a studio, a retailer and an ad platform

The human where the risk owner is

Legal reviewer, editor, operator, account manager: each decides at the point where a wrong decision costs money or trust; the system proposes, logs and learns. The approval threshold is a product decision, agreed with the owner, and widened only as the reversal rate stays low.

Probabilistic inside, deterministic around

Models extract, rank, annotate and narrate; code resolves rules, checks presence, detects faults, enforces limits and validates grounding. The deterministic shell is what makes the probabilistic core shippable in a regulated or money-moving process.

Owned, versioned knowledge

A graph of rules, a taxonomy of sounds, a campaign hierarchy, a security master: the knowledge that decides applicability lives outside prompts, with versions and effective dates, owned by the people who know it.

Typed judges with evidence

Fit, compliance, quality: judges answer typed criteria and cite evidence, are calibrated against humans, and gate before they weight.

Ordinary use as training data

Reviewer edits, editor swaps, operator overrides, account-manager actions: logged with versions and propensities, they become evaluation sets, pairs, labels and rewards without a labelling project.

Frozen sets and gates before every version

Goldens split by project, task or date; recall, agreement, win rate, precision; a version ships only without regression and with a rollback path.

Bias handled by design

Position bias with randomised slots and propensity weights; popularity bias with logQ; self-preference with a second model family and swaps; confounding in elasticity with controls and pooling.

Numbers with four parts

Every figure says what it measures, against what baseline, over what window, and who agreed the definition. That is what survived finance, legal and interviewers.

Formulas & metrics: retrieval and ranking, auctions and pricing, forecasting and elasticity, learning and agreement, experiments and agents

The arithmetic behind the ten use cases on one card, in the form it is said at a whiteboard. Each line names the quantity, gives the formula, and says where on the page it is used.

Retrieval and ranking

cosine similarity: cos(a, b) = a·b / (‖a‖ ‖b‖); with normalised vectors the dot product is the cosine (cards 5, 6, 9)
InfoNCE (one direction): L = −(1/N) Σ_i log [ exp(s_ii/τ) / Σ_j exp(s_ij/τ) ]; symmetric loss averages audio→text and text→audio (card 6)
sampled softmax with logQ correction: logit_ij = s_ij/τ − log q(item_j); q = the item’s sampling probability in the batch stream (card 9)
recall@k = |relevant ∩ top-k| / |relevant|; precision@k = |relevant ∩ top-k| / k; for one relevant item recall@k is a hit rate (cards 4, 5, 9)
MRR = (1/|Q|) Σ_q 1/rank_q; nDCG@k = DCG@k / IDCG@k, DCG@k = Σ_{i≤k} (2^{rel_i} − 1) / log₂(i + 1) (card 5)
reciprocal rank fusion: score(d) = Σ_lists 1 / (k + rank_list(d)), k ≈ 60 (card 5)
pairwise ranking loss (RankNet / LambdaMART): L = Σ_{(i≻j)} w_ij · log(1 + exp(−(s_i − s_j))); LambdaMART weights pairs by their nDCG change (card 5)
propensity-weighted pairs: w = 1 / P(examined | slot); estimated from randomised-slot sessions (cards 5, 9)
calibration ratio = Σ pCTR / Σ clicks; expected calibration error ECE = Σ_bins (n_b/N) · |acc_b − conf_b|; isotonic or Platt to fix (card 9)
ANN index recall@k = |approx top-k ∩ exact top-k| / k, measured against brute force on every build; gate ≥ 0.95 (card 9)
cascade budget: p99 ≤ 50 ms = filters + lookup + tower + ANN + ranker(50) + auction + network; replicas ≈ QPS / (QPS per replica) with headroom (card 9)

Auctions and pricing

eCPM = bid_CPC × pCTR × 1000 (click-priced); eCPM = bid_CPA × pCTR × pCVR × 1000 (action-priced); CPM bids are already per thousand (card 9)
second-price payment = max(second-highest eCPM, floor) scaled back to the winner’s pricing unit; first-price payment = own bid (card 9)
bid landscape: P(win | b) = 1 / (1 + exp(−k (b − b₅₀))) as a logistic form; with censoring, use a survival model on bids with event = won (card 9)
bid shading (first price): b* = argmax_b (v − b) · P(win | b); in practice a quantile of the minimum-winning-bid distribution (card 9)
floor revenue per request: R(f) = E[ max(f, shaded bid) · 1{value ≥ f} ]; fill(f) = P(value ≥ f); the optimum is interior because bidders shade (card 9)
pacing: target spend rate = remaining budget / remaining time; control the participation rate or bid multiplier toward it (card 10)
constant-elasticity demand: D(p) = D₀ (p/p₀)^ε; unconstrained optimum p* = ε · c / (1 + ε) for marginal cost c (ε < −1) (card 8)
fee-aware margin on a marketplace: m(p) = (1 − f) p − (landed + fulfilment); optimum p* = ε (landed + fulfilment) / ((1 − f)(1 + ε)) (card 8)
12-week objective: Σ_t [ D_t m(p) − h I_t − penalty(I_t) ], I_{t+1} = I_t − D_t + inbound_t; weeks of cover = I / D̄ (card 8)
guardrails: p ≥ MAP; p ≥ (landed + fulfilment) / (1 − f − m_min); |Δp| ≤ 10% per week; p ≤ 1.05 × competitor median (card 8)

Forecasting, elasticity and event studies

WAPE = Σ|y − ŷ| / Σ|y|; accuracy = 1 − WAPE; MAPE = mean(|y − ŷ| / |y|) (undefined at zero); bias = Σ(ŷ − y) / Σ y (card 8)
MASE = MAE / MAE of the seasonal naive forecast; < 1 beats naive (cards 8, 9)
hierarchical reconciliation (MinT): ỹ = S (S′ W⁻¹ S)⁻¹ S′ W⁻¹ ŷ, S the summing matrix, W the error covariance; the family total equals the sum of its SKUs (cards 8, 9)
log-log elasticity: ln D = α + ε ln p + β·controls; ε = d ln D / d ln p; pooled ε̃ = w ε_sku + (1 − w) ε_family, w = (1/se²) / (1/se² + 1/τ²) (card 8)
probabilistic forecast interval: quantiles q₀.₁ … q₀.₉ from DeepAR / TFT; guaranteed delivery commits at a chosen quantile (card 9)
market model: r_t = α + β r_m,t + e_t on an estimation window; abnormal return AR_t = r_t − (α + β r_m,t); CAR = Σ_window AR_t (card 4)
materiality prior by event type = mean |CAR| over history, shown as history, never as a forecast for the event at hand (card 4)
novelty: new if no event of the same type for the same entity in the last 72 h; update if figures changed; repeat otherwise (card 4)

Learning from preferences, and agreement

Bradley–Terry: P(a ≻ b) = σ(r(a) − r(b)); reward-model loss −log σ(r(y_w) − r(y_l)) (card 3)
DPO: L = −log σ( β [ log π(y_w|x)/π_ref(y_w|x) − log π(y_l|x)/π_ref(y_l|x) ] ) (card 3)
GRPO: A_i = (r_i − mean_G(r)) / std_G(r); maximise Σ_i min(ρ_i A_i, clip(ρ_i, 1 ± ε) A_i) − β KL(π ‖ π_ref) (card 3)
rubric reward: R = gates × Σ_j w_j v_j / Σ_j w_j; gates = Π (gate items pass) (cards 2, 3)
weighted score with negatives (Autorubric form): score = clip( Σ w_j v_j / Σ_{w_j>0} w_j , 0, 1 ) (card 2)
LoRA update: W′ = W + (α/r) B A, B ∈ ℝ^{d_out×r}, A ∈ ℝ^{r×d_in}; parameters per matrix r (d_in + d_out) (card 6)
Cohen’s κ = (p_o − p_e) / (1 − p_e); Krippendorff’s α = 1 − D_o / D_e; 0.8 reliable, 0.67–0.8 tentative (cards 2, 3)
precision = TP/(TP+FP); recall = TP/(TP+FN); F1 = 2PR/(P+R); macro-F1 = mean over classes; top-k accuracy = share with the truth in the top k (cards 1, 4, 10)
swap consistency = share of pairs whose verdict is unchanged under position swap; gate ≥ 0.9 (card 2)
field-level F1 for structured annotation: per field, exact or tolerance match (times within ±0.25 s), averaged (card 6)

Experiments, intervals and agents

two-proportion z-test: z = (p_t − p_c) / sqrt( p̄(1 − p̄)(1/n_c + 1/n_t) ); relative lift CI = Δ/p_c ± z_{α/2} · se/p_c (card 9)
sample size per arm (proportions): n ≈ (z_{α/2} + z_β)² · (p₁(1−p₁) + p₂(1−p₂)) / (p₂ − p₁)²; 1.6% → 1.76% CTR at 80% power ≈ 100,000 per arm (card 9)
Wilson interval for k of n: (p̂ + z²/2n ± z sqrt(p̂(1−p̂)/n + z²/4n²)) / (1 + z²/n); 14/20 → 48–85% at 95% (cards 2, 3)
sequential testing: fix the looks in advance (daily) or use an always-valid method (mSPRT); never read p-values hourly (card 9)
inverse propensity scoring: V̂(π) = (1/n) Σ r_i · π(a_i|x_i) / p_i; doubly robust: V̂ = (1/n) Σ [ Σ_a π(a|x_i) r̂(x_i, a) + π(a_i|x_i)/p_i · (r_i − r̂(x_i, a_i)) ] (card 10)
Thompson sampling: sample θ_a ~ posterior_a, choose argmax_a x·θ_a; propensity = frequency of the arm among draws (card 10)
holdout attribution: lift = (treated − control) outcome over the window, seasonality-adjusted; value = lift × units × margin (card 8)
reversal rate = auto-applied actions undone by a human / auto-applied actions; the signal that widens or narrows limits (card 10)
cost per item = Σ_calls (tokens_in × price_in + tokens_out × price_out) + infrastructure; route the strong model to the low-confidence share (cards 1, 5)
queueing sanity: replicas = (arrival rate × service time) / target utilisation; scenes in parallel shorten the video, not the model (card 6)
