# 21. Databricks and the data-platform side: Unity Catalog, Mosaic AI, Agent Bricks, Vector Search, MLflow — plus Snowflake, Fabric and BigQuery

> **What you need to be able to say:** why AI projects live or die on the data platform; what a lakehouse is; the Databricks building blocks and what each replaces; how Snowflake, Microsoft Fabric and BigQuery answer the same needs; and how you would stand up a governed RAG or agent on each. Go deeper: Part 6 → *Databricks + AWS agentic AI reference* and the industry studies.

## 21.1 Why the data platform decides the AI project

Every FDE post-mortem has the same first line: the model was fine, the data was not reachable, not permitted, not fresh, or not trusted. The platform answers four questions an agent needs answered on every call: *where is the data* (tables, files, vectors, features), *may this user see it* (governance), *is it current* (pipelines), and *can we prove what happened* (lineage, audit). Databricks, Snowflake, Fabric and BigQuery compete on exactly these.

## 21.2 The lakehouse idea

A **lakehouse** stores data as open files in object storage (S3/ADLS/GCS) in a table format with ACID transactions, schema enforcement and time travel — **Delta Lake** (Databricks), **Apache Iceberg** (the cross-vendor standard: Snowflake, AWS S3 Tables, BigQuery, Fabric all read and write it), **Apache Hudi** — and runs SQL, Spark, ML and streaming engines over the same copy. The point is one governed copy of data serving BI, ML and now LLM workloads, instead of a warehouse here, a data lake there and a feature store somewhere else. The **medallion** convention names the layers: bronze (raw), silver (cleaned, conformed), gold (business-ready aggregates and features).

## 21.3 Databricks building blocks (2026)

- **Unity Catalog** — the governance layer: a three-level namespace (catalog.schema.table) for tables, files (volumes), models, functions and now vector indexes and agents; fine-grained permissions (row filters, column masks), attribute-based access, lineage, audit, data sharing (Delta Sharing) and an open-sourced core. For agents, Unity Catalog is where **tools** are registered as governed SQL or Python functions (UC Functions) so an agent can only call what the catalog allows the user to run.
- **Delta Lake and Lakeflow** — storage and pipelines: Lakeflow Connect (managed ingestion), Lakeflow Declarative Pipelines (formerly Delta Live Tables; declarative, incremental, with expectations as data-quality tests; the core was contributed to Apache Spark as Spark Declarative Pipelines in 2025), Lakeflow Jobs (orchestration), Lakeflow Designer (no-code; GA June 2026), Auto Loader for files, Structured Streaming for real time.
- **Lakebase** — managed Postgres (from the Neon acquisition; separated compute and storage, branching, scale-to-zero; GA and expanded with hybrid "Lakebase Search" in preview at the June 2026 Summit) for operational and transactional workloads next to the lakehouse: the natural home of an agent's session state, or of pgvector for small indexes, with reverse-ETL "synced tables" from Delta.
- **Databricks SQL** with serverless warehouses, Photon engine, AI/BI dashboards and **Genie** (natural-language BI over governed tables, with **Unity Catalog metric views** as the semantic layer plus instructions and example SQL) — the "talk to your data" product that Databricks customers compare your agent against. In 2026 the Genie brand widened: **Genie One** (an agentic assistant across structured and unstructured data), **Genie Code** (a coding agent for data and ML work) and Genie Agents were announced as GA at the June 2026 Summit (verify per-feature status in the release notes).
- **Mosaic AI** — the ML/GenAI stack (Databricks has been retiring the "Mosaic AI" label in 2026 in favour of plain product names, so expect both in job descriptions): **Model Serving** (serverless endpoints for custom models, foundation models pay-per-token or provisioned — including hosted Claude, Gemini and OpenAI models — and external model endpoints), **AI Gateway** — since August 2026 **Unity AI Gateway** (GA 5 August 2026): one governed control plane for models, coding agents, MCP servers and tools, with per-user/team/app cost attribution and hard spend caps, prompt/response and tool-call inspection, payload logging, fallbacks and (beta) quality/cost-aware routing — **Vector Search**, renamed **AI Search** on 1 June 2026 when it gained full-text search (managed index synced from Delta tables, hybrid search, governed by Unity Catalog; standard endpoints for low latency and storage-optimized endpoints for billions of vectors at lower cost), **managed agent memory** (beta, June 2026), **Feature Store and Feature Serving**, **AI Functions** in SQL (`ai_query`, `ai_extract`, `ai_classify`, `ai_parse_document`, `vector_search` — call models from SQL over whole tables), **Agent Framework** (author agents with any library, log them as MLflow models with signatures, deploy with one call, with built-in **Agent Evaluation** and LLM judges), **on-behalf-of-user authorization** for agents (the endpoint carries the caller's identity so UC permissions apply per user), and **Agent Bricks** (describe the task, connect the data, and the platform builds, evaluates and optimizes the agent: Information Extraction, Knowledge Assistant, Multi-Agent Supervisor, Custom LLM/fine-tuned models; cost–quality trade-off slider).
- **MLflow 3** — tracking, model registry (in Unity Catalog), prompt registry and versioning, **tracing** for agents (OpenTelemetry-compatible), evaluation with judges, deployment jobs; open source and the de facto standard outside Databricks too.
- **Compute** — serverless everything (SQL, jobs, notebooks, model serving) plus classic clusters; GPU clusters and the Mosaic training stack for fine-tuning and pretraining.
- **Databricks Apps and Databricks One** — host internal apps (Streamlit, Dash, Gradio) and a simplified business-user workspace.
- **Free Edition** — a no-cost, limited workspace for individuals to learn on real serverless infrastructure (chapter 34).

A governed RAG agent on Databricks in one breath: documents land in a Unity Catalog volume → a Lakeflow pipeline parses and chunks them into a Delta table (`ai_parse_document`, `ai_query` for enrichment) → Vector Search (AI Search since June 2026) indexes the table and stays in sync → an agent authored with LangGraph or the Agent Framework calls `vector_search` and UC Functions as tools → logged with MLflow, evaluated with Agent Evaluation judges on a curated question set → deployed to Model Serving behind the AI Gateway with payload logging → permissions flow from the user's Unity Catalog grants (on-behalf-of-user auth on the endpoint), so the agent never retrieves what the user cannot read. One caveat interviewers like: index-level permissions are coarse. Databricks' documentation states that you cannot create an AI Search (Vector Search) index from a table that has row filters or column masks applied, so per-document access has to be carried as an ACL column (allowed groups) in the source table and enforced as a filter on every query from the caller's identity — or handled with one index per security domain.

## 21.4 Snowflake

Snowflake answers the same needs with **Cortex AI**: the **Cortex AI Functions** in SQL (introduced as "Cortex AISQL" in June 2025: `AI_COMPLETE`, `AI_CLASSIFY`, `AI_FILTER` for semantic `WHERE` clauses and joins, `AI_AGG` and `AI_SUMMARIZE_AGG` for aggregating text across rows, `AI_EXTRACT`, `AI_EMBED`, `AI_SIMILARITY`, `AI_PARSE_DOCUMENT`, `AI_TRANSCRIBE`, `AI_REDACT`, `AI_TRANSLATE`; the older `SNOWFLAKE.CORTEX.COMPLETE`, `SUMMARIZE`, `EXTRACT_ANSWER` and `EMBED_TEXT_1024` still work), **Cortex Search** (hybrid vector + keyword over tables, managed), **Cortex Analyst** (text-to-SQL over semantic models/views), **Cortex Agents** (GA November 2025; orchestrate Search, Analyst and custom tools) and **Snowflake Intelligence** (GA November 2025; the business-user agent front end, with a managed MCP server so external agents can call Snowflake), fine-tuning, document AI, **Snowpark** (Python/Java/Scala in the warehouse) and **Snowpark Container Services** (host your own models and apps), plus Iceberg tables, Horizon governance, and Streamlit in Snowflake for UIs. Strength: zero-ops SQL-centric experience and governance; weaker on heavy ML training and streaming than Databricks. Pick it when the customer's analytics already live there and the AI use case is retrieval and SQL analytics.

## 21.5 Microsoft Fabric

Fabric unifies Azure's data services under **OneLake** (one logical lake, Delta/Parquet, shortcuts to S3/ADLS): Data Factory (pipelines), Data Engineering (Spark), Data Warehouse (T-SQL), Real-Time Intelligence (KQL/Eventhouse), Data Science (MLflow, notebooks, AI functions), Power BI (with Copilot and Direct Lake), plus Fabric data agents and the Microsoft Foundry integration for RAG over OneLake data. **Fabric IQ** (preview; announced November 2025) adds an **ontology** of business entities, relationships and rules bound to OneLake data, a graph engine and operations agents, so agents query "customers at risk" rather than raw tables — Fabric Graph and the operations agent reached GA in mid-2026 while the ontology itself was still in preview as of August 2026. Strength: the Microsoft 365/Power BI estate and Entra ID security end to end; capacity-unit pricing simplifies budgeting and complicates sizing (one F-SKU capacity is shared by every workload, so a runaway notebook throttles the Power BI reports). Pick it when the customer is a Microsoft shop and Power BI is the front door.

## 21.6 BigQuery (Google Cloud)

BigQuery is serverless SQL at petabyte scale with **BigQuery ML** and the newer **AI functions** (train classical and deep models; call Gemini row-wise via `AI.GENERATE` and its typed variants `AI.GENERATE_BOOL/INT/DOUBLE`, or the older `ML.GENERATE_TEXT`; extract structured columns with `AI.GENERATE_TABLE`; forecast zero-shot with `AI.FORECAST` on TimesFM; embeddings via `ML.GENERATE_EMBEDDING`; `VECTOR_SEARCH` with vector indexes), BigLake and Iceberg tables over GCS, Dataform/Dataflow/Pub-Sub for pipelines, Dataplex for governance and lineage, and the Gemini Enterprise Agent Platform (formerly Vertex AI) next door for agents and serving, plus BigQuery's own data agents. Strength: the simplest path from "data in a warehouse" to "LLM over that data" entirely in SQL. Watch the bill: a row-wise LLM function over a 50M-row table is 50M model calls, priced as Gemini tokens on top of bytes scanned — always prototype on a `LIMIT 1000` sample and estimate. Pick it when the customer is on Google Cloud or wants pure serverless analytics.

## 21.7 The AWS native stack (for completeness)

S3 (with S3 Tables for Iceberg), Glue (catalog and ETL), Athena (serverless SQL), Redshift (warehouse, with ML and now embeddings), EMR (Spark), Kinesis/MSK (streaming), Lake Formation (governance), SageMaker Unified Studio and Lakehouse (the 2025 attempt to unify them), Neptune (graph), OpenSearch (search and vectors), DynamoDB and Aurora (operational), Bedrock Knowledge Bases over all of it. More assembly required than Databricks or Snowflake; maximum flexibility.

## 21.8 Concepts every data-platform conversation touches

- **Governance**: catalog, lineage, row/column security, masking, PII tagging, access via the end user's identity (not a service account) so that an agent inherits permissions — the single most common interview question about "limiting what an agent can see" (chapters 30 and 39).
- **Data quality**: expectations/tests in pipelines, freshness SLAs, schema evolution, deduplication, slowly changing dimensions.
- **Batch vs streaming**: micro-batch Structured Streaming, Flink, Kafka; exactly-once semantics; watermarking; when an agent needs real-time features.
- **Feature engineering for ML and features for LLMs**: feature stores, point-in-time correctness, and the newer pattern of materializing LLM-generated features (summaries, classifications) back into tables with AI functions.
- **Semantic layers** (dbt semantic layer, Cortex Analyst semantic models/views, Unity Catalog metric views, Power BI semantic models, Looker, Fabric IQ ontology) as the foundation for reliable text-to-SQL. On public text-to-SQL benchmarks over realistic enterprise schemas (BIRD, Spider 2.0) raw generation is far from solved — Spider 2.0's enterprise tasks were in the 20–60% range for frontier agents through 2025 — which is the quantitative case for a semantic layer.
- **Cost controls**: serverless autoscaling, cluster policies, query cost attribution, caching, Photon/BigQuery slot management, and budgets on LLM-in-SQL functions (they turn a cheap scan into millions of model calls).

### Critic's additions: the LLM-in-SQL pattern and its failure modes

Every platform now lets you call a model from SQL (`ai_query`, `AI_COMPLETE`, `AI.GENERATE`, Fabric AI functions). It is the fastest way to enrich a table — and the fastest way to burn a budget. What to say when asked:

- **Cost is rows × tokens.** 10M support tickets × 600 input tokens × a $0.30/MTok model ≈ $1,800 per full pass; the same pass on a $3/MTok model is $18,000. Run on new or changed rows only (incremental pipelines), materialize the results, and never put an LLM function in a dashboard query that re-runs on every refresh.
- **Throughput and quotas.** The function fans out to the model endpoint; provisioned throughput or batch inference is cheaper and steadier than pay-per-token for large backfills (Databricks `ai_query` uses batch inference on provisioned endpoints; BigQuery and Snowflake have their own quotas).
- **Determinism and versioning.** Pin the model version and the prompt in the pipeline code; store model and prompt identifiers next to the generated column, so a later re-run with a new model is visible in lineage.
- **Quality checks.** Add expectations on generated columns (allowed labels, non-null rate, distribution drift versus last week) exactly as for any other pipeline output; sample a few hundred rows for human review when the prompt or model changes.
- **Governance.** The model sees whatever the query selects; mask PII columns before the call (column masks apply to the function's input too), and route through the platform's gateway so usage is attributed and capped.

## 21.9 Scenarios

- **"Build a knowledge assistant over 2 million policy documents for 20,000 employees with department-level access."** Databricks: volumes + Lakeflow parsing + Vector Search (AI Search) over a chunk table that carries an `allowed_groups` column, filtered on every query by the caller's groups (row filters on the source table are not supported for index creation) + Agent Framework with on-behalf-of-user auth + AI Gateway; evaluation set from support tickets including negative access tests; latency target p95 under 3 s. Snowflake: Cortex Search over a documents table with an ACL attribute filter + Cortex Agents (check the current row-access-policy support for Cortex Search before relying on it). Fabric: OneLake + Azure AI Search security trimming + Foundry Agent Service with Entra groups.
- **"Give analysts natural-language access to sales data."** Semantic layer first (dbt or Cortex Analyst/Genie semantic models), then text-to-SQL with query validation against the semantic model, then an eval set of 200 question–SQL pairs; never raw text-to-SQL over 400 unmodeled tables.
- **"Extract fields from 300,000 contracts a month."** Agent Bricks Information Extraction or `ai_extract`/`ai_query` in a Lakeflow pipeline, sampled human review, drift monitoring on field distributions, cost per document tracked through the AI Gateway.
- **"Forecast demand and feed the planning agent."** Feature tables from the gold layer, a gradient-boosting or NeuralProphet model registered in MLflow, served through Feature Serving; the agent calls a `forecast(sku, horizon)` UC Function rather than computing anything itself.

**Interview line:** *"I put the agent on the data platform the customer already governs — Unity Catalog, Horizon, OneLake or Dataplex — register tools as governed functions, let retrieval inherit the user's permissions, log every run with MLflow or OpenTelemetry, and measure with an eval set from real tickets. The model is a component; the catalog is the product."*
