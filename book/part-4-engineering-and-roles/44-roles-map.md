# 44. The roles map: AI Engineer, Forward Deployed Engineer, ML Engineer, MLOps, DevOps/Platform, Data Engineer, FinOps, SRE, Solutions Architect, Data Scientist

> **The idea:** titles overlap, but each role owns a different failure. Knowing what each role does, what it must know, and how it works with the others lets you read a JD correctly (chapter 35), position your resume honestly (chapter 7), and answer "how would you work with the platform team?" with specifics. Each role below has: what they own, a typical week, the knowledge required, the interview focus, adjacent roles, and three example use cases.

## 44.1 Side-by-side

| Role | Owns | Primary metric | Core knowledge | Typical interview |
|---|---|---|---|---|
| **AI Engineer / Applied AI / LLM Engineer** | LLM features and agents in production | quality on evals, cost per request, latency | Python, LLM APIs, RAG, agents, evals, observability, one cloud | project deep dive, system design, coding |
| **Forward Deployed Engineer (FDE)** | customer outcomes: POC → production inside the customer's environment | time-to-value, renewals, production go-lives | everything the AI engineer knows plus integration, security reviews, discovery, communication | use-case walkthrough, design with constraints, presentation, behavioural |
| **ML Engineer** | models trained and served at scale (classic + deep) | model metrics online, serving latency, retraining health | PyTorch/sklearn/XGBoost, feature engineering, serving, experiment design | ML theory, coding, modeling case |
| **MLOps / LLMOps Engineer** | the lifecycle machinery: pipelines, registries, serving, monitoring, evals | deployment frequency, drift caught, reproducibility | MLflow/W&B, Kubernetes, CI/CD, feature stores, monitoring, prompt/eval ops | platform design, debugging a pipeline, infra coding |
| **DevOps / Platform Engineer** | the paved road: CI/CD, IaC, clusters, environments, developer experience | lead time, change failure rate, MTTR, platform adoption | Terraform, Kubernetes, GitHub Actions/GitLab, cloud networking/IAM, containers | infra design, troubleshooting, scripting |
| **SRE** | reliability: SLOs, incidents, capacity, on-call | SLO compliance, MTTR, toil reduced | observability, incident management, performance, automation | incident scenario, system design for reliability |
| **Data Engineer** | pipelines and data models that everyone else depends on | freshness, quality, cost per TB, pipeline success | SQL, Spark, Airflow/Dagster/dbt, lakehouse formats, streaming, modeling | SQL/Spark coding, pipeline design |
| **Data Scientist / Applied Scientist** | analysis, experiments, models that answer business questions | decision impact, experiment validity | statistics, causal inference, ML, SQL, communication | case study, stats, modeling |
| **FinOps Practitioner / Cloud Cost Engineer** | cloud and AI spend visibility, optimization and governance | unit cost trends, commitment coverage, waste eliminated | billing data, tagging, commitments, rightsizing, Kubernetes and AI cost | cost case, stakeholder scenario |
| **Solutions Architect (AI/Cloud)** | the design and the buy-vs-build decisions across teams | architectures adopted, risks avoided | breadth across clouds and patterns, security, cost, communication | architecture review, trade-off discussion |
| **AI Product Manager** | what to build and why; acceptance criteria; adoption | adoption, outcome metrics | product discovery, evals as acceptance tests, basic ML literacy | product case |
| **Analytics Engineer** | the modeled, tested, documented tables and semantic layer that BI and text-to-SQL depend on | model test pass rate, dashboard trust, time-to-answer | SQL, dbt, dimensional modeling, semantic layers, data tests | SQL modeling case, dbt project walkthrough |
| **Security Engineer (AppSec / AI security)** | the attack surface: identity, secrets, supply chain, prompt-injection and tool-abuse controls, red-team program | vulnerabilities found before production, time-to-remediate, red-team pass rate | OWASP (web, LLM, agentic), threat modeling, IAM, secrets, scanning, incident response | threat model of a design, secure code review, red-team scenario |

**Critic's additions: the failure each role owns, and how to spot the role in a JD.** The sentence "each role owns a different failure" is the most useful lens for reading job descriptions, so here it is made explicit. When a JD mixes two rows, the role is a hybrid and the interview will test the failure listed first in the responsibilities section.

| Role | The failure it is paged for | JD phrases that reveal it | The question that exposes a mislabelled JD |
|---|---|---|---|
| AI Engineer | the agent gave a wrong, unsafe or expensive answer | "ship LLM features", "RAG", "evals", "tool use", "latency and cost per request" | "Who owns the eval set today, and what blocks a prompt change from reaching production?" |
| FDE | the customer did not get to production or did not renew | "customer-facing", "on-site", "ambiguity", "security questionnaires", "travel 25–50%" | "What share of your deployments reached production in the last 12 months, and what stopped the rest?" |
| ML Engineer | the model's online metric decayed or the endpoint fell over | "train and deploy models", "PyTorch", "feature engineering", "A/B tests", "serving latency" | "How do you detect that a model is stale before the business does?" |
| MLOps / LLMOps | a release cannot be reproduced, rolled back or explained | "pipelines", "registry", "CI/CD for models", "monitoring", "reproducibility" | "What is the rollback path for a model version and for a prompt version?" |
| DevOps / Platform | engineers cannot ship, or shipped something broken, because of the road | "paved road", "developer experience", "golden path", "Terraform", "clusters", "internal platform" | "What is your lead time from merge to production, and what is the change failure rate?" |
| SRE | the SLO was breached and nobody knew why | "SLOs", "on-call", "incident", "post-mortem", "toil", "capacity" | "Which SLO was last breached and what changed afterwards?" |
| Data Engineer | the table was late, wrong or expensive | "pipelines", "Spark", "dbt", "Airflow", "lakehouse", "data quality", "CDC" | "How do consumers learn that a column changed meaning?" |
| Data Scientist | the decision was based on a biased or underpowered analysis | "experiments", "causal", "insights", "stakeholders", "statistics" | "Describe an experiment you stopped because the design was wrong." |
| FinOps | the bill surprised finance | "cloud cost", "unit economics", "commitments", "tagging", "showback" | "What share of spend is allocated to an owner today?" |
| Solutions Architect | thirty teams built thirty incompatible things | "reference architectures", "build vs buy", "review board", "vendor evaluation" | "Which of your reference architectures was ignored, and why?" |

**Critic's additions: adjacent titles you will meet in JDs.** *Research Engineer* (implements and scales research code; interview is coding plus paper discussion), *Evaluation Engineer / Model Quality Engineer* (owns eval sets, judges and quality dashboards; a growing title in 2026), *Prompt Engineer* (declining as a standalone title; the work moved into AI engineering and evaluation), *AI Solutions Engineer / Sales Engineer* (pre-sales demos and POCs; closer to FDE but without owning production), *Developer Advocate* (content, samples, community; judged on adoption), *Member of Technical Staff* (lab-style generic title; read the team description, not the title), *Staff/Principal* prefixes (scope across teams and the expectation that you write the ADRs others follow). *Analytics Engineer* and *Security Engineer* are in the table above because AI teams increasingly hire both.

## 44.2 AI Engineer (Applied AI, LLM Engineer, GenAI Engineer)

**Owns.** Features and agents built on models: prompts, tools, retrieval, orchestration, structured outputs, guardrails, evals, cost and latency — integrated into product code. **Typical week.** Iterating on an agent's tool design against a failing eval slice; adding a reranker and measuring recall; wiring OTel traces; a design review for a new use case; a cost review; on-call for the LLM gateway. **Must know.** Chapters 14–34 of this book; production Python (chapter 49); one cloud deeply; API design; testing and CI. **Adjacent.** ML engineers (models), data engineers (corpora), platform (runtime), product (acceptance criteria). **Use cases.** Policy assistant with permissions (chapter 40 A); support agent with actions (40 B); document extraction (40 D).

## 44.3 Forward Deployed Engineer

**Owns.** A customer's outcome: discovery, scoping, building the first use case in the customer's environment, security and compliance review, production go-live, enablement of the customer's team, and the feedback loop to the product. **Typical week.** Two days on-site or in customer calls (discovery, demos, workshops), two days building (integration, data access, evals), one day on security questionnaires, documentation and internal product feedback. **Must know.** AI-engineer skills plus: enterprise integration (SSO, VPC, IAM, APIs without docs), data access negotiation, security reviews (SOC 2, HIPAA, data residency), writing acceptance criteria, presenting to executives, handling ambiguity and politics, travel tolerance. **Interview focus.** Use-case walkthroughs (chapter 36), design under constraints, a presentation, behavioural stories about customers. **Use cases.** Deploying a vendor's agent platform inside a bank's VPC with their identity provider; building a claims triage POC for an insurer and taking it to production; standing up a RAG assistant on a hospital's SharePoint with PHI controls; running a two-day workshop to turn a utility's ten ideas into three scoped use cases with evals.

## 44.4 ML Engineer

**Owns.** Training and serving models: data prep and features, model development, offline and online evaluation, serving infrastructure, retraining, monitoring. **Must know.** PyTorch/TensorFlow, scikit-learn, gradient boosting, deep learning for the domain (vision, NLP, recommenders), feature stores, model serving (TorchServe/Triton/vLLM/SageMaker/Gemini Enterprise Agent Platform endpoints — the platform Google called Vertex AI until April 2026), experiment tracking, A/B testing. **Interview focus.** ML fundamentals, coding, a modeling case. **Use cases.** Two-tower ranking at 10K QPS (chapter 36.3); demand forecasting for inventory (36.4); segmentation models for drone inspection (36.5); fine-tuning a small LLM for classification (chapter 26).

## 44.5 MLOps / LLMOps Engineer

**Owns.** The machinery: training pipelines (Kubeflow, Agent Platform Pipelines — formerly Vertex AI Pipelines — SageMaker Pipelines, Databricks Lakeflow Jobs, Airflow), experiment tracking and model registry (MLflow, W&B, Unity Catalog), feature stores, serving platforms and autoscaling, monitoring (drift, performance, data quality), CI/CD for models and prompts, evaluation infrastructure, cost. **LLMOps additions.** Prompt registries and versioning, eval datasets and judges in CI, gateways with routing and caching, tracing with GenAI conventions, guardrail services, RAG index refresh pipelines. **Must know.** Kubernetes and containers, CI/CD, IaC, Python, the cloud's ML platform, observability, security basics. **Interview focus.** Design a training/serving platform; debug a failing pipeline; write infra code. **Use cases.** A retraining pipeline with validation gates and canary rollout for the ranking model; a prompt-and-eval CI gate for the marketing reviewer agents; an index refresh pipeline with ACL sync for the policy assistant; cost dashboards per feature from OTel token attributes.

## 44.6 DevOps / Platform Engineer

**Owns.** The paved road for all engineers: source control workflows, CI/CD pipelines, artifact registries, infrastructure as code, Kubernetes clusters or serverless platforms, environments, secrets, networking, identity, developer portals and golden templates — plus the GPU and model-serving infrastructure in AI-heavy organizations. **Must know.** Chapter 45. **Interview focus.** Design a deployment pipeline; troubleshoot a broken cluster; write Terraform; explain blue/green vs canary. **Use cases.** GitOps with Argo CD for forty microservices; a GPU node pool with autoscaling for model serving; a secure Bedrock access path with VPC endpoints and IAM; an internal template that stands up a new agent service with tracing and eval gates in an hour.

## 44.7 SRE

**Owns.** Reliability as an engineering discipline: SLIs/SLOs and error budgets, incident response and post-mortems, capacity planning, performance, toil automation, on-call health. **Must know.** Observability stacks, distributed systems failure modes, load testing, chaos engineering basics, cloud and Kubernetes operations, scripting. **Interview focus.** Incident scenarios ("latency doubled at 9 am"), SLO design, system design for reliability. **AI additions.** Provider rate limits and outages (fallback models), GPU saturation, cost as a reliability signal, quality SLOs via judge sampling. **Use cases.** An SLO for the support agent (p95 < 3 s, 99.5% availability, faithfulness ≥ 0.95 sampled); a runbook for provider outages with automatic model fallback; capacity planning for a product launch in tokens per minute.

## 44.8 Data Engineer

**Owns.** Ingestion, transformation, modeling and serving of data: batch and streaming pipelines, lakehouse/warehouse tables, data quality, lineage, cost; increasingly the document and embedding pipelines that feed RAG. **Must know.** Chapter 48. **Interview focus.** SQL and Spark problems, pipeline design, data modeling. **Use cases.** Medallion pipeline from five retail data sources into a unified model (36.4); streaming features for ad ranking (36.3); a document pipeline that parses, chunks, embeds and indexes 2M files with ACLs (40 A); CDC from an ERP into the lakehouse for an agent's tools.

## 44.9 Data Scientist / Applied Scientist

**Owns.** Turning questions into analyses, experiments and models; measurement and causal reasoning; communicating decisions. **Must know.** Statistics and experiment design, causal inference and uplift (Part 6), ML modeling, SQL, visualization, domain context. **Interview focus.** Case studies, statistics, modeling, communication. **AI additions.** Designing evals as experiments, judge calibration, offline/online metric alignment. **Use cases.** Promotional-lift analysis for e-commerce; churn and CLV models with actuaries (36.6); footfall analytics for retail locations; A/B gates for ranking launches.

## 44.10 FinOps Practitioner / Cloud Cost Engineer

**Owns.** Visibility (tagging, allocation, showback/chargeback, unit economics), optimization (rightsizing, scheduling, storage tiers, commitments, architecture changes), and operation (budgets, anomaly alerts, forecasting, governance) of cloud and AI spend — in partnership with engineering and finance. **Must know.** Chapter 47. **Interview focus.** A cost case ("spend doubled; find why and fix it"), commitment strategy, stakeholder scenarios. **Use cases.** Attributing LLM spend per feature with OTel attributes and cutting 69% (chapter 31); a 25% pipeline cost reduction via scheduling and rightsizing (36.5); Kubernetes cost allocation per team; a commitment plan for steady GPU workloads.

## 44.11 Solutions Architect (AI/Cloud)

**Owns.** Target architectures, reference patterns, build-vs-buy, vendor and model selection, security and compliance alignment, and the review process that keeps thirty teams consistent. **Must know.** Breadth across chapters 14–34 and 45–50; the ability to draw and defend an architecture in front of executives and engineers. **Interview focus.** Architecture review of a proposed design; trade-off discussions; presentation. **Use cases.** The enterprise agent platform (40 F); a multi-cloud model strategy behind a gateway; a migration from a classic Dialogflow ES bot to a hybrid agent (deterministic flows in Conversational Agents, an LLM agent for open dialogue); a build-vs-buy review that keeps a managed RAG service for the HR assistant but builds custom retrieval for the legal corpus because the eval set showed a 15-point recall gap on jargon.

## 44.12 How the roles fit together on one project

Take the policy assistant (40 A): the **data engineer** builds the document pipeline with ACLs; the **AI engineer** builds retrieval, prompts, agent and evals; the **MLOps engineer** wires the eval gate, tracing and index refresh; the **platform engineer** provides the runtime, gateway and CI/CD; the **SRE** sets SLOs and runs incidents; the **FinOps practitioner** attributes and trends cost; the **architect** approves the design and the vendor choices; the **data scientist** designs the adoption experiment; the **FDE** does all of it inside the customer's environment with a smaller team and tells the customer's executives what they got. Knowing which hat you are wearing in each conversation is half of being senior.

**Critic's additions: the same project under incident — who does what, in what order.** Interviewers who ask "how would you work with the platform team?" are really asking whether you know the handoffs. Walk them through an incident.

*Tuesday 09:12.* The nightly index refresh for the policy assistant shipped 1,800 new chunks without ACL principals because the SharePoint connector's permission field was renamed. At 09:40 an engineer asks about parental-leave policy and sees a quote from a restricted HR document.

1. **SRE** (09:41) receives the guardrail alert ("citation to document with empty ACL list"), declares a Sev-2 under the quality SLO ("0 permission leaks per month" is a hard SLO, not an error-budget one), and pages the on-call AI engineer. Artifact: incident channel, timeline, status page entry for the internal tool.
2. **AI engineer** (09:50) flips the feature flag that disables retrieval for documents indexed after 02:00, verifies with the negative test ("engineer asks about HR-restricted content, expects abstention"), and keeps the assistant up in degraded mode. Artifact: flag change, trace ids of the leaked responses.
3. **Data engineer** (10:05) traces the chunk rows to the connector run, finds the renamed field, adds a contract test ("ACL list must be non-empty for sources that have permissions"), quarantines the 1,800 rows, and reruns the refresh. Artifact: data-contract change, quarantine table, backfill run id.
4. **MLOps engineer** (10:30) adds the negative test to the CI eval gate and makes the index refresh pipeline fail closed when the ACL coverage of a run drops below 100% of documents from permissioned sources. Artifact: pipeline gate, new eval cases.
5. **Platform engineer** (11:00) confirms that the connector's service account could read the restricted library only because of a broad site-level grant and narrows it. Artifact: IAM change in IaC, policy-as-code rule.
6. **Security engineer** (same day) assesses exposure (12 users saw 3 restricted passages), triggers the data-protection notification process if required, and adds the case to the red-team suite.
7. **FinOps** notes the reindex cost (an extra 40 million embedding tokens) and that the refresh pipeline now runs with a cap; **data scientist** checks whether the adoption experiment's metrics were contaminated by the degraded hours; **architect** records the ADR: "ACL filtering is enforced in the retrieval service from the document table, never from the index alone"; **FDE** tells the customer's CISO what happened, what changed, and what evidence shows it cannot recur.

Post-mortem action items have owners from six roles, and the eval set grew by four cases. That is what "working well with the platform team" looks like in practice; say it with this level of detail and the interviewer stops probing.
