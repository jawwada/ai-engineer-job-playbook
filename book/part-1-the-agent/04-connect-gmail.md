# 4. Connect Gmail

Gmail does two jobs in this system: job-alert emails come *in* (LinkedIn, Indeed and Dice alerts are the cheapest, most reliable feed of fresh postings), and recruiter conversations go *out* as drafts you approve. The connection is the claude.ai Gmail connector, which Claude Code inherits automatically when you are logged in with your claude.ai account — there is nothing to install on the machine and the agent never sees your Google password.

**Connect it (once, in the browser):**

1. Open claude.ai → Settings → Connectors, find Gmail and click Connect. Google shows its consent screen; you approve it yourself. The agent is not involved in this step and must not be asked to do it.
2. Back in Claude Code, type `/mcp`. Gmail should be listed with its tools (search threads, read messages, list labels, create drafts, and the send, reply and forward tools that the kit's `settings.json` denies). If it shows as needing authentication, select it in the `/mcp` panel to sign in.
3. Test it with one sentence: *"List my Gmail labels."* You should get a list (with `Jobs/Alerts` and `Jobs/Recruiters` once you have created them, below), not an error. A label listing is a better test than a mailbox search, because inside `~/job-search` the standing rules forbid reading mail outside the two job labels.

**Prepare the inbox so the agent reads only what it should.** Create two labels in Gmail, `Jobs/Alerts` and `Jobs/Recruiters`, and two filters: alert mail (for example `from:(jobalerts-noreply@linkedin.com OR indeed.com OR dice.com)`) gets `Jobs/Alerts` and skips the inbox; recruiter mail (labelled by hand, or by a filter on words such as "C2C", "W2", "rate" or "end client") gets `Jobs/Recruiters`. You create the labels and filters yourself; the agent does not. The label names live in `gmail.labels` in `profile.yaml`, and the kit's `CLAUDE.md` tells the agent to search only those labels and read nothing else. Because the connector's search takes label IDs rather than names, the skills first look the IDs up with the list-labels tool, then search `label:<ID> newer_than:1d` for alerts and `newer_than:3d` (by default) for recruiter mail. If you would rather not point an agent at your personal mailbox at all, create a fresh Gmail address for the job search and use it everywhere; many people find this cleaner anyway.

**Set up the alerts that feed it.** On LinkedIn, run each search you care about (for example *Forward Deployed Engineer*, remote, United States, past 24 hours) and switch on the job alert, daily. Do the same on Indeed and on Dice (Dice alerts can be filtered to contract/C2C). Three to five alerts per site is plenty; the agent de-duplicates across them.

**What the agent does with mail — and what it never does.** The `/recruiter-inbox` skill reads the last three days of threads under `Jobs/Recruiters` (`/recruiter-inbox 7d` widens the window), saves each to `inbox/<date>/`, and hands them to the `inbox-triager` subagent, which classifies each (real role with details, vague mass mail, interview logistics, rejection, other) and extracts the facts you need (role, vendor and end client, rate or salary, location and remote, W2/C2C/1099, duration, contact). The skill then updates the tracker (a `mail-<thread id>` row for a new real role) and writes a reply as a **Gmail draft** in the thread, using only facts from the truth file and the answers bank. Job-alert mail is read by `/job-scout`, not by this skill. Sending is yours: the kit denies the connector's send, reply and forward tools, so not even "send the draft to X" works — you open the draft in Gmail, attach the resume where the draft says `[attach resume]`, and send it. Keep it that way even in auto mode; a wrong application costs little, a wrong email to a recruiter costs a relationship. Possible scams (payment requests, crypto, a sender domain that does not match the company) get no draft, only a warning, and identity numbers never go into a draft.

**If you cannot or do not want to connect Gmail:** `/job-scout` still works from LinkedIn, Dice and Indeed, and `/recruiter-inbox` simply has nothing to read; paste a recruiter's email into the session when you want a reply drafted as text. Avoid pointing the agent at the Gmail web app through Chrome instead: in the browser it could click *Send*, which the connector's deny rules would otherwise make impossible.
