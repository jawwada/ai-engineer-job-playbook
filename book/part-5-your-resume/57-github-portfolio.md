# 57. The GitHub portfolio: what to show, how to show it

> **Why it matters:** for AI-engineer and FDE roles, two or three public repos with measured results answer "have you actually built this?" better than any resume line, and they are what interviewers open while you talk. This chapter audits a typical senior profile (the reference profile has a dozen public repositories accumulated over a decade — Bedrock experiments, a chatbot application, sensor anomaly detection, PySpark with TensorFlow, a map-matching research codebase, a geospatial AWS project, a personal site — plus private work) and lays out the portfolio that matches the roles in this book.

## 57.1 The audit (apply it to your own profile)

| Check | Typical state on a senior profile | Fix |
|---|---|---|
| Pinned repos | none or random | pin six: three labs from chapter 34, this playbook, one research/legacy project with a strong README, one tool |
| READMEs | empty or boilerplate | problem, architecture (Mermaid), how to run, results with numbers, cost, what you learned |
| Descriptions | blank | one line each; the profile page is scanned, not read |
| Recency | newest activity months old | one commit a week on a lab keeps the activity graph alive |
| Secrets and personal data | occasionally in old repos | scan (gitleaks), rewrite history if needed, remove resumes and private documents |
| Forks vs originals | forks clutter | unpin forks; keep only forks you changed |
| Profile README | missing | a 10-line profile README: who you are, what you build, three links |
| Private experiments | valuable but invisible | publish sanitized versions (no client data) of the best two |
| Employer and client intellectual property | code written on an employer's time or against a client's systems sits in personal repos | check your invention-assignment and confidentiality clauses before publishing anything built at work; rebuild the idea on synthetic data in your own time, with your own code, and say so in the README |
| Notebooks | outputs stripped or, worse, outputs full of client data | keep one narrative notebook with outputs on synthetic data; move the real logic into a package with tests |
| Dependencies | unpinned, abandoned, with known CVEs | lockfile committed, Dependabot or Renovate enabled, one `make setup` that works on a clean machine (a devcontainer or Codespaces config proves it) |

**What a reviewer sees in sixty seconds.** Hiring managers and FDE interviewers rarely read code before the call; they scan. The scan order is the profile README, the six pinned cards (name, one-line description, language, last commit), the first screen of the top repo's README (the headline number, the architecture picture, a demo GIF), and then, if they are still interested, the test folder and the CI badge. Stars do not matter at this scale; recency and clarity do. Three consequences: the one-line description on each repo is the most-read sentence in your portfolio, the first screen of each README must carry the result and the picture, and a repo with a green CI badge and a `tests/` folder beats one with twice the features and neither.

## 57.2 The six-repo portfolio for AI Engineer / FDE roles

1. **RAG with permissions on a cloud** (lab 1 or 3 or 6): ingestion pipeline, hybrid retrieval, reranking, ACL filters, eval set with recall@k and faithfulness, traces, cost per query, IaC, README with numbers.
2. **Agent on a managed runtime** (lab 2 or 4): a supervisor with two tools and memory on AgentCore or Google's Agent Runtime (formerly Agent Engine); trajectory evals; a short demo GIF.
3. **Evaluation and observability kit** (lab 9): judges calibrated against human labels, promptfoo/DeepEval in GitHub Actions, OpenTelemetry to Langfuse/Phoenix; the harness interviewers ask about.
4. **A domain project from your background** (voice agent, document pipeline, knowledge graph, ranking model) with real-looking synthetic data and a measurement.
5. **This playbook** — the job-search agent kit and the book; it demonstrates agent design, skills and documentation.
6. **One research or legacy repo with a rewritten README** (e.g., the map-matching codebase) — shows depth and history.

**How a number in a README becomes credible.** "recall@10 0.88" in a README is a claim; interviewers have seen too many invented ones. The mechanism that makes it evidence is reproducibility in the repo itself:

- the eval set is committed (or generated by a committed script with a fixed seed), with its size and source stated;
- `make eval` regenerates the results table from `results/*.json`, and a GitHub Actions job runs it on every push to `main` and fails if a metric regresses beyond a tolerance;
- the README's results table is pasted from that job's output, with the commit hash and model version next to it;
- one trace (a Langfuse or Phoenix screenshot, or an exported OTel JSON) is linked for a single request so the latency and token numbers can be checked against the cost claim;
- the "what regressed and why" paragraph names a real regression you fixed, because a results history with no regressions reads as fiction.

For a legacy or research repo where re-running is impractical (old dependencies, data you no longer have), say so in the README and give the paper, the original numbers and what you would do differently; honesty about reproducibility is itself a signal.

**Repos that hurt.** Tutorial clones with the tutorial's README; a dozen "langchain-test" repos with three commits each; forks you never changed; notebooks named `Untitled3.ipynb`; a `config.py` with an API key from 2021 (rotate it, then rewrite history); anything containing a real customer's name or data. Archive or delete these before pinning anything; the profile is judged by its weakest visible repo.

## 57.4 Hygiene rules

- No secrets, ever; `.env.example` only; pre-commit `gitleaks`.
- No client data, no personal documents, no resumes in repos.
- Licenses on everything you want reused (MIT for code; CC BY for writing).
- Tag releases; keep `main` runnable; CI badge green.
- Issues and a short CONTRIBUTING file make a repo look alive even if you are the only contributor.
- Datasets: commit only data you have the right to redistribute (your own synthetic data, or sets whose license allows it); name the license next to the data; never commit scraped content from sites whose terms forbid it (chapter 54).
- A `SECURITY.md` with a contact line, pinned GitHub Actions versions, and secrets only in repository secrets; the `make destroy` target in every cloud lab so a reviewer who runs it is not billed for a forgotten index.
- Cost warnings in the README for anything that creates cloud resources, with an estimate ("about $2 to run the eval once on Gemini Flash").

## 57.5 How to talk about the portfolio in interviews

Lead with the number and the problem; open the README's architecture diagram; show the eval results and the trace screenshot; say what broke and what you changed. A repo you can narrate in three minutes is worth more than ten you cannot.

**The three-minute narration, with timings.** Interviewers interrupt, so front-load. *0:00–0:20* — the problem and the constraint in one sentence ("policy questions from 4,000 employees, every answer had to respect document permissions and cost under a cent"). *0:20–0:50* — the headline result and how it was measured ("recall@10 went from 0.62 to 0.88 on a 300-question gold set; faithfulness 0.94 by a judge calibrated to 150 human labels"). *0:50–1:40* — the architecture, pointing at the diagram: ingestion with ACLs, hybrid retrieval, reranker, generation with citations, traces. *1:40–2:20* — what broke: the first version leaked a restricted document through a cached embedding; the fix was filtering at query time and a negative test in CI. *2:20–3:00* — what you would do next and what it would cost. Then stop and let them ask. Practice it against a timer; the version that fits in three minutes is the one that survives a nervous interview.
